# 入站送达异步化评估（Flow B 的 ack 时延解耦）

> 版本：v1.0（2026-09-22）｜性质：**评估稿（未实施）**，拍板后才开工
> 起因：2026-09-22 排查「模拟回调报 500」时发现 —— **「ack 与送达解耦」目前只在「成败」上成立，在「时延」上仍耦合**。
> 本文给出量化、方案对比、推荐与待拍板点。姊妹文档：《M3开发计划.md》（D-M3-2/D-M3-3）、《API中心设计方案.md》§5.5/§6.1。

## 0. 结论摘要（先看这个）

| 项 | 结论 |
|---|---|
| **问题** | ack 的返回时间 = 验签 + 链 + **同步送达（含内联短重试）** |
| **最坏量化** | 送达对端「可达但每次都挂到读超时」时：**ack 延迟 ≈（1+maxRetries）× timeout_ms + 退避和** —— `maxRetries=4` 配新默认 `timeout_ms=10000` ⇒ **≈53 秒**（旧默认 3000ms 时 ≈18 秒） |
| **第二个代价** | 同一段内联重试还被 **worker 重送路径复用** ⇒ 单条慢记录会**阻塞扫描线程**（`ThreadPoolTaskScheduler(2)`，扫描串行） |
| **推荐** | **分两步**：① **首投不回内联重试**（≈0.5 人日，低风险、收益最大）② **收到即回 ack + 后台首投**（≈1.5~2 人日，目标态） |
| **不做** | 去掉 worker 兜底（必要）、改动 ack 报文格式/协议（供应商无需感知） |

## 1. 现状时序与量化

```
供应商 ──POST──▶ 网关 ──▶ 验签 ──▶ 链(DECODE→MAPPING→ENCODE) ──▶ insert(inbound_delivery, PENDING)
                                                              │
                                              deliver()  ← **同步**，且复用带 @Retryable 的 UpstreamInvoker
                                                              │  预算 = interface.max_retries
                                                              │  尝试 #1..#(1+maxRetries)，退避 200/400/800/1600ms
                                                              ├─ 2xx ─────────▶ ACKED
                                                              ├─ 4xx(非 429) ─▶ DEAD_LETTER
                                                              └─ 其他/超时 ───▶ PENDING(+3s) ──▶ worker 重送
                                                              ▼
供应商 ◀──HTTP 200 ack── ackRenderer.render()   ← ack 的时延 = 上面**全部**之和
```

| 送达对端状态 | 单次尝试耗时 | 尝试次数 | 退避和 | **ack 延迟（timeout_ms=3000 / 10000）** |
|---|---|---|---|---|
| 立即被拒（端口无服务） | ≈0 | **5** | 3.0s | **≈3s** ／ ≈3s |
| 正常（毫秒级） | ≈10ms | 1 | 0 | ≈链耗时（忽略不计） |
| **每次都挂到读超时** | = `timeout_ms` | **5** | 3.0s | **≈18s** ／ **≈53s** |

> 依据：`RetryPolicy` 默认 `maxRetries=4`（`UpstreamInvoker.MAX_RETRIES`）⇒ 共 5 次尝试；
> 退避 `delay=200, multiplier=2, maxDelay=2000` ⇒ 200+400+800+1600 = **3.0s**；`InboundEngine.RETRY_INTERVAL_SECONDS=3`。

## 2. 影响面

| 场景 | 现状影响 |
|---|---|
| 回调地址不可达（本地没起 stub） | ack **白等 ≈3s** |
| 回调地址「慢」（每次挂到读超时） | ack 等 **18~53s** |
| **供应商回调有超时**（常见 5~30s） | 供应商可能**超时重发** ⇒ 平台收到重复回调 ⇒ 多行 `inbound_delivery`；**平台无幂等开关**（设计 §6.3：依赖供应商对业务键幂等） |
| worker 重送 | 单条慢记录阻塞扫描线程，**其他 PENDING 记录重送被推迟**（池仅 2 线程，且与告警 worker 共享） |
| 不受影响 | 链本身 / 送达状态语义（`PENDING`/`ACKED`/`DEAD_LETTER`）/ 补偿预算与死信 / 出站方向 |

## 3. 方案对比

| 方案 | 时序（收到回调后） | ack 延迟 | 改动面 | 主要风险 | 工作量 |
|---|---|---|---|---|---|
| **A 保持现状**（已做缓解：管理面自调 20s 专用作用域 + `50401` 可读报错 + 文档化） | 同步送达 → ack | 3s ~ **53s** | 0 | 供应商超时重发风险仍在；worker 被阻塞 | 0 |
| **B 完全异步**：落 PENDING → 立即 ack → **worker** 首投 | 立即 ack | **≈毫秒级** | `InboundEngine.handle` 去掉同步 `deliver` | 首投**延迟最多 3s**+调度抖动；同请求内看不到送达结果（工具/验收/测试要改） | ≈1 人日 |
| **C 首投不回内联重试**（半解耦） | 只投**一次** → 失败即 PENDING(+3s) → worker 重送 | 不可达 ≈0；慢对端 = **1×timeout_ms**（3s/10s） | `InboundEngine.deliver`：预算置 0（或新增 `invokeOnce`） | **改变 M3 定的「短重试」语义**（内联退避 → worker 3s 间隔）；对端 5xx 时节奏变化 | ≈0.5 人日 |
| **D 立即 ack + 后台首投一次**（目标态） | 落 PENDING → **提交异步首投** → 立即 ack | **≈毫秒级** | `InboundEngine` 拆 `deliverOnce` + **专用 executor**（有界队列 + 拒绝策略）+ 工具/验收/测试同步 | 线程模型变更；需防「同一 delivery 并发投递」（`claimForRedeliver` 已可复用）；结果不可同请求观察 | ≈1.5~2 人日 |

> **B 与 D 只差「首投是否延迟 3s」** ⇒ 做 D 则 B 无必要；D 可视为「B 的即时版」。
> **C 是 D 的前置**：D 落地后 worker 仍会在重送路径复用内联重试 ⇒ 若不一并去掉，单条慢记录仍会阻塞扫描。

## 4. 推荐与实施顺序

**第一步：C（首投不回内联重试）—— 建议先做**

- 收益：ack 延迟从「3s / 53s」降到「≈0 / 1×timeout_ms」；顺带缓解 worker 被单条拖住
- 低风险：状态机 / 死信 / 补偿语义**不变**（失败仍是 `PENDING(+3s)` → 重送 → 耗尽 → 死信）
- 代价：与 D-M3-2「5xx/429 短重试」的字面语义有出入 ⇒ **须在 M3 文档标注修订**（重试由内联退避改为 worker 3s 间隔）

**第二步：D（立即 ack + 后台首投）—— 目标态**

- 需要：专用 executor（建议独立 1~2 线程 + 有界队列）、`deliverOnce` 复用、可观测口径与验收/测试同步

**出口标准（两步都要）**
1. 不可达回调地址：`test-callback` 返回 P95 < 500ms（第一步 ≈0）；
2. 慢对端（每次挂到读超时）：ack 延迟 ≤ 1×`timeout_ms`（第一步）/ ≈链路耗时（第二步）；
3. 送达语义回归：原有 `M3IntegrationTest` 送达用例（ACKED / 4xx 死信 / 耗尽死信）全绿；
4. 文档同步：M3 开发计划 + 设计方案 §5.5 + 使用教程 + 验收方案。

## 5. 若做第二步，必须同步的清单（易漏）

| 项 | 现状 | 改后 |
|---|---|---|
| 验收方案 §3.1-③ | `deliveryStatus` 在同一响应里能看到 `ACKED`/`PENDING` | 恒为 **`PENDING`**（首投未做）⇒ 断言改为「稍后到监控页看」 |
| `/test-callback` 返回语义 | `deliveryStatus` 反映首投结果 | 恒 `PENDING` ⇒ **返回体需加提示**（否则会被当成"送达失败"） |
| `M3IntegrationTest` 送达用例 | 依赖同步送达后即 `ACKED` | 改为「等待/触发 worker 后再断言」 |
| M3 手动验收方案 / 整体测试方案 B 系列 | 同上 | 同上 |
| `CompensationWorker` 扫描 | 首投不在扫描内 | 首投失败行会出现在扫描队列（已有 `findDuePending` ✓） |

## 6. 风险与回退

| 风险 | 对策 |
|---|---|
| 异步后「同一回调重复投递」 | 复用 `claimForRedeliver` 的条件认领（仅 PENDING 才 attempt+1） |
| executor 队列打满 | 有界队列 + 拒绝策略（拒绝即**仅靠 worker 兜底**，日志告警）；不复用 2 线程的 `taskScheduler`（它与补偿/告警共享） |
| 进程崩溃丢首投 | 不丢：`inbound_delivery` 已落 `PENDING`，worker 会扫到 |
| 回退 | 两步都是**局部**改动：C 改一处预算；D 加开关（`app.api-center.inbound-async-delivery: false` 即回落同步） |

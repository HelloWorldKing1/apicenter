# 技术踩坑记录（Spring 7 / Jackson 3 / WireMock 3 适配经验）

> 记录 M1/M2 编码中踩过的 API 差异坑，全部为 Spring Boot 4.1 / Spring Framework 7 / Jackson 3 相对旧版的破坏性变化。
> **教训：Spring 7 大量沿用类名但改签名/改行为，凡用旧版记忆写代码，先查本文件再动手。**

## 1. Spring 7 内置 @Retryable（替代 spring-retry，差异巨大）

| 项 | 旧 spring-retry | Spring 7 内置（实际） |
|---|---|---|
| 包 | `org.springframework.retry.annotation` | `org.springframework.resilience.annotation`（启用注解 `@EnableResilientMethods` 同包） |
| 退避配置 | `@Backoff` 注解 | **内联属性**：`delay` / `multiplier` / `maxDelay` / `jitter` / `timeUnit`（无 @Backoff 类） |
| 重试条件 | `retryOn` | `includes` / `excludes` / `value` |
| 动态次数 | `maxAttemptsExpression` | `maxRetriesString`（SpEL）——**注意：见下方大坑，实际不可动态**；语义是**重试次数**（非总次数，total attempts = 1 + maxRetries） |
| 耗尽异常 | `RetryExhaustedException`（包装原异常） | **透传最后一次的原异常**（无包装） |

**写法范例**（独立 Invoker 类——AOP 自调用不触发代理）：

```java
@Retryable(includes = {HttpServerErrorException.class, TooManyRequests.class, ResourceAccessException.class},
        predicate = UpstreamInvoker.InterfaceRetryBudgetPredicate.class,  // 动态预算走 predicate（见下）
        maxRetries = RETRY_CAP,  // 注解值固定为上限；真实预算由 predicate 按次判定
        delay = 200, multiplier = 2, maxDelay = 2000, timeUnit = TimeUnit.MILLISECONDS)
public ResponseEntity<byte[]> invoke(...) { ... }
```

验证方式：`javap -classpath spring-context-7.0.8.jar org.springframework.resilience.annotation.Retryable` 看属性。

### 1.1 大坑：`maxRetriesString` 的 SpEL 并非每次调用求值（M4 缺陷修正）

`RetryAnnotationBeanPostProcessor.getRetrySpec` 把 `MethodRetrySpec` 按方法级 key 缓存
（`retrySpecCache: Map<MethodClassKey, MethodRetrySpec>`），`maxRetriesString` 的 SpEL
**只在首次调用该方法时求值一次**，之后所有调用复用缓存的 `maxRetries`——
「`maxRetriesString = "#{@bean.currentMaxRetries()}"` + ThreadLocal」方案**实际不生效**：
整个 JVM 内该方法的重试次数被首次调用时的 ThreadLocal 值固定
（M4 集成测试暴露：上下文首次调用是 maxRetries=0 的接口，后续 maxRetries=2 的接口不再重试）。

**正确姿势**：用 `@Retryable(predicate = Xxx.class)` 扩展点（每次尝试后回调，与 includes 取 AND）
承担真实预算——注解 `maxRetries` 固定为上限常量，predicate 内按 ThreadLocal 失败计数与
本次调用引擎设置的接口级预算比对。引擎须以 `beginRetryBudget(n)` / `endRetryBudget()`
包裹顶层调用（重置/清理 ThreadLocal，Tomcat 线程池复用防串账）。实现见 `UpstreamInvoker`。

## 2. Jackson 3（tools.jackson.*）

- 包名 `tools.jackson.*`，不是 `com.fasterxml.jackson.*`（依赖 `tools.jackson.dataformat:jackson-dataformat-xml`）。
- **`JsonNode.fields()` 已更名为 `properties()`**（ObjectNode 遍历）。
- Spring 注入的 `ObjectMapper` 是 `tools.jackson.databind.ObjectMapper`。

## 3. Spring 7 Web 客户端

| 坑 | 结论 |
|---|---|
| `HttpClientErrorException.TooManyRequests` 构造器**全部私有** | 用静态工厂 `HttpClientErrorException.create(statusCode, statusText, headers, body, charset)`——按状态码返回对应子类（429 → TooManyRequests 实例），重试类型匹配不受影响 |
| `JdkClientHttpRequestFactory` **无 `setConnectTimeout`** | 只有 `setReadTimeout(Duration)` |
| `@RequestBody` 无 `value` 属性 | 只有 `required`；显式命名只用于 `@PathVariable` / `@RequestHeader` |
| `HttpHeaders.addAll(MultiValueMap)` 不适用 | 逐条目添加：`spec.headers().forEach(h::addAll)`（`addAll(String key, List<String> values)`） |
| **声明式客户端（@HttpExchange）URI 模板变量被路径编码** | 完整 URL（含 `://`）作为 `{url}` 变量时经 DefaultUriBuilderFactory 展开被编码（`://` → `%3A%2F%2F`），scheme 丢失报 `URI with undefined scheme`。**动态完整 URL 场景不用声明式客户端**，改用 `RestClient` 直调：`restClient.method(m).uri(URI.create(url)).headers(...).body(...).retrieve().toEntity(byte[].class)`（`uri(URI)` 不经过模板展开）。详见 M0-03 C1 验证点结论 |
| **RestClient 直调默认对 4xx/5xx 抛异常**（声明式客户端返回 ResponseEntity 不抛） | 用 `defaultStatusHandler(HttpStatusCode::isError, (req, resp) -> {})` 禁用，统一返回 ResponseEntity 由引擎分类（4xx 死信 / 429·5xx 由 Invoker 手动抛触发重试） |
| `JdkClientHttpRequestFactory` **无 `setConnectTimeout`** | 只有 `setReadTimeout(Duration)`；连接超时须经自定义 `HttpClient.newBuilder().connectTimeout(...)` 设置 |
| **`JdkClientHttpRequestFactory.setReadTimeout` 是实例级字段（无 per-request 入口）** | `createRequest(uri, method)` 只读 `this.readTimeout`；`JdkClientHttpRequest` 及其构造器均为**包私有**（业务包无法逐请求构造）；`ClientHttpRequestInitializer` 只能改 header/body。**要按请求改读超时只有两条路**：① 委托 + **按超时值缓存工厂实例** + 栈式 ThreadLocal 作用域（本项目采用：`PerRequestReadTimeoutFactory` + `UpstreamInvoker.dispatch` 声明作用域，D-PS-0）；② 换 `HttpComponentsClientHttpRequestFactory`（Apache HttpClient 5，`RequestConfig` 支持 per-request，但要加依赖）。另：Spring 的读超时是**本地等待取消**（`TimeoutHandler` cancel CompletableFuture），供应商是否已收到不可判定 → 超时映射 UNKNOWN 对账的语义不变 |
| **`addCorsMappings` 白名单写死单 Origin → 403 `Invalid CORS request`** | Spring **只跳过同源**请求的 CORS 校验；`127.0.0.1` ≠ `localhost`（不同 Origin），Vite 端口自增（5173→5174）同理 ⇒ 未列入白名单的来源上**所有写请求**（带 Origin 的 POST/PUT/DELETE）被拒在 CORS 层，**不进引擎**（无 call_log，易误判业务故障）。用 `allowedOriginPatterns("http://localhost:[*]", "http://127.0.0.1:[*]")`（端口通配有效）+ 配置项可覆写；置空则不注册（同源/反代无需 CORS） |
| 注解按参数名匹配（`@PathVariable` 等）依赖 `-parameters` | Maven 默认不开，**显式命名** `@PathVariable("url")` 最稳（不过 URI 模板坑仍然存在，见上） |

- **Boot 4 移除了 `TestRestTemplate`（2026-09-18）**：`org.springframework.boot.test.web.client` 已不存在（spring-boot-test 4.1 无该类）。集成测试发真实 HTTP 统一用 `RestClient` + `@LocalServerPort`，并 `defaultStatusHandler(HttpStatusCode::isError, (req, resp) -> {})` 禁抛以便断言状态码（与 M3/M4/M5 同款）。
- **`JdbcTemplate` 位置绑定错位不报错（2026-09-18）**：`insertBatch(sql, entries, size, setter)` 全位置绑定——加列/改列顺序时若只改 SQL 不改 `ps.setXxx(i, …)` 序号，会**静默把值写进相邻列**（不抛异常）。`call_log` 加 `step_code` 时必须同步四处：DDL、列清单与占位符、setter 序号、投影列与 `toView`。

## 6. 测试与种子数据

- **列表接口不带子表**（`InterfaceService.list()` 的 params 等恒空）——断言/校验子表必须走 `detail()`；SeedDataInitializer 完整性校验也用 detail。
- **集成测试数据自清理**：cleanup 必须先级联删测试接口（6 子表）再删应用，否则残留接口污染后续测试（唯一键冲突）。
- **乐观锁测试要真跑两遍 update**：M1 曾把响应的 model 类型子表误塞进请求 DTO（ParamRow vs ParamDto），类型不匹配编译失败。
- `UnifiedModel.get()` 契约上把 NULL 标量视为「不存在」——测试要区分「写了 null」与「没写」时直接读 `root()` 字段。

- **改完必须确认“真的落地了”（2026-09-18 教训）**：批量编辑工具按“文件 + 片段”匹配，一旦路径/片段写错会整体不应用且容易忽略返回值——本轮 `AlertService.evictRule` 的修复就这样丢了，最终由针对性测试抓回。**纪律**：每批改动后 ① `grep` 确认关键行存在、② 编译、③ 至少一条针对性用例覆盖该行为（本次新增用例的价值就在这里）。

## 7. 排查方法论

- 引擎 catch-all 分支（"平台内部错误"）会吞根因：**log.error 带完整堆栈**，排查时用 `mvn test -Dtest=XxxTest 2>&1 | grep -B2 -A15 "执行异常"` 快速定位。

## 8. M5 版本化与灰度（2026-09-07 新增）

- **同 impl 多版本启用的 D6 冲突**：原「同 impl 至多 1 条 enabled」校验会堵死灰度（同 impl 第二版本无法启用）。M5 放宽为 **(impl, version) 维度唯一**——`AdapterRepository.countEnabledByImplVersion`，同版本重复实例仍拒绝（`M5IntegrationTest.d6放宽` 覆盖）。
- **链缓存真实烘焙面比注释小**：M5 二轮核实发现原链缓存只烘焙协议选择与 ifType——绑定/映射/参数/凭证全是每请求实时读（远程库 ~百毫秒/次，正是 M4 实测 IN ~1s 主因）。解析时机上移后**绑定/映射/参数一次烘焙**，凭证保持实时；配置即时生效从此依赖 `ConfigChangedEvent`（新增配置入口必须补发事件，见 CLAUDE.md Gotchas）。
- **响应信封适配与链必须同源**：OutboundEngine 原单独直读 binding/adapter 解析 MESSAGE（忽略 version），灰度后响应剥壳会与请求方向用的版本不一致——改为 `ChainEngine.boundInstance(interfaceId, "MESSAGE")` 取链装配烘焙实例。
- **配置 JSON 字符串断言别带引号**：version detail 的 `configJson` 是 JSON 字符串，内层引号被转义（`\"order_state\"`）——子串断言用 `order_state`（无引号），否则必挂。
- **事件失效断言要清 WireMock 计数**：`verify(0, ...)` 前必须 `resetAll()`——前面请求已计入同 URL 匹配，否则假阳性（M5 s2 首跑即踩）。
- **变更说明走 `X-Change-Note` 头而非扩展 DTO**：避免改 `InterfaceRequest` record 波及 15+ 构造调用点（M1-M4 测试 + seed）。

### H1/H2 代码评审修复（2026-09-07）
- **链缓存失效必须在事务提交后**：原 @EventListener 在 @Transactional 方法内同步清缓存（早于 commit）——「clear → 并发请求从旧配置重装入缓存 → commit 后无二次事件」，陈旧链最长残至 TTL 5 分钟（灰度「即时生效」并发下不成立）。改 ChainEngine 监听为 `@TransactionalEventListener(fallbackExecution = true)`（默认 AFTER_COMMIT；无事务发布立即执行）。新增配置入口仍须补发事件，但不必担心发布时机——监听端统一后置。
- **change_note 超长直插 500**：列 VARCHAR(255)，header/回滚拼接无约束时超长抛 DataIntegrityViolation。三层防护：RollbackRequest.operator/reason `@Size(max=100)`、`InterfaceService.update` 唯一入口限长 250 兜底、前端 maxlength 提示。

## 9. 前端（Vue3 + Vite，2026-09-12 新增）

- **computed/watcher 在 JS 里必须 `.value`**：`<script setup>` 中 `const view = computed(...)` 之后，**只有模板会自动解包**；在 JS 表达式里写 `view.formatted` / `view.pretty` 一律得到 `undefined`（静默，不报错）。
  - 实证：`PayloadViewer.vue` 的 `shown = computed(() => mode.value === 'pretty' && view.formatted ? view.pretty : view.raw)` → `shown` 恒为 `undefined` → 抽屉正文恒显占位符「—」，而工具栏（模板里 `view.lang` / `view.length`）**恰好正常**，极易误判成数据没返回。
  - 排查手法：`node -e` 里直接跑 `view.formatted` vs `view.value.formatted` 对比，或对组件做 SSR 渲染看输出（`vite build --ssr` + `vue/server-renderer`，本项目已固化为 `npm run test:ssr`）。
  - 防复发：跨组件复用的展示规则提成纯函数（如 `pickPayloadText`），并补「非空必显」断言 + 组件级 SSR 冒烟。
- **报文格式化不要 parse 重建**：`JSON.parse`+`stringify` 会改写 19 位数字尾数（`7494312521977267257`→`…267000`）、`1.10`→`1.1`、`1e3`→`1000`、重复键丢前一个；XML `DOMParser` 会规范化 CDATA / 实体 / 属性引号。改用字符串感知的扫描式缩进（只增删空白），截断报文也能用。
- **前端单测零依赖方案**：Node 24 内置 `node --test`，工具文件用 `.mjs` 后缀即可直接跑（无需给 package.json 加 `"type": "module"`）；脚本里需给 esbuild 设置 target 或避免顶层 `await`（`vite build --ssr` 默认 target 不含 TLA）。

### 前端 P2 补记（2026-09-12）
- **XML tokenizer 需要 `expectValue` 状态**：只判「是否已出现标签名」会把属性值（`a="1"` 里的 `"1"`）当成下一个属性名（`attr`）。正确做法：`=` 后置 `expectValue`，引号值整段作为 `attrvalue`，裸值（`a=1`）同样按 `attrvalue` 收。
- **Worker 在 Vite 下要 `{ type: 'module' }` 且必须做能力守卫**：`new Worker(new URL('../workers/x.mjs', import.meta.url), { type: 'module' })` 才会被打成独立分块（构建产物 `assets/*.worker-*.js`）；SSR/老环境没有 `Worker`，组件里必须 `typeof Worker !== 'undefined'` 守卫 + try/catch 降级，否则 `npm run test:ssr` 直接崩。
- **SSR 冒烟里断言 Element Plus 文案要先 stub 组件**：未注册的 `el-*` 渲染为占位注释，按钮/标签内的文案根本不出现在输出里（`展开全部（共 N 行）` 曾因此断言失败）。stub 用 `setup(props,{slots}) => () => h('span', slots.default?.())` 即可。
- **断言渲染文本要先剥标签再解码实体**：顺序反了会把报文里被转义的 `&lt;tag&gt;` 先还原成 `<tag>`，再被「剥标签」正则吃掉，导致 XML 断言假失败。

## 10. 时间窗 / DATETIME 精度（2026-09-12 新增，两条真坑）

- **MySQL `DATETIME`(0) 会四舍五入到秒，让「立即重试」变成「下一句才生效」**：
  `next_retry_at` 写入 `11:09:14.845` 被存成 `11:09:15`，而补偿 worker 用 `now=11:09:14.86` 查询
  `next_retry_at <= now` → 判定未到期，`C3` 用例随机失败（同一秒内调用 scan 必挂）。
  统一修法：所有时间列写入走 `repository/SqlTimes.ts(...)`，**先 `withNano(0)` 再进 SQL**（调度最多提前 <1s）。
  新增写 `next_retry_at` / 其他 DATETIME 列时务必复用它。
- **统计时间窗上界不要截断到秒**：`MonitorService.statWindow` 原来 `to = now().withNano(0)`，
  而 `call_log.created_at` 是 DATETIME(0)（DB 侧 CURRENT_TIMESTAMP）→ **本秒刚写入的行**满足
  `created_at == to`，被半开区间 `[from, to)` 排除；表现是 `top-interfaces` 偶发少一条（MonitorStatsIntegrationTest 抖动）。
  修法：`to = LocalDateTime.now()`（带毫秒），DATETIME(0) 比较天然把当前秒算进去。

## 11. 测试抖动的成因（2026-09-12 首轮三条 + 2026-09-18 补齐两条，值得复用）

- **窗口太短 + WAN 延迟**：M4 熔断用例用 10s 滑窗，5 次失败（每次含 2 次退避重试）在远程 PolarDB 下可能跨 10s →
  计数滑出窗口 → 偶发不开闸。测试里把 `sliding-window-seconds` 放宽到 120s（生产参数不变）。
- **共享上游的全局计数断言**：`wireMock.countRequestsMatching(...)` 的「前后采样相等」会被**后台 worker 的异步重放**
  污染（同一 URL）。改用**按 traceId 归属**断言：测试自造 `X-Trace-Id`（引擎会透传上游），
  `postRequestedFor(url).withHeader("X-Trace-Id", equalTo(trace))` 计数为 0 即证「未触达上游」。
- **有界批量扫描 + 立即断言**：补偿 worker `LIMIT 100` 且按 `next_retry_at` 排序，测试造的行可能被历史积压挤出本批 →
  改「有界重扫（最多 5 次、每次 200ms）」再断言，既确定又不放水。
- **`@Scheduled` 的「启动首跑」是和用例抢跑的黑手**：`fixedDelay` 任务在**上下文启动后立即执行一次**，
  它可能正好插在「用例造数」与「用例手动 scan()」之间，把 COMPENSATING 记录判成 DEAD_LETTER（StateChain 偶发）。
  修法：给两个 worker 增加 ***-initial-delay-ms** 配置（默认 0 保持生产行为），集成测试统一置 1h，用例完全手动驱动。
  加了线程池（poolSize=2）后两个 worker 的启动首跑从「串行」变「并行」，会让这类竞态更早暴露——不是池的错，是竞态本来就在。
  > **2026-09-18 追记：上面说的「集成测试统一置 1h」当时只盖了 M2/M3/M4/StateChain 四个类**；M1/M5/MonitorStats/ApicenterApplicationTests
  > 仍用默认 initial-delay=0 → 它们各自上下文的**启动首跑**（以及 Spring 上下文缓存下残留的 scheduler）会在全量套件里
  > 与其它类的用例抢跑。已在 2026-09-18 补齐（8 个类全部覆盖四个属性）。
- **`scan()` 是全局的，库里的历史残留行会「替别人跑」（2026-09-18）**：`compensationWorker.scan()` 的
  `findDueCompensating` / `downgradeExpiredUnknown` **不按应用过滤**——用例手动 scan 时，库中任何应用、
  乃至**上一次运行遗留**的到期行都会被处理（日志可见 `outbound_request 1` / `inbound_delivery 9` 这类小 id 残留）。
  症状：状态链凭空多出 `COMPENSATING → DEAD_LETTER` 节点、replay 的行被别人先耗尽。
  三件事一起做：① 测试类全部置大 initial-delay（见上条）；② 开发库不留孤儿死信
  （`DELETE FROM dead_letter WHERE biz_type='OUTBOUND' AND ref_id NOT IN (SELECT id FROM outbound_request)`，INBOUND 同理）；
  ③ 耗尽告警带诊断数值（`CompensationWorker` 已补 `attempt/max/interface/biz_id`，2026-09-18），下次再红一眼定位。
- **开发库 = 测试库：断言「seed 资产的库态」的用例会被真实使用打破（2026-09-18 实测两处）**：
  `M1IntegrationTest#黄金用例配置可回读校验` 直接断言 seed 资产的当前库态，而真实联调会改这些库态——
  ① 给 `IF-FM-001` 补前置适配映射 ⇒ 原断言 `mappings()).isEmpty()` 变红；
  ② 真机更新出站凭证 ⇒ M0-04 轮换语义（新→ACTIVE、旧→ROTATING 24h，再更新则 RETIRED）⇒ 原断言 `hasSize(1)` 变红。
  两类修法都是**改成语义断言**：映射「空（透传）**或**含联调目标」二选一；凭证「**恰有 1 条 ACTIVE**，其余只能是 ROTATING/RETIRED」。
  结论：**断言库态的地方不要写死条数/是否为空**（要写死就用测试自建夹具，如 M2 的 `goldenInterface(...)`）。
- **测试造数不要用 `NOW()` 做“立即到期”（2026-09-18）**：把 `next_retry_at` 置为 `NOW()` 后立即调 `scan()`，在**远程库**（PolarDB）上会因库时钟相对应用时钟**领先**（百毫秒级）而让该行落入未来 → `findDueCompensating` 不命中 → 用例发捣（本地库往往看不出）。造数一律写成 `NOW() - INTERVAL 5 SECOND`。注意生产代码（`resetForReplay` / `degradeUnknownToCompensating`）仍写 `NOW()`：最坏只推迟一个扫描周期（3s）后自愈，不影响正确性。
- **链内钩子抛出的异常必须在引擎层捕获（2026-09-18，前置编排）**：`ChainEngine.assemble` 的 MAPPING 闭包内抛出的 `PreStepFailure`，而 `OutboundEngine.doInvoke` 的 `chainEngine.execute(...)` **在它的 try/catch 之外**——不补捕获边界，异常会直接冒到 `execute()` 的 `catch(BizException)` 原样透出，记录停在 `INIT`，`COMPENSATING`/`UNKNOWN` 两个出口永远走不到（设计稿 v0.1.1 曾漏计这一改动，v0.1.2 评审时修正）。同类风险：以后任何「往链里插钩子」的方案都要同时确认**谁捕获、写到哪个出口**。
- **链引擎与执行器的构造环用 `ObjectProvider` 破（2026-09-18）**：`PreStepExecutor → ResponseJudger → ChainEngine`，而 `ChainEngine` 又需要在装配时调用 `PreStepExecutor` → 构造期直接注入会循环。用 `ObjectProvider<PreStepExecutor>` 拿延迟句柄（请求期解析，此时本 Bean 已构造完），比 `@Lazy` 代理更直白。
- **`interface_step` 保留键与命名空间（2026-09-18）**：前置步骤结果挂 `steps.<stepCode>.<field>`，写入**必须**用字面量键（`ObjectNode.fields().put`），**禁**走 `UnifiedModel.set("steps.a.b.c")` 点路径解析（前置接口的字段名含 `.` 会被拆层）；交前置前 `withoutSteps`、宿主 ENCODE 前 `stripSteps`——两道缺一就会把数据发给不该发的一方。

- **多态 `ref_id` 的清理会误删另一方向（2026-09-18）**：`dead_letter.ref_id` 是**多态引用**
  （OUTBOUND→`outbound_request.id`，INBOUND→`inbound_delivery.id`），两表自增 id 空间重叠——
  `WHERE ref_id IN (SELECT id FROM outbound_request WHERE app_id=?)` **不筛 biz_type 会误删同 id 的入站死信**
  （症状：「死信凭空少一条」，且只在 id 碰巧重叠时偶发）。修法：两个 `deleteByApp` 已各加 `AND biz_type='OUTBOUND'|'INBOUND'`。

## 12. 事务边界与模型共享（2026-09-18 新增，两条真坑）

- **批处理循环不要挂方法级 `@Transactional`**：补偿/TTL 这类 worker 是「扫一批、逐行处理」，方法级事务会让
  **一行失败回滚整批**（丧失部分进度）。正解：注入 `PlatformTransactionManager` 自建 `TransactionTemplate`，
  在**循环体内逐行** `executeWithoutResult(...)`（状态写 + 审计写同成败），单行异常单独 catch 记录。
  已按此处理 `MonitorService.downgradeExpiredUnknown`（另一处 `reconcile`/`replayDeadLetter` 是单次操作，方法级即可）。
- **`UnifiedModel` 的共用实例会串链（前置编排真坑）**：`AdapterContext.payload` 是可变的链路载体，而
  `MappingEngine` 在规则非空时会执行 `ctx.payload().root(newRoot)`。任何「把宿主模型交给另一条子链」的地方
  **必须返回新的 `UnifiedModel` 包装**（哪怕只是 `UnifiedModel.of(同一个 root 节点)`）——共享同一实例时，
  子链的 MAPPING 会把 root 写回宿主载体，宿主后续字段映射将基于**子链的映射结果**（症状：宿主自己的字段变成
  `null`，且很久都看不出原因）。修法见 `ReservedKeys.withoutSteps`；判别用例
  `PreStepIntegrationTest#前置接口自身带映射_不得污染宿主模型`（用精确报文断言 + 临时还原旧行为反证过）。

## 13. 前置编排的入参语义与透传陷阱（2026-09-18 真实事故，五条）

> 事故：`POST /brief/create`（宿主 A）→ `40001 前置步骤 fm 失败：业务失败（HTTP 200，code=1：params error）`。
> 根因不是编排坏了，而是**责任边界没被理解**：把「被调接口」当成了会按自己 IN 声明取值的正常入站调用。

- **前置调用的入参 = 宿主入站模型原样**（`ReservedKeys.withoutSteps(宿主模型)`，DECODE 跳过）；
  **被调接口的「入站参数」声明完全不参与取值**——它只描述「别人直调它」时的入站契约（解码类型提示/文档/校验）。
  于是「`seller_id` 怎么变成第三方的 `filter.seller_id`」只能由**被调接口自己的字段映射**负责（点路径 target 会自动建中间对象）。
- **被调接口映射为空 = 整体透传 ⇒ 宿主的多余字段会外泄给第三方**（事故里把宿主的 `prompt` 一起发了过去），
  第三方常见反应就是 `params error`；**规则非空即切白名单**（只输出 target 命中字段）——补映射顺带修掉外泄。
- **`nullStrategy` 语义要用对**（`MappingEngine.applyNullStrategy`）：`KEEP` = 源缺失时**写出 JSON null**（`{"page":null}` 常被判参错）、
  `NULL` = **省略该字段**（大多数场景的正解）、`DEFAULT` = 零值 `""`、`ERROR` = 直接抛错。
  多形态入参（同一接口既被直调又被前置复用）一律用 `NULL`：两条 rename 互相缺席即省略，天然共存。
- **`default` 写的是字符串**：用它给数字字段补 `page=1` 会发出 `"page":"1"` → 第三方判参错。
  数字/数组必须由调用方传**原生 JSON**，或走 `typeCast`（但 `typeCast` 的 source 只能读**入站**模型，读不到同批规则刚写入的值，无法链式补齐）。
- **宿主映射在前置之后执行** ⇒ 宿主的映射**无法**影响前置入参（想做「先整形再传」需编排二期 overlay/入参显式声明）；
  调试口径：**调用日志里「步骤=xxx」那条的 `reqBody` 就是「发给第三方什么」的实录**（`step_code` 列已落地，可按步骤筛）。

> 回归守护：`PreStepIntegrationTest#前置接口映射把宿主扁平报文适配成第三方嵌套报文_白名单且缺席字段省略`
> （严格报文相等 + `notContaining("prompt")` + `notContaining("null")`）；界面侧在「前置步骤」Tab 顶部常驻语义提示。

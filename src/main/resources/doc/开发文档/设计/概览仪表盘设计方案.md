# 概览仪表盘（Dashboard）升级设计方案

> 版本：v0.1（2026-09-07 待评审，已按拍板落地）｜范围：`frontend/src/views/Dashboard.vue` + 少量监控查询端点
> 实施状态：B1 采纳（ECharts 按需）；B2 首版仅调用量降序；B3/M4 索引已应用开发库并同步 schema.sql；B4 趋势随全局范围切换手动刷新、主卡 10s 轮询。对应后端端点 `/monitor/stats/trend`、`/monitor/stats/top-interfaces`。
> 目标读者：评审确认后即编码；本稿只做「页内信息架构 + 数据口径 + 接口契约」，不改既有页面路由与后端告警/对账逻辑。

## 1. 现状与问题

现状（对应代码事实）：
- 顶部 4 统计卡：应用数 / 接口数（来自 `/apps`、`/interfaces` 列表）+ 今日调用量 / 今日成功率（来自 `/monitor/overview`，终态口径 SUCCESS/(SUCCESS+DEAD_LETTER)、无终态显示 100）；
- 中部「最近调用日志」8 条（复用 `/monitor/call-logs`，仅展示，无跳转/详情）；
- 底部「使用提示」纯静态文本（内容还停留在「下一步 M5」的旧叙事）。

问题：
1. **只有「此刻/今日」一个时间断面**，看不到趋势——供应商健康度恶化、限流误触发、QPS 突刺都无法在首页体感；
2. 卡片无**健康语义**：成功率/积压孤立呈现，异常不醒目（没有阈值变色、不指向告警）；
3. 最近日志**只展示不可查**：无 traceId 直达监控/审计、无请求/响应体详情（数据已在 call_log 落库且脱敏）；
4. 「使用提示」信息陈旧且与使用无关——概览页应承载数据而非叙事；
5. 无**接口/应用排行**：多接口（fastmoss + M3/M4/M5 演示）时看不出谁在产生流量/失败。

## 2. 设计目标与原则

- **30 秒判健康**：进页即回答——现在通不通（终态成功率 + 积压）、在涨还是在跌（趋势）、谁在失败（排行）；
- **口径唯一且可追溯**：凡数字均标注口径来源（状态机终态 / call_log HTTP / Prometheus），并在页面悬浮提示写明定义，杜绝「两个页面数字对不上」；
- **浅层数据、深层跳转**：Dashboard 只放聚合；点 traceId / 接口 / 应用 → 跳「接口监控」对应过滤态（query 参数深链）；
- **沿用 Element Plus**；趋势图引入 **ECharts 5（按需注册）**（见 §6 拍板点 B1）；
- 新增聚合端点一次性做齐，Dashboard 与 Monitor 共用，避免两边各写一套口径。

├────────┬────────┬────────┬────────┬──────────────────────────┤
│ 应用数 │ 接口数 │ 今日调用│ 今日成功│ （四个主卡，含积压/告警角标） │
│   12   │   34   │ 1,203  │  98.2% │                          │

## 4. 区块详设

### 4.1 主卡区（4 卡 + 角标）
| 卡 | 值 | 副文案 | 口径 / 数据源 |
|---|---|---|---|
| 应用数 | 数量 | `本月新增 N / 启用 M` | `/apps`（长度 + status 计数，一次拉取前端统计） |
| 接口数 | 数量 | `已发布 N` | `/interfaces`（status 计数） |
| 今日调用量 | 数量 | `成功 S · 死信 D` | `/monitor/overview`（现状复用） |
| 今日成功率 | % | 终态口径提示 | `/monitor/overview`（现状复用） |

增强点（在 4 卡旁新增两个**健康角标位**，不改变 4 卡布局）：
- 红色角标：`死信/对账中`（deadLetterBacklog + unknown）> 0；
- 黄色角标：`待补偿/待重送`（compensating + pendingRedelivery）> 0；
- 角标可点击 → 跳 Monitor 对应区块（深链）。
- 时间范围（1h/24h/7d）只作用于**趋势与排行**，主卡恒为「今日」（口径与 overview 严格一致）。

### 4.2 调用流量趋势（新增，核心）
- 图型：折线；双 Y：左=IN 调用量（入站流量，即客户看到的平台流量），右=OUT 失败数（出站终态失败）；
  - 简化：单图两条线 = IN calls 总量 + 出站 FAIL 数（COMPENSATING→SUCCESS 前的失败瞬间不计，**FAIL 口径 = 按小时终态 DEAD_LETTER+UNKNOWN 计数**，见 §4.5 口径表）。
- 空态：无数据时给引导文案（引导看 Monitor 调用日志）。
- 数据：新增 `GET /monitor/stats/trend`（§5.2）。

### 4.3 延迟趋势 P50/P99（出站）
- 数据：call_log direction=OUT、status 非 4xx 客户端错（含超时），分桶取 P50/P99；
- 与告警 `p99_latency`（近 5 分钟、最新 5000 条近似）**同一列、同近似算法**，悬浮提示写明「近似值（最新 N 条），长窗口为抽样」；
- 折线两条（P50/P99），同一 Y 轴 ms。

### 4.4 今日 TOP 接口
- 列：接口（code + 平台路径）、应用、调用（IN 次数，call_log）、终态成功率、P99（OUT）、操作（「监控」深链）；
- 排序默认按调用量降序、`limit=8`；`metric` 切换 qps / p99 / failRate（拍板点 B2：首版是否只做调用量降序）；
- 数据：新增 `GET /monitor/top-interfaces`（§5.3），聚合口径以 call_log + outbound_request 终态为准。

### 4.5 运行队列面板
- 复用 `/monitor/overview` 四个积压字段直接渲染（compensating/pendingRedelivery/deadLetterBacklog/unknown）；
- 每项带色点 + 「去处理」深链（UNKNOWN → Monitor 对账区块 / 死信 → Monitor 死信区块）；
- **自动轮询 10s**（沿用 Monitor 现状节奏），tab 不可见时暂停（页面可见性 API）。

### 4.6 最近调用 + 详情抽屉
- 默认 8 条、展开「加载更多 20 条」；列沿用现状；
- 行点击 → 右侧抽屉：
  - 基础：方向/接口/应用/URL/HTTP 码/耗时/traceId；
  - **请求/响应（脱敏后原文）**：直接展示 call_log.req_headers/req_body/resp_body（落库即脱敏 + 4096 截断，正文标注截断提示）；
  - 操作：「复制 traceId」「在监控中追踪」（跳 Monitor?traceId=xxx 过滤态）「打开接口详情」（跳接口页）；
- 数据：现有 `/monitor/call-logs`（pageSize≤100 已够）。

### 4.7 「使用提示」替换
- 删除静态叙事段；替换为 3 行环境信息条（后端连接 / 种子数据提示可折叠）：
  - 折叠面板「数据说明」：口径表 + 保留策略说明（v1.1 归档）+ 本页数据链路（overview 实时查库 / 趋势为聚合查询）。

## 5. 数据与接口契约

### 5.1 口径总表（页面所有数字必须落在此表内，防口径漂移）
| 名称 | 精确定义 | 来源 | 用于 |
|---|---|---|---|
| 今日调用量 todayCalls | 今日 call_log IN 条数（接入口径，含失败） | `/monitor/overview` | 主卡 |
| 今日成功率 successRate | 今日 outbound_request 终态 SUCCESS/(SUCCESS+DEAD_LETTER)，无终态=100 | `/monitor/overview` | 主卡/TOP 接口 |
| 失败数 FAIL | 出站终态 DEAD_LETTER + UNKNOWN（按时间窗） | outbound_request.updated_at | 趋势 |
| P50/P99（出站） | call_log OUT 条 latency_ms 分位（近似：窗口内最新 5000 条，与 AlertWorker.p99 同算法） | call_log | 延迟图/TOP 接口 |
| IN 调用量 | call_log direction=IN 条数 | call_log | 趋势/TOP 接口 |
| 积压四件 | COMPENSATING / PENDING / DEAD_LETTER(PENDING 死信) / UNKNOWN 当前计数 | `/monitor/overview` | 队列面板 |

> 注：成功率不走 call_log HTTP 口径（业务失败 code≠0 会污染 2xx 统计），终态口径是状态机事实，两者差异在口径表悬浮提示中写明。

### 5.2 新增端点 `GET /api/admin/monitor/stats/trend`
```
入参：range=1h|24h|7d（默认 24h）· step 由后端按 range 归一（5min/30min/2h）
      appId? interfaceId? direction?（默认全量）
出参：{ buckets:[ {ts, inCalls, inFailHttp, outCalls, outSuccess, outDead, outUnknown, outP50, outP99} ] }
```
- 聚合 SQL：IN 桶取自 call_log（GROUP BY 桶 by created_at）；出站终态桶取自 outbound_request（updated_at 桶，SUCCESS/DEAD_LETTER/UNKNOWN 计数）——与 alert 的 idx_outreq_updated 同索引；
- 空桶补 0；桶数上限 ~ 7d/2h = 84 点（图表可读）；
- 成本/缓存：远程 PolarDB 每 SQL ~百毫秒 → 结果内存缓存 60s（`@Cacheable` 或简单 LRU，单机），键含入参哈希；
- 索引建议（拍板点 B3）：call_log 现无 (app_id, created_at) 组合索引，若 appId+7d 查询变慢，追加 `idx_call_app_time (app_id, created_at)`（同 idx_call_time 可复用，7d 无过滤可不用新索引）。

### 5.3 新增端点 `GET /api/admin/monitor/top-interfaces`
```
入参：range（同 5.2，默认今日? 建议 range 与全局时间范围联动）· limit(默认 8, ≤20)
出参：{ list:[ {interfaceId, code, path, appId, appName, inCalls, successRate,
                dead, unknown, p50, p99} ] }  排序字段入参 metric=qps|successRate|p99 之二选一/全部
```
- 实现建议：一次性聚合（call_log IN 计数 + outbound 终态按接口）→ Java 内存 join → 排序截取；
- 冷门接口零流量也保留列表尾部（`interface` LEFT JOIN），便于看到「配置了但没跑」的接口（运维价值）。

### 5.4 复用端点（不新增）
`/monitor/overview`、`/monitor/call-logs`、`/apps`、`/interfaces`——均已有参数/性能可用。

## 6. 实施拆解与拍板点

### 6.1 拆解（前端为主）
| 任务 | 内容 | 依赖 |
|---|---|---|
| T1 布局改造 | 4 卡角标 + 时间范围切换 + 队列面板 + 折叠数据说明 | — |
| T2 图表底座 | 引入 ECharts 按需；趋势/延迟两图组件 | 拍板 B1 |
| T3 聚合端点 | `/stats/trend` + `/top-interfaces` + 60s 缓存 + 索引（可选） | 后端 |
| T4 日志详情抽屉 + 深链 | 抽屉渲染脱敏体、traceId/接口跳转 | — |
| T5 联调与口径核对 | 与 Monitor/Overview 对同一批造数核对一致 | T1–T4 |

### 6.2 验收点
- 同一时间窗下 Dashboard 与 Monitor/告警的 成功率/P99 数字一致（口径表生效）；
- 深链跳转后 Monitor 过滤态与点击来源一致（含 traceId）；
- 空数据环境无图表报错、有引导文案；轮询停止随页面隐藏。

### 6.3 开放问题（拍板后编码）
- **B1 图表库**：推荐 ECharts 5 按需（折线面积图）——体积 ~50KB gzip；备选 0 依赖（CSS 渐变条 + 数字）作为降级；是否接受引入？
- **B2 TOP 排行排序**：首版仅「调用量降序」or 支持 metric 切换（qps/p99/失败率）三 tab？
- **B3 索引**：趋势查询按 app 过滤 7d 时是否接受追加 `idx_call_app_time`（需执行 ALTER，开发库可随时加，生产 PolarDB 需评审）？
- **B4 自动刷新**：趋势图是否轮询（建议 60s，仅 range=1h 时活跃），还是仅手动刷新？

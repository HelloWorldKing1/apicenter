## 2. 设计定稿（编码前必读）

### 2.1 D-M3-1 XML 编解码语义（XmlProtocolAdapter）

M0-01 D5 平台默认参数（无命名空间 / 元素映射 attrVsElement=ELEMENT / 根元素约定名）的落地解释：

| 方向 | 语义 |
|---|---|
| 解码 | 元素 → OBJECT fields（**多次同名元素合并为 ARRAY，单次保持单值**）；**空元素 → NULL（与编码对称，保证编解码往返一致）**；XML 属性 → `UnifiedModel.attributes`（M2 已预留；**JSON 输出时属性丢弃，仅 XML→XML 场景保留**）；CDATA 按文本；**混合内容（文本与子元素并存）→ 40002 拒绝**；命名空间首期忽略（剥离前缀）；根元素名不进入模型 |
| 类型 | XML 全文本，解码后按接口入站参数声明（`interface_param.type`）经 TypeRegistry 转换（仅**顶层字段**，参数声明为扁平结构），未声明参数保持 STRING（M0-01 §1 既定） |
| 编码 | fields → 元素、attributes → 属性；输出 `<?xml version="1.0" encoding="UTF-8"?>` + 约定根元素（请求 `<request>` / 响应 `<response>`，按方向）；NULL 写空元素（D5 空值包含） |
| 协议头 | Content-Type / Accept = `application/xml`；推导：`protocol_in/out=XML` → XmlProtocolAdapter（ChainEngine `protocolAdapter()` 现有「M3 交付」占位落地） |

- 报文大小限制（M0-03 §1.3 默认 1MB，超限 40002）：**已核实 M2 未落地**，M3 在网关层双向补齐（出站请求 + 入站回调，均指进入平台的**请求体**；上游响应不做大小限制，读超时兜底）+ 测试点（>1MB → 40002）。
- **XML 安全（XXE）**：M3 引入 XML 解析即新增 XXE 攻击面——解码必须**禁止 DTD / 外部实体**（含 DTD 报文 → 40002 拒绝），实施时显式配置并加安全测试点（DTD / 外部实体注入报文拒绝）。

### 2.2 D-M3-2 入站执行引擎语义（InboundEngine + HMAC 回调验签）

**路由**：GatewayController 通配路由按 `findByPath` 命中接口的 `if_type` 分流——OUTBOUND → OutboundEngine（现状）、INBOUND → InboundEngine（新）；未命中 40401。**响应通道注意**：网关现有签名返回 `ResponseEntity<ApiResult<?>>`（统一信封），INBOUND 分支的 ack 不走信封——网关需为入站回调提供裸报文出口（`ResponseEntity<byte[]>` + 按 protocol_in 推导的 Content-Type；已核实 M2 网关无此出口，需扩展）。

**HMAC 回调验签**（`HmacCallbackVerifyAdapter`，CALLBACK_AUTH 角色，INBOUND_AUTH 阶段）：

- 参数（与设计方案 §5.8 元数据一致，进 `AdapterImplCatalog`）：`signatureAlgorithm`（HMAC-SHA256/SHA1/SHA512，默认 SHA256）、`signatureHeader`（默认 `X-Partner-Signature`）、`timestampToleranceSeconds`（默认 300）、`replayProtection`（默认 false）；
- 签名字符串（首期固定约定）：签名字符串 = `timestamp + "." + UTF-8(rawBody)`——时间戳头固定 `X-Timestamp`，报文按原始字节 UTF-8 解码拼接，整体按 UTF-8 编码后计算 HMAC，结果 hex 小写（rawBody 由网关在链执行前注入 ctx，INBOUND_AUTH 阶段读取）；
- 密钥来自 `app_credential`（kind=CALLBACK，AES-256-GCM 解密）；**ROTATING 新旧并存均验，任一命中即通过**（M0-04 验签并存）；
- 失败：验签失败 / 时间戳头缺失 → HTTP 401 + 40100；时间戳超出容差 → 401 + 40101；**不落 `inbound_delivery`**（M0-01 D7）；replayProtection=true 时按 (appId, signature) 在容差窗口内内存去重（单实例内存 LRU，分布式去重 v1.1）；
- 「连续验签失败告警 / 临时封禁」（设计 §5.3）：告警通道属 M4、封禁属安全能力——**均不在 M3**，由 M4 与多鉴权批承接；
- 出站 HMAC 签名（HmacAuthAdapter）不在 M3 主盘（多鉴权批一并行），但共享同一 HMAC 工具类；**两个 impl 的 catalog schema 相互独立**——回调验签的默认签名头 `X-Partner-Signature` / 时间戳头 `X-Timestamp` 以本计划为准（出站签名头的默认值由供应商要求另行定义，二者不共用默认值）。

**执行流程**（同步送达，首期）：

```
验签（INBOUND_AUTH）→ 应用启用 + 接口 PUBLISHED 校验（40102 / 40401）
→ 链（DECODE→MESSAGE→MAPPING→ENCODE→OUTBOUND_AUTH 默认 Noop）
→ 落 inbound_delivery（PENDING，next_retry_at=now+5s）→ 同步送达（复用 UpstreamInvoker 短重试 5xx/429，固定 POST）
→ 成功 ACKED / 失败保持 PENDING 并更新 next_retry_at → 无论成败回 ack（HTTP 200，§2.3 渲染）
```

- **定稿补充（崩溃安全 + 防抢跑）**：首期落库即 PENDING、送达成功转 ACKED——「落 RECEIVED → 送达 → 改态」存在进程崩溃窗口（记录永久卡 RECEIVED 而 worker 不扫），PENDING 首落使崩溃后由 worker 自然兜底，RECEIVED 态保留不启用（schema 无变更）；**落库 next_retry_at = now + 5s（初始延迟覆盖短重试最坏窗口，防 worker 与同步送达并发重放）**，送达失败后按常规间隔更新；
- 落库字段：`payload`=ENCODE 后送达报文快照、`callback_url_snapshot`=接口当前回调地址快照、`max_attempts`=`interface.max_retries + 1`（与出站口径对齐）、`ack_to_partner`=ACKED（首期恒回）、`callback_event_id` 从回调报文顶层字段 `event_id`（其次 Header `X-Event-Id`）提取，取不到为 NULL；`attempt_count` 首期落库 = 1（首送），补偿重放逐次 +1，**短重试不计入**——与 M2 出站实际口径一致（代码已核实）；trace_id 沿用网关现有透传（X-Trace-Id / traceparent），**供应商未带则平台生成**；
- 送达：复用 `UpstreamInvoker` + `OutboundRequestSpec`（url=快照地址，**首期固定 POST**，v1.1 可配），读超时 = `interface.timeout_ms`；5xx/429 → 短重试；**4xx（非 429）→ 直接 DEAD_LETTER + 死信（对齐出站「4xx 不重试」语义；`inbound_delivery` 无 error_code 列，死因写 `dead_letter.reason`，如「送达 4xx（HTTP 404）」）**；超时 / 连接异常 / 重试耗尽 → 保持 PENDING（入站无 UNKNOWN 对账态，重送安全按 ADR5 依赖调用方幂等）；
- 链失败（DECODE/MAPPING 等）→ 错误信封直接响应，不落运行表（D7）；**入站分支的异常响应通道**：链失败与内部错误统一走平台统一信封 JSON（错误响应是平台侧格式、不按供应商协议渲染），且 InboundEngine 需自行消化全部异常后渲染响应、绕过 GlobalExceptionHandler 的 ApiResult 拦截（与裸 ack 通道同机制）；
- **补偿**：CompensationWorker 扩展扫描 `(delivery_status=PENDING, next_retry_at)` → 按 **payload 快照 + callback_url_snapshot 重放**（不重新走链、不随接口改址漂移；重放 Content-Type 按接口当前 protocol_out 推导——重放不锁传输元数据，不匹配则送达失败 → 死信，可观测）→ 成功 ACKED / 重放遇 4xx（非 429）或 `attempt_count ≥ max_attempts` → DEAD_LETTER + 写 `dead_letter`（biz_type=INBOUND，payload 快照）；
- **SSRF 防护**（M0-03 §4 点名 M3）：管理面保存 `callback_url` 时校验（仅 http/https + 拒绝内网 / 回环 / 链路本地地址），运行时送达前再兜底校验一次；新增配置开关 `app.api-center.callback-allow-private`（**开发 / 测试默认 true**——WireMock 回环地址依赖，生产文档注明必须 false；**开关同时作用于保存校验与运行时兜底**）；
- **管理面测试端点「模拟回调」**（手动验收工具，约 0.5 人日）：`POST /api/admin/interfaces/{id}/test-callback`（仅 INBOUND）——按接口入站参数预填可编辑回调报文，用当前 CALLBACK 凭证按 §2.2 约定**正确签名**后自调平台回调端点（真实网关路径），返回供应商视角 ack + 最新 `inbound_delivery` 状态（按 trace_id 回查）；前端在 INBOUND 接口详情加「模拟回调」按钮；**已核实 M2「测试接口」按钮与后端 `/test` 端点均无 ifType 门控**（INBOUND 接口点它会错误地走出站链路）——M3 需同步加 OUTBOUND 门控（INBOUND 详情隐藏「测试接口」、显示「模拟回调」）；**自调走真实网关路径，接口需已发布**（草稿态按钮置灰并提示，与网关路由语义一致）。

### 2.3 D-M3-3 响应 / ack 字段运行时语义

**RESP 出站响应字段（白名单过滤 + 类型转换）**：

- 生效位置：上游响应经协议适配器解码（§2.4）与信封适配之后、包统一信封之前，作用于 `data` 顶层字段；
- 语义：`interface_field_def`（kind=RESP）声明的 `name` 为白名单，未声明字段丢弃；**仅成功路径生效**（4xx/5xx/超时等失败路径直接错误信封，不做过滤）；`data` 为 null / 非对象时不过滤；
- 类型域映射约定（field_def.type 为自由文本，TypeRegistry 为 5 类型枚举；**注意 XML 响应解码后全为 STRING，声明类型的解析转换由此矩阵覆盖**）：`string` → 实际非 STRING 时转 STRING；`number` → 实际 INT / DECIMAL 兼容，实际 STRING 按数值解析（失败保原值）；`boolean` → 实际 BOOLEAN 兼容，实际 STRING 按 "true"/"false" 解析（失败保原值）；`date` → ISO 解析（失败保原值）；`array` / `object` → 结构不符则保原值 + warning；转换失败一律记 warning 并保留原值（响应方向宽松策略）；array/object 等复合字段**内部透传**（field_def 无嵌套声明能力）；
- **RESP 为空 = 不过滤**（既有接口不受影响；G1 按此矩阵回归不变——total:number 实际 INT 属兼容不转换）。

**ACK 回执字段（字段名可配、值固定）**：

- 生效位置：入站回调的 HTTP 响应体（回供应商，不走平台统一信封）；**渲染格式按 protocol_in 推导**（JSON 回调 → JSON ack / XML 回调 → XML ack，复用协议适配器 ENCODE，Content-Type 对应 application/json / application/xml）；
- 语义：`interface_field_def`（kind=ACK）按 `sort_order` 排序——第 1 个字段 = code（值 0）、第 2 个 = message（值 "success"），其余声明忽略 + warning；`type` 决定数值写法（number → `0`，string → `"0"`）；ACK 无声明 → 兜底平台统一信封 `{code:0, msg:"ok", data:null}`（同样按 protocol_in 渲染格式）；
- 无 schema 变更（`interface_field_def` 不加列）。

### 2.4 D-M3-4 响应方向收敛回协议适配器（M2 技术债）

技术架构 §4.1.1 已点名的 M2 债务：OutboundEngine 内联 `parseResponse` 与协议适配器重复、且无 XML 分支。M3 收敛：

- 响应方向按 `protocol_out` 推导协议适配器，**与请求方向同走一条 DECODE 路径**（JSON/XML 一个分支）——收敛对象是 `OutboundEngine.parseResponse` 的内联 JSON 解析（已核实为 JSON-only、无 XML 分支）；
- `EnvelopeMessageAdapter.adaptResponse` 输入**已是 UnifiedModel（M2 现状，已核实）**，签名与职责均不变（剥壳 / 判成败 / 错误码映射 / messageField 透传）——M3 只移除引擎侧与其重复的解析代码；
- 错误响应（4xx/5xx/超时）按 HTTP 状态分类，**不解码为业务模型**（与 M2 行为等价）；收敛后实施 §2.3 的 RESP 过滤；G1-G4 黄金用例回归必须全绿（行为等价）。

| B4 | 回调地址持续失败（5xx 重送耗尽 / 4xx 直接死信） | PENDING → 重送耗尽 → DEAD_LETTER + dead_letter（biz_type=INBOUND）落库 |
| B5 | 重送期间改接口回调地址 | 重送**仍按 callback_url_snapshot 旧地址**（漂移防护） |
| B6 | 供应商 **XML** 回调（xml→json 入站交叉场景） | ack 200、inbound_delivery 状态正确；其余入站协议组合（json→xml / xml→xml 送达）可参数化并入 |
| X1 | json-xml 出站（调用方 JSON → 平台发 XML → mock 供应商 XML 响应） | 端到端成功 + RESP 过滤生效 |
| X2 | xml-xml 出站（调用方 XML → XML 供应商） | 端到端成功 |
| X3 | xml-json 出站（调用方 XML → JSON 供应商） | 端到端成功 |

**阶段一：XML 出站 + RESP 白名单（约 10 分钟）**

1. 管理面建演示应用 `M3DEMO`（服务地址 `http://localhost:18080`，Noop 鉴权；避免与 M2 手动方案的 HTTPBIN 应用撞名）+ 接口 `IF-XML-01`：OUTBOUND、POST、平台路径 `/demo/xml`、protocol_in=JSON、protocol_out=XML、上游路径 `/xml-supplier`、RESP 字段声明 `total`/`items`，**发布**；
2. curl：

```bash
curl -X POST http://localhost:8080/demo/xml -H "Content-Type: application/json" -d '{"hello":"world"}'
```

   预期：统一信封 `code=0`，`data` 只含 `total`/`items` 两字段、`ts` 被过滤（**XML 响应解码 + RESP 白名单过滤生效**）；
3. 变体：编辑接口清空 RESP → 再调 → `data` 出现全部字段（含 `ts`，演示「空声明不过滤」）；点接口详情「测试接口」按钮走同一链路（XML 推导已生效）。

**阶段二：入站回调全链路（约 15 分钟）**

1. 配置（全走前端）：`M3DEMO` 应用补 CALLBACK 凭证（值 `demo-secret`）→ 适配器新建 HMAC 回调验签实例（impl=HMAC 回调验签，算法 HMAC-SHA256、签名头 X-Partner-Signature、容差 300）→ 应用「回调验签适配器」选中它 → 新建接口 `IF-CB-01`：INBOUND、POST、平台路径 `/callback/demo/order`、回调地址 `http://localhost:18080/delivery-ok`、ACK 字段 returnCode(number)/returnMsg(string)、映射示例（eventId→order_id rename），**发布**；
2. **① 正常闭环**：接口详情 → 「模拟回调」按钮 → 报文预填（可改）→ 发送 → 页面显示供应商视角 ack `{"returnCode":0,"returnMsg":"success"}` 与送达状态 ACKED → 查库：

```sql
SELECT id, delivery_status, attempt_count, max_attempts, callback_url_snapshot, ack_to_partner
FROM inbound_delivery ORDER BY id DESC LIMIT 3;   -- ACKED；payload 列为送达报文快照
```

3. **② 验签失败**：curl 手工发错签名 / 过期时间戳回调 → HTTP 401（40100/40101）→ 再查库**无新记录**（验签失败不落运行表）：

```bash
# 错签名（签名值乱填）：
curl -X POST http://localhost:8080/callback/demo/order -H "Content-Type: application/json" \
  -H "X-Timestamp: $(date +%s)" -H "X-Partner-Signature: deadbeef" \
  -d '{"eventId":"evt-001"}'
# 过期时间戳（超出容差 300s）：
curl -X POST http://localhost:8080/callback/demo/order -H "Content-Type: application/json" \
  -H "X-Timestamp: $(($(date +%s) - 600))" -H "X-Partner-Signature: deadbeef" \
  -d '{"eventId":"evt-001"}'
```
4. **③ 送达失败 → 补偿成功**：编辑接口回调地址改 `/delivery-flaky` → 模拟回调 → **ack 仍回**（供应商视角成功）→ 查库 PENDING（attempt=1）→ 每 3 秒 worker 重送，attempt_count 递增（日志可看）→ 第 4 次重放 scenario 放行 → **ACKED**（PENDING→ACKED 手动可见）；
5. **④ 耗尽 + 快照漂移**：回调地址改 `/delivery-fail` → 模拟回调 → PENDING → 等待 attempt 接近上限时把接口回调地址改成 `/delivery-ok` → 观察重送**仍按旧快照 `/delivery-fail`** 继续失败 → 耗尽 → DEAD_LETTER，查库：

```sql
SELECT id, delivery_status, attempt_count FROM inbound_delivery ORDER BY id DESC LIMIT 1;  -- DEAD_LETTER
SELECT * FROM dead_letter WHERE biz_type='INBOUND' ORDER BY id DESC LIMIT 2;               -- 死信落库
```

6. 顺带浏览种子 fastmoss 入站回调用例（IF-FM-CB-001）与 HMAC 回调验签适配器实例配置。

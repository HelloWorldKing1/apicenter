# 开发文档 · 索引（**唯一入口**）

> **这份文件解决什么**：`开发文档/` 下曾有 35 份文档**平铺**、混着"已落地 / 设计稿未排期 / 契约冻结 / 史料"，
> 读之前无法判断该不该照它做。现在**按文档生命周期分 7 个目录**，并在这里给出**全量清单 + 当前状态**。
>
> **状态列的口径**（**状态写在表里，不写进文件名/路径** —— 状态会变，路径不该跟着变）：
>
> | 标记 | 含义 |
> |---|---|
> | ✅ **已落地** | 设计已实施（文档内通常带"落地记录"节）；**读它 = 读现状** |
> | 🟡 **部分落地 / 设计稿** | 一部分已实施，或整篇是**待排期**的设计；读它前先看"未做"清单 |
> | 📌 **契约冻结** | 已评审通过、作为编码依据；**不随实现改动**（要改需走评审） |
> | 🗂️ **史料** | 评审快照 / 一次性草稿；只在追溯"当时怎么定的"时读 |

## 3. 新增文档的约定

1. **按生命周期选目录**（目录承载"这是什么"）：
   `契约/`（要评审冻结的接口级约定）· `设计/`（怎么做）· `计划/`（怎么排期/拆任务）· `验收/`（怎么手工验）·
   `测试/`（怎么自动化测）· `演示/`（怎么讲给别人听）· `记录/`（坑、评审、评估）
2. **文件名后缀与目录一致**（便于 grep）：
   `设计/…设计方案.md` · `计划/…开发计划.md` · `验收/…手动验收测试方案.md` · `记录/…踩坑记录.md` / `…代码评审记录.md` / `…评估.md`
3. **不把状态写进文件名**（"v2 定稿""最终版"这类词会过期）；状态写进**本文件 §2 的状态列**。
4. **落地后在文档里"就地"补落地记录**（如 `## N. 落地记录`），**不要新建"XX 落地报告"** —— 避免同一特性散成多份。

## 5. 维护约定

1. **改动本目录结构后**：跑一次"带路径引用是否仍可解析"的检查（应从全绿，**唯一允许的例外**是 §4 的通配写法）；
2. **新增文档**：放进 §3 的对应目录，并**在本文件 §2 的表里登记一行**（文件 + 定位 + 状态）；
3. **状态变化时**（设计落地 / 压测回填 / 评估被采纳）：**只改本表的状态列**，并在该文档内补落地记录节；
4. **不删除**：文档只增不删（确需淘汰时移入 `记录/` 并在本表标注 🗂️ 史料，保留可追溯性）。

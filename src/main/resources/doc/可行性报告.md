# API 中心 · 可行性报告

> 依据《API中心设计方案.md》《API中心时序图与流程图.md》《API中心原型.html》编制，实现技术引用《技术架构和实现方案.md》§3/§4。
> 结论先行：**技术可行、形态已被原型验证、风险可控，建议按 M1–M5 分阶段交付**。

## 1. 项目概述

### 1.1 目标

建设「API 三方接口统一调用平台」组件：

- 五大模块：应用管理（供应商）、分组管理、接口管理、接口监控、适配器；
- 核心能力：JSON/XML 协议中转、多鉴权（含云厂商签名与回调验签）、字段映射、可靠传输（重试/补偿/死信/对账/熔断）、全链路可观测；
- 两条链路：Flow A 出站（调用方 → 平台 → 供应商）、Flow B 入站（供应商回调 → 平台 → 调用方）；
- 定位边界：只做连接 + 适配 + 可靠传输，不承接业务决策；只建模供应商侧，调用方鉴权由平台统一处理。

### 1.2 交付形态

| 部分 | 形态 |
|---|---|
| 管理面 | Web 配置界面（应用/分组/接口/监控/适配器 5 页面，原型已定义全部交互与数据模型） |
| 执行面 | 运行时网关：接入路由、适配器链、出站/入站执行引擎 |
| 数据面 | MySQL 8 配置表 + 运行表（见《表结构设计.html》） |
| 可靠性 | 补偿 worker、对账查询、死信管理、熔断器 |

## 3. 需求分析

### 3.1 功能需求

| # | 模块 | 需求点 |
|---|---|---|
| F1 | 应用管理 | 应用 CRUD；生命周期（草稿→启用→停用→注销）；出站凭证 + 回调验签凭证双类（加密存储/轮换/失效）；服务地址；IP 黑白名单；QPS/日配额限流 |
| F2 | 分组管理 | 应用→分组→接口层级；跨应用两级视图；增删改查与接口移动；新建接口两级下拉 |
| F3 | 接口管理 | 接口定义模型（类型/方法/路径/协议/目标地址/两侧请求参数+Body/字段映射/响应·ack/鉴权/超时重试）；归属唯一应用；生命周期与版本化（回滚/灰度）；下线停路由 |
| F4 | 接口监控 | 调用日志（traceId/脱敏）；Micrometer/Prometheus 指标（调用量/成功率/P50/P95/P99）；OpenTelemetry 链路；阈值告警；UNKNOWN 对账查询、死信查看与重放 |
| F5 | 适配器 | 三类（鉴权/协议/报文）+ 字段映射接口级；参数元数据驱动；10 种鉴权实现（API Key/HMAC/云厂商签名/云厂商回调验签/OAuth2×2/Bearer/Basic/mTLS/无鉴权）；JSON/XML 协议；信封/报文头适配；版本化/灰度 |
| F6 | 出站链路 | Flow A：适配器链执行 + 状态机（INIT→…→SUCCESS/DEAD_LETTER/UNKNOWN）+ 5xx/429 短重试 + 补偿 + 死信 + 对账 + 熔断 |
| F7 | 入站链路 | Flow B：回调验签 + 送达回调地址 + ack 回执（与送达解耦）+ 补偿重送 + 死信 |

### 3.2 非功能需求

- **可靠性**：补偿/死信/对账/熔断四件套；重放安全依赖上游对业务键幂等（不设平台侧幂等开关）。
- **可观测**：日志/指标/链路/告警全链路（traceId 贯穿）。
- **安全**：凭证加密存储、脱敏、验签时间戳容差 + 防重放、连续失败封禁。
- **性能**：限流配额（QPS/日配额），超限拒绝 + 告警不污染状态机。

## 4. 技术可行性

| # | 能力 | 实现方案 | 成熟度 | 风险 |
|---|---|---|---|---|
| T1 | 适配器链引擎 | 责任链 + 契约接口（type/order/supports/process）+ 无状态配置驱动 | 高（成熟模式） | 低 |
| T2 | JSON/XML 编解码 | Jackson（JSON）+ Jackson XML，每应用独立实例；命名策略/日期/空值/精度可配 | 高 | 低 |
| T3 | 动态字段映射 | 运行时规则解释器（6 操作 + param，SpEL/Aviator 表达式内核）；MapStruct 保留于固定结构映射 | 中 | 中：类型转换与聚合的边界场景需测试兜底 |
| T4 | 多鉴权（双方向） | 策略模式；authenticate（回调验签）/ applyCredential（供应商签名）分离；10 种实现 | 高 | 中：云厂商签名（TC3/SigV4/ACS3）与回调验签各规范实现工作量大 |
| T5 | 出站状态机 + 重试/补偿/死信 | 表驱动状态机 + `@Retryable`（独立 Invoker 类）+ 补偿 worker | 高 | 中：短重试/补偿部分复用既有验证模式（低）；UNKNOWN 对账依赖上游查询接口，缺查询能力时需人工对账兜底 |
| T6 | 熔断 | 三态熔断器（CLOSED/OPEN/HALF_OPEN），按「接口+供应商」维度；闸门置于 @Retryable Invoker 调用前 | 高 | 低 |
| T7 | 入站回调 + 送达补偿 | `@HttpExchange` 通用客户端（动态 URI/凭证）+ 回执解耦 + worker 重送 + 死信 | 高 | 低 |
| T8 | 可观测 | Spring AOP（@Aspect）日志 + Micrometer/Prometheus + OpenTelemetry（自动埋点 + 适配器节点手动 span） | 高 | 低 |
| T9 | 版本化/灰度 | 配置快照（interface_snapshot）+ 适配器按 impl+version 索引绑定 | 中 | 中：灰度路由与回滚一致性需专门设计 |

**整体判定**：无技术不可行项。T2 / T5（重试补偿部分）/ T7 / T8 的实现技术已在既有代码基线验证，**风险较初版下修**；中风险项收敛为 **T3（动态映射）**、**T5 的对账兜底** 与 **T9（灰度一致性）**。

## 6. 风险与应对

| 风险 | 类别 | 影响 | 应对 |
|---|---|---|---|
| 动态映射的类型转换/聚合边界不收敛 | 技术 | 映射结果不符合预期 | 明确类型注册表与边界行为；映射结果落 mapped_payload 供诊断；单测覆盖 6 操作 × 空值策略矩阵 |
| 声明式客户端动态 URI / 凭证组装出错 | 技术 | 调错目标或凭证错配 | 客户端接口按协议维度定义 + URI/Header 组装独立成可测组件；单测覆盖四种场景（json-json/json-xml/xml-xml/xml-json） |
| condition 表达式注入 | 安全 | 管理员配置的表达式被利用执行任意代码 | 表达式沙箱 / 白名单约束（SpEL 需显式限制可访问类型与函数）；注入用例进单测与安全专项 |
| UNKNOWN 对账无上游查询接口 | 技术 | 状态无法收敛 | 人工对账入口 + 超时自动降级为 COMPENSATING（可配） |
| 云厂商签名/回调验签规范多且版本演进 | 技术 | 实现与维护成本 | 策略模式隔离；按 scheme 子类实现；逐厂商联调验收 |
| 版本化/灰度时新旧配置不一致 | 技术 | 路由行为漂移 | 快照发布 + 绑定原子切换；灰度按比例路由并全程留痕 |
| 回调验签凭证泄漏 | 安全 | 伪造回调 | 凭证加密存储 + 轮换 + 泄漏即时失效；连续验签失败告警/封禁 |
| 送达回调地址被滥用（SSRF） | 安全（补充建议） | 内网探测 | 回调地址 URL 校验 + 内网地址限制 |
| 真实对端联调环境缺失 | 依赖 | 交付延期 | 以模拟对端（本地 mock 服务）先行联调，再换真实供应商 |
| 供应商协议文档不全 | 依赖 | 映射/报文适配返工 | 先按「信封报文 + 字段映射」分层约定，缺省字段显式报错 |

## 7. 结论与建议

1. **可行**：设计方案逻辑自洽、原型已验证产品形态，四项核心实现技术（@HttpExchange/@Retryable/AOP/OpenTelemetry）在既有代码基线已验证，整体无探索性风险。
2. **建议分期**：先 M1+M2 垂直打通「json-json 出站链路」（含 5 种首期核心鉴权），快速获得可用闭环；再横向扩展 XML、入站回调、容错与灰度。
3. **建议首期鉴权范围**：HMAC、API Key、Bearer Token、云厂商签名、云厂商回调验签 5 种（Bearer 为 fastmoss 黄金用例依赖，见《开发计划.md》§2）；OAuth2 授权码与 mTLS 后置。
4. **三个重点设计项**（开工前定稿）：动态映射的类型/聚合边界；UNKNOWN 对账的上游查询协议与兜底策略；通用声明式客户端接口（按协议维度 + 动态 URI/凭证组装）的约定。

# M4 手动验收测试方案

> 用途：M4 容错与监控的手动端到端验收（补充自动化测试的平台实操验证），全程约 35 分钟。
> 模拟上游用**本地 WireMock**（stub 随仓库 `src/test/resources/m4-manual-stubs/`：熔断 scenario / 慢上游 / 死信 404→200 / 正常回显）。
> 本方案按实施后实际行为校准（对应 `M4开发计划.md` §5，D-M4-1~6 语义）。
> 前置：M4 DDL 已应用（reconcile_audit / alert_event 两表 + idx_outreq_updated 索引——开发库已于 2026-09-04 执行；其他环境先跑 schema.sql 增量段）。

## 前置：启动（三个终端）

```bash
# 终端 1：后端
mvn spring-boot:run                       # 8080，seed 幂等导入（含 fastmoss 黄金用例与入站回调用例）

# 终端 2：前端
cd frontend && npm run dev                # http://localhost:5173

# 终端 3：本地 WireMock（在项目根目录执行；pom 已含 wiremock-standalone 3.9.1）
java -jar ~/.m2/repository/org/wiremock/wiremock-standalone/3.9.1/wiremock-standalone-3.9.1.jar \
  --port 18080 --root-dir src/test/resources/m4-manual-stubs
```

> 注意：WireMock 占 18080 与集成测试同端口——**手动验收期间勿同时跑 `mvn test`**（端口冲突），验收完毕再跑测试。

stub 约定（已随仓库）：

| stub | 行为 | 用途 |
|---|---|---|
| `/echo-ok` | 恒 200 `{"ok":true}` | 可观测演示的正常上游 |
| `/breaker-supplier` | 恒 500 | 熔断开闸演示（恢复经 WireMock 管理 API 运行时切 200，见②步骤 4） |
| `/slow-supplier` | 200 但**固定延迟 5 秒**（> 默认读超时 3s） | 制造 UNKNOWN（对账演示） |
| `/reject-supplier` | **scenario：第 1 次 404 → 之后 200** | 制造死信（重放后恢复） |

## 阶段一：可观测——call_log 双向 / 脱敏 / traceId 贯穿 / 指标（约 10 分钟）

1. 管理面建演示应用与接口（若 M3 已建 `M3DEMO` 可复用）：
   - 应用 `M4DEMO`：服务地址 `http://localhost:18080`，鉴权留空（Noop）；
   - 接口 `IF-OBS-01`：OUTBOUND、POST、平台路径 `/m4/obs`、protocol_in/out=JSON、上游路径 `/echo-ok`、读超时 3000 / 重试 4（默认），**发布**；
2. curl 两次（带调用方凭证头 + traceId，验证透传与脱敏）：

```bash
curl -X POST http://localhost:8080/m4/obs -H "Content-Type: application/json" \
  -H "Authorization: Bearer my-demo-token-123456789" -H "X-Trace-Id: trace-m4-manual-1" \
  -d '{"hello":"world"}'
```

   预期：统一信封 `code=0`、`data={"ok":true}`；
3. 打开管理面「**接口监控**」页：
   - 统计卡：今日调用量 ≥2、今日成功率 100%、待补偿/待重送 0/0、死信/对账中 0/0；
   - 调用日志表：出现 **4 条**（2 次调用 × IN/OUT 各一），方向列 IN/OUT 标签区分；按 traceId `trace-m4-manual-1` 过滤 → 恰 2 条；
4. 查库（脱敏与贯穿验证）：

```sql
SELECT direction, status_code, latency_ms, trace_id, LEFT(req_headers, 120) AS headers_masked
FROM call_log WHERE trace_id = 'trace-m4-manual-1' ORDER BY id;
-- 预期：IN + OUT 各 1（每次调用）；req_headers 中 Authorization 已遮蔽为 "Bearer****6789"（前4+****+后4）；
-- 原值 my-demo-token-123456789 不得出现
```

5. 指标（Prometheus 抓取端点）：

```bash
curl -s http://localhost:8080/actuator/prometheus | grep apicenter_ | grep -v "^#"
```

   预期出现：`apicenter_gateway_requests_total{...direction="IN"...}`、`...direction="OUT"...`、
   `apicenter_gateway_latency_seconds{...}`（含 P50/P95/P99 分位）、`apicenter_backlog{kind=...}`（compensating/pending/dead_letter/unknown 四个 kind）、`apicenter_circuit_state{interface=...}`；
6. 顺带验证**日志行 traceId**：终端 1 的后端日志中，上述请求的处理日志行带 `[traceId=trace-m4-manual-1]` 前缀（MDC 输出，与运行表 / call_log 同源）。

## 阶段二：容错——熔断 / UNKNOWN 对账 / TTL 降级（约 15 分钟）

**① 熔断三态（D-M4-1，约 3 分钟含冷却等待）**

1. 建接口 `IF-BRK-01`：OUTBOUND、POST、平台路径 `/m4/breaker`、上游路径 `/breaker-supplier`（应用同 M4DEMO），**发布**；
2. 连续 curl 12 次：

```bash
for i in $(seq 1 12); do
  echo "--- 第 $i 次 ---"
  curl -s -o /dev/null -w "%{http_code} 耗时 %{time_total}s\n" \
    -X POST http://localhost:8080/m4/breaker -H "Content-Type: application/json" -d '{}'
done
```

   预期（默认参数：窗口 10 秒 / 最小 10 次 / 失败率 50%——补偿 worker 的重放同样计入失败样本，开闸点略有浮动）：
   - 前若干次：HTTP 502、统一信封 `code=50201`（上游 5xx，短重试耗尽转补偿），**每次耗时约 3.5 秒**（5 次尝试 + 指数退避）；
   - **中途起**（约第 8~12 次）：HTTP 502、`code=50202`（**上游熔断短路**），**耗时 < 0.5 秒**——不开上游连接、不触发短重试，直接转 COMPENSATING 顺延；
   - 后端日志出现「出站请求 xx 熔断短路（接口 xx OPEN）」；
3. 查库确认短路记录（不计数、只顺延）：

```sql
SELECT id, status, attempt_count, error_code, next_retry_at
FROM outbound_request WHERE interface_id = (SELECT id FROM interface WHERE code='IF-BRK-01')
ORDER BY id DESC LIMIT 3;
-- 短路记录：status=COMPENSATING、error_code='50202'、attempt_count 不再增长（未触达上游不计尝试）
```

4. **冷却后半开恢复**：先经 WireMock 管理 API 运行时注册高优先级 200 stub（模拟上游恢复，无需重启 WireMock）→ 等 31 秒（默认 open-duration=30s）→ 连续 curl 2 次（默认 half-open-probes=2，两次探测均成功才闭合）：

```bash
# 上游恢复：注册高优先级（priority=1）200 stub 覆盖恒 500 的文件 stub
curl -X POST http://localhost:18080/__admin/mappings -H "Content-Type: application/json" \
  -d '{"priority": 1, "request": {"method": "POST", "url": "/breaker-supplier"},
       "response": {"status": 200, "jsonBody": {"ok": true}}}'

sleep 31
curl -s -X POST http://localhost:8080/m4/breaker -H "Content-Type: application/json" -d '{}'; echo
curl -s -X POST http://localhost:8080/m4/breaker -H "Content-Type: application/json" -d '{}'; echo
```

   预期：两次均 `code=0`（探测走完整链路含短重试）；恢复闭合后，此前积压的 COMPENSATING 记录被 worker 逐条重放成功——**监控页「待补偿」卡片在数秒内归零**（熔断期间顺延不计数、恢复后自然消化）；`curl -s http://localhost:8080/actuator/prometheus | grep circuit_state` 值回落。

**② UNKNOWN 人工对账（D-M4-2，M2 缺口闭环）**

1. 建接口 `IF-SLOW-01`：平台路径 `/m4/slow`、上游路径 `/slow-supplier`（应用同 M4DEMO），**发布**；
2. curl（约 3 秒后返回）：

```bash
curl -s -X POST http://localhost:8080/m4/slow -H "Content-Type: application/json" -d '{}'; echo
# 预期：HTTP 504、code=50401「上游超时，结果待对账（UNKNOWN）」
```

3. 管理面「接口监控」→ **对账（UNKNOWN）**面板：出现该记录（10 秒轮询）→ 点「**置为已到达**」→ 弹窗操作人填 `admin`（必填）、依据说明随意（如「上游后台确认」）→ 确认 → 记录从列表消失（已收敛 SUCCESS）；
4. 查库审计留痕：

```sql
SELECT o.id, o.status, a.from_status, a.to_status, a.source, a.operator, a.created_at
FROM outbound_request o JOIN reconcile_audit a ON a.outbound_request_id = o.id
WHERE o.interface_id = (SELECT id FROM interface WHERE code='IF-SLOW-01')
ORDER BY o.id DESC LIMIT 3;
-- 预期：status=SUCCESS + 一条 audit（UNKNOWN→SUCCESS、source=MANUAL、operator=admin）
```

5. 变体（可选）：再造一条 UNKNOWN → 点「**置为未到达**」→ 转 COMPENSATING 入补偿队列；因 `/slow-supplier` 恒慢，重放会再次超时回到 UNKNOWN（重放不盲目、回 UNKNOWN 对账是设计语义）——如需看到重放成功，把接口上游路径改回 `/echo-ok` 后再置位。

**③ TTL 自动降级（M0-03 §3.1 分支二）**

1. 再造一条 UNKNOWN（curl 同②），然后回拨时间：

```bash
curl -s -X POST http://localhost:8080/m4/slow -H "Content-Type: application/json" -d '{}'; echo
```

```sql
UPDATE outbound_request
SET updated_at = DATE_SUB(NOW(), INTERVAL 11 MINUTE)
WHERE interface_id = (SELECT id FROM interface WHERE code='IF-SLOW-01')
  AND status = 'UNKNOWN';
```

2. 等补偿 worker 一轮（3 秒）→ 查库：

```sql
SELECT id, status, error_code FROM outbound_request
WHERE interface_id = (SELECT id FROM interface WHERE code='IF-SLOW-01') ORDER BY id DESC LIMIT 1;
-- 预期：status=COMPENSATING（error_code 保留 50401 超时成因）
SELECT source, operator FROM reconcile_audit ORDER BY id DESC LIMIT 1;
-- 预期：source=TTL、operator=TTL-WORKER（审计两来源齐备）
```

## 阶段三：死信重放 / 告警 / 限流（约 10 分钟）

**① 死信重放（D-M4-3）**

1. 建接口 `IF-REJ-01`：平台路径 `/m4/reject`、上游路径 `/reject-supplier`（应用同 M4DEMO），**发布**；curl 一次：

```bash
curl -s -X POST http://localhost:8080/m4/reject -H "Content-Type: application/json" -d '{}'; echo
# 预期：HTTP 502、code=50201、msg 含「死信编号 N」（上游 404 → 4xx 不重试直接死信）
```

2. 管理面「接口监控」→ **死信**面板：PENDING 记录（类型 OUTBOUND、死因「上游 404…」）→ 点「**重放**」→ 确认（提示：重新入队，由 worker 自然重放）；
3. 等 3 秒（worker 扫描）→ 查库：

```sql
SELECT o.status, o.attempt_count, d.status AS dead_status, d.handled_at
FROM outbound_request o JOIN dead_letter d ON d.ref_id = o.id
WHERE o.interface_id = (SELECT id FROM interface WHERE code='IF-REJ-01')
ORDER BY o.id DESC LIMIT 1;
-- 预期：o.status=SUCCESS（stub scenario 已放行 200）、o.attempt_count=0 重置后重放、
-- d.status=HANDLED、handled_at 非空
```

   死信面板刷新后该记录变「已处理」标签、重放按钮置灰；再点重放（直连 curl 或刷新前）→ 40001「已处理」拒绝。

**② 告警规则（D-M4-5）**

1. 管理面「接口监控」→ 告警面板 → 「**＋ 新建规则**」：规则名 `死信堆积演示`、指标 `死信PENDING堆积（条）`、阈值表达式 `> 0`、启用 → 保存（提示：生效延迟 ≤ 60s 缓存刷新）；
2. 因①已产生一条 PENDING 死信（若已 HANDLED 则再造一条：把 IF-REJ-01 上游改 `/reject-supplier` 且 WireMock 重启后再 curl 一次）→ **等约 30~90 秒**（alert worker 30s 轮询 + 规则缓存 60s）→ 告警面板出现「严重」级事件（内容含当前值与阈值）；
3. 再等 30 秒以上确认**不重复**（规则命中冷却 5 分钟）；查库：

```sql
SELECT level, metric, message, created_at FROM alert_event ORDER BY id DESC LIMIT 3;
```

4. 变体（可选，内置告警）：对种子入站回调接口连发 10 次错误签名：

```bash
for i in $(seq 1 10); do
  curl -s -o /dev/null -X POST http://localhost:8080/callback/fastmoss/order-state \
    -H "Content-Type: application/json" -H "X-Timestamp: $(date +%s)" \
    -H "X-Partner-Signature: deadbeef" -d '{"event_id":"evt-x","order_id":"O-1","state":"PAID"}'
done
# 等 30~90 秒 → 告警面板出现「应用 FASTMOSS 回调验签连续失败 10 次（5 分钟窗口）」（rule_id 为空的内置告警）
```

**③ QPS 限流（D-M4-6，M2 缺口闭环）**

1. 管理面编辑应用 `M4DEMO` → **QPS 限流 = 2** → 保存（立即生效，应用配置无缓存）；
2. 快速连发 6 次（IF-OBS-01）：

```bash
for i in $(seq 1 6); do
  curl -s -o /dev/null -w "%{http_code} " -X POST http://localhost:8080/m4/obs \
    -H "Content-Type: application/json" -d '{}'
done; echo
# 预期：出现 200 与 429 混合（同秒窗口上限 2；跨秒边界时至多 4 个 200）
```

3. 拒绝响应体验证：`curl` 单发到 429 时输出信封 `code=42901`「QPS 限流」；查库确认**不污染状态机**：

```sql
SELECT COUNT(*) FROM outbound_request
WHERE interface_id = (SELECT id FROM interface WHERE code='IF-OBS-01');
-- 增量 = 放行（200）次数，被拒请求无记录
```

4. 变体（可选，IP 黑名单）：编辑 `M4DEMO` 黑名单填 `127.0.0.1` → 再 curl → HTTP 403 `code=40103`「来源 IP 被拒（黑名单）」→ 移除后恢复。

## 验收对照

| 步骤 | 对应定稿 / 出口标准 |
|---|---|
| 阶段一 | call_log 双向 + 脱敏 + traceId 贯穿（日志/运行表/上游三方，D-M4-4）+ 指标全套（D-M4-5） |
| 二.① | 熔断三态：OPEN 短路（不触达上游、不触发短重试、不计数只顺延）→ 冷却 → 半开探测 → CLOSED（D-M4-1） |
| 二.②/③ | 人工对账 + TTL 自动降级 + 审计两来源（MANUAL/TTL）（D-M4-2，M2 缺口闭环） |
| 三.① | 死信查看与重放（重新入队 → worker 自然补偿 → HANDLED；已处理拒绝）（D-M4-3） |
| 三.② | 告警规则触发 + 冷却 + 监控页展示；验签连续失败内置告警（D-M4-5） |
| 三.③ | QPS 限流拒绝 + 不污染状态机（D-M4-6，M2 缺口闭环） |

## 已知边界（非缺陷，验收时知悉）

- **通知渠道未对接**（邮件 / IM v1.1）：notify_channel 仅随告警事件记录；
- **熔断 / 限流 / 日配额为单实例内存口径**：多实例部署各实例独立（v1.1 分布式）；日配额重启后重新计数；
- **`/test`、`/mock-callback` 调试端点不落 IN 条 call_log**（避免污染成功率口径）；OUT 条照常落库——IN/OUT 条数不配对属预期；
- **`/mock-callback` 自调真实网关**：该路径会产生 IN 条 call_log（走真实网关，非调试直调）；
- **告警规则生效延迟最长约 90 秒**（worker 30s 轮询 + 规则缓存 60s）；
- **IP 黑白名单为精确 IP 匹配**（CIDR v1.1）；来源地址默认取 remoteAddr，生产反代后需开 `trust-xff: true`；
- **P99 统计卡为空**：前端卡片数据来自 overview SQL（调用量/成功率/积压），P99 走 Prometheus Timer（`/actuator/prometheus` 的 `apicenter_gateway_latency_seconds` 分位）——压测与看板接入在 M5。

> 查库可用 Navicat 连 PolarDB（开发实例 alicloud.mysql.polardb.rds.aliyuncs.com，白名单已通），库名 apicenter。

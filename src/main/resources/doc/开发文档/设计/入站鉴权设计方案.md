## 0. 先思考：现状盘点与结论（设计起点）

现状是三套机制各自为政，缺口清晰：

| # | 机制 | 主体 | 执行位置 | 现状 |
|---|---|---|---|---|
| ① | `AdminAuthFilter` + `admin_session` | 平台运营人员 | Servlet Filter（`/api/admin/**`） | ✅ 已落地（2026-09-18） |
| ② | **调用方鉴权** | 平台客户（ERP / 业务系统） | —— | ❌ **完全没有**——`GatewayController` 路由命中即执行，任何知道路径的人都能调 |
| ③ | 回调验签 `CALLBACK_AUTH` | 供应商 | 链内 `INBOUND_AUTH`（`HmacCallbackVerifyAdapter`） | ⚠️ 有，但**只有 HMAC 一种方式**，且**无 IP / 方式留痕** |
| ④ | `GatewayGuard` | 应用（供应商） | 网关入口 | ⚠️ 有 QPS / 日配额 / IP 名单，但**无「调用方」维度** |

**四件事目前都做不到**（逐条对应本设计要解决的问题）：

1. **调用方无法鉴权**——`ChainEngine.assemble` 里 Flow A 的 `INBOUND_AUTH` 阶段是**硬编码 Noop 占位**：
   ```java
   // 1. 入站鉴权：Flow A 调用方鉴权属平台统一能力（范围外）→ Noop 占位
   ```
   设计 §3.1 / §5.3 明确写着「调用方鉴权由平台统一处理，**不在本模型内**」——《API中心项目说明.md》§2
   甚至把它列为「平台**不做**的事」。**本设计就是把这句「范围外」落地成「范围内」。**

2. **没有「调用方」这个主体**——`app` 表 = 供应商（既是归属也是转发目标），全库**没有任何表**描述
   「谁在调用平台」。所以「记录调用方的名称」无处可取。

3. **没有记录来源 IP 的地方**——`call_log` 有 `direction/url/method/status_code/interface_id/app_id/step_code/latency_ms/trace_id/req_*/resp_*`，但**没有 `client_ip` 列**，也**没有鉴权主体 / 方式 / 结果**；
   `outbound_request` / `inbound_delivery` 更没有。事后想回答
   「刚才那批 401 是谁打过来的」——**查不到**。

4. **没有「鉴权方式」的口径**——`HmacCallbackVerifyAdapter` 验签失败只抛 `BizException(40100)` +
   `alert_event`（`metric=verify_fail_streak`），**不记录用了哪种方式、哪个适配器实例、主体是谁**。

**由此得到本设计的三个判断**：

- **判断 1（主体模型）**：调用方必须是**独立于 `app` 的新主体**。`app` 是「被代理的一方」，
  调用方是「发起调用的一方」，把调用方塞进 `app` 会让 `app_id` 这个对外契约（URL / 凭证归属 /
  监控过滤）语义崩塌。→ 新增 `client_app`，与 `app` **对称设计**（目录表 + `adapter`(auth)
  引用 + 独立凭证表 + 名单/限流字段）。
- **判断 2（执行位置）**：调用方鉴权归**网关入口闸门**（`GatewayController` 内、引擎之前），不归链内
  ——理由是设计原话「平台统一处理，不在接口模型内」：它**不进接口配置快照、不受链缓存影响、
  拒绝不落 `outbound_request`**（与 M4 「防护拒绝不污染状态机」同一条纪律）。
  而回调验签**留在链内**（M3 已验证的 `CALLBACK_AUTH` + 绑定解析 + 链缓存），**不动**——
  见 §3.3 的取舍理由。
- **判断 3（统一的是口径，不是位置）**：两处执行、**四样东西必须统一**——**鉴权方式目录**（同批适配器
  impl）、**凭证注入契约**（适配器不查库）、**审计表**（`access_auth_log` 一张）、**错误码**
  （401xx 段）。这样「调用方鉴权」与「回调验签」在运维视角是**一个功能**，在实现视角是**两处薄胶水**。

### 0.1 顺带发现的两个既有缺陷（本设计一并修正）

| # | 缺陷 | 事实 | 影响 | 处置 |
|---|---|---|---|---|
| B1 | **可配置的密钥头名不进脱敏清单** | `SensitiveDataMasker` 的敏感头是**写死清单**（`authorization` / `x-api-key` / `x-auth-token` / `x-partner-signature` / `x-signature` …）；而 `ApiKeyAuthAdapter` / `HmacCallbackVerifyAdapter` 的**头名是适配器参数可配的**（`headerName` / `signatureHeader`） | 配成 `appKey` / `X-Custom-Sign` 时，**密钥/签名明文落 `call_log.req_headers`** | 敏感头名**动态注册**（§6.3 D-CA-13）：鉴权适配器声明的头名 + 配置项 `client-auth.mask-header-names` 一并进 masker |
| B2 | **应用级 IP 名单对 OUTBOUND 语义错位** | `GatewayController` 用 `routed.appId()`（**供应商**）的 `ip_whitelist` 去校验**调用方**的来源 IP | 某供应商应用为「回调来源保护」配了白名单，会**连带拦掉该供应商出站接口的正常调用方** | **本次不改行为**（兼容 M4 `c8` 用例），但**在文档中把语义钉死**并给待拍板项（§12.2）：是否另立 `callback_ip_whitelist` |

> B2 的处理体现一条纪律：**发现语义歧义时，先记录+给选项，不在鉴权设计里顺手改别人的行为**。
> 详见 §12.2 待拍板 D-CA-11。

## 1. 目标与非目标

| | 内容 |
|---|---|
| **目标** | ① 调用方（平台客户）调平台时**强制可配的鉴权**（API Key / HMAC / Bearer / 仅 IP 名单）② 供应商回调验签**方式扩展**（从只有 HMAC 扩到同一批方式）③ **接入审计**：每次鉴权判定留痕「主体（id + 名称）· 来源 IP · 鉴权方式 · 结果 · 失败原因 · traceId」④ 调用方维度的 IP 名单（40103 复用）⑤ 管理面「调用方管理」页 + 「接入鉴权」审计查询⑥ **可灰度**（观察 → 可选 → 强制三态），不搞一刀切上线的惊喜 ⑦ 失败告警（连续失败，复用 `AlertService` 口径） |
| **非目标** | ① **授权**（调用方能访问哪些接口的 ACL —— 鉴权 ≠ 授权，P2 见 §18）② mTLS / OAuth2 client_credentials / Basic（P2/P3）③ 分布式凭证/防重放（单实例内存口径，与熔断/限流一致，v1.1）④ 临时封禁（v1.1，与 M4 结论保持一致）⑤ 管理面 SSO / 操作审计表 ⑥ 向回调地址签名（设计 §5.3 明确「可选，默认无」，本次不启用） |

## 2. 决策记录（D-CA-*，评审重点）

| # | 决策 | 理由 / 备选（含被否方案） |
|---|---|---|
| **D-CA-1** | **调用方 = 新主体 `client_app`**，不复用 `app`，不塞进 `app_credential` | `app` = 供应商（被代理方），语义互斥；复用会让 `app_id` 契约崩塌（URL/凭证归属/监控过滤全绑它）。备选「`app_credential` 加 `owner_type/owner_id` 多态」被否：改的是 M0-04 已验证的核心表 + 其函数唯一索引议题，风险远大于新表 |
| **D-CA-2** | **调用方鉴权在网关入口闸门执行**（`GatewayController` 路由命中后、引擎之前），**不进链、不进接口模型** | 设计原话「由平台统一处理，不在接口模型内」；好处：不污染 `outbound_request`（拒绝发生在 `createRecord` 前，与 D-M4-6 同口径）、不进接口快照/版本 diff、不受链缓存 TTL 影响 |
| **D-CA-3** | **入站鉴权按 `if_type` 二分**：`OUTBOUND` → 调用方鉴权（闸门）；`INBOUND` → 回调验签（链内 `INBOUND_AUTH`，M3 既有，**不搬迁**） | 一个接口的入站方**只可能是其中之一**（出站中转的入站方=调用方；入站回调的入站方=供应商），与设计 §3.1「类型互斥」一致。**不把回调验签搬进闸门**的理由：绑定解析（接口覆盖→应用默认→平台默认）+ 链缓存烘焙 + `rawBody/headers` 通道全在 `ChainEngine`，搬迁等于重写 M3 已验证路径（见 §3.3） |
| **D-CA-4** | **显式主体标识头** `X-Client-Id`（头名可按调用方配置），凭证走各自 Header / 签名串 | 与既有「`appId` + secret」心智模型对称；O(1) 定位调用方（无需密钥摘要反查、无需给凭证表加 UNIQUE 哈希列）；审计的「名称」直接可得。备选「单头 + 密钥 SHA-256 反查」被否：HMAC/Bearer 无法由摘要定位（HMAC 要 secret 才能验），且多一套索引 |
| **D-CA-5** | **鉴权方式复用 `adapter`（`type=auth`）配置化**：新增 4 个 `INBOUND_AUTH` 验签 impl，调用方经 `client_app.auth_adapter_id` 引用（无应用/接口级继承） | 复用 D6' 适配器模型（`adapter.name` 全表唯一 / 绑定即实例 / 停用即回退）+ `AdapterImplCatalog` 元数据 → 前端表单**自动渲染**（`AdapterParamsEditor`），零新增方式专表；「鉴权方式」在审计里 = impl 语义名 |
| **D-CA-6** | **契约扩展 `InboundAuthAdapter`**（`Adapter` 的子接口）：`method()` 审计口径 + `credentialKind()` 期望凭证类型；**适配器不查库**，凭证由注入方经 `ctx.attrs("inboundCredentials")`（`List<String>`，ACTIVE+ROTATING 并存）提供 | 修正既有 `HmacCallbackVerifyAdapter` **直接查库**的耦合（适配器本该无状态、配置驱动，M0-01 §5.2）；同一适配器可同时服务于「调用方鉴权（凭证来源 `client_credential`）」与「回调验签（凭证来源 `app_credential(kind=CALLBACK)`）」——**唯一差异就是注入方**，正好呼应 M0-04「两类凭证分离」。存量 impl 保留兼容（§9.3） |
| **D-CA-7** | **默认 fail-closed**：启用后，调用方**未配鉴权方式 / 无可用凭证 → 拒绝**（40108 / 40100） | 「没配 = 放行」是最常见的鉴权事故。唯一例外是显式的 `IP_WHITELIST` 方式（且白名单必须非空，否则拒） |
| **D-CA-8** | **三态灰度开关** `client-auth.mode = OFF \| OPTIONAL \| ENFORCED`（默认 `OFF`），**平台级唯一**；接口级豁免走调用方 ACL（P2） | 一次性强制 = 线上全量 401。三态 + 观察期（§16）是安全上线的前提。**不新增 `interface` 列**（否则动 DTO / 快照 `config_json` / 版本 diff / 前端表单，改动面翻倍） |
| **D-CA-9** | **审计独立表 `access_auth_log`**，**PASS / REJECT 全记**（可配只记失败），**异步批量写**（复用 `CallLogWriter` 模式），默认保留 90 天 | 不塞 `call_log` 的理由：① 审计要按「主体 / IP / 结果」检索、要独立保留期，与按 trace 检索的高频日志是两种用途；② `call_log` 已「列表瘦身」且**加列要同步三处**（`insertBatch` 位置绑定序号 / `LIST_COLUMNS` / `CallLogView`+`toView`），错位会**静默写错列**；③ 拒绝请求可能发生在 `CallLogContext` 填充**之前**（闸门比引擎早），`call_log` 那行 `interface_id/app_id` 恒空，承载不了主体信息 |
| **D-CA-10** | **IP 名单归「鉴权」，限流/配额归「防护」**：调用方维度 IP 名单进闸门（40103）；QPS / 日配额仍留 `GatewayGuard`（42901/42902），位置在闸门**之后** | 职责切干净：**「你是谁」= 鉴权（401xx，一次判定）**；**「放你多少」= 防护（429xx，计数态）**。IP 拒绝也是鉴权结论，必须进审计表；限流是配额，不进审计（它已有 `Counter{outcome=rejected}` + `call_log`） |
| **D-CA-11** | **应用（供应商）维度的 IP 名单 / 配额行为本次不动**，仅**语义钉死 + 文档澄清**；是否另立 `callback_ip_whitelist` **待拍板** | 动它会破坏 M4 `c8_QPS限流_超限42901_不落运行表`（该用例用 OUTBOUND 接口 + `app.qps_limit`）。**调用方维度与应用维度是 AND 叠加**（任一拒绝即拒），这样既有配置继续有效、新维度更细。详见 §12.2 |
| **D-CA-12** | 错误码：**复用** 40100（凭证/签名不匹配）/ 40101（时间戳超容差）/ 40103（来源 IP 被拒）；**新增** 40107（调用方未知 / 已停用）、40108（调用方未配置鉴权方式）；HTTP 统一 401，`msg` **描述性** | 40100/40101/40103 已是「入站鉴权」语义，复用它让调用方与供应商的**联调说法一致**。描述性 msg 是取舍（有轻微枚举信息泄露），选「运维可调试优先」——与 FastMoss 联调时「先取证再二分」的团队习惯一致（§6.6 记录取舍） |
| **D-CA-13** | 安全口径：凭证 **AES-256-GCM 密文**（复用 `CryptoService`）+ 接口**只回尾 4 / 指纹**（复用 `CredentialService` 口径）+ **常量时间比较**（`MessageDigest.isEqual`）+ 敏感头名**动态注册**进 `SensitiveDataMasker` + 审计只记 `client_ip`/`xff_chain`/UA 截断 | 与 M0-04（凭证不落明文）、账号登录（令牌只存摘要）同一条纪律。B1 缺陷说明「写死脱敏清单」在「可配头名」下必然漏，所以**动态注册是硬要求** |
| **D-CA-14** | 管理面：新增**「调用方管理」页**（`views/Clients.vue` + 路由 + 菜单）+ 监控页新增**「接入鉴权」Tab**（审计查询） | 与既有页面结构对齐（Apps / Users / Monitor 五区块）。写端点自动受 `AdminAuthFilter` 的 VIEWER 只读规则保护（40302），**无需新增角色代码**（§13.3） |
| **D-CA-18**（v1.2） | **入站鉴权凭证池**：入站凭证不再必须挂在调用方档案上，而是**三级属主共用一张表** —— `INTERFACE`（接口专属池）→ `PLATFORM`（平台级共享池，所有接口通用）→ `CLIENT`（档案专属，可选）；**一凭证一行 + `label`（发给谁/何时）**；闸门**逐条试**（`ACTIVE` + 未过期 `ROTATING`），命中即通过并记 `credential_label` | 开放集第三方（未知、持续新增）不可能先建档：建档 = 每来一个调用方要运维介入一次。**凭证池**让「接入」退化为「**发一把密钥**」（1 步），同时因**一凭证一行**而保留「单独吊销某一方」与「按标签统计/告警」。**不做**「唯一的全局共享密钥」：那样泄露即全员换密钥、且无法归因（详见 §2.1 取舍表） |
| **D-CA-19**（v1.2） | **鉴权方式的归属 = 接口**（绑定角色 `CLIENT_AUTH`，接口覆盖 → 平台设置 `inbound_auth_setting.default_adapter_id`）；**`X-Client-Id` 降级为可选自报**（`client-auth.require-client-id=false` 时缺失不再拒） | 「方式」描述的是**平台这个接口对外要求什么**（如「本接口要求 `X-Api-Key`」），与「谁在调」正交；挂在调用方上会导致「同一个接口对不同调用方要求不同方式」这种无法表达的组合。复用既有 `interface_adapter_binding` ⇒ 快照/版本 diff/详情 API 自动携带，无需给 `interface` 加列（D-CA-8 论证过加列成本） |
| **D-CA-20**（v1.2） | **审计新增 `credential_label` + `credential_fingerprint`**；`principal_*` 语义细化为「**自报**主体（未经验证）」并新增 `principal_type=UNVERIFIED` | 共享凭证下「身份」不可得，但「**哪把密钥**」是**不可伪造**的事实：它同时是可归因（谁在用）、可吊销（删哪一行）、可告警（某把密钥失败激增 = 疑似泄露/被扫）的抓手。**自报主体只能用于统计分组，绝不可用于管控判定**（可伪造）——这条必须写进 UI 与文档，否则会被误用为「身份」 |
| **D-CA-17** | **平台自身发起的调用必须豁免闸门**（新增，v1.1）：管理面「模拟回调」`/test-callback` **自调网关**（`POST http://localhost:{port}{platformPath}`）⇒ `ENFORCED` 下会被闸门拒，**该调试工具直接失效**（验收方案 §3.1 正依赖它）。方案：**内部调用令牌** —— 启动时 `SecureRandom` 生成（仅存内存，**不进配置/不落库**，多实例各自独立即可，因为自调是**本实例到自己**），自调时带 `X-Internal-Token`；闸门**先判令牌**（常量时间比较），命中即 `PLATFORM_SELF` 放行并**仍写审计**。**禁止**用"来源是回环 IP"作豁免判据（反代/容器下可被伪造） | 见 §3.4 |

### 2.2 两级模型（默认低摩擦，需要时才精细化）

| 级别 | 怎么接入 | 平台侧要做什么 | 能单独吊销吗 | 适用 |
|---|---|---|---|---|
| **L1 凭证池**（**默认**） | 平台**发一把密钥**给调用方（无登记） | 建适配器实例（方式）+ 在凭证池加一行（`label` 写「发给谁/何时」） | ✅ 删那一行 | 开放集第三方、内部系统、临时联调 |
| **L2 调用方档案**（**可选**） | 建档 `client_app` + 专属凭证 | 档案 + 凭证 + （将来的）单独配额 | ✅ 停用/吊销 | 大客户要配额、要精确身份、要审计归属 |

> **默认 L1**。当出现以下任一诉求时才升级到 L2：① 该调用方要**单独限流/日配额**（P2）；
> ② 需要**经验证的身份**作为审计/合规依据；③ 需要**按调用方维度的 IP 名单**做例外处理。
> 两级**共存**且取值顺序固定：**接口池 → 平台池 → 该调用方档案凭证**（见 §6.1 步骤③）。

## 3. 总体架构

### 3.1 三类主体（一次说清，避免术语漂移）

| 主体 | 表 | 谁 | 平台与它的关系 | 鉴权机制 |
|---|---|---|---|---|
| **运营人员** | `admin_user` | 平台自己的运维/管理员 | 内部 | `AdminAuthFilter`（`/api/admin/**`） |
| **调用方 / 接入方**（开放集，v1.2） | **`client_app`（可选档案）+ 凭证池** | 第三方（已存在与**尚未出现**的调用方） | 平台**签发凭证**给它（**不强制建档**） | **调用方鉴权**（本设计，网关闸门；判定中心 = 凭证是否命中池） |
| **供应商 / 应用** | `app` | 被代理的第三方（FastMoss、evoLink…） | 平台**持有**它的凭证 | **回调验签**（M3，链内）+ 出站签名（`AUTH`） |

> **术语纪律**（沿用 2026-09-08 定稿）：对用户可见文案继续用「供应商」指被代理方；本设计新增的
> **「调用方」= 平台客户**，文档与 UI 统一用「调用方」（不叫「客户端 / 商户 / 租户」）。
> 唯一例外是**线协议头名 `X-Client-Id`** 与**表名 `client_app`**（HTTP 语义与既有 `app_id` 对称，避免 `X-Caller-Id` 与
> `X-Biz-Id` 混淆）。

### 3.2 执行顺序（网关入口，改造后全景）

```
GatewayController.gateway(path, body, request)
 1. 路径归一化 / traceId（TraceIdFilter 已写入属性）/ bizId / 报文大小兜底（40002）
 2. 路由解析：interfaceRepository.findByPath(fullPath)  →  iface（供应商应用 = app）
 3. 【新】入站鉴权闸门 GatewayInboundAuth.authenticate(request, iface, body)
      ├─ if_type = OUTBOUND → 调用方鉴权 ClientAuthVerifier（v1.2：以凭证为中心）
      │    ① 可选自报主体（X-Client-Id → client_app，**仅用于审计**；require-client-id=false 时缺失/未知均不拒）
      │    ② 鉴权方式解析（**接口 CLIENT_AUTH 绑定 → 平台设置** `inbound_auth_setting.default_adapter_id`（缓存读）；
      │       未配 → 40108 fail-closed；适配器停用 → 40108，**不回退 Noop**）
      │    ③ IP 名单（v1.2：名单来自**适配器 params**，黑先白后 → 40103）
      │    ④ 凭证注入（**凭证池三级取值**：接口池 → 平台池 → 档案池，kind = adapter.credentialKind()，
      │       ACTIVE + 未过期 ROTATING 逐条试） ※ 池为空 / 无命中 → 40108 / 40100
      │    ⑤ 适配器校验（40100 / 40101 / 防重放）
      │    ⇒ 结论写入 AccessAuthContext（PASS / REJECT + method + credential_label + 自报主体 + ip）
      └─ if_type = INBOUND  → 仅登记审计上下文（principal=SUPPLIER/app，method 待链内回填）
 4. GatewayGuard.check(app, clientIp)   ← 限流 / 日配额（应用维度，既有 42901/42902；P2 叠加调用方维度）
 5. 分流：INBOUND → InboundEngine.handle(...)   OUTBOUND → OutboundEngine.dispatch(...)
      └─ InboundEngine：链执行（INBOUND_AUTH 回调验签）后回填 AccessAuthContext（PASS / 401xx REJECT）
 6. CallLogAspect.aroundGateway  try/catch/finally
      ├─ 既存：IN 方向 call_log + Counter/Timer + CallLogContext.clear()
      └─ 【新】AccessAuthContext.flush() → AccessAuthWriter.offer(...)（异步批量）
```

**三处关键性质**（都要有测试钉住）：

- **不落运行表**：闸门在 `OutboundEngine.dispatch → createRecord` **之前**，鉴权失败 ⇒ `outbound_request`
  零增量（与 D-M4-6 同口径，可复用「计数不变」断言）。
- **不污染状态机**：失败只抛 `BizException`，统一信封返回（`GlobalExceptionHandler`，HTTP = `code/100`）。
- **一定留痕**：即使请求在闸门就被拒，`CallLogAspect.aroundGateway` 的 `catch` 分支照常写 IN 条 `call_log`，
  `finally` 里 flush 审计 ⇒ **拒绝也有审计行**（安全审计的核心价值）。

### 3.3 为什么不把回调验签也搬到闸门（D-CA-3 的展开）

| 维度 | 留在链内（选） | 搬到闸门（否） |
|---|---|---|
| 绑定解析 | 复用 `ChainEngine.resolveBound`（接口覆盖 → 应用默认 → 平台默认 + `enabled` 校验 + 逐层回退 + `log.warn`） | 要在闸门里**重写一套**（或把 `ChainEngine` 的方法暴露成公共 API，耦合反向） |
| 链缓存烘焙 | 已在装配期烘焙（M5 D-M5-2），零额外成本 | 每请求实时解析（或另建一套缓存 + 事件失效） |
| 请求上下文 | `ctx.attrs("headers"/"rawBody")` 现成 | 要为闸门另造 `AdapterContext` 构造路径（本设计为调用方鉴权造了，但没必要再造一份给回调） |
| M3 回归面 | **零**（`HmacCallbackVerifyAdapter` 不动，只在 `InboundEngine` 加一处 try/catch 回填审计） | 全量重测 M3 回调验签（B1-B6 + X1-X3） |
| 代价 | 两处执行点 | 一处执行点，但绑定解析双份实现 |

**结论**：统一「口径」（方式目录 / 凭证契约 / 审计 / 错误码），**不统一「执行点」**。
`InboundEngine` 里只加一处 5 行的 try/catch 回填审计（§9.2）——这是本设计对 M3 的唯一改动。

### 3.4 平台自身发起的调用（内部路径，闸门必须区分）

> 闸门在 `GatewayController` 内 ⇒ **凡走到网关的请求都会过闸门**，**包括平台自己发出的那些**。
> 逐一交代，避免实现时"漏一个就把自家功能打死"：

| 内部路径 | 经网关？ | 闸门下会怎样 | 处理 |
|---|---|---|---|
| 管理面**「模拟回调」** `POST /interfaces/{id}/test-callback` | ✅ **经**（自调 `http://localhost:{port}{platformPath}`） | **会被拒**（无 `X-Client-Id`）⇒ **工具失效** | **D-CA-17 内部令牌豁免** → `PLATFORM_SELF`，**仍写审计** |
| 管理面**「测试接口」** `POST /interfaces/{id}/test` | ❌ 不经（直调引擎） | 不受影响 | 无需处理；**也不写**审计（§10.1） |
| **前置编排**（`PreStepExecutor` → `ChainEngine`/`UpstreamInvoker`） | ❌ 不经 | 不受影响 | 无需处理（**不要**给前置调用加调用方鉴权） |
| **补偿 / 重送 worker**（出站补偿、入站重送） | ❌ 不经 | 不受影响 | 无需处理 |
| 浏览器 **CORS 预检 `OPTIONS`** | ✅ 经 | 预检**不带凭证头** ⇒ 会被拒 ⇒ 浏览器直调场景全废 | 闸门对 `OPTIONS` **豁免**（与 `AdminAuthFilter` 同口径） |
| `/actuator/**`（健康检查）、管理面 `/api/admin/**` | ❌ 不同路径 | 不受影响 | 无需处理 |

> ⚠️ **两条硬约束**（实现时最容易漏）：
> ① 内部令牌比对必须用**常量时间比较**（`MessageDigest.isEqual`），且**令牌为空一律不豁免**（禁止"空令牌放行"）；
> ② **不要**用"来源 IP 是回环地址"作为豁免判据 —— 反向代理 / 容器场景下真实客户端 IP 的取法见 §11，
>    按 IP 放行等于给外部流量开了一条后门。

### 4.2 删除策略（追加到 `schema.sql` 末尾的删除约定）

```
· 删调用方     → 级联删其凭证（client_credential）；**审计表不删**（access_auth_log 只靠保留期清理，
                 主体已删则靠 principal_id/principal_name 快照回溯）；存在引用 forbidden?（无引用方，允许删）
· 删鉴权适配器 → ① 清 `client_app.auth_adapter_id`（L2 档案默认方式，若有）、② 删/清 `interface_adapter_binding` 里该 adapter 的 `CLIENT_AUTH` 行（走既有绑定删除规则）、③ 平台设置 `inbound_auth_setting.default_adapter_id` 指向它时**必须人工改配置**（启动期属性，非 DB）
                 ⇒ 任一环节缺失 ⇒ 该接口 fail-closed `40108`（**不回退 Noop**，§6.5）
· 删入站凭证行 → **即时生效**（下一请求即失效，无缓存/不需重启）—— 这是「单独吊销某个调用方」的正式手段
· 删接口       → 不删 access_auth_log（interface_id/interface_code 快照保留）
· 审计表清理   → 保留期任务（默认 90 天）或手工 SQL；不进 worker（P2，§18）
```

### 4.3 为什么审计**必须**冗余名称快照

`principal_name` / `interface_code` 是**快照**而非外键 join 结果：审计表的价值在于
「三个月后还能回答**当时**是谁」。若靠 join，调用方改名或删除后，历史审计行会变成
「未知主体」——这正好抹掉了审计要保留的信息。同理 `client_ip` 与 UA 也是**事实记录**，不做解析归一。

## 5. 鉴权方式目录（方式矩阵）

### 5.1 四种 P1 方式（+ Noop 兼容）

| 方式 | 线协议（默认，头名可配） | 凭证 `kind` | 校验要点 | 审计 `auth_method` |
|---|---|---|---|---|
| **API Key** | `X-Client-Id: ERP-PROD`<br>`X-Api-Key: <secret>` | `API_KEY` | 常量时间比较；ACTIVE+ROTATING 逐条试 | `API_KEY` |
| **HMAC 签名** | `X-Client-Id`<br>`X-Timestamp: <秒级>`<br>`X-Signature: <hex>` | `HMAC_SECRET` | ①时间戳容差（默认 300s）②`Hex(HMAC(algo, secret, ts + "." + UTF-8(rawBody)))` ③防重放 | `HMAC-SHA256` / `HMAC-SHA1` / `HMAC-SHA512` |
| **Bearer Token** | `X-Client-Id`<br>`Authorization: Bearer <token>` | `BEARER_TOKEN` | 常量时间比较；`prefix` 可配（`Bearer` / `Token` / 空 = 裸 token） | `BEARER` |
| **仅 IP 名单** | 无需凭证头（**白名单必须非空**） | —— | 名单命中即通过；**无名单 + 无凭证 → 一律拒**（D-CA-7） | `IP_WHITELIST` |

**HMAC 签名串沿用既有口径**（`HmacSigner`：`timestamp + "." + rawBody`，hex 小写）——**不新造算法**：
调用方与供应商可以用**同一个签名工具 / 同一份联调脚本**，这是一条实打实的运维减法。复用
`HmacSigner.sign/verify`（含 `MessageDigest.isEqual` 常量时间比较），零新增密码学代码。

**凭证从哪来（v1.2 修订）**：不再是「**该调用方的凭证**」，而是 **凭证池**（§6.1 步骤④ 三级取值：
接口池 → 平台池 → 档案池），因此：

| 项 | v1.1 | **v1.2** |
|---|---|---|
| 方式（适配器）归属 | `client_app.auth_adapter_id` | **接口绑定 `CLIENT_AUTH` → 平台默认**（D-CA-19） |
| 凭证归属 | `client_credential.client_id` | **`owner_type` / `owner_id` 三级**（D-CA-18） |
| IP 名单来源 | `client_app.ip_whitelist/ip_blacklist` | **适配器 params**（`ipWhitelist`/`ipBlacklist`，见下表）；档案名单保留为可选精确维度 |
| 可归因抓手 | `principal_id`（登记名） | **`credential_label` + `credential_fingerprint`**（不依赖登记）|
| `X-Client-Id` | **必需**（未知 → 40107） | **可选自报**（仅审计；`require_client_id` 控制） |

### 5.2 待确认项（P2/P3，不在本次）

Basic（`BASIC`）、云厂商签名（调用方是云厂商客户端的场景，可复用 `CloudSignatureAdapter` 思路）、
OAuth2 client_credentials（需 token 端点与缓存，成本高）、mTLS（需连接级配置 + 证书存储）。

> 的**校验逻辑与「是谁的凭证」无关**，因此**同一批适配器实例既可用于入站鉴权**
> （v1.2：绑到接口 `CLIENT_AUTH` 角色，或作为平台设置 `inbound_auth_setting.default_adapter_id`），
> **也可绑到接口 `CALLBACK_AUTH` 角色（回调验签）**——见 §9.3。

## 6. 调用方鉴权流程（Flow A）详规

### 6.1 判定顺序（闸门内：步骤 ⓪ + 五步；**v1.2 以凭证为中心重写**）

> **步骤 ⓪（先于一切）**：`OPTIONS` → 直接放行（CORS 预检不带凭证）；`X-Internal-Token` 命中
> → `PLATFORM_SELF` 放行（§3.4 / D-CA-17）。**以下 ①~⑤ 仅针对外部调用方。**

```
① 可选自报主体  X-Client-Id（可配头名）→ 查 client_app
                · 缺失 → **不拒**（仅审计；`require_client_id=1` 时按 §6.2 拒 40107）
                · 命中档案 → 审计用档案名（principal_type=CLIENT）
                · 未知 / status=DISABLED → **不再拒**（v1.2）；仅记审计 reason（自报不等于身份）
                · ⚠️ **是否登记不改变放行判定**（放行只看凭证）；档案只影响：审计归属 + 档案池凭证是否参与取值
② 方式解析     接口绑定 CLIENT_AUTH → 平台设置 `inbound_auth_setting.default_adapter_id` → adapter(type=auth, enabled=1)
                · 未配 / 适配器已停用 → 40108「本接口未配置可用的入站鉴权方式」
                · 适配器停用即拒（**不回退 Noop**——与链内「逐层回退到 Noop」语义相反，见 §6.5）
③ IP 名单      **来源 = 适配器 params**（`ipWhitelist` / `ipBlacklist`）：黑先白后 → 40103（与 GatewayGuard 同口径、同错误码）
                （若自报主体命中档案且档案也配了名单 ⇒ 叠加为 AND，任一拒绝即拒）
④ 凭证注入     **凭证池三级取值**（INTERFACE(interface.id) → PLATFORM(owner_id=NULL) → 命中档案的 CLIENT）
                kind = adapter.credentialKind()，status ∈ {ACTIVE, 未过期 ROTATING} → CryptoService.decrypt → List<String>
                · 池为空（该 kind 无任何可用凭证） → 40108「平台未配置可用的入站凭证」
                · 池非空但无命中 → 40100（带了凭证但不对；或 ENFORCED 下未带）
                · ⚠️ 单条解密失败 → try/catch continue（坑预判 #7），不整次 500
⑤ 适配器校验   adapter.process(ctx) → 通过 / BizException(40100 / 40101)
                · 命中时把 **credential_label / credential_fingerprint** 写入审计（D-CA-20）
```

> **⭐ 凭证池取值语义（v1.2 关键，极易被实现成「并集」）**：三级**逐级短路** ——
> 从 `INTERFACE(interface.id)` 开始，**某一级存在可用凭证（该 `kind` + `ACTIVE` 或未过期 `ROTATING`）就用这一级、不再向下取值**；
> 该级为空才继续（→ `PLATFORM` → 命中档案的 `CLIENT`）。
>
> - **为何不用并集**：短路是**能力超集** —— 要「本接口额外接受某些密钥」只需把那些密钥**也放进接口池**；
>   反之，若用并集，则**接口无法表达「只认本接口的密钥」**（平台共享密钥会自动对所有接口生效）。
> - **短路的依据是「该级是否有可用凭证」而非「是否命中」**：接口池有凭证但请求带的是平台池密钥 ⇒ **`40100`（不回落到平台池）** —— 这正是「接口隔离」的语义；
> - **反证用例**（§16.1 用例 42）：接口池有凭证时，平台池密钥必须被拒；删掉接口池那一行后，同一请求变 200。

### 6.2 模式真值表（**实现照此写，测试照此测**；v1.2 重画：判定中心 = 凭证）

**主表（判定中心 = 凭证是否命中池）**：

| `mode` | 凭证头 | 池中命中 | 结论 | `result` | `auth_method` |
|---|---|---|---|---|---|
| `OFF` | 任意 | —— | **跳过鉴权**（不校验、不报错） | `PASS` | `NONE`（reason：未启用入站鉴权） |
| `OPTIONAL` | 无 | —— | 放行（灰度观察流量） | `PASS` | `NONE`（reason：OPTIONAL 未带凭证） |
| `OPTIONAL` | 有 | **命中** | 走 ⑤ 完整校验 | `PASS` / `REJECT` | 方式名 |
| `OPTIONAL` | 有 | 未命中 | **拒 `40100`**（带了凭证却无效 ⇒ 配置错误或伪造，不能静默忽略） | `REJECT` | 方式名 |
| `ENFORCED` | 无 | —— | **拒 `40100`**（缺少入站凭证） | `REJECT` | 方式名 |
| `ENFORCED` | 有 | **命中** | 走 ⑤ 完整校验 | `PASS` / `REJECT` | 方式名 |
| `ENFORCED` | 有 | 未命中 | **拒 `40100`**（不区分「密钥错」与「未发放」，防枚举） | `REJECT` | 方式名 |

**前置拒绝（按序先于主表）**：

| 序 | 条件 | 结论 | 错误码 |
|---|---|---|---|
| ⓪a | `OPTIONS` 预检 | 放行 | —— |
| ⓪b | `X-Internal-Token` 命中 | 放行（`PLATFORM_SELF`，**仍写审计**） | —— |
| 1 | 适配器未配 / 已停用 | 拒 | `40108`（**不回退 Noop**，§6.5） |
| 2 | IP 名单：黑名单命中 / 白名单非空未命中 | 拒 | `40103` |
| 3 | 池为空（该 `kind` 无任何可用凭证） | 拒 | `40108`（「平台未配置可用凭证」**≠ 调用方的错**，与 `40100` 分开） |
| 4 | `require_client_id=1` 且自报主体缺失/未知/停用 | 拒 | `40107`（**v1.1 兼容档**，见下） |

**主体语义：什么能用作管控依据（v1.2 新增，**必读**）**：

| 场景 | `principal_type` | `principal_id / name` | 能否用于吊销 / 配额等管控 |
|---|---|---|---|
| 未带 `X-Client-Id` | `UNVERIFIED` | 空 | ❌ |
| 自报、命中档案，**且命中的是「档案池」凭证** | `CLIENT` | client_id / 档案名 | ✅ **这是 L2 登记的核心收益**：凭证与档案绑定 ⇒ 等价于已验证身份 |
| 自报、命中档案，但命中的是「平台池」凭证 | `UNVERIFIED` | 自报值 / 档案名 | ❌（密钥是共享的，谁都能自称） |
| 自报但档案未知 / 已停用 | `UNVERIFIED` | 自报值 | ❌（仅统计分组） |
| 回调方向（Flow B） | `SUPPLIER` | app_id / 应用名 | ✅（回调验签已验签名） |
| 平台自调（D-CA-17） | `PLATFORM_SELF` | —— | —— |

**`require_client_id` 两档行为（避免一次性破坏 v1.1 已验收的行为）**：

| 取值 | 语义 | 缺主体时 | 主体未知 / 停用时 | 适用 |
|---|---|---|---|---|
| `true`（**默认**，v1.1 兼容） | 主体必须声明且可识别 | `OFF` 跳过 / `OPTIONAL` 放行 / `ENFORCED` 拒 `40107` | **拒 `40107`** | 已登记的封闭集（现状） |
| `false`（**开放集推荐**） | 主体可选自报 | 不拒（按主表判凭证） | **不拒**（仅审计标注） | 未知且持续新增的第三方（D-CA-19） |

> `OFF` 行仍写审计，是为了支持**观察期**：`mode=OFF + audit.enabled=true` = 「先看清谁在调，再决定卡谁」。
> 这是本设计推荐的灰度第一步（§15）。
>
> ⚠️ **实现要点（v1.1 全量套件抓到过，v1.2 仍然适用）**：**`OFF` 的判断必须放在最前面** ——
> `OFF` 下**任何**输入组合（含"带了凭证头却没有主体头"）都必须**跳过鉴权、不报错**。
> 把任何主体/凭证判定放到 `mode` 判断之前会**误伤既有调用方**
> （真实案例：`M4IntegrationTest.c6` 的调用方自带 `Authorization` 头用于验证日志脱敏，
> 而平台未启用鉴权 ⇒ 被误判 40107 打成 401）。回归守护：`ClientAuthVerifierTest#OFF_无主体但带了凭证头_仍放行_真值表第一行`。
>
> ⚠️ **v1.2 对已落地用例的影响**：`ClientAuthVerifierTest` 中依赖「无主体 → 40107」的用例在
> `require_client_id=1` 下**全部保留且必须继续绿**（兼容档）；新增用例覆盖 `false` 档的开放集行为（§16.1）。

### 6.3 敏感头名动态注册（B1 缺陷修正，硬要求）

### 6.4 防重放与时间戳（仅 HMAC）

- 时间戳头缺失 / 非法 → `40100`；超容差 → `40101`（与 M3 回调验签完全一致，文案复用）。
- 防重放：`replayProtection=true` 时按 `(clientId, signature)` 在容差窗口 ×2 内**内存去重**；
  单实例口径；缓存有界（沿用 `HmacCallbackVerifyAdapter` 的 `MAX_REPLAY_CACHE=10_000` 与惰性清理策略）。
- **不引入 Redis / 分布式去重**（与熔断/限流同口径，v1.1）。

### 6.5 「不回退 Noop」与「停用即拒」——两处语义（v1.2 更新）

| 场景 | 链内（`ChainEngine.resolveBound`） | 闸门（本设计） | 为什么相反 |
|---|---|---|---|
| 适配器停用 / 缺失 | **逐层回退**：接口绑定 → 应用默认 → 平台默认 `Noop`（+ `log.warn`） | **回退到平台默认**（接口 `CLIENT_AUTH` → 平台设置 `inbound_auth_setting.default_adapter_id`），**但平台默认也缺失 → 一律拒 40108**。**绝不回退 Noop** | 链内回退是「出站行为可降级」（Noop = 不加签名，功能仍可用，有告警）；闸门回退 Noop = **鉴权系统自动打开大门**，是安全事故。**这条必须写进代码注释**（否则后来者「为了对齐链内语义」而改成回退） |
| **「停用某个调用方」（v1.2 语义位移）** | —— | **不再靠 `client_app.status` 拦截主体**（L1 开放集路径上根本没有档案），而是：**吊销其凭证**（`RETIRED` / 删行）；若走 L2 档案，则档案 `DISABLED` 时**其档案池凭证不参与取值** | 凭证池模型下「身份」不是入口，**凭证才是入口**；把停用语义落在凭证上，L1/L2 两条路径**用同一个开关**，不会出现「停用了却还能调」（L1）的漏洞 |

### 6.6 错误信息粒度取舍（D-CA-12 的展开）

| 选项 | 优点 | 缺点 | 选择 |
|---|---|---|---|
| 统一「鉴权失败」泛化文案 | 防主体枚举 | 联调期无法自助定位（本项目已多次因「看不清上游/平台差异」耗费排查时间） | ✗ |
| **描述性 msg + 精确 `error_code` + 审计留原因** | 联调自助（`40107 调用方不存在：ERP-PROD`） | 轻微枚举信息泄露（可得「该 client_id 是否存在」） | ✓ |

缓解措施：连续失败告警（§14.2）+ 观察期先摸清合法流量（§16）。**这是明确取舍，不是遗漏。**

## 9. 回调验签（Flow B）统一口径

### 9.1 方式扩展（从「只有 HMAC」到「同批方式」）

| 现状 | 本设计 |
|---|---|
| `HmacCallbackVerifyAdapter`（唯一手段，且**直接查库**读 `app_credential`） | 接口 `CALLBACK_AUTH` 角色可绑 **`ClientApiKeyVerifyAdapter` / `ClientHmacVerifyAdapter` / `ClientBearerVerifyAdapter`**（通用批，凭证由 `ChainEngine.injectCallbackCredential` 注入）；`HmacCallbackVerifyAdapter` **保留可用**（存量配置零迁移） |

**凭证来源不变**：仍是 `app_credential(kind=CALLBACK)`（M0-04：回调验签凭证独立于出站签名凭证）。
**唯一差异是凭证由谁注入**——这正是 D-CA-6 的价值：**一套验签代码，两个维护入口**。

### 9.2 审计回填（`InboundEngine` 5 行）

```
① 网关闸门（INBOUND 分支）登记：direction=CALLBACK，principal=SUPPLIER/{app_id, app.name}，client_ip，UA
② 链内验签结果回填：
   成功 → AccessAuthContext.pass(method=adapter.method(), adapterId)
   BizException(401xx) → AccessAuthContext.reject(code, msg)
③ 非 401xx 的链失败（40001 映射失败等）→ 审计**保持 PASS**（鉴权确实通过了），
   由 call_log / 状态机负责；审计不承担业务失败记录（职责边界）
```

### 9.3 是否迁移 `HmacCallbackVerifyAdapter`（待拍板 D-CA-16）

| 选项 | 说明 |
|---|---|
| **A（推荐，P5 可选）** | 把 `HmacCallbackVerifyAdapter` 改写为「读注入凭证」的薄适配器，**impl 名与 params schema 完全不变**（存量 `adapter` 行零迁移，数据库不动）。收益：删掉一处「适配器查库」的反模式，两方向彻底同构 |
| B | 保留现状（两套验签代码并存，但零 M3 回归风险） |

## 10. 接入审计设计（`access_auth_log`）

### 10.1 写入路径（唯一入口，与 `call_log` 同构）

```
闸门 / 链内  →  AccessAuthContext.set(...)（ThreadLocal；不可变记录 + 可变结论）
网关切面 finally → AccessAuthContext.flush() → AccessAuthWriter.offer(entry) → 【异步批量】DB
```
- **清理契约**：**闸门/引擎登记、网关切面清理**（照 `CallLogContext` 的既有纪律，防止 ThreadLocal 泄漏）。
- **两个管理面调试端点的结局不同**（**v1.1 复核更正**）——
  · `POST /interfaces/{id}/test`（测试接口）→ **直调引擎、不经网关** ⇒ **不写审计**（与「不落 IN 条 `call_log`」口径一致）；
  · `POST /interfaces/{id}/test-callback`（模拟回调）→ **自调网关**（`POST http://localhost:{port}{platformPath}`）
    ⇒ **会走闸门** ⇒ 走 §3.4 的内部令牌豁免（`PLATFORM_SELF`），**写审计**。
    ⚠️ 初版把两者都写成"不经网关"是**事实错误**（把自调当成了直调）；照初版实现，`ENFORCED` 下
    「模拟回调」会被自家闸门拒掉。
- **未命中接口的路径**：默认**不写审计**（`record-unmatched=false`）——否则任何人扫路径都能往审计表灌数据；
  改为 `Counter{result=unknown_interface}` + 采样 `log.warn`（P2 可开）。

### 10.2 保留期与体积估算

| 项 | 值 |
|---|---|
| 每条审计行（除 `trace_id`/`reason` 外基本定长） | ~250–350 字节 |
| 假设量级 | 与 `call_log` IN 条**同量级**（每次入站鉴权 1 条） |
| 默认保留 | **90 天**（`access-auth.audit.retention-days`，独立于 `call_log` 的归档策略） |
| 降量开关 | `record-pass=false`（只记失败）→ 体积通常降一个数量级；**观察期必须为 true** |

### 10.3 查询与展示

- 端点：`GET /api/admin/monitor/access-logs`（分页 + 组合过滤；**时间窗强制 ≤7 天**，未传按近 24h，
  与 `call-logs` 关键字检索同一条纪律——防全表扫）。
- 前端：Monitor「接入鉴权」Tab（表 + 筛选 + 抽屉详情），Observation 摘要卡（通过/拒绝/未知主体）。
- **交叉检索**：审计行有 `trace_id` → 可直接跳到「调用日志」看该 trace 的 IN/OUT 报文
  （这是把「谁调的」与「调了什么」串起来的关键路径，§17 手动验收 C-3 会验证）。

### 10.4 凭证归因（v1.2 新增：`credential_label` / `credential_fingerprint`）

**为什么加这两列**：共享凭证模型下 `principal_*` 是**自报**（不可信），唯一**不可伪造**的事实是
「**命中了哪一把凭证**」。它一次性格外回答三个运维问题：

| 问题 | 靠什么回答 | 用途 |
|---|---|---|
| 「这把密钥是谁的？」 | `credential_label`（发出去时人工填的备注） | 出事时能叫上人 |
| 「这把密钥还有人用吗？」 | 按 `credential_fingerprint` 统计近 N 天命中数 | **吊销前必问**（避免吊销后才发现是自己某个内部系统在用） |
| 「是不是有人在扫 / 密钥泄露了？」 | 按指纹看失败率与失败量趋势 | 告警（比按 IP 精确得多） |

**两个硬约束**：
- ❌ **不要把 `credential_label` / `fingerprint` 做成 Micrometer 指标标签** —— label 是运维输入，
  基数据不可控（**指标标签基数爆炸**是 Micrometer/Prometheus 的典型事故）；指标仍按
  `direction/principal/method/result` 打标签；
- ✅ 告警分桶可以用指纹，但必须在告警侧做**基数上限**（仅跟踪 Top N + 其余归 `other`），照 `AlertService` 现有分桶习惯。

## 11. 来源 IP 与可信代理

| 项 | 口径 |
|---|---|
| 取值 | 默认 `request.getRemoteAddr()`；`app.api-center.trust-xff=true` 时取 `X-Forwarded-For` **首值**（复用既有 `GatewayGuard.resolveClientIp`，**单一实现点**，不新写一份） |

## 12. 与「接入层防护」（D-M4-6）的职责重划

### 12.1 职责表（改造后）

| 检查 | 维度 | 位置 | 错误码 | 进审计表 | 进 `call_log` | 落运行表 |
|---|---|---|---|---|---|---|
| **来源 IP 名单（调用方）** | 调用方 | **闸门（新）** | `40103` | ✅ | ✅ | ❌ |
| **调用方鉴权（主体 + 凭证）** | 调用方 | **闸门（新）** | `40100/40101/40107/40108` | ✅ | ✅ | ❌ |
| 来源 IP 名单（应用） | 应用（供应商） | `GatewayGuard`（既存） | `40103` | ❌（既存行为） | ✅ | ❌ |
| QPS 限流 | 应用（供应商） | `GatewayGuard`（既存） | `42901` | ❌ | ✅ | ❌ |
| 日配额 | 应用（供应商） | `GatewayGuard`（既存） | `42902` | ❌ | ✅ | ❌ |
| QPS / 日配额（调用方，**P2**） | 调用方 | `GatewayGuard` 扩展 | `42901/42902` | ❌ | ✅ | ❌ |

**顺序**：闸门（身份）→ 防护（配额）。理由：**未认证的请求不该消耗配额**，且配额按已认证主体计数更准确。
**叠加语义**：调用方维度与应用维度 **AND**（任一拒绝即拒），既不破坏既有配置，又提供更细粒度。

> 📌 **同一个 40103 有"两个维度"**（v1.1 补充）：**调用方维度**（`client_app`，闸门内）与
> **应用维度**（`app`，`GatewayGuard` 内）**AND 叠加**，任一拒绝即拒。因此 `msg` **必须能区分是哪张名单拦的**：
> `「调用方来源 IP 被拒（黑名单）：1.2.3.4」` / `「应用来源 IP 被拒（不在白名单）：1.2.3.4」`
> —— 同码不同文案，运维才能一眼定位（否则"被拒了但不知道是哪张名单"）。
>
> **v1.2 补充（限额与共享凭证的关系，**必读**）**：`GatewayGuard` 的 QPS / 日配额**仍只按 `app`（供应商）**计算 ⇒
> **一个接口的额度是所有调用方共享的**。共享凭证下，**一个滥用者能吃掉整个接口的额度、连带打死其他调用方** ——
> 这是「低摩擦接入」的**已知代价**（不是缺陷，是取舍）。缓解路径：
> ① 上线后靠审计 + `auth_fail_streak` 告警（IP / 凭证指纹维度）发现异常来源；
> ② 真正需要「按调用方限流」时，才把该调用方升级到 **L2 档案**（P2 落地 `client_app.qps_limit/daily_quota`）。
> **不可**把共享凭证当成「按调用方隔离」的基础——它在语义上就不携带身份。

### 12.3 「平台默认鉴权方式」变更的影响面（v1.2）

| 变更 | 影响 | 平台要不要补动作 |
|---|---|---|
| 改 `default_adapter_id`（页面） | 只影响**未绑定 `CLIENT_AUTH` 的接口** | 页面保存后**即时生效**（发 `ConfigChangedEvent`）；已绑定接口**零影响**（现场隔离，这是接口级覆盖的设计目的） |
| 旧默认适配器**被停用/删除** | 未绑定接口 → `40108` fail-closed | 页面在保存时**校验引用存在**；删除适配器时给出「N 个接口将失去默认方式」提示（§4.2） |
| `require_client_id` 1→0（放松） | `X-Client-Id` 缺失/未知不再拒（开放集放开） | 属**放松**动作 ⇒ 二次确认 + `log.warn` + 告警；建议先回 `mode=OFF` 观察一轮 |

- **两个管理面调试端点的结局不同**（**v1.1 复核更正**）——
  · `POST /interfaces/{id}/test`（测试接口）→ **直调引擎、不经网关** ⇒ **不写审计**（与「不落 IN 条 `call_log`」口径一致）；
  · `POST /interfaces/{id}/test-callback`（模拟回调）→ **自调网关**（`POST http://localhost:{port}{platformPath}`）
    ⇒ **会走闸门** ⇒ 走 §3.4 的内部令牌豁免（`PLATFORM_SELF`），**写审计**。
    ⚠️ 初版把两者都写成"不经网关"是**事实错误**（把自调当成了直调）；照初版实现，`ENFORCED` 下
    「模拟回调」会被自家闸门拒掉。

现状：`GatewayGuard.check(routed.app)` 用**供应商应用**的 `ip_whitelist` 校验**调用方** IP。三种可能意图：

| 选项 | 语义 | 影响 |
|---|---|---|
| **A（本次采纳）** | 「该应用**全部入站流量**的来源 IP」（含 OUTBOUND 的调用方 + INBOUND 的回调来源） | 行为不变（M4 `c8` 绿）；缺点是**一个供应商应用无法分别为「调用方」与「回调来源」配名单**→ 用调用方维度名单补（新表字段） |
| B | 拆列：`app.ip_whitelist` 只管回调来源，另加 `app.client_ip_whitelist` 管调用方 | 更精确，但要改 `app` 表 + DTO + 前端 + 迁移，且 M4 用例语义要复核 |
| C | 语义收紧：`app.ip_whitelist` **只对 INBOUND 生效** | 语义最干净，但**会改既有行为**（OUTBOUND 调用不再受应用名单约束）→ M4 `c8` 用的是 `qps_limit` 不受影响，但 `GatewayGuardTest#白名单非空未命中_40103` 的集成用法需复核 |

**建议**：本次取 **A**（零行为变更，靠新调用方维度补足精度）；
把 **B** 记入 backlog（若出现「同一供应商既回调用固定 IP、又有多个调用方」的真实诉求，再按 B 拆列）。
**评审时请明确表态**。

| `apicenter.auth.unknown_principal` | `ip` | 未知主体探测（P2 用于封禁决策） |

### 13.2 告警（复用 `AlertService`）

- **连续鉴权失败**：按主体（`principal_id`，主体未知时按 `client_ip`）5 分钟窗口计数 ≥
  `client-auth.fail-alert-threshold`（默认 10）→ `alert_event`（`rule_id=NULL`，`metric=auth_fail_streak`，
  `level=CRITICAL`），文案含主体名 + IP + 最后错误码。**逐行照抄** `AlertService.recordVerifyFailure`
  的实现模式（含「命中即重置窗口」）。
- **验签连续失败**：既有 `metric=verify_fail_streak` **保留**（回调方向），两条并行不冲突
  （口径差异：一条按 app，一条按 principal）。
- **临时封禁**：**不做**（与 M4 结论一致，安全能力 v1.1）。

### 13.3 日志

- 闸门判定**单行结构化**：`鉴权结论 result=REJECT principal=ERP-PROD ip=1.2.3.4 method=API_KEY code=40100 reason=...`
  （便于 `grep` 与日志平台正则）。
- **禁止**打印凭证（明文 / 密文 / 摘要）与完整签名——只打尾 4 或指纹（`SensitiveDataMasker.maskValue` 口径）。

  api-center:
    client-auth:
      # 灰度三态：OFF 不校验（现状）/ OPTIONAL 有凭证就验、无凭证放行 / ENFORCED 必须通过
      # 推荐上线路径：OFF+审计（观察）→ OPTIONAL（灰度）→ ENFORCED（强制）
      mode: OFF
      # 【v1.2 重要】下列两项**不再放配置** —— 改为**落库 + 页面可改 + 改后即时生效**（§4.1 表 26 `inbound_auth_setting`）：
      #   · 平台默认鉴权方式（`inbound_auth_setting.default_adapter_id`）
      #   · 是否强制自报主体（`inbound_auth_setting.require_client_id`）
      # 理由：它们是**日常运维/接入**要频繁调的旋钮（新增一个调用方/换一种方式不该重启服务）；
      #       而 `mode`（上线与应急总开关）**刻意留在配置** ⇒ 改它必须重启 = 一个「有意动作」，
      #       避免误点导致鉴权整体关闭（与 `require_client_id` 默认 true 同一条安全默认纪律）。
      # ⚠ 实现要求：新表读取必须走**内存缓存 + ConfigChangedEvent 失效**（照 M5.2 链缓存纪律，
      #   新增配置入口必须补发事件，否则最长 5 分钟不生效）。
      # 主体标识头名（平台默认；单个调用方可在其适配器 params.idHeaderName 覆盖）
      id-header: X-Client-Id
      # 额外需脱敏的头名（兼容既有可配头名，见 §6.3 B1 缺陷）
      mask-header-names: ""
      audit:
        enabled: true          # 独立开关：OFF + audit=true = 「观察模式」（先看清流量）
        record-pass: true      # false = 只记拒绝（降量，但观察期必须 true）
        record-unmatched: false # 未命中接口的路径不写审计（防刷表）
        retention-days: 90     # 仅供人工/脚本清理参考（P1 不做自动清理任务）
      fail-alert-threshold: 10 # 5 分钟窗口内同主体连续失败达阈值 → alert_event
      # 注：**内部调用令牌（D-CA-17 / §3.4）无需配置项** —— 启动时 SecureRandom 生成、仅存内存、
      #     进程内比对；自调是本实例到自己，多实例各自独立即可（也避免把密钥写进仓库/配置）
    # 复用既有：trust-xff（默认 false，见 §11）

## 21. 附：与既有设计/表的关系一览（评审速查）
10. **自家闸门把自家工具打死**（v1.1 新增）：闸门在 `GatewayController` 内 ⇒ **平台自调也会过闸门**；
    最典型的是管理面「模拟回调」（`/test-callback` → 自调网关）：`ENFORCED` 一上线，该工具立刻 401。
    照 §3.4 的清单**逐条过一遍**（自调 / `OPTIONS` / 前置编排 / worker），漏一个就是一次线上事故。
11. **用「回环 IP」当豁免判据 = 开后门**（v1.1 新增）：反代 / 容器 / K8s 场景下 `client_ip` 的取法见 §11；
    一旦按 IP 豁免，外部流量只要能构造出回环来源就会**完全绕过鉴权**。→ 只认**内部令牌**（且空令牌不豁免）。


```
既有 25 张表（v1.2 落地后 **26**）           本设计
├─ app（应用=供应商）          ──── 对称参考 ──→ client_app（调用方档案，【v1.2 降级为**可选**】）  【23】
├─ app_credential（两类凭证）  ──── 同构   ──→ client_credential（**入站凭证池**，三级属主）  【24，v1.2 语义升级】
├─ adapter（三类适配器）       ──── 复用   ──→ +4 个 auth impl（调用方/回调通用验签）
├─ interface_adapter_binding   ──── 复用   ──→ +角色 CLIENT_AUTH（鉴权方式挂接口；**不新增 interface 列**）
├─ call_log（调用日志）        ──── 分工   ──→ access_auth_log（鉴权审计，v1.2 +凭证归因两列）  【25】
├─ （无对应）                  ──── 新增   ──→ inbound_auth_setting（入站鉴权平台设置，**单行、运行期可改**）【26，v1.2】
├─ admin_user/admin_session    ──── 不涉及（管理面鉴权独立）
└─ outbound_request/…          ──── 不涉及（鉴权失败不落运行表）
```

**一句话总结（v1.2）**：新增**一个可选档案（调用方）+ 一张凭证池 + 一张审计表 + 一个入口闸门**，把
「**谁在调平台 / 谁在回调平台 · 从哪来 · 用什么方式 · 结果如何**」变成**可配置、可灰度、可查询**的事实；
**默认路径无需登记**（持有平台签发的凭证即可调用），**吊销与归因由凭证池承担**（`label` + 指纹）；
**不新增 `interface` 列**、不碰状态机、不碰 M3 已验证路径、不改 M4 既有行为（Q1=A 时）。

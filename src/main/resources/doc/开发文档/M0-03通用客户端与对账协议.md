## 1. 通用声明式客户端约定

### 1.1 接口形态（按协议维度，不按渠道写死）

**定稿 C1**：单一通用客户端接口 `ExchangeClient`，URL / 方法 / Content-Type / Header / Body 全参数化（与旧版 demo 按渠道写死 PartnerAClient/PartnerBClient 的差异点）：

```java
@HttpExchange(method = "POST", url = "{url}", contentType = "application/octet-stream")
ResponseEntity<byte[]> post(@PathVariable String url,
                            @RequestHeader Map<String, String> headers,
                            @RequestBody byte[] body);
// PUT / GET / DELETE 三个同构签名（GET/DELETE 无 body）
```

- `url` 为绝对地址（`app.base_url + interface.upstream_path`），由 `OutboundRequestBuilder` 组装。
- Content-Type / Accept 由 `headers` 参数传入（JSON：`application/json`；XML：`application/xml`），覆盖注解静态值。
- **验证点（M2 实现首日验证）**：`@RequestHeader Map` 覆盖 Content-Type 在 Spring 7 声明式客户端是否生效；若不生效，退化方案 = 按协议定义 `JsonExchangeClient` / `XmlExchangeClient` 两个接口（固定 contentType），URI/Header 组装仍集中在 OutboundRequestBuilder，不影响其余契约。
- 构建方式沿用既有经验：`RestClient` + `HttpServiceProxyFactory`（Boot 4 不自动装配 `RestClient.Builder`，需手动构建）。

### 1.2 OutboundRequestSpec 与 OutboundRequestBuilder

```java
public record OutboundRequestSpec(
    String url,                          // base_url + upstream_path / callback_url_snapshot
    String method,                       // 接口声明的 HTTP 方法
    MultiValueMap<String, String> headers, // 公共头（traceId 透传）+ 出站鉴权凭证
    byte[] body,                         // 协议编码结果
    int readTimeoutMs                    // = interface.timeout_ms
)
```

- `OutboundRequestBuilder` 为**独立可测组件**（可行性风险应对）：输入 = 链上下文 + 接口配置，输出 = OutboundRequestSpec。单测覆盖四种场景（json-json / json-xml / xml-xml / xml-json）的 URI / 凭证组装。
- 凭证附加：出站鉴权适配器（链 OUTBOUND_AUTH 阶段）调用 `applyCredential(outbound)` 向 headers 写入签名 / token；Builder 只负责公共部分（traceId 头、Content-Type/Accept）。
- 入站送达复用同一 Builder：url = `inbound_delivery.callback_url_snapshot`（重送按快照地址，不随接口改址漂移）。

### 1.3 连接池与超时

- 全局单一连接池（RestClient 默认工厂）；不按渠道建池（渠道是运行时配置）。
- 每请求读超时 = `interface.timeout_ms`（默认 3000ms），通过 per-request 超时配置生效；实现点 M2 验证（requestFactory 每请求 options 或 per-request 属性）。
- 请求体大小限制：入站/出站报文上限（默认 1MB），超限拒绝（错误码 40002）——防止大报文拖垮链（呼应 M0-01 §1「深度防护交给报文大小限制」）。

### 1.4 短重试（沿用既有验证模式）

- `@Retryable` 置于**独立 Invoker 类**（Spring AOP 自调用不触发代理，旧版 PartnerInvoker 已验证）。
- 参数：`maxAttempts = interface.max_retries + 1`（默认 5 次含首送）、指数退避 200ms×2 上限 2s（沿用旧版经验值，后续压测调整）。
- 重试条件：HTTP 5xx、HTTP 429、连接类 IOException。
- **熔断闸门（M4）置于 Invoker 调用之前**：OPEN 时短路，不触发 @Retryable（技术架构 §4.5 已定）。

## 2. 结果判定与异常 → 状态机映射表

| 结果 | 判定 | 状态机流转 |
|---|---|---|
| HTTP 2xx + 信封适配判定业务成功 | codeField == successValue（或未配置信封适配） | SUCCESS |
| HTTP 2xx + 信封适配判定业务失败 | codeField != successValue | **SUCCESS（定稿 C2）**：传输层已获明确结果；业务失败经 codeMappings 映射平台错误码、msg 透传 messageField，随统一信封回调用方；不落死信 |
| HTTP 4xx（非 429） | — | 写 `dead_letter`（payload 快照 + reason）→ DEAD_LETTER |
| HTTP 429 | — | RETRYING（短重试）→ 耗尽 COMPENSATING |
| HTTP 5xx | — | RETRYING → 耗尽 COMPENSATING |
| 读超时 / 连接异常（ResourceAccessException） | 请求可能已达上游，结果不确定 | UNKNOWN → 对账（§3） |

- **定稿 C2（业务失败 ≠ 死信）**：状态机语义为「传输可靠性」视角——2xx 即送达且拿到明确业务结果，属 SUCCESS；死信只承接传输层失败（4xx / 重试耗尽 / 补偿耗尽）。黄金用例 G2（上游 401）为传输层失败 → 死信，与本定稿一致。
- COMPENSATING 由补偿 worker 按 `(status, next_retry_at)` 扫描重试，超 `max_attempts` → 死信 + 告警；重放安全依赖上游对 biz_id 幂等（既定 ADR 5）。
- 以上流转均写 `outbound_request`，`attempt_count` 累计（首送 + 短重试 + 补偿重试）。

## 3. UNKNOWN 对账协议

### 3.1 触发与收敛三分支（对应开发计划 M4 测试点）

| 分支 | 触发 | 收敛 |
|---|---|---|
| 人工对账 | 管理员在监控页 UNKNOWN 列表操作 | 「已到达」→ SUCCESS；「未到达」→ COMPENSATING（补偿重放） |
| 超时自动降级 | UNKNOWN 持续超过 `unknown_ttl`（默认 10 分钟，可配） | 自动转 COMPENSATING（前提：上游对 biz_id 幂等兜底） |
| 自动查询（v1.1） | 接口配置了对账查询 | 查上游真实状态：已成功 → SUCCESS；明确未到达 → COMPENSATING |

- **定稿 C3（分阶段范围）**：
  - **M2**：UNKNOWN 落状态 + 人工对账入口（查询 / 置位），黄金用例 G4 断言到此为止；
  - **M4**：超时自动降级（unknown_ttl）+ 对账操作审计留痕；
  - **自动查询协议 = v1.1 扩展，不在 M2/M4 范围**（可行性风险应对「缺查询能力时人工对账兜底」）。
- **自动查询 v1.1 扩展点**：`interface` 表新增 `reconcile_path`（查询路径，复用出站鉴权凭证），按 biz_id 查上游状态；届时再定查询响应解析协议（复用信封适配配置）。当前表结构不加列。
- 对账结果变化均写 `outbound_request`（status + error_code + updated_at），并记调用日志。

### 3.2 对账安全

- 人工置位为管理面操作，需权限校验 + 操作留痕（谁、何时、UNKNOWN→SUCCESS/COMPENSATING）。
- 自动降级为「补偿重放」，重放请求携带同一 `biz_id`，去重依赖上游幂等（既定设计 §6.3，无平台侧幂等开关）。

## 4. 入站送达复用约定（Flow B，简要）

- 送达调用同一 `ExchangeClient` + `OutboundRequestBuilder`；url = `callback_url_snapshot`；向回调地址签名默认无（设计 §5.3「可选，默认无」）。
- 送达读超时 / 重试复用接口级 `timeout_ms / max_retries` 语义（技术架构 §4.6 已定）。
- 回调地址安全：URL 校验 + 内网地址限制（防 SSRF，可行性风险表已列）——M3 实现时纳入。

## 5. 定稿决策记录（ADR）

| # | 决策 | 备选 | 理由 |
|---|---|---|---|
| C1 | 单一通用 ExchangeClient + header 动态传 Content-Type | 按协议两个接口 | 与「按协议维度、不按渠道写死」一致；退化方案已留 |
| C2 | 2xx + 业务失败 = SUCCESS（透传业务码），不落死信 | 业务失败落死信 | 状态机是传输可靠性语义；明确结果非不确定，不应死信 |
| C3 | 对账分阶段：M2 人工、M4 自动降级、v1.1 自动查询 | M4 即做自动查询 | 表结构无 reconcile 列；可行性报告已定「缺查询能力人工兜底」 |

# M0-04 · 凭证轮换存储方案

> 状态：**草稿 v0.1（待评审）**
> 依据：《API中心设计方案.md》§1.2（两类凭证、轮换 / 重置 / 即时失效）、§5.3（密钥管理）、《表结构设计.html》表 01 app
> 背景：设计 §1.2 要求「两类凭证均支持轮换（新旧短暂并存，平滑切换）、重置与即时失效」，但 `app` 表凭证仅单列（`outbound_secret` / `callback_secret` VARCHAR(255)），单列无法承载「新旧短暂并存」。本方案为该缺口的定稿，是 M1 凭证管理任务的前置。

## 1. 缺口与场景分析

两类凭证各自存在「并存窗口」需求：

| 场景 | 方向 | 并存诉求 |
|---|---|---|
| 平台发起轮换出站凭证 | 平台签名 → 供应商验签 | 供应商侧需先配置新凭证才能验新签名，切换有窗口期，期间平台需按约定时间启用新凭证 |
| 供应商轮换回调密钥 | 供应商签名 → 平台验签 | 供应商已用新密钥签名、平台尚未更新的窗口期内，平台需**同时接受新旧两个密钥**验签 |

结论：**验签方向必须「新旧并存」**（多凭证逐个试）；**签名方向由管理员控制激活时机**（激活即切新，并存主要服务验签）。单列存储（直接替换）无法满足验签并存，需引入多凭证存储。

## 2. 方案对比

| 方案 | 形态 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A：app 表双列 | `outbound_secret` + `outbound_secret_prev`（回调同理） | 改动小 | 轮换语义硬编码进列；无历史留痕；未来三窗口 / 复合凭证无法扩展；「哪一列是当前」易错 | ❌ |
| B：独立凭证表 | 新表 `app_credential`（app_id + kind + 密文 + 状态机） | 并存 / 即时失效 / 审计留痕天然支持；凭证与 app 解耦 | 表数量 15 → 16；运行时多一次查询（可缓存） | ✅ **推荐** |
| C：凭证列存 JSON 数组 | 单列 TEXT 存 `[{ver,value,active}]` | 不加表 | 列内结构化数据无法 SQL 约束 / 索引；更新并发易坏；加解密需整列重写 | ❌ |
| D：单列直接替换 | 轮换 = 替换密文，无并存 | 零改动 | 与设计 §1.2 冲突；回调验签窗口期必然验签失败 | ❌ |

## 3. 表设计（新增第 16 张表 app_credential）

```sql
-- 16 应用凭证：出站签名 / 回调验签两类，支持轮换并存（ACTIVE + ROTATING 双窗口）
CREATE TABLE app_credential (
    id             BIGINT       AUTO_INCREMENT PRIMARY KEY,
    app_id         VARCHAR(32)  NOT NULL COMMENT '所属应用',
    kind           VARCHAR(16)  NOT NULL COMMENT 'OUTBOUND 出站签名凭证 / CALLBACK 回调验签凭证',
    credential     TEXT         NOT NULL COMMENT '凭证内容（可逆加密存储；复合凭证 JSON 化，如 {"secretId":..,"secretKey":..}）',
    status         VARCHAR(16)  NOT NULL DEFAULT 'ACTIVE' COMMENT 'ACTIVE 当前使用 / ROTATING 轮换并存 / RETIRED 已失效',
    activated_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '生效时间',
    retired_at     DATETIME     COMMENT '失效时间（即时失效或窗口结束）',
    rotating_until DATETIME     COMMENT 'ROTATING 并存窗口截止（过期后任何读取路径惰性视为 RETIRED）',
    created_at     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    KEY idx_credential_app (app_id, kind, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='应用凭证（出站签名 / 回调验签，支持轮换并存）';
```

配套变更（`app` 表）：

- **删除** `outbound_secret`、`callback_secret` 两列（凭证统一迁移至 `app_credential`）；
- `app` 表注释更新：「出站 / 回调凭证见 app_credential 表（kind=OUTBOUND / CALLBACK）」；
- 删除策略约定追加：删应用 → 级联删 `app_credential`。

### 3.1 凭证状态机

```
[签发] --> ACTIVE --轮换激活--> ROTATING --窗口结束/手动完成--> RETIRED
              ^                          |
              |-- 重置（旧全部 RETIRED）--|
```

- **ACTIVE**：当前生效凭证，每 (app_id, kind) 至多 1 条；出站签名用它、回调验签首选它。
- **ROTATING**：轮换并存窗口，每 (app_id, kind) 至多 1 条；仅参与回调验签（签名不用它）；`rotating_until` 过期后惰性视为 RETIRED（读取路径判断，物理置位可后置）。
- **RETIRED**：已失效，任何读取路径不可见；`retired_at` 记录失效时间。

### 3.2 使用规则（运行时）

| 读取路径 | 取用规则 |
|---|---|
| 出站签名（链 OUTBOUND_AUTH 阶段） | 仅取 `status=ACTIVE` 的凭证解密后交给鉴权适配器 |
| 回调验签（链 INBOUND_AUTH 阶段） | 取 `status IN (ACTIVE, ROTATING)` 且未过 `rotating_until` 的**全部**凭证，逐个验签，任一命中即通过；全不中 → 40100 验签失败 |
| 管理面展示 | 一律遮显（只展示尾 4 位指纹 + 状态 + 生效时间），不回显明文 |

- 缓存：凭证随链缓存（M0-01 §7），**凭证变更（轮换 / 重置 / 失效）须触发链缓存失效事件**。
- 校验约束（应用层，M1 单测）：ACTIVE 缺失时阻止「删除最后凭证」；轮换激活时旧 ACTIVE 必须先转 ROTATING 再激活新凭证（事务内完成）。

### 3.3 管理面操作流程

**① 轮换出站凭证（平台主动）**
1. 点「轮换」→ 生成新凭证行 `status=ROTATING`（此阶段不影响运行，仍在用旧 ACTIVE）；
2. 界面提示：先到供应商侧配置新凭证；
3. 管理员确认供应商已配置 → 点「激活」→ 事务内：旧 ACTIVE → ROTATING（`rotating_until = now + 24h`）、新 ROTATING → ACTIVE；
4. 旧凭证到期自动失效（惰性），或点「完成轮换」提前置 RETIRED。

**② 更新回调验签凭证（供应商主动轮换，平台被动）**
1. 供应商告知新回调密钥 → 管理面「更新回调凭证」填写新值；
2. 保存即激活：新凭证入 ACTIVE，旧 ACTIVE → ROTATING（并存 24h，覆盖供应商侧切换窗口）；
3. 过期自动失效或手动「完成轮换」。

**③ 重置（无并存诉求，如怀疑泄漏后换新）**
新凭证直接入 ACTIVE，旧全部 → RETIRED（立即失效）。

**④ 即时失效（泄漏应急）**
目标凭证行 → RETIRED + `retired_at=now`；若 ACTIVE 被置 RETIRED 且无替代，则该方向鉴权降级为「无可用凭证」（出站签名失败 / 回调验签全拒 + 告警），管理面强制引导补发。

### 3.4 凭证格式与加密

- `credential` 列存储密文：**AES-256-GCM** 可逆加密（设计 §1.2「不得单向哈希——签名 / 验签需明文重算」），格式 `base64(iv ‖ ciphertext ‖ tag)`。
- 复合凭证（云厂商 secretId+secretKey、OAuth2 clientId+clientSecret 等）明文侧 JSON 化后整体加密。
- 主密钥来源：生产 = KMS / 环境变量注入；开发 = 本地配置（application.yaml 不提交真实密钥，使用环境变量占位）。密钥丢失 = 凭证不可恢复，须重新签发。
- 遮显 / 脱敏：管理面指纹回显（尾 4 位）；日志一律不落明文（M4 AOP 脱敏覆盖 `credential` 字段）。

## 一、缺陷（3 条，**均已修复**）

| # | 位置 | 问题 | 为什么是真问题 | 修复 |
|---|---|---|---|---|
| **1** | `controller/admin/InboundCredentialController#retire` | 返回 `ApiResult.error(0, warning)` —— 而既有凭证端点的口径是 **`ApiResult.ok(warning)`**；前端 `api/http.js` 在 `code===0` 时**只取 `data`**，放进 `msg` 的内容**被静默吞掉** | 「该类型已无 ACTIVE 凭证，请立即补发」这条**唯一的安全提示**永远不会显示 ⇒ 运维在把某池最后一枚凭证吊销后**没有任何提示**，等到调用方报 40108 才发现；同仓 `/apps/{id}/credentials/{id}/retire` 与 `/clients/{id}/credentials/{id}/retire` 都是 `ok(...)` ⇒ 属于**新代码没对齐既有契约** | 改 `ApiResult.ok(warning)` + 注释写明原因（回归：`InboundAuthSettingIntegrationTest`/手测可验；前端 `InboundAuth.vue` 原本就按字符串处理，无需改） |
| **2** | `service/ClientAuthVerifier`（v1.2 新增的审计归属） | ① 40107「调用方不存在」分支给 `Decision.principalType` 传 `null`，而 `settle` 的兜底是「`clientId` 非空 ⇒ **`CLIENT`**」；② 该兜底本身把「**自报**」当成了「**已验证身份**」 | 审计是「谁在调」的**唯一证据**：把一个伪造的 `X-Client-Id` 记成 `principal_type=CLIENT`（= 已登记、已验证）会让事后追责**指向错误对象**，且与设计方案 §6.2 主体语义表「自报但档案未知 ⇒ `UNVERIFIED`」**直接矛盾**（旧 v1.1 单测正好把这个错行为断言下来了） | ① 引入 `known`（**命中档案**，含停用）与 `client`（**启用**档案：参与方式回退/档案池取值）两个语义，审计归属一律以 `known` 为准；② 兜底改为**恒 `UNVERIFIED`**（不允许由 `clientId` 非空推断出已验证）；③ 旧断言改为 `UNVERIFIED`（`ClientAuthVerifierTest#审计上下文_拒绝也登记且字段齐全`）；④ 设计稿 §6.2 表「已停用」一行同步修正（命中档案即视为已验证身份，停用只影响其**档案池凭证**是否参与取值） |
| **3** | `ClientAuthGateIntegrationTest.tearDown` + `InboundCredentialPoolIntegrationTest.cleanup` | 收尾直接 `credentialRepository.deleteByOwner(CredentialOwner.PLATFORM, null)` ⇒ **清空整个平台共享池** | 平台池是**全局共享状态**：它会删掉①人工验收刚发放的凭证（下一步手测立刻 40108，且**查不出原因**）、②其他用例或历史遗留的凭证、③将来别人按 label 做的台账。测试只应回收**自己创建的行** | 两个测试类改为**登记自己创建的凭证 id**（`createdCredentialIds`），收尾按 id 精确删除（池用例加 `newPlatformCredential(...)` 辅助方法统一登记）；平台设置的复位保持（那是单行表语义，且已按"改回默认"处理） |

> 缺陷 1/2 属于「**新代码未对齐既有契约**」，正是评审最容易漏的一类：它们都不报错、不影响测试通过，只在**真实运维**时才暴露。

## 二、建议与遗漏（6 条，**已记录、未修**，含理由）

| # | 位置 | 问题 | 建议 | 优先级 |
|---|---|---|---|---|
| **S1** | `ClientAuthVerifier#resolveAdapter` | 方式**逐层回退无留痕**：接口绑定的适配器被停用/删除后，会**静默滑到平台默认**（可能是更宽松的方式，如 IP 名单）——设计与代码都把这当「预期回退」，但**运维不可见** | 回退发生时 `log.warn`（含接口 id、期望适配器、实际命中层）；审计 `reason` 或新增字段标注「方式来自哪一级」（第 1/2/3 级） | **P2**（安全可见性；改动小但需定审计列口径） |
| **S2** | `ClientAuthVerifier#firstPresent` | 「是否带了凭证头」只查**默认头名清单**（`X-Api-Key`/`X-Signature`/`Authorization`/…）⇒ 适配器把凭证头**改名**后，`OPTIONAL` 档下会把它当成「没带凭证」而**放行**（违反"带了就必须对"） | 方式解析后（适配器已知）用**适配器 params 的头名**（`credentialHeaderName`/`headerName`）重算「是否带了凭证」 | **P2**（档位语义缺口；兼容档下才有影响） |
| **S3** | `ClientAuthVerifier` 热路径 | **每请求**多一次 `interfaceRepository.findBindings(interfaceId)`（v1.1 无此查询）。这是「改绑定即时生效」的代价，但**未量化** | 在 M5 压测（吞吐/P99）里确认增量；若需要，按 M5.2 模式加「绑定解析缓存 + `ConfigChangedEvent` 失效 + TTL 兜底」（与链缓存同思路） | **P2**（性能待测） |
| **S4** | `AlertService` | 原计划的「**按凭证指纹分桶**告警」未做（仅对失败窗口做了 2000 键上限 + `overflow` 桶） | 需要时再按「指纹 Top N + 其余归 other」实现（**必须先做基数上限**） | **P2**（设计稿 §19.2 C4 已写明偏差与理由） |
| **S5** | `InboundAuthSettingService#save` | 变更事件在**事务内**发布（同事务监听 ⇒ 读到的是未提交值）；若事务回滚，缓存会短暂持有回滚值（60s TTL 自愈） | 与 `ChainEngine` 保持一致：`@TransactionalEventListener(AFTER_COMMIT, fallbackExecution=true)` | **P3** |
| **S6** | `schema.sql` vs 开发库 | `client_credential.client_id` 已放宽为 NULL 且代码不再读写，但**列尚未 drop**（刻意：删列必须与代码同批上线，且不能打断运行中的旧实例） | 待使用者用新代码重启实例后执行 `ALTER TABLE client_credential DROP COLUMN client_id;`（schema.sql 已注明） | **P3**（已知、有明确前置条件） |

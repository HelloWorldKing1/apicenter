## 3. 压测对象与放大点（瓶颈预期，报告的「原理」依据）

### 3.1 单次出站请求（Flow A，SUCCESS 路径）的固定开销

| 类别 | 明细 | 次数 | 备注 |
|---|---|---|---|
| **DB 读** | `interfaceRepository.findByPath`（路由）+ `findById`（链）+ `appRepository.findById`（链内） | 3 次/请求（实时，不可烘焙——状态 / baseUrl 需实时） | 另有 `GatewayGuard` 用 App 行（与上共享查询结果则不计） |
| **DB 读（已烘焙，M5.2）** | 绑定解析 / 字段映射 / 参数声明 / 适配器定义 | **0 次/请求**（仅链缓存未命中装配 1 次；凭证仍每请求实时读 `findActive`） | **对比 M4 基线：8~10 次/请求** → 读放大消除 |
| **DB 写** | `outbound_request` insert + `transition`（SENDING/终态）+ `incrementAttempt`/`updateState` | insert ×1 + update ×2~3 | 高频 update 合并是**预置调优候选**（§8-5） |
| **DB 写（状态链）** | `flushStateChain` 批量写 `outbound_request_state_log` | 1 批/请求（节点数 = 状态迁移数） | M5 后新增；压测需单独统计写入行数 |
| **DB 写（日志）** | `call_log` 异步批量（IN + OUT 各 1 条，攒 50 条 / 1s flush） | 2 条/请求入队 | 队列容量 1000，满则丢弃 + `apicenter.calllog.dropped` |
| **上游 HTTP** | WireMock 本机 | 1 次 | 毫秒级，非瓶颈 |
| **内存态** | 熔断计数 / QPS 窗口 / 日配额 | 常量 | 无锁竞争热点（ConcurrentHashMap） |

> **结论预期**：远程库下瓶颈 = **DB 往返次数 × RTT**（非 CPU）。因此场景 1 的核心不是「QPS 有多高」，而是**烘焙前后 P99 的相对变化**与**写路径占比**。

### 3.2 本轮不压 / 不覆盖（防误判为漏项）

| 项 | 原因 |
|---|---|
| 真实供应商 / 公网链路 | 会引入不可控变量（限流 / 抖动）；本地 WireMock 隔离 |
| 多实例横向扩展、分布式限流 | 当前为**单实例内存口径**（v1.1），无分布式语义可测 |
| TLS / 网关（Nginx）层 | 无部署形态，压测直连 :8080 |
| 长稳（7×24） | 可选，不进 M5 出口（《整体测试方案》§9 列为可选） |
| 熔断 / 告警 / 对账的**语义**正确性 | 已由 M4 自动化 + 手动分册覆盖；本压测只观察其**开销与稳定性**（如 OPEN 期间不应雪崩） |

## 4. 指标体系与采集口径

### 4.1 指标定义

| 维度 | 指标 | 采集方式 | 合格线 |
|---|---|---|---|
| 吞吐 | Req/Sec（wrk 汇总） | wrk 输出 | 场景相关，无绝对 KPI（见 §1 口径提醒） |
| 延迟 | Latency Avg / P50 / P95 / P99 | wrk 输出 + Prometheus `apicenter_gateway_latency_seconds{quantile="0.99"}` | 场景 1：烘焙后 P99 ≤ M4 基线（§6.1.3） |
| 错误率 | 非 2xx 占比 / wrk `Socket errors` | wrk 输出 | **< 0.5%，且无 5xx** |
| 限流 | 42901 通过/拒绝数 | `apicenter_gateway_requests_total{outcome="rejected"}` + 查库 | 通过量 ≈ limit（±10%） |
| 异步写 | 丢弃数 | `apicenter_calllog_dropped_total`（**恒 0**）+ 后端 `call_log 写入队列已满` 日志 | **0** |
| 补偿积压 | backlog | `apicenter_backlog{kind="compensating"}` + `SELECT COUNT(*)` | 单调下降至 0 |
| DB 写入量 | 行数 | `outbound_request` / `outbound_request_state_log` / `call_log` 压测前后 `COUNT(*)` 差 | 与请求数一致性核对（见 §6.1 断言） |
| 资源 | CPU / 内存 / GC / 连接池 | `jvm_memory_used_bytes`、`jvm_gc_*`、`hikaricp_connections_active` / `-pending`、`top -pid $(pgrep -f apicenter)` | 无 OOM、`pending` 不持续为正 |
| 熔断 | 状态 | `apicenter_circuit_state{interface}`（0/1/2） | 场景 1 应为 0（无失败注入） |

### 4.2 Prometheus 速查（meter 点分隔 → exposition 下划线）

```bash
curl -s http://localhost:8080/actuator/prometheus | grep -E \
 'apicenter_gateway_requests_total|apicenter_gateway_latency_seconds|apicenter_calllog_dropped_total|apicenter_backlog|apicenter_circuit_state|apicenter_chain'
# 关注：
#   apicenter_gateway_requests_total{direction="IN|OUT",outcome="success|rejected|...",interface=,app=}
#   apicenter_gateway_latency_seconds{quantile="0.99",direction=...}   ← publishPercentiles(0.5,0.95,0.99)
#   apicenter_calllog_dropped_total                                    ← 必须恒 0
#   apicenter_circuit_state{interface="..."}                           ← 0=CLOSED 1=OPEN 2=HALF_OPEN
#   apicenter_backlog{kind="compensating|pending|dead_letter|unknown"}
```

### 4.3 采样节奏（每次压测统一，保证可比）

`压测前 10s` 抓一次快照 → `压测中每 5s` 抓一次（或 curl 循环落文件）→ `压测后静置 10s（等队列 flush）` 再抓终值 → Monitor 页截图留档（统计卡 / 趋势 / TOP 接口）。

### 4.4 测量偏差控制（写结论必须声明）

1. **同机竞争**：wrk 与后端同机，100 并发时 wrk 自身吃 CPU → 记录 wrk 线程数与后端 CPU，必要时降 `-t`；结论标注「同机压测」。
2. **远程库 RTT**：绝对值不可外推；相对比较（烘焙前后 / 场景间 / 与 M4 基线）才有效。
3. **连接池**：HikariCP 默认 10 连接——100 并发下必然排队，**排队等待会混入 P99**（属预期「DB 往返 × 连接数」约束，报告需写明）。
4. **首次请求冷启动**：链缓存未命中（含装配）与 JIT 预热会让第 1 秒脏数据 → 每场景先跑 `10s 预热`，正式数据只取后 30s（或分段报告）。
5. **`-d` 时长固定 30s**（与规格一致）；时长变动必须重跑对照场景。

### 5.2 压测基线件（每次执行前重建，避免历史数据干扰）

```sql
-- 基线计数（压测前后各执行一次，差值即写入量）
SELECT
  (SELECT COUNT(*) FROM outbound_request)               AS outreq_total,
  (SELECT COUNT(*) FROM outbound_request_state_log)     AS state_log_total,
  (SELECT COUNT(*) FROM call_log)                       AS call_log_total,

### 6.5 场景 5（P5）：入站同步送达压测与异步化决策

| 项 | 内容 |
|---|---|
| **目的** | 量化「供应商视角 ack 延迟」中**送达耗时占比**，为「入站送达是否异步化」提供 v1.1 决策依据（M3 遗留） |
| **语义事实（结论的依据）** | 代码时序为 **验签 → 链 → 落 `inbound_delivery`(PENDING) → 同步送达回调地址 → 回 ack**（`InboundEngine.handle`）。「与送达解耦」指的是**送达成败都回 ack**（供应商不重发），**不是**「先回 ack 再异步送达」——故 ack P99 内含送达耗时，这正是本场景要测的量 |
| **前置** | 建 INBOUND 接口，回调地址 = 本地 WireMock stub；**回调验签适配器选 Noop**（否则 `wrk-callback.lua` 的 `bypass-demo` 头会被拒），并在报告中记录该简化 |
| **命令** | `wrk -t4 -c100 -d30s -s src/test/resources/m5-load/wrk-callback.lua http://localhost:8080/<入站回调平台路径>` |
| **观测** | ack P99（wrk）、`apicenter_gateway_latency_seconds{direction="IN"}`、`inbound_delivery` 行数 / `delivery_status` 分布、后端日志中 deliver 耗时 |

**数据表（回填）**

| 指标 | 实测 |
|---|---|
| ack Req/Sec / P50 / P99（回调地址 = 本机 stub，毫秒级） | 待填 |
| ack 延迟中送达占比（对照：回调地址恒「慢 stub」5s 延迟时 ack P99 是否被拖到 ~5s） | 待填（**对照实验是决策关键**：可注册 WireMock `fixedDelay` stub） |
| 回调地址超时 / 失败时的 ack 行为 | 待填（预期仍 200 ack + `inbound_delivery=PENDING` → 补偿重送） |
| `inbound_delivery` 落库条数 vs 请求数 | 待填 |
| `calllog.dropped` | 待填（应 0） |

**决策矩阵（§9 结论直接引用本表）**

| 观测结果 | 结论倾向 | 代价 |
|---|---|---|
| 慢回调（5s）会把 ack P99 拖到同量级，且真实供应商回调地址不可控 | **需要异步送达**（v1.1）：先回 ack，送达交 worker / 队列 | 需引入投递队列与「已 ack 未送达」状态语义；供应商侧幂等假设需重新表述 |
| 送达恒为毫秒级、且超时 / 失败已被 PENDING 重送兜住 | **维持同步送达**，仅把「送达超时」压到远小于供应商 ack 超时 | 供应商 ack 超时风险（超时后供应商重发 → 依赖业务幂等） |
| 介于两者之间 | 折中：**异步 + 送达超时上限**（如 2s 内尽力同步，超时转 worker） | 实现复杂度最高 |

7) 调优落地：<#n 已做>；未做项理由：<...>
```

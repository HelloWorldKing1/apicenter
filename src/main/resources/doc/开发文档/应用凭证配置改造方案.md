# 应用凭证配置改造设计方案（应用弹窗内联凭证）

> 版本：v0.1（2026-09-11 起草，**待评审**）｜范围：管理面「应用管理」新增 / 修改弹窗内联凭证录入（前端为主 + 后端两项小修）
> **拍板状态**：D1–D5 待评审（§7，每条给出推荐项）。评审通过后按 §8 实施。
> **目标读者**：评审选型后即编码。文中所有约束均对照现有代码（文件 + 行号）给出：凭证状态机与 M0-04 一致，**不新增旁路写入**，不改 `app_credential` 表结构（方案 A）。
> **一句话**：把凭证入口从「应用详情抽屉 + 手工选 kind」搬到「应用弹窗内、紧跟签名适配器、按适配器 impl 渲染该适配器需要的凭证字段」，落库仍走既有 `POST /apps/{appId}/credentials/update|reset`。

---

## 1. 背景与目标

### 1.1 现状（代码事实）

| # | 事实 | 位置 |
|---|---|---|
| 1 | 应用弹窗只有 3 个适配器下拉（供应商签名 / 回调验签 / 默认报文），**无凭证入口** | `frontend/src/views/Apps.vue` L62 / L70 / L78 |
| 2 | 凭证只能从「应用详情抽屉」维护，且必须**手工选凭证类型 kind**（OUTBOUND / CALLBACK），与当前选中的适配器无关 | `Apps.vue` L108–123（凭证弹窗）、L349–372（`openCredDialog/saveCred`） |
| 3 | 适配器 impl 元数据**已声明**凭证类字段：`ApiKeyAuthAdapter→apiKey`、`BearerTokenAuthAdapter→token`、`CloudSignatureAdapter→secretId+secretKey`、`CloudCallbackSignatureAdapter→token` | `service/AdapterImplCatalog.java` |
| 4 | 这些字段在适配器参数表单里被渲染成 **disabled 灰字**，提示「凭证值请到『应用管理 → 点击应用 → 凭证』中维护」 | `components/AdapterParamsEditor.vue` L36–37 |
| 5 | 后端**显式拦截** secret 落 `adapter.params`（400：「凭证类参数不落适配器配置」） | `service/AdapterService.java` L133 |
| 6 | `app_credential` 表注释已预留「复合凭证 JSON 化」`{"secretId":..,"secretKey":..}` | `doc/schema.sql` L261、`M0-04` §3.4 |
| 7 | 出站凭证注入 = 每请求实时读 `(app, OUTBOUND)` 的 ACTIVE，**不区分适配器**；凭证不进链缓存 | `engine/ChainEngine.java` L254 / L402–407、`config/ConfigChangedEvent.java` 注释 |
| 8 | 原型 `API中心原型.html` 本来就画的是「应用弹窗内 password 型 secret 字段」（单 secret / 应用） | `API中心原型.html` L818、L1141 |

### 1.2 痛点

- **认知断层**：选了「Bearer Token」适配器，界面不告诉你「它需要 Token」；用户按直觉找凭证，实际要「先保存应用 → 回列表点行 → 抽屉里选 kind → 填值」，跨 3 个界面。
- **错配风险**：kind 是手选的，回调验签密钥填到 OUTBOUND 不会报错，直到运行期验签失败（40100）才暴露。
- **静默降级**：未配置凭证时适配器只 `ctx.warn`，请求仍发出（缺签名头）→ 供应商 401，排查成本高（`ChainEngine` / `ApiKeyAuthAdapter`）。
- **新建应用首配缺失**：新建流程里完全没有凭证环节，必须二次进入。

### 1.3 目标与非目标

**目标**
1. 应用弹窗内，选择签名 / 回调验签适配器后，**就地出现**该适配器所需的凭证录入区；
2. 凭证录入区**跟随 impl 元数据**（0 字段不显示、1 字段单输入、≥2 字段多输入 → JSON 复合）；
3. 与 M0-04 状态机**完全兼容**：更新（旧值并存 24h）/ 重置（旧值立即失效）语义不变，指纹遮显、明文永不回显；
4. 新建应用可一次性配好凭证（保存应用 + 写凭证两步串行，失败可补救）。

**非目标（本期不做）**
- 不做「每个适配器实例一套独立凭证」（方案 B，见 §3/§7 D1）；
- 不做弹窗内的「平台生成随机值 → prepare → 激活」完整轮换流（保留在应用详情抽屉，弹窗内只给 update / reset + 状态提示）；
- 不改 `app_credential` 表结构、不改链引擎读取口径、不改 `AdapterService` 的 secret 拦截规则。

## 2. 关键约束（任何方案都必须满足）

| # | 约束 | 来源 / 事实 |
|---|---|---|
| C1 | 凭证按 `(app_id, kind)` 存储，kind ∈ {OUTBOUND, CALLBACK}，每 kind 至多一条 ACTIVE | `schema.sql` L257–268；`CredentialService.validateKind` |

| C9 | 接口级 AUTH 绑定可覆盖应用默认适配器，但**凭证仍按应用维度共享**（方案 A 下的已知语义） | `interface_adapter_binding.role=AUTH`；`ChainEngine.injectCredential` |

## 3. 候选方案

### 方案 A：UI 按 impl 渲染凭证字段，存储仍按 kind（**推荐**）

- **交互**：应用弹窗内，选中适配器 → 依据该 adapter 的 `impl` 从 `/adapters/impls` 取 `kind==='secret'` 的字段 → 渲染凭证卡片（label 用元数据 `label`，并展示现有 ACTIVE / ROTATING 状态与指纹）。
- **提交**：复用 `POST /apps/{appId}/credentials/update`（默认）或 `/reset`（用户显式切换）。多 secret 字段 → `JSON.stringify({...})` 作为 `credential` 值（与 `schema.sql` L261 注释、`M0-04` §3.4 一致）。
- **优点**：后端必要改动为 0；不动状态机 / 引擎 / 测试基线；用户心智与适配器一致；一次性解决 1.2 全部痛点。
- **缺点**：一个应用仍只有一条 OUTBOUND 凭证 —— 若同应用下不同接口绑定不同签名适配器且**各自密钥不同**，A 方案无法表达（→ 方案 B）。该限制需在界面与文档中明示（C9）。

### 方案 B：凭证按适配器实例归属 `(app_id, adapter_id, kind)`

- **语义**：`app_credential` 增 `adapter_id VARCHAR(16) NULL`（NULL = 应用级兜底）；键必须是 **(app_id, adapter_id)**，因为 `adapter` 是全局注册表（可被多个应用引用），只按 adapter_id 存会导致跨应用共用密钥。
- **引擎**：`injectCredential` 需拿到链上**实际生效的 auth 实例 id**（含接口级覆盖），回退序 = 接口覆盖实例凭证 → 应用默认实例凭证 → kind 兜底；每请求多一次索引查询。
- **优点**：同应用多签名体系（如 Bearer + HMAC 各一套密钥）语义正确；接口级覆盖不再有凭证歧义。
- **代价**：DDL（列 + 索引 + M5 生产加固的唯一约束需改成含 adapter_id）+ 全套凭证 API 加 scope 参数 + 前端凭证区从「跟 impl」变「跟实例（一个应用可能 N 个签名实例）」+ M1/M2/M3 集成测试与 seed / 演示脚本回归；≈ 3–5 人日。
- **建议**：本期不落地，作为 D1 的备选；触发条件 = 出现真实「同应用多签名密钥」需求。

### 方案 C：新建应用时后端原子端点（`POST /apps` 携带 credential 草稿）

- **语义**：`AppRequest` 增可选 `credentials[]`（kind + 明文），服务端在一个事务内「插 app → 写凭证」，避免前端串行两步的半成功状态。
- **优点**：原子、无「应用已建凭证失败」中间态；一次请求。
- **代价**：改 `AppDtos` / `AppService`（新增事务步骤与校验）、`AppRequest` 被凭证明文污染（版本快照 / 日志脱敏面扩大）、与「更新 / 重置」语义要在请求体里二选一表达；对「更新应用」路径语义含糊（是 update 还是 reset？）。
- **建议**：本期不做（D2 推荐前端串行 + 失败补救），若后续要求原子性再加。

### 方案对比

| 维度 | A（推荐） | B | C |
|---|---|---|---|
| 后端改动 | ≈0（+2 项建议小修） | 表 + API + 引擎 + 测试 | DTO + 事务 + 校验 |
| 语义正确性（多签名体系） | 部分（应用级共享） | ✅ 完整 | 同 A |
| 新建应用一步到位 | ✅（前端串行） | ✅ | ✅ 原子 |
| 回归面 | 前端 + 文档 | 全量（含 180 用例中的凭证相关） | 应用模块 + 脱敏 |
| 工作量 | ≈3 人日 | ≈3–5 人日（纯后端增量，不含前端返工） | ≈1.5 人日 |

## 4. 详细设计（方案 A）

### 4.1 组件结构与数据流

```
Apps.vue（新建 / 编辑弹窗）
 ├─ 供应商签名适配器  el-select ─┐ 选中 adapterId
 │                              └→ impl = adapters.find(id).impl
 ├─ <CredentialEntry kind="OUTBOUND"
 │      :app-id="dialog.isEdit ? form.appId : ''"
 │      :secret-fields="secretFieldsOf(impl)"
 │      :adapter-label="labelOf(impl)"
 │      :credential="credState.OUTBOUND"        ← 编辑态 GET /apps/{appId}.credentials
 │      :pending="!dialog.isEdit"
 │      v-model:value="credDraft.OUTBOUND"
 │      v-model:mode="credMode.OUTBOUND" />
 ├─ 回调验签适配器   el-select ─→ <CredentialEntry kind="CALLBACK" …>
 └─ 默认报文适配器（无凭证字段，不渲染）
```

**新增单文件组件** `frontend/src/components/CredentialEntry.vue`（**不改造** `AdapterParamsEditor`，避免污染「适配器管理」页的只读语义）：

```js
props: {
  appId: String,          // 编辑态有值；新建态为空字符串
  kind: String,           // 'OUTBOUND' | 'CALLBACK'
  secretFields: Array,    // ImplMeta.fields.filter(f => f.kind === 'secret')
  adapterLabel: String,   // 如 "Bearer Token·生产（BearerTokenAuthAdapter）"
  credential: Object,     // CredentialView | null（编辑态从详情取）
  pending: Boolean        // 新建态：应用尚未落库
}
emits: ['update:value', 'update:mode']   // value: { [key]: 明文 }，mode: 'update' | 'reset'
```

`impl` 解析优先级：`form.authAdapterId` → `adapters.find(a => a.id === …)?.impl`；若刚通过「＋ 自定义」内联创建，`load()` 后新实例已在下拉中，同样可解析（`saveInlineAdapter` 已回填 `form[targetField]`，`Apps.vue` L245–260）。

> 「显示哪张卡片」看角色（供应商签名 / 回调验签 下拉），「卡片里画几个输入框」看 impl 的 secret 字段 —— 两条规则分开，见 §4.4。

视觉规格：
- 凭证卡片**紧跟对应适配器**（不是页面底部），浅底（`#fafbfc`）+ 左侧 2px 主色条 + 8px 圆角，形成「适配器的从属块」语义；
- 状态行三态：`⚠ 未配置`（warning） / `● ACTIVE ****xxxx · 生效时间`（success） / `◐ 存在轮换中凭证（并存至 MM-DD HH:mm）`（warning）；
- 多 secret 字段（≥2）：字段纵向排列，全部同一张卡片；
- 高级轮换（`prepare` / 激活 / 完成轮换 / 吊销 / 历史）保留在详情抽屉，卡片底部给一行链接文案「高级轮换（生成 / 激活 / 收尾）在应用详情 → 凭证区」。

### 4.3 交互稿（新建态：草稿凭证 + 串行提交）

`CredentialService.requireApp()` 使「新建弹窗中 appId 未落库」时无法写凭证（约束 C7），故采用**草稿凭证 + 保存后串行提交**：

```
┌ 新建应用 ───────────────────────────────────────────┐
│ 应用标识 [QD1        ]   ← 未落库                    │
│ 供应商签名适配器 [ Bearer Token ▾ ][＋自定义]          │
│ ┏ 出站签名凭证（OUTBOUND）  〔待创建〕───────────────┐ │
│ ┃ Token *  [•••••••••••••••••••••••]               │ │
│ ┃ ⓘ 保存应用后自动写入（同一操作内串行两步）          │ │
│ ┗─────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

### 4.4 渲染规则（显示条件 + 字段来源，唯一需要写进规范的两条）

**规则 1：卡片是否显示 —— 由「角色 + impl」决定，不由 secret 字段决定。**

因为 impl 元数据的 secret 声明**不完整**：`HmacCallbackVerifyAdapter`（回调验签主力实现）的 schema 里**没有** secret 字段，但运行时必须读 `kind=CALLBACK` 凭证（`HmacCallbackVerifyAdapter.verify()` L70 起，L108 `findVerifiable(appId, "CALLBACK")`）；`HmacAuthAdapter` 同样无 secret 字段且**无 Bean 实现**（`adapter/auth/` 仅有 `ApiKeyAuthAdapter` / `BearerTokenAuthAdapter` / `NoopAuthAdapter` / `HmacCallbackVerifyAdapter`）。

| 凭证卡片 | 显示条件 |
|---|---|
| 出站签名凭证（OUTBOUND） | 供应商签名适配器下拉已选中，且 impl ≠ `NoopAuthAdapter`；**或**该应用已有 OUTBOUND 凭证（编辑态，显示只读状态行） |
| 回调验签凭证（CALLBACK） | 回调验签适配器下拉已选中，且 impl ≠ 无鉴权；**或**该应用已有 CALLBACK 凭证 |

**规则 2：卡片内字段 —— 由 impl 的 secret 字段决定，缺失时退化为单通用输入。**

| secret 字段数 | 渲染 | 提交载荷 | 示例 impl |
|---|---|---|---|
| 1 | 单输入框（`type=password` + 眼睛开关），label 取元数据 `label` | 原样字符串 | `ApiKeyAuthAdapter.apiKey`、`BearerTokenAuthAdapter.token`、`CloudCallbackSignatureAdapter.token` |
| ≥2 | 同源多输入框 | `JSON.stringify({ [key]: value, … })`，**键名取元数据 key** | `CloudSignatureAdapter.secretId + secretKey` |
| 0（但规则 1 判定需显示） | 单通用输入框，label =「密钥 / Token」，附注「该适配器未声明凭证字段名，按单值密钥处理」 | 原样字符串 | `HmacCallbackVerifyAdapter`、`HmacAuthAdapter` |

补充规则：
- **留空 = 不改动**（凭证不可回显，空值不能解释为「清空」）；
- **部分填写 = 前端拦截**并列出缺失字段 label（避免写入半截复合凭证）；
- 复合凭证（≥2 字段）的**运行时消费方尚未交付**（`CloudSignatureAdapter` / `CloudCallbackSignatureAdapter` 无 Bean），凭证区对无 Bean 的 impl 显示 `〔实现未交付，凭证按 JSON 预留〕` 灰字提示，不阻断保存（D4）；
- 可选精化 E4（§5）：`ImplMeta` 增 `credentialKind`（`OUTBOUND` / `CALLBACK` / `null`），由后端元数据显式声明，替代规则 1 的角色推断——本期不做也能工作。

### 4.5 状态矩阵（评审逐行确认）

| 场景 | 凭证区表现 | 保存行为 |
|---|---|---|
| 未选签名适配器 / 该角色选了 Noop（无鉴权） | 不渲染 | 无 |
| 选中 impl 无 secret 字段（如 `HmacCallbackVerifyAdapter`） | 单通用输入框（§4.4 规则 2） | 同 ACTIVE 路径（原样字符串） |
| 新建 + 已填凭证 | `〔待创建〕` tag + 输入框 | 串行 `POST /credentials/update` |
| 编辑 + 未配置 | `⚠ 未配置` + 输入框（+ 若为 CALLBACK 且应用下有已发布入站接口 → 黄色硬警告） | 有输入才提交 |
| 编辑 + ACTIVE | 指纹 / 生效时间 + 输入框 | 默认 `update`（旧值 ROTATING 24h） |
| 编辑 + 用户切「重置」 | 红字风险说明 + `ElMessageBox.confirm` | `POST /credentials/reset` |
| 编辑 + 存在未过期 ROTATING | 黄条「存在轮换中凭证（并存至 …），建议先激活或收尾」 | 仍可 update；提示 `prepare` 会被 400（缺陷 D-1） |
| 编辑 + ROTATING 已过期 | 灰条「已过期（惰性视为失效）」 | 同 ACTIVE 路径 |
| impl 无 secret 字段但存在历史凭证 | 一行只读状态 + 「去详情管理」 | 不动凭证 |

### 4.6 提交时序（`Apps.vue save()` 改造）

```js
async function save() {
  const payload = appPayload()              // 显式构造：只含 AppRequest 字段，剔除凭证草稿
  const drafts = collectCredentialDrafts()  // [{ kind, value }]，value 已按 §4.4 组装
  if (dialog.isEdit) {
    await http.put(`/apps/${form.appId}`, payload)
    await submitCredentials(form.appId, drafts)   // 失败逐条 error 提示，不回滚应用
  } else {
    await http.post('/apps', payload)             // 1) 建应用（DRAFT，§C7）
    try {
      await submitCredentials(form.appId, drafts) // 2) 写凭证（update：无旧值 → 直接 ACTIVE）
      ElMessage.success('应用与凭证已保存')
    } catch (e) {
      ElMessage.warning('应用已创建，但凭证写入失败，请重新进入编辑补填')
      dialog.visible = false; await load(); openEdit(apps.value.find(a => a.appId === form.appId))
      return
    }
  }
  dialog.visible = false; load()
}

const submitCredentials = (appId, drafts) => Promise.all(drafts.map(d =>
  http.post(`/apps/${appId}/credentials/update`, { kind: d.kind, credential: d.value })))
```

要点：
- **必须显式构造 payload**（不依赖 Jackson 忽略未知字段），保证凭证明文不长在 `/apps` 请求体里；
- 编辑态打开弹窗时额外 `GET /apps/{appId}` 取 `credentials[]` 填充状态行（现 `openEdit` 只用列表行数据，`Apps.vue` L281–292）；列表接口的 `credentials` 恒为空（列表不带子表），**不要**指望列表行；
- 内联创建适配器（`＋ 自定义`）后 `load()` 刷新下拉 → impl 解析自动生效；`AdapterParamsEditor` 内的 secret 字段保持 disabled（它属于适配器管理语义），凭证输入只出现在应用弹窗的凭证卡片里。

### 4.7 文案与安全

- **明文永不回显**：输入框 `type=password`；眼睛开关仅本弹窗内有效，关闭弹窗即清空草稿；不写 `sessionStorage` / `localStorage`；
- 只做 `trim` + 非空校验，不限长度/字符集（供应商密钥形态各异，如 JWT 带点号）；
- 只有 `reset` 走二次确认（不可逆语义）；`update` 不弹窗；
- 卡片底部固定一行说明：`保存后仅显示尾 4 位指纹；接口版本回滚不会回滚凭证（凭证独立于接口快照）`（对应约束 C8）。

### 4.8 校验与提示（不阻断保存，D5 推荐）

| 情况 | 级别 | 文案 |
|---|---|---|
| 选中非 Noop 适配器但该 kind 无 ACTIVE 凭证 | 黄色 alert（可保存） | 「未配置出站签名凭证，运行期请求将不带签名头（供应商 401）」 |
| 应用下存在已发布 INBOUND 接口 + CALLBACK 无凭证 | 黄色 alert（可保存） | 「入站回调验签将直接 40100，请补充回调验签凭证」 |

| 复合凭证部分填写 | 阻断 + 字段级错误 | 「请填写完整的 <label1> / <label2>」 |

## 9. 验收要点（评审通过后即作为手动回归清单）

1. **新建带凭证**：新建应用 → 选 `BearerTokenAuthAdapter` 实例 → 填 Token → 保存 → 应用列表出现该行；`GET /apps/{appId}` 的 `credentials[]` 出现 `OUTBOUND / ACTIVE / ****尾4`；库里 `credential` 列为密文（`SELECT` 肉眼确认不可读）。
2. **编辑更新（并存）**：再进弹窗填新值 → 保存 → 旧值 `ROTATING`（`rotating_until ≈ now+24h`）、新值 `ACTIVE`；指纹随之变化。
3. **重置（不可逆）**：切「重置」→ 确认框 → 保存 → 旧行 `RETIRED`、`retired_at` 有值。
4. **回调验签错配防护**：`HmacCallbackVerifyAdapter` 场景，CALLBACK 凭证未配 → 弹窗黄色警告；配好后 `POST /interfaces/{id}/test-callback` 通过。
5. **impl 驱动渲染**：切换适配器（Noop ↔ Bearer ↔ 云厂商签名）→ 凭证卡片出现/消失/变多字段；复合凭证提交后 DB 中为 JSON 明文加密态。
6. **留空不改动**：编辑态不填任何凭证 → 保存后指纹与状态不变。
7. **边界**：接口级 AUTH 覆盖为另一 impl 时，出站请求仍使用应用级 OUTBOUND 凭证（C9 明示）；接口版本回滚后凭证不受影响（C8 明示）。

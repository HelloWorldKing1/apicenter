## 阶段二 · 出站报文取证（**本能力的主战场**，页面）—— 约 6 分钟

> **为什么测**：声明 / 根元素 / 命名空间只体现在**出站报文的字节**上。
> 页面上的"最权威取证点" = **接口管理 →「测试接口」触发一次真实出站** →
> **接口监控 →「调用日志」→ 该接口 OUT 行 →「明细」抽屉 → 请求体**。

> **这个上游到底是什么类型**（容易误解，先说清）：`…/2.5_day.atom` 是 **Atom 1.0 聚合 Feed**
> （`Content-Type: application/atom+xml`，带 **GeoRSS 扩展** `georss:point`/`georss:elev`）——
> 属「**XML 文档型只读 API**」，**不是 SOAP**（无 Envelope/Body）、**不是 WSDL 服务**、**不是 XML-RPC**；
> **只接受 GET**（POST → 403），内容**每 60 秒滚动更新**（`cache-control: max-age=60`）。
> ⇒ 所以它能验证「**XML 解码 + RESP 白名单**」与「**平台编出的 XML 长什么样**」，
> 但**不能验证上游是否真的消费了我们的 XML 请求体**（GET 不携带 body，见阶段三 §3.3）。
> 同一数据的其他序列化：`.geojson`（JSON）、`.csv`、`.quakeml`（**QuakeML 行业 XML 标准**）；`.kml` 不可用
> （注意它返回 **HTTP 200 但响应体是 `404 File Not Found`**——又一个"别用状态码判成功"的例子）。
>
> **离线/确定性备选**：用仓库内的真实响应快照（裁剪为 2 条 entry，2044 字节）做 WireMock 桩：
> `src/test/resources/b1-protocol-params/usgs-atom-2.5day-2entries.xml`
> （保留三个可测特征：**默认命名空间** Atom、**`georss:` 前缀扩展**、**纯属性元素** `<link rel=… href=…/>` 与 **CDATA**）。

### 2.1 先固化「默认」基线（最重要的一条）


1. 在「高级 → XML 协议参数」里，**version 保持 `1.0`、encoding 保持 `UTF-8`、根元素与命名空间都留空**（= 平台内置默认）→ **保存**；
2. **接口管理 → 详情 →「测试接口」**：请求体填

   ```xml
   <request><requestId>REQ-1</requestId></request>
   ```

   点执行 → **预期**：拿到供应商真实响应（USGS 的 feed，`data` 里含 `title`/`updated`）。

   > **为什么填 XML**：接口的**「入站协议」= XML**（§1.1-d 的终点），而「测试接口」的请求体就是**入站报文**
   > ⇒ 必须填 XML。平台收到 XML → 解码成模型 → 再按「XML 协议参数」**编码成 XML** 发给 USGS（第 3 步的 OUT 请求体）。
   >
   > ⚠️ **若你的接口是「入站 JSON」**（例如没关「同入站」而只改了出站，或手工另配），这里就要填 JSON
   > `{"requestId":"REQ-1"}` —— **填错格式的报错是明确的**：
   > · 入站 XML 却填 JSON → `40002 报文格式非法：Unexpected character '{' … expected '<'`
   > · 入站 JSON 却填 XML → 前端直接提示"请求体不是合法 JSON（该接口「入站协议」是 JSON）"
   > （后者在 2026-09-22 前会抛 `Unexpected token '<'…` 原文而无从下手，已修复。）
   >
   > 📌 **两种入站格式得到的是同一个出站请求体**（报文格式只决定"怎么收"，不改变"怎么发"）—— 已实测 ✓
3. 打开 **接口监控 →「调用日志」**，用「接口」筛 `PM-B1-REAL`，找到 **方向 = OUT** 的那行 → 点「明细」→
   抽屉里看 **请求体**（右上可切「**原文**」视图，便于逐字节对比）：

- [x] 请求体 = `<?xml version='1.0' encoding='UTF-8'?><request><requestId>REQ-1</requestId></request>`
      —— **与改造前逐字节一致**（这是"本次改造没改变既有行为"的唯一直接证据）

> **本行已实测（2026-09-22，真实 USGS）**：调用后，调用日志 OUT 条的 `reqBody` 原文即是上面这一行
> （平台用**单引号**写声明、`version='1.0'` 与 `encoding` 之间**无空格** —— 这是 Woodstox 的输出格式，
> **逐字节比对时不要按自己的习惯改写**）。

> 说明：调试端点**有意不落 IN 条调用日志**（避免调试流量污染成功率），所以这里只会有 OUT 那一行，属正常。

## 阶段三 · 边界与解耦（页面，**别把设计边界当缺陷**）—— 约 4 分钟

### 3.1 ack 与出站「同源」，但根元素仍为约定值

1. **接口管理 → 「＋ 新建接口」**：类型 **入站回调**、方法 `POST`、平台侧路径 `/pm/b1-ack`、
   入站协议 **XML**、回调地址填本地可达地址（如 `http://localhost:18080/delivery-ok`）、
   在「响应字段」页签加 **ACK** 两条：`returnCode`(number)、`returnMsg`(string)；
2. 「高级 → XML 协议参数」：声明 **version = 1.1**、根元素填 `MyAck`（故意填一个非 `response` 的值）→ 保存 → **发布**；
3. **接口管理 → 详情 →「模拟回调」**：回调报文填

   ```xml
   <request><event_id>evt-1</event_id></request>
   ```

   点执行 → 看返回的 **ack 报文**（该接口入站协议 = XML，所以回调报文就该填 XML
   ——「模拟回调」同样按**入站协议**发送报文）。

- [ ] ack 报文声明是 **`1.1`**（跟着配置走 = 同源）
- [ ] ack 根元素**仍是 `response`**（**没有**被 `MyAck` 覆盖，D-XD-6）
- [ ] ack 里含 `returnCode`/`returnMsg`，且**不是 SOAP 包裹**（SOAP 属 B2，未实施）

### 3.2 入站解码与协议参数**解耦**

> ✅ **用「入站协议 = XML」的接口**：阶段二的 `PM-B1-REAL` 按 §1.1-d 就是 **XML 入站**，可以直接用；
> 用 3.1 建的 `PM-B1-ACK`（入站回调，同样是 XML 入站）也可以。
> ⚠️ 前提是**入站协议 = XML** —— 若接口是 JSON 入站，XML 报文是投不进去的（报文格式必须与入站协议一致）。

用 **3.1 的入站回调接口**（入站 XML），在「模拟回调」里把**入站报文换着声明**提交四轮：
① `<?xml version="1.0"?>` ② `<?xml version="1.1"?>` ③ **不写声明** ④ 声明为 `GBK` 但字节其实是 UTF-8。

- [ ] 四种都能正常解码、正常回 ack（说明**入站方向不读协议参数**：入站解码只看报文本身，Q17）
- [ ] 顺带确认：界面上「XML 协议参数」里的声明/根元素/命名空间**只影响出站**，对入站报文毫无作用

### 3.3 GET 接口的「请求体有值」≠「已发给上游」（**同一件事，两处口径不同**）

- [ ] **调用日志** 的 OUT 条**请求体有值**（= **编码产物**：平台确实编出了那段 XML），但上游（USGS）**仍返回 200**
      —— 因为 **GET/DELETE 不携带请求体**（既有行为，非缺陷）
- [ ] 打开 **接口监控 →「状态机与对账」→ 该条 → 明细**：**「出站报文 `out_payload`」是空的**（并显示一段说明）
      —— 同样是 GET 的既有行为：**`out_payload` 的口径是「实际发送的报文」**，GET 没发 body ⇒ 空

> 📌 **两处口径对照（这是最容易误判的一点）**：
>
> | 位置 | 字段 | 口径 | GET 接口的表现 |
> |---|---|---|---|
> | 接口监控 → 调用日志 → 明细 | **请求体** | **编码产物**（平台编出来的报文，无论是否真发送） | **有值** ✓ |
> | 接口监控 → 状态机 → 明细 | **出站报文 `out_payload`** | **实际发送的报文** | **空**（+ 界面说明） |
>
> 所以"状态机里出站报文为空、调用日志里请求体有值"**不是数据不一致**，是两个字段**语义不同**。
> 要看"平台编出来的 XML 长什么样"→ 去**调用日志**；要看"实际发出去了什么"→ 看**状态机**。

## 6. 常见误判（**先看这张表再报缺陷**）

| 页面上的现象 | 是不是缺陷 | 说明 |
|---|---|---|
| encoding 选 GBK 后，报文里中文显示成 `&#x4e2d;` 而不是 GBK 字节 | ❌ **不是** | 有意语义：`encoding` **只改声明**，非 ASCII 走字符引用、字节恒 ASCII 安全（Woodstox 实测产不出原生 GBK 字节，已记 backlog） |
| 下拉里**没有** UTF-16 / UTF-32 选项 | ❌ 不是 | 显式排除（会产原生非 ASCII 字节，破坏上述前提） |
| 「XML 协议参数」区在 JSON 协议时**不显示** | ❌ 不是 | 有意：JSON 接口配 xml 段会被后端拒（`40001`），界面直接不给入口 |
| 根元素填 `ns:QueryRequest` 被拒 | ❌ 不是 | 前缀要用「命名空间前缀」单独填 |
| 留空的项在回读时**没被写进配置** | ❌ 不是 | 前端**只下发非空键**（想过默认值就留空，而不是填空串） |
| GET 接口的 OUT 请求体有值，但上游说没收到 body | ❌ 不是 | GET/DELETE 不携带请求体（既有行为）；`请求体` 只代表"编码产物" |
| 「测试接口」执行后，调用日志里**只有 OUT 一行** | ❌ 不是 | 调试端点有意不落 IN 条（避免污染成功率口径） |
| 改了协议参数，**别的接口**也变了 | ✅ **是缺陷** | 协议参数是**接口级**（先确认是否误改到了同一接口 / 复制时选错行） |
| 状态机明细的「出站报文 `out_payload`」为空（GET 接口） | ❌ **不是缺陷** | `out_payload` 的口径是**实际发送**的报文；**GET/DELETE 不携带请求体** ⇒ 恒为空（后端有意不落）。要看**编码产物**请去「调用日志」该次 OUT 条的**请求体**（界面已给出这段说明） |
| 报 `40002 报文格式非法：Unexpected character '{' … expected '<'` | ❌ **不是缺陷** | 接口**入站协议 = XML**，却提交了 **JSON** 报文 —— 按「入站协议」把请求体改成 XML 即可。**请求体格式必须与「入站协议」一致**（本方案统一 XML） |
| 报 `Unexpected token '<', "<request><"... is not valid JSON` | ❌ **不是平台故障**（已修） | 反向情形：接口**入站协议 = JSON**，却提交了 **XML** 报文。2026-09-22 前工具**无条件 `JSON.parse`**，入站 XML 接口填 XML 必报此错；现已**按入站协议发送**并给可读提示 |
| 「命名空间前缀」填了、保存也成功，重新打开却像**没保存** | ❌ **不是缺陷**（旧版不友好，已改） | 前缀**从属于** URI：**URI 为空时前缀无意义、不落库**。现已改为**URI 为空则前缀输入框禁用 + 提示**、清空 URI 时**联动清空前缀**（旧版是静默丢弃，极易误判为缺陷） |
| 上游明明回的是"参数缺失"，平台却走**重试+补偿**而不是 `50203` | ❌ **不是** | 平台**只能按报文里的 `faultcode` 分类**（SOAP 规范给的唯一可靠信号）。实测该服务把请求侧错误报成了 **`soap:Server`** ⇒ 归服务端类（供应商瑕疵，已入回归样本） |
| `code=50203` 且**不重试**、**不计熔断** | ❌ **不是** | 客户端类 Fault（`Client`/`Sender`/`VersionMismatch`/`MustUnderstand`）属**我们的错**，重试无意义 ⇒ 有意直接死信（B2 核心价值） |
| 上游回 **HTTP 200**，但结果是错的（如数字字段传了 `abc`） | ❌ **不是** | 供应商**静默兜底**（实测该服务会把 `abc` 当数字算）。平台**无法检测**，属供应商行为 |
| 选了 SOAP 后，「根元素」标签变成「**Body 内业务元素**」 | ❌ 不是 | 有意：SOAP 下它填的就是 `<Body>` 内的业务元素（不是 `Envelope`/`Body`） |

# M3 手动验收测试方案

> 用途：M3 协议与入站的手动端到端验收（补充自动化测试 103/103 全绿的平台实操验证），全程约 30 分钟。
> 模拟供应商与回调地址用**本地 WireMock**（stub 随仓库 `src/test/resources/m3-manual-stubs/`，含 XML 供应商 / 送达成功 / 恒 500 / flaky scenario）。
> 本方案按实施后的实际行为校准（对应 `M3开发计划.md` §5，D-M3-1~4 语义）；已知偏差见文末「已知问题」。

## 前置：启动（三个终端）

```bash
# 终端 1：后端
mvn spring-boot:run                       # 8080，seed 幂等导入（含 fastmoss 入站回调用例 IF-FM-CB-001）

# 终端 2：前端
cd frontend && npm run dev                # http://localhost:5173

# 终端 3：本地 WireMock（在项目根目录执行；pom 已含 wiremock-standalone 3.9.1）
java -jar ~/.m2/repository/org/wiremock/wiremock-standalone/3.9.1/wiremock-standalone-3.9.1.jar \
  --port 18080 --root-dir src/test/resources/m3-manual-stubs
```

> 注意：WireMock 占 18080 与集成测试同端口——**手动验收期间勿同时跑 `mvn test`**（端口冲突），验收完毕再跑测试。

stub 约定（已随仓库）：

- `/xml-supplier` → 200 `application/xml`，返回 `<response><total>2</total><items><item>…</item>…</items><ts>1690000000</ts></response>`（`ts` 未声明，专用于演示过滤差异）；
- `/delivery-ok` → 200（送达成功目标）；`/delivery-fail` → 恒 500（耗尽 / 漂移演示）；
- `/delivery-flaky` → **scenario：前 8 次 500，之后 200**（前 5 次被首送 + 短重试消耗，PENDING 后 worker 重放 3 次失败、第 4 次放行）。

## 阶段一：管理面浏览（验收 M3 配置面与按钮门控，约 5 分钟）

1. 打开 http://localhost:5173：
   - **应用管理 → FastMoss 详情**：凭证区出现两个 kind——OUTBOUND（Bearer，M2 种子）+ **CALLBACK（回调验签，M3 种子新增）**，均遮显；
   - **接口管理**：新增的 `IF-FM-CB-001`（入站回调）已发布 → 详情查看：ACK 字段 returnCode(number)/returnMsg(string)、绑定 **CALLBACK_AUTH → ADP-301**、字段映射（event_id/order_id 保形 rename + state→order_state rename——非空白名单语义）；
   - **适配器 → 鉴权 tab**：出现「**HMAC 回调验签**」实例 ADP-301（M3 新增 impl）；
2. **按钮门控**（M3 前端改动）：出站接口详情显示「测试接口」，入站接口详情显示「**模拟回调**」（二者按 ifType 互斥，不再出现 INBOUND 误走出站链路）。

## 阶段二：XML 出站 + RESP 白名单（约 10 分钟）

1. 管理面建演示应用 `M3DEMO`（服务地址 `http://localhost:18080`，鉴权留空 = Noop；避免与 M2 手动方案的 HTTPBIN 应用撞名）+ 接口 `IF-XML-01`：OUTBOUND、POST、平台路径 `/demo/xml`、protocol_in=JSON、protocol_out=XML、上游路径 `/xml-supplier`、RESP 字段声明 `total`(number)/`items`(array)，**发布**；
2. curl：

```bash
curl -X POST http://localhost:8080/demo/xml -H "Content-Type: application/json" -d '{"hello":"world"}'
```

   预期：统一信封 `code=0`，`data` 只含 `total`/`items` 两字段、`ts` 被过滤（**XML 响应解码 + RESP 白名单过滤生效**）；`total=2`（XML 全文本按声明 number 解析为数字）；`items` 为对象、其内部同名 `item` 合并为数组（长度 2，D-M3-1 同名合并语义）；
3. 变体：编辑接口清空 RESP → 再调 → `data` 出现全部字段（含 `ts`，演示「空声明不过滤」）；点接口详情「测试接口」按钮走同一链路（XML 推导已生效）。

## 阶段三：入站回调全链路（约 15 分钟）

1. 配置（全走前端）：`M3DEMO` 应用补 **CALLBACK** 凭证（值 `demo-secret`）→ 适配器新建 HMAC 回调验签实例（impl=HMAC 回调验签，算法 HMAC-SHA256、签名头 X-Partner-Signature、容差 300）→ 应用「回调验签适配器」选中它（应用级默认）→ 新建接口 `IF-CB-01`：INBOUND、POST、平台路径 `/callback/demo/order`、回调地址 `http://localhost:18080/delivery-ok`、入站参数 event_id/order_id/state、出站参数 event_id/order_id/order_state、映射（state→order_state rename，event_id/order_id 保形 rename）、ACK 字段 returnCode(number)/returnMsg(string)，**发布**；
2. **① 正常闭环**：接口详情 → 「模拟回调」按钮 → 报文预填（可改）→ 发送 → 页面显示供应商视角 ack `{"returnCode":0,"returnMsg":"success"}` 与送达状态 ACKED → 查库：

```sql
SELECT id, delivery_status, attempt_count, max_attempts, callback_url_snapshot, ack_to_partner
FROM inbound_delivery ORDER BY id DESC LIMIT 3;   -- ACKED；payload 列为送达报文快照
```

3. **② 验签失败**：curl 手工发错签名 / 过期时间戳回调 → HTTP 401（40100/40101）→ 再查库**无新记录**（验签失败不落运行表）：

```bash
# 错签名（签名值乱填）：
curl -X POST http://localhost:8080/callback/demo/order -H "Content-Type: application/json" \
  -H "X-Timestamp: $(date +%s)" -H "X-Partner-Signature: deadbeef" \
  -d '{"event_id":"evt-001","order_id":"ORD-1","state":"PAID"}'
# 过期时间戳（超出容差 300s）：
curl -X POST http://localhost:8080/callback/demo/order -H "Content-Type: application/json" \
  -H "X-Timestamp: $(($(date +%s) - 600))" -H "X-Partner-Signature: deadbeef" \
  -d '{"event_id":"evt-001","order_id":"ORD-1","state":"PAID"}'
```

4. **③ 送达失败 → 补偿成功**：编辑接口回调地址改 `/delivery-flaky` → 模拟回调 → **ack 仍回**（供应商视角成功）→ 查库 PENDING（attempt=1）→ 每 3 秒 worker 重送，attempt_count 递增（后端日志可看）→ 第 4 次重放 scenario 放行 → **ACKED**（PENDING→ACKED 手动可见）；
5. **④ 耗尽 + 快照漂移**：回调地址改 `/delivery-fail` → 模拟回调 → PENDING → 等待 attempt 接近上限时把接口回调地址改成 `/delivery-ok` → 观察重送**仍按旧快照 `/delivery-fail`** 继续失败 → 耗尽 → DEAD_LETTER，查库：

```sql
SELECT id, delivery_status, attempt_count FROM inbound_delivery ORDER BY id DESC LIMIT 1;  -- DEAD_LETTER
SELECT * FROM dead_letter WHERE biz_type='INBOUND' ORDER BY id DESC LIMIT 2;               -- 死信落库
```

## 附：种子 fastmoss 入站用例直测（可选，2 分钟）

接口管理 → `IF-FM-CB-001` 详情 → 「模拟回调」（平台自动用 fastmoss 的 CALLBACK 凭证 `fastmoss-callback-demo-secret` 正确签名，无需手算 HMAC）→ 回调地址指向 `http://localhost:18080/delivery-ok`（种子配置，与 stub 一致）→ 页面显示 ack + 送达状态 ACKED，且 `callback_event_id` 从报文 event_id 提取。

## 验收对照

| 步骤 | 对应出口标准 / 设计定稿 |
|---|---|
| 阶段一 | M3 配置面（CALLBACK 凭证 / HMAC 回调验签实例 / 入站接口互斥校验）+ 前端按钮门控 |
| 阶段二 | json-xml 端到端 + RESP 白名单过滤与类型解析（D-M3-3）+ XML 同名合并（D-M3-1） |
| ③① | 入站闭环：验签（D-M3-2）→ 送达 → ACKED + ack 回执（ack 与送达解耦） |
| ③② | 验签失败 401 不落运行表（D7） |
| ③③ | PENDING → worker 重送 → ACKED |
| ③④ | 重送耗尽 → DEAD_LETTER + 死信落库；快照漂移防护 |
| 附 | 种子入站用例 + 模拟回调自签名闭环 |

> 查库可用 Navicat 连 PolarDB（开发实例 alicloud.mysql.polardb.rds.aliyuncs.com，白名单已通），库名 apicenter。

## 已知问题（评审记录待修复，验收时可见）

- **缺陷 1（INBOUND 送达误带应用默认出站签名头）**：当前版本入站送达请求会附带应用的出站签名头（如 fastmoss 用例送达时 WireMock 可看到 `Authorization: Bearer fastmoss-test-token`）——语义偏差 + 密钥外泄面，修复方案见 `M3代码评审记录.md` 缺陷 1；修复后送达请求应无该头（届时 ③① 可顺带验证 WireMock 收到的送达请求头）。

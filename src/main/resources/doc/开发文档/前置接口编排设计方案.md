# 前置接口编排（既有接口复用为前置）设计方案

> 版本：v0.1.1（2026-09-13 评审稿，**待拍板**；**前置条件 PS-0 已落地**）｜范围：出站接口（OUTBOUND）可挂「前置步骤」，按 `seq` 串行复用既有接口作为前置（`A → B → 第三方`）
> 一句话方案：**不改 `if_type`、不改 `ChainPhase` 六阶段枚举、不新增运行表**——新增 1 张配置子表 `interface_step` + 链内 3 处小改（DECODE 可跳过 / MAPPING 前插前置 / ENCODE 剥离保留键）+ 1 个新执行器 + 1 个新前端组件。
> **兼容承诺（影响小的硬指标）**：未配置前置的接口，行为与今日**逐字节一致**——透传语义、状态链节点数量、call_log 条数、错误码、重试预算全部不变。表为空即零影响。
> 目标读者：评审选型后即编码；本文所有约束均对照现有代码给出（`ChainEngine` / `OutboundEngine` / `MappingEngine` / `UpstreamInvoker` / `InterfaceService/Repository` / `SnapshotSerializer` / Monitor）。
>
> **事实基准（已核对的代码事实）**
> 1. 链为固定六阶段枚举，装配在 `ChainEngine.assemble`（:188）时烘焙进缓存链（M5 D-M5-2）：`DECODE`(:218) / `MAPPING`(:231) / `ENCODE`(:235) 均为 `steps.put` 的闭包，**加阶段外钩子无需改枚举**。
> 2. `ChainEngine.execute(interfaceId, inboundPayload, traceId, rawBody, initialAttrs)`（5 参重载，:101）已支持注入 `initialAttrs` 与外部 payload；但 DECODE 会**无条件覆盖** payload（JSON 空 raw → 空对象）。
> 3. `MappingEngine.apply` 空规则 = **整体透传**（M0-01 D3）；非空 = `target` 白名单（未声明的字段被丢弃）。
> 4. `OutboundEngine` 自带 `CHAIN_BUFFER`（ThreadLocal，:104）+ `beginChain/chainAppend/endChain`（:107-122），`flushStateChain` 按 `recordId` 一次批量落库；`OutboundRequestRepository.transition` 的「from==to 不记节点」只作用于 `transition()` 路径，**批量通道 `flushStateChain` 不校验 from==to**（步骤留痕可复用）。
> 5. `UpstreamInvoker` 的重试预算走 ThreadLocal（`MAX_RETRIES` / `RETRY_FAILURES` + `beginRetryBudget/endRetryBudget`），`endRetryBudget()` 是 `remove()` 语义——**嵌套调用会清掉外层预算**。
> 6. `OutboundEngine.execute` 内 `CallLogContext.set(...)`（:131）+ 网关切面 finally 清理；嵌套调用会覆盖外层上下文。
> 7. 配置子表共 6 张（snapshot / param / body / mapping / field_def / binding），全量更新走 `deleteChildren` + `insertXxx`（`InterfaceRepository:165-172`）；快照 `config_json` 由 `SnapshotSerializer` 完整可重建（`SnapshotSerializerTest` 为保护网）。
> 8. Monitor 状态链时间线对未知 `trigger` 有兜底渲染（`TRIGGER_LABEL[s.trigger] || s.trigger`，`Monitor.vue:405-409`），**新增 trigger 无需改渲染逻辑**（仅补 1 行标签）。
> 9. `M5IntegrationTest` 等 192 个 @Test 全量依赖开发库；本方案新增用例须入 M1-M5 同款集成测试体系。

## 1. 背景与目标

**场景**：新接口 A 需要「先拿一个已有的能力，再打自己的第三方」。典型前置：

| 前置类型 | B 的形态 | A 用途 |
|---|---|---|
| 公共鉴权 / 换 token | 打鉴权服务，返回 `token` | A 把 token 放进自己的出站报头/字段 |
| 主数据 / 字典查询 | 打内部主数据服务，返回 `merchant_id` / `region_code` | A 补齐第三方必填字段 |
| 额度 / 风控校验 | 打业务前置服务，返回 `quota` / `pass` | A 用 `condition` 决定是否继续 |
| 地址 / 路由解析 | 打配置中心，返回 `endpoint_key` | A 用返回值选目标 |

**目标**

1. **零重配复用**：B 已有的应用归属、供应商路径、出站凭证、协议、字段映射、报文适配器、短重试预算、熔断器、日志——全部按 B 现有配置生效，**不在 A 里重抄一遍**；
2. 前置结果以**稳定命名空间** `steps.<步骤名>.<字段>` 暴露给 A 的字段映射与 `condition`（M0-02 语法零新增）；
3. 失败语义明确且**不放大不确定结果**（超时/熔断必须按 A 的状态机正确传播，见 §6.4）；
4. 配置可**版本化 / 回滚 / 复制**（进快照），可**校验**（自环、间接环、深度、引用存在）；
5. 全链路可观测（traceId 贯穿 A / B / 第三方；Monitor 能看到「A 卡在哪一步」）。

**非目标（一期明确不做）**

- 不做**业务级补偿/回滚**（A 的前置成功而 A 的第三方失败时，不回滚 B）——超出「连接 + 适配 + 可靠传输」定位；
- 不做**异步/并行前置**（前置的意义是提供上下文，异步化等于拿不到结果）；
- 不做**跨接口字段映射 DSL**（一期靠「B 用自己的既有映射从共享模型取字段」解决，见 §6.2）；
- 不做**编排可视化画布**、不做**条件分支 DAG**（只做串行 + 可选单步条件）。

## 2. 现状约束（代码事实）

| # | 约束 | 事实 | 对本方案的含义 |
|---|---|---|---|
| C1 | 链阶段 | 六阶段枚举固定，装配期烘焙（M5） | 前置只能作为**阶段内的钩子**，不能新增阶段 |
| C2 | 缓存失效 | `ConfigChangedEvent`（INTERFACE / ADAPTER / APP）→ `@TransactionalEventListener` AFTER_COMMIT | steps 是 INTERFACE 子表，`update` 路径已发事件 → **即时生效无需新增发布点** |
| C3 | 协议差异 | A / B 可 JSON↔XML 不同 | 前置入参必须走**已解码模型**，不能把 rawBody 二次交给 B（§6.2 D-PS-2） |
| C4 | 透传语义 | 空映射规则 = 整体透传（含 payload 全部字段） | 合并进 payload 的 `steps` 子树会被原样发给第三方 → **必须剥离**（§6.3） |
| C5 | 运行表 | `outbound_request` 是状态机唯一载体；worker 按 `(status,next_retry_at)` 扫描 | 前置**不得**产生可被 worker 独立重扫的子记录（否则出现「A 已失败、B 仍在异步重放」的孤儿）→ 一期**不落子记录**（§6.2） |
| C6 | 引用完整性 | 无 DB 外键，应用层保证（schema.sql 约定）；`interface.code` 可被 update 修改 | 前置引用存**数字主键**；被引用接口删除要守卫（§10） |
| C7 | 状态链 | `state_log` append-only；(from,to,attempt,error_code,trigger_src,detail,trace_id) | 步骤留痕可用批量通道写「同态节点」，**运行期零 DDL**（§9） |
| C8 | ThreadLocal | 重试预算 / 状态链缓冲 / CallLogContext 均为 ThreadLocal 且非嵌套安全 | 前置执行器**绕开 `OutboundEngine`**，只复用 `ChainEngine` + `UpstreamInvoker`（§6.2） |

## 3. 候选方案与选型

### 方案 A：把前置做成第 7 个链阶段 / `InternalCallAdapter`

- 做法：新增 `ChainPhase.PRE_CALL`，配置落在 `adapter.params`。
- **否决**：① 违反 M0-01「固定六阶段」契约，动枚举会波及所有适配器与测试；② `Adapter` 契约明确定义为**无状态、配置驱动**，而前置调用带子请求/超时/失败传播语义，塞进去会污染契约；③ `interface_adapter_binding` 的 `uk_binding(interface_id, role)` 决定一个角色只能绑一个实例 → **一个接口只能有一个前置步骤**，表达力不足；④ 配置落在适配器上，无法随接口版本化/回滚。

### 方案 B：新增 `if_type = ORCHESTRATION` 编排接口类型

- 做法：编排接口 + 步骤子表，A 只做编排，自身出站作为最后一步。
- **否决（一期）**：改动面最大——类型互斥矩阵、网关路由、监控口径、快照、前端两大分支、192 个测试全受影响；而绝大多数需求是「A 本身就要调第三方，只是先补一个前置」，引入新类型属于过度设计。保留为 v2 演进方向。

### 方案 C（推荐）：保持两种 `if_type`，OUTBOUND 接口挂 `interface_step` 配置子表

- 做法：第 7 张配置子表 + 链内 3 处小改 + 1 个 `PreStepExecutor`。
- 优点：改动面可控（§7 逐项清单）；与 M5 缓存/事件/快照体系天然兼容；未配置即零影响；留了 B 方案（编排类型）与二期策略的演进位。
- 缺点：多前置步骤是**串行**语义（顺序敏感），并行/分支需二期。

**选型结论：方案 C。** 一期范围收敛为 **MODEL 入参 + ABORT 策略 + 串行**（D-PS-2/3），把 `CONTINUE/FALLBACK/overlay/条件`列入二期。

## 4. 目标架构与执行时序

```
调用方 ── POST /A/path ──▶ 网关（限流/配额/IP，按 A 的 app）
                              │
                              ▼
                     OutboundEngine.execute(A)
                       ├─ 落 outbound_request(A, INIT) + 状态链缓冲 begin
                       └─ ChainEngine.execute(A)
                            ├─ INBOUND_AUTH（Noop 占位）
                            ├─ DECODE    A 的 protocol_in → 模型 M
                            ├─ MESSAGE
                            ├─ MAPPING   ┌─────────────────────────────────────────┐
                            │            │ 【新增】PreStepExecutor：              │
                            │            │  for step in steps(seq):               │
                            │            │    B = interface(step.target)          │
                            │            │    M' = M 剥离保留键 steps + overlay    │
                            │            │    bCtx = ChainEngine.execute(B, M',…,  │
                            │            │              {preDecoded:true,…})      │
                            │            │    （B 的 DECODE 跳过，其余五阶段照跑） │
                            │            │    熔断 tryAcquire(B) → invoke(B)       │
                            │            │    分类 → 合入 M.steps.<stepCode>       │
                            │            │    → chainAppend(PRE_STEP 节点)         │
                            │            └─────────────────────────────────────────┘
                            │            → MappingEngine.apply(M, rules)（A 的规则可引用 steps.b.xxx）
                            ├─ ENCODE    【新增】剥离保留键 steps（透传防护）→ 出站报文
                            └─ OUTBOUND_AUTH  注入 A 的 app 出站凭证
                              │
                              ▼
                     UpstreamInvoker.invoke(A 的规格) ──▶ 第三方
                              │
                              ▼
                     结果分类（SUCCESS / DEAD_LETTER / COMPENSATING / UNKNOWN）
```

## 5. 数据模型

### 5.1 第 20 张表：`interface_step`（第 7 张配置子表）

```sql
-- 20 前置步骤（接口编排）：OUTBOUND 接口在自身链 MAPPING 前，按 seq 串行复用其他接口
CREATE TABLE interface_step (
    id                  BIGINT        AUTO_INCREMENT PRIMARY KEY,
    interface_id        BIGINT        NOT NULL COMMENT '宿主接口（仅 OUTBOUND）',
    seq                 INT           NOT NULL DEFAULT 0 COMMENT '执行顺序（升序；顺序敏感）',
    step_code           VARCHAR(32)   NOT NULL COMMENT '步骤名（同接口内唯一；= steps.<步骤名> 命名空间与日志标识）',
    target_interface_id BIGINT        NOT NULL COMMENT '前置接口（必须 OUTBOUND；存数字主键，防上游改 code 断链）',
    failure_policy      VARCHAR(16)   NOT NULL DEFAULT 'ABORT' COMMENT '一期仅 ABORT；CONTINUE/FALLBACK 二期',
    enabled             TINYINT(1)    NOT NULL DEFAULT 1 COMMENT '停用 = 保留配置不执行',
    created_at          DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at          DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_step (interface_id, step_code),
    KEY idx_step_target (target_interface_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='接口前置步骤（编排）';
```

**为什么引用存 `target_interface_id` 而不是 `target_code`**：`interface.code` 当前可被 `update` 修改（`uk_interface_code` 只保证唯一，不保证不变），存 code 会出现「改一次 code，全部引用静默断链」。展示层 join 出 `code / name / app_id` 即可（沿用 `app.id` 与 `app_id` 并存的口径：**对外契约用 code，内部引用用 id**）。

**为什么快照存 code**：`config_json` 需要跨环境/跨库可移植（开发库与生产库的自增 id 不同）。见 5.2。

### 5.2 快照扩展（`interface_snapshot.config_json`）

新增 `steps` 段（与 `params/bodies/mappings/fieldDefs/bindings` 平级）：

```jsonc
"steps": [
  { "seq": 0, "stepCode": "auth", "targetCode": "IF-AUTH-001", "failurePolicy": "ABORT", "enabled": true }
]
```

| 落点 | 改动 | 说明 |
|---|---|---|
| `SnapshotSerializer.toJson` | 追加 `steps` 数组（`targetCode` 由 id 反查 code，查不到写 null + warning） | 快照可重建 |
| `SnapshotSerializer.toRequest` | 读取 `steps`，`targetCode` → id 解析；解析失败 → `40001`「快照引用的前置接口不存在：{code}」 | 回滚不静默丢步骤 |
| `SnapshotChangeDiff` | 摘要：「前置步骤 1→2」「前置 auth：A→B」；旧快照无 `steps` 字段 → 视为空（**向前兼容**） | 版本历史可读 |
| `SnapshotSerializerTest` / `SnapshotChangeDiffTest` | 增补往返与 diff 用例（保护网要求：加子表必须同步） | — |
| `M5IntegrationTest` | 回滚断言补 steps | — |

### 5.3 被否的「零新表」尝试（记录，避免重复讨论）

| 尝试 | 否决理由 |
|---|---|
| 复用 `interface_adapter_binding`（新 role `PRE_STEP`） | `uk_binding(interface_id, role)` 限制**每接口仅 1 个前置**；`adapter_id VARCHAR(16)` 放不下接口 id；语义混淆 |
| 复用 `interface_param`（`side='PRE'`） | 承载不了 `target_interface_id / failure_policy / enabled`；且参数表会被前端参数编辑器误读 |
| 复用 `interface_field_mapping`（`op='preCall'`） | 映射是「字段→字段」的纯函数语义，前置是「调用+失败传播」；塞进去会破坏 M0-02 契约与 24 例预期矩阵 |

## 6. 运行时设计

### 6.1 插入点（对应 `ChainEngine.assemble`，3 处小改）

```java
// ① DECODE（:218）：允许「模型已就绪」的内部调用跳过解码（前置调用专用；网关路径永远不加此 attr）
steps.put(ChainPhase.DECODE, ctx -> {
    ctx.attrs().put("adapterParams", objectMapper.createObjectNode());
    ctx.attrs().put("paramTypes", inParamTypes);
    if (Boolean.TRUE.equals(ctx.attrs().get("preDecoded"))) {
        return ctx;                       // payload 已由调用方注入（前置链，见 §6.2）
    }
    return decodeIn.process(ctx);
});

// ② MAPPING（:231）：前置执行必须早于字段映射（A 的规则要引用 steps.*）
List<InterfaceStepRow> preSteps = "OUTBOUND".equals(ifType) && preStepEnabled
        ? interfaceRepository.findSteps(iface.id())   // 装配期一次读取，烘焙进缓存链（与 rules 同源）
        : List.of();
steps.put(ChainPhase.MAPPING, ctx -> {
    if (!preSteps.isEmpty()) {
        preStepExecutor.execute(ctx, preSteps);       // 合入 payload.steps.<code> + 追加状态链留痕
    }
    return mappingEngine.apply(ctx, rules);
});

// ③ ENCODE（:235）：剥离保留键（防「透传模式」把 steps 子树发给第三方）
steps.put(ChainPhase.ENCODE, ctx -> {
    if (!preSteps.isEmpty()) {
        ReservedKeys.stripSteps(ctx.payload());       // 仅当本接口配置了前置时才动，老接口零影响
    }
    ctx.attrs().put("adapterParams", objectMapper.createObjectNode());
    return encodeOut.process(ctx);
});
```

> **关键**：三处改动全部在 `assemble` 内、全部带前置存在性守卫——**未配置前置的接口走的还是原来的三个闭包**（这就是「零影响」的实现方式）。

### 6.2 `PreStepExecutor`（新类，`engine/PreStepExecutor`）

刻意做成 `OutboundEngine.doInvoke` 的「瘦身版」：**只复用链与传输，绝不进入状态机**（落 `outbound_request` 记录的是 A 自己；B 不落运行记录 → 不会产生被补偿 worker 独立重扫的孤儿，见 C5）。

```java
void execute(AdapterContext parent, List<InterfaceStepRow> steps) {
    ObjectNode stepsNode = (ObjectNode) parent.payload().root() ... // 建/取保留键 steps
    for (InterfaceStepRow step : steps) {                 // 已按 seq 升序
        if (!step.enabled()) continue;
        InterfaceRow b = interfaceRepository.findById(step.targetInterfaceId()).orElse(null);
        if (b == null || !"OUTBOUND".equals(b.ifType()) || !"PUBLISHED".equals(b.status())) {
            throw new BizException(40001, "前置步骤 " + step.stepCode() + " 不可用：目标接口缺失/未发布");
        }
        // 入参：A 的当前模型（剥离保留键）+ overlay（二期）→ 交 B 的链；B 的 DECODE 跳过
        UnifiedModel bIn = ReservedKeys.withoutSteps(parent.payload());   // 浅隔离：B 看不到 A 的步骤输出
        AdapterContext bCtx = chainEngine.execute(b.id(), bIn, parent.trace().traceId(), null,
                Map.of("preDecoded", true, "stepCode", step.stepCode(), "invocationRole", "PRE",
                       "parentInterfaceId", parent.iface().id()));
        // B 的出站规格：B 自己的 app.baseUrl + B 的 upstreamPath/method/超时（D-M5-2 烘焙链已解析绑定/映射）
        iface: bCtx.outbound().url(appOf(b).baseUrl() + b.upstreamPath());
               bCtx.outbound().method(b.method());
               bCtx.outbound().readTimeoutMs(b.timeoutMs());
               bCtx.outbound().interfaceId(b.id()); appId(b.appId()); traceId(trace);
               header("X-Trace-Id", trace);
        // 熔断（B 的粒度）+ 预算（save/restore，防污染 A）+ 调用
        if (!circuitBreakerRegistry.tryAcquire(b.id()))           → fail(step, PRE_CIRCUIT_OPEN)
        try (var budget = UpstreamInvoker.saveBudget()) {         // ← 新增 10 行：嵌套安全
            UpstreamInvoker.beginRetryBudget(b.maxRetries());
            resp = upstreamInvoker.invoke(bCtx.outbound());
        }
        // 分类：2xx → 复用 B 的信封适配 + B 的 RESP 白名单（同一判定路径，不另写一套成功率口径）
        UNode out = judgeByEnvelopeAndRespFilter(b, resp);        // 封装 OutboundEngine 现有 envelopeParamsOf/respDefs 逻辑
        stepsNode.fields().put(step.stepCode(), literal(out));    // ★ 字面量键，绝不做点路径解析
        chainAppend("MAPPING", "MAPPING", attempt, null, "PRE_STEP",
                step.stepCode() + " " + httpStatus + " " + elapsedMs + "ms code=" + bizCode);  // §9
    }
}
```

**为什么前置调用绕开 `OutboundEngine`**（这是「影响小」的核心决策，对应 C4/C5/C8）：

| 若复用 `OutboundEngine.execute(B)` | 后果 |
|---|---|
| `beginChain()` 重置 `CHAIN_BUFFER` | **A 已攒的状态链节点被 B 的 flush 写进 B 的 recordId**（数据串档） |
| `CallLogContext.set(B)` | A 的 IN call_log 被记成 B 的接口（归属错） |
| `endRetryBudget()`（ThreadLocal `remove`） | 清掉 A 的重试预算 → A 后续 invoke 退回默认 4 次 |
| 落 B 的 `outbound_request` | worker 会把 B 的 COMPENSATING 当独立消息重放 → 「A 已失败、B 仍在打第三方」（孤儿） |

四个问题在「绕开」方案下**全部不存在**，代价只是 B 的调用不在 `outbound_request` 留档（可观测性由 §9 补齐，足够）。

### 6.3 保留键 `steps` 与两道剥离

| 位置 | 动作 | 目的 |
|---|---|---|
| 前置入参构造（`PreStepExecutor`） | `ReservedKeys.withoutSteps(parent.payload())` | B 看不到 A 的步骤输出 → B 的透传也不会把 A 的 token 发给 B 的供应商 |
| 宿主 ENCODE 前（§6.1 ③） | `ReservedKeys.stripSteps(ctx.payload())` | A 的透传模式不会把 `steps` 子树发给第三方 |

配套约定（保存期强制，§10）：`steps` 为**保留字段名**——IN 侧参数名与映射 `target` 名都不得为 `steps`；运行时若宿主 IN 报文自带根字段 `steps`，**以步骤输出为准（覆盖）**，并在 `chainTrace` 中提示。

### 6.4 失败传播矩阵（最关键的语义）

**核心原则：结果不确定必须向上传播，绝不能被降级成「可安全重试」**——否则 A 重放 = 对第三方的双提交。

| 前置结果 | 一期（ABORT，默认且唯一） | 二期 CONTINUE | 二期 FALLBACK |
|---|---|---|---|
| 2xx + 信封判定成功 | 继续下一步 | 同 | 同 |
| 2xx + 信封业务失败 | A 链失败（`BizException`，**不落 A 运行表**，M0-01 D7） | 继续，缺失字段交 A 映射的 `null_strategy` | 写 `fallback_json` 后继续 |
| 4xx（非 429） | A 链失败 + 步骤留痕（`detail` 带 HTTP 码与响应片段） | 同 CONTINUE | 同 FALLBACK |
| 5xx / 429 短重试耗尽 | **A 转 COMPENSATING 顺延（不 `incrementAttempt`）** | 同 CONTINUE | 同 FALLBACK |
| 读超时 / 连接异常 | **A 必须转 UNKNOWN（50401）** | 同 CONTINUE（需业务显式接受不确定性） | 同 FALLBACK |
| B 熔断 OPEN | 同 5xx：A 转 COMPENSATING 顺延（与既有「短路即顺延、不杀消息」一致） | 同 | 同 |
| B 缺失 / 未发布 / 停用 | A 链失败（配置类错误，立即可见） | 同 | 同 |

实现：`PreStepExecutor` 抛结构化的 `PreStepFailure(kind, stepCode, detail)`，`OutboundEngine.doInvoke` 的**既有分类器**按 kind 落到 `UNKNOWN / COMPENSATING / 链失败` 三条既有出口——**不新增状态、不新增错误码段**（复用 50401 / 50201 / 50202 / 40001）。

### 6.5 幂等与 trace

- **traceId**：A 与 B 与第三方**共用同一个 traceId** → Monitor 按 traceId 一次看到 A 的 IN/OUT + B 的 OUT 三条记录；`X-Trace-Id` 头照旧透传。
- **bizId**：B 的子调用 `bizId = {A.bizId}#{stepSeq}`（`seq` 而非 `stepCode`，`stepCode` 改名不影响幂等键）。**同一 A 请求的每一轮重放都用同一值** → 依赖供应商对 `biz_id` 幂等（ADR 5 既有约定，前置只是把它的适用面从「A→第三方」扩展到「B→B 的供应商」）。
- 不在 DB 落 B 的 bizId（不落子记录），仅在日志/留痕 `detail` 中体现，便于对端核对。

### 6.6 熔断 / 限流 / 超时 / 并发

| 维度 | 语义 |
|---|---|
| 熔断 | 按 **B 的 `interface_id`** 生效（`CircuitBreakerRegistry` 现有粒度，天然正确）；B OPEN 时 A 顺延（§6.4） |
| 限流 / 日配额 / IP | 前置为**内部调用，不过 `GatewayGuard`**（不吃 A 的配额、不重复计 QPS）；B 自身 app 的限额对内部调用不计入——**口径须写入文档** |
| 超时 | 一期继承 B 的 `timeout_ms`；`timeout_ms_override` 列二期再开。**前置条件已满足（PS-0 已落地，2026-09-13）**：`interface.timeout_ms` 已按请求真实生效（`PerRequestReadTimeoutFactory` + `UpstreamInvoker.dispatch` 作用域），故「每跳按各自接口超时」开箱可用；未配 / 非法值 / 未声明作用域回退 `default-read-timeout-ms`（3000ms） |
| 并发 | 同一 A 请求内**串行**；不同请求互不影响（B 的链为无状态缓存链，`AdapterInstance` 只读） |
| 顺序 | 严格按 `seq` 升序（顺序敏感：先取 token 再带上 token） |

### 6.7 递归与深度防护（双保险）

- **保存期**：自环 / 间接环（DFS）+ 步数 ≤ 5 + 引用深度 ≤ 3 —— 见 §10；
- **运行期**：`attrs("preCallDepth")` 计数（A=1，B 链内若也有前置再 +1），超 3 直接 `40001` —— 防手工改库绕过校验造成无限递归。

### 6.8 配置即时生效

`interface_step` 是 INTERFACE 子表：`InterfaceService.update / rollback / publish / offline / delete` 已发 `ConfigChangedEvent.interfaceChanged(id)` → `ChainEngine` AFTER_COMMIT 精准移除该接口的缓存链 → **下次请求即重新装配**。**无需新增事件发布点**（符合 CLAUDE.md「新增配置入口必须补发事件」的要求，此处已天然满足）。`TTL 5 分钟`仍为兜底。

**全局开关**：`app.api-center.pre-step.enabled`（默认 `true`）。置 `false` 时装配期忽略 steps（配置保留、不执行）——线上应急一键回到今日行为。

## 10. 校验与安全

### 10.1 保存期校验（`InterfaceService.validate`，权威）

| 检查 | 规则 | 报错 |
|---|---|---|
| 宿主类型 | 仅 `OUTBOUND` 可提交非空 `steps`（INBOUND 提交即拒） | `40001`「入站回调接口不支持前置步骤」 |
| 步骤名 | 非空、`^[A-Za-z0-9_]{1,32}$`、同接口内唯一（不区分大小写）、**不得为 `steps`** | `40001` |
| 目标接口 | 存在、`ifType=OUTBOUND`、`status=PUBLISHED`、`id != 宿主 id` | `40001`（缺失/未发布分别给不同文案） |
| 保留字段名 | IN 侧参数名、映射 `target` 名不得为 `steps` | `40001` |
| 环检测 | 以「宿主 → 各 target」为边做 DFS，命中回边即拒（含间接环） | `40001`「前置链存在环：IF-A → IF-B → IF-A」 |
| 数量 / 深度 | 步数 ≤ 5；引用深度（含间接）≤ 3 | `40001` |
| 失败策略 | 一期只接受 `ABORT`（其余值保留枚举但拒绝） | `40001`「失败策略 CONTINUE 为二期能力」 |

### 10.2 运行期安全

- **双重递归防护**：`attrs("preCallDepth")`（§6.7）；
- **保留键两道剥离**（§6.3）：防 token 类数据泄给第三方的供应商；
- **`out_payload` 明文风险（代码评审 P1-1.3/P3）**：本方案会放大「凭证明文落 `out_payload`」的既有问题（前置取回的 token 常被映射进出站报文）。建议**同期执行独立的加固小改**：写 `out_payload` 前过 `SensitiveDataMasker`（或对 `steps` 子树强制脱敏）——属独立改动，不作为本方案的上线阻塞项，但必须在同一批次评估；
- **内部调用不过网关防护**：明确语义（§6.6），避免「前置被当成外部流量二次限流」的误判；
- **B 的凭证隔离**：B 用自己 app 的 `app_credential`（`injectCredential` 按 B 的 `appId` 读），A 不会拿到 B 的密钥明文（除 B 的响应体本身）。

### 10.3 删除 / 变更守卫（引用完整性，应用层）

| 场景 | 语义 |
|---|---|
| 删除被引用的接口 B | **拒绝**：`40001`「接口被 N 个前置步骤引用：IF-X(步骤 auth)、IF-Y(步骤 route)」→ 提示先解除引用或下线 |
| B 下线（OFFLINE） | 允许（生命周期自由），但 A 运行时校验会失败 → 建议前端在 A 的 Tab 上标黄；可选：下线时返回 warning 文案 |
| 改 B 的 `code` | **允许**（引用存 id，不受影响）；展示层 join 自动跟随 |
| 改 B 的 `if_type` | 现有 `update` 允许改类型 → 运行时校验会拒（非 OUTBOUND）；**保存期**对「被引用的接口改类型」加警告 |
| 删除 A（宿主） | 走既有删除守卫（有运行数据仅允许下线），`deleteCascade` 清理自己的 `interface_step` |

## 12. 验收测试点

**自动化（`PreStepIntegrationTest`，WireMock 两个上游）**

1. **串行两步**：`auth` 取 token → `route` 取资方 → A 打第三方；断言第三方收到的报文含 token（WireMock `verify`），且 A/B 的请求都到达；
2. **模型隔离**：B 收到的入参**不含** A 的 `steps` 子树（WireMock 请求体断言）；
3. **透传防护**：A 无映射规则 + 配了前置 → 第三方收到的报文**不含** `steps` 键（回归 C4）；
4. **映射引用**：A 的规则 `source=steps.auth.token → target=api_token` 正确落进第三方报文；`condition` 里 `steps.auth.code == 0` 生效；
5. **失败传播四分支**：B 返回 400 → A 不落运行表（D7）；B 500 耗尽 → A `COMPENSATING` 且 `attempt` 不变；B 读超时 → A `UNKNOWN`；B 熔断 OPEN → A 顺延不 `incrementAttempt`；
6. **预算不污染**：前置调用后 A 的短重试次数仍按 A 的 `max_retries`（回归 C8 的第 3 条）；
7. **IN 归属**：call_log 的 IN 条 `interface_id = A`（回归 C8 的第 2 条）；
8. **幂等键稳定**：A 重放两次 → B 收到的 `biz_id` 相同；
9. **留痕**：A 的 `state_log` 出现 `trigger=PRE_STEP` 节点，`detail` 含步骤名与 HTTP 码；
10. **配置**：环（A→B→A）与超深（A→B→C→D）保存期 `40001`；B 被引用时删除被拒；`pre-step.enabled=false` 时不执行；
11. **快照**：update 后新版本 `config_json` 含 `steps`；回滚恢复步骤；复制携带步骤；`SnapshotSerializerTest` 往返通过；
12. **零影响回归**：`interface_step` 为空时全量 192 个既有用例**无断言变更**全绿。

**手动验收（并入《整体测试方案》用例库，约 15 分钟）**

M1. 界面配置 A 的两步前置 → 保存 → 列表出现 `⇢2 步` 徽标 → 详情抽屉可见；
M2. `POST /interfaces/{id}/test` → 响应 `chainTrace.steps` 两步均 200，`result` 正常；
M3. 真实调用 A（WireMock 或 stubs）→ Monitor 状态链出现两条「前置步骤」节点；调用日志按 traceId 过滤能看到 3 条记录；

M5. 删除 B → 被引用拒绝，提示引用方；
M6. `Ctrl+F5` 无关项：未配置前置的既有接口（fastmoss 黄金用例）调用行为与改动前一致。

## 13. 边界与不做（写进设计契约）

| 不做 | 原因 |
|---|---|
| 业务补偿 / Saga 回滚 | 超出「连接 + 适配 + 可靠传输」定位；需业务语义 |
| 异步 / 并行前置 | 前置的作用是提供上下文，异步即拿不到结果；并行需处理部分失败语义（二期再议） |
| 条件分支 DAG / 循环 | 编排引擎复杂度陡增；一期仅支持「单步可选条件」（`condition_expr`，二期） |
| 跨接口字段映射 DSL | 一期由「B 用自己映射从共享模型取字段」覆盖；引入第二套映射语义会破坏 M0-02 契约 |
| 前置调用进入补偿/对账状态机 | 会产生与 A 生命周期不一致的孤儿记录（C5） |
| 前置的输出缓存 / 复用 | 前置是请求级上下文，缓存会造成跨请求串数据（如 token 串号）；如需要「低频全局数据」应另做「共享上下文节点」（独立特性） |
| 前置调用计 A 的配额 / QPS | 内部调用不应消耗调用方配额（口径须同步到使用教程） |

**决策矩阵：什么时候用前置编排，什么时候别用**

| 需求 | 推荐 | 理由 |
|---|---|---|
| 需要**每次请求实时**的外部数据（token / 配额 / 路由） | ✅ 前置编排 | 正是本方案 |
| B 的结果**低频变化**（码表 / 汇率 / 城市） | ❌ 用「定时预热 + 平台级缓存」（后续特性） | 每请求串一次 B 会把 A 的 P99 拖成 A+B |
| B 只是**静态参数补充** | ❌ 用 A 自己的映射 `op=default` / `interface_body.raw` 模板 | 零成本，不需要一次网络调用 |
| B 的调用**允许失败且必须继续** | ⏳ 等二期 `CONTINUE` | 一期 ABORT 语义更安全，不要让用户"猜" |

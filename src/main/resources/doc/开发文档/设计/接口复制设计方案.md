# 接口复制功能设计方案

> 版本：v0.1（2026-09-07 评审通过并落地）｜范围：管理面接口模块新增「复制」能力（后端 + 前端）
> **拍板结果（2026-09-07）**：选方案 B；code/path 置空由用户必填（不做自动建议）；**不支持跨应用复制**（固定源应用/源分组，弹窗与服务端均无 appId/groupId）；产物 DRAFT 不自动发布；入口仅接口详情抽屉。
> 目标读者：评审选型后即编码。文档中的约束均对照现有代码（InterfaceService.create/validate、schema uk、M5 快照）给出，复制语义须与下述「关键约束」一致，不新增旁路写入。

## 1. 背景与目标

配置相似接口（如同一供应商的多个同构端点、灰度/沙箱环境复制）时，逐字段重建成本高且易漏子表。目标：
- 一键把源接口**当前配置**复制为新接口（新 id、新 code/path），新接口可立即独立演进出自己的版本历史；
- 复制必须**可安全纠偏**：code/path 全局唯一冲突、跨应用/分组、凭证边界都要有明确语义，不许复制出“带不动”的配置；
- 不复制任何**运行时数据**（出站/送达记录、call_log、死信、对账、监控指标）——全部随新 id 从零开始。

## 2. 关键约束（方案都要满足，代码事实）

| 约束 | 现状 |
|---|---|
| 唯一键 | code / path 均为库级全局唯一（uk_interface_code / uk_interface_path）；复制必须改名或自动生成 |
| 子表 | 6 张：snapshot / param / body / mapping / field_def / binding（create 走 insertChildren 全量重建） |
| 快照 | 新接口从 **v1.0** 起一份首快照；**不继承源快照历史**（源历史属于源接口 id） |
| 校验 | create 内 validate（类型互斥 / 必填 / 路径禁协议·`..` / 回调地址禁内网依开关）+ validateBelong + 唯一性，复制复用同一入口 = 校验零旁路 |
| 凭证 | 凭证属于**应用**（app_credential，kind=OUTBOUND/CALLBACK），随应用走，**复制接口不复制凭证**；跨应用复制后，新接口继承新应用默认/自身绑定引用的适配器（全局 id），供应商鉴权用新应用的凭证 |
| 绑定 | binding.adapter_id 为全局适配器实例 id，可跨接口/应用复用；复制沿用源绑定行（含 M5 灰度 version），但停用/缺失时运行时按矩阵回退（不阻塞复制） |
| 审计 | 复制是「新建配置」：change_note 建议携带「复制自 xxx」来源信息，随 v1.0 快照落库 |
| 运行数据 | 一律不复制（见目标第 3 条）；复制生成 DRAFT，可先编辑/测试再发布 |

## 3. 候选方案

### 方案 A：前端「复制为新建」——浏览器侧拷贝预填
- 交互：接口列表/详情 →「复制」→ 打开现有**新建表单**并预填源接口全部字段（子表逐项拷贝），仅清空 code/path 并聚焦让用户改名 → 保存走既有 `POST /interfaces`。
- 实现：前端 GET detail → 深拷贝 payload（复用现有 openCreate 数据结构的拷贝函数）→ 覆盖 code/name/path → 用户自填后提交。后端**零新增**。
- 优点：改动最小、天然复用校验/唯一性/兜底；用户可顺手大改（复制后即编辑态）。
- 缺点：数据经过浏览器中转（多子表大 payload 复制慢）；**跨应用粘贴依赖用户理解**；「复制」语义弱（本质是“预填新建”）；无法程序化调用（无 API）。

### 方案 B：后端「复制接口」端点（服务端深拷贝，推荐）
- 交互：接口详情/列表 →「复制」→ 弹窗（必填**新接口标识**、可预填**名称=原名-副本**、平台路径**默认自动生成建议**，可改；高级可改**目标应用/分组**；其余沿用源配置）→ `POST /api/admin/interfaces/{id}/copy` → 成功后打开新接口详情。
- 实现：新增 `InterfaceService.copy(long id, CopyRequest req)`：
  1. 源 = detail(id)（六段子表全量）；
  2. `req.code / req.path` 必填并做唯一性预检（沿用 create 同款报错语义）；
  3. appId/groupId 缺省 = 源归属；显式传入则按新应用校验（类型互斥等 create.validate 全量跑）；
  4. 组装 `InterfaceRequest`（status=DRAFT，version=BASE 1.0）→ **直接调用现 create(req, changeNote=“复制自 {code}#v{源当前版本}”）**——复用全量替换路径的校验与插入，零旁路；
  5. changeNote 随首快照落库（前端版本历史即可见来源）。
- 请求体（拍板后：固定源归属、code/path 置空必填）：
  ```json
  {
    "code": "IF-NEW-01",    // 必填，全局唯一（不做自动建议）
    "path": "/new/path",    // 必填，全局唯一
    "name": "XX 副本",      // 可空 = “{源名} 副本”
    "upstreamPath": "/up",  // 可空 = 沿用源（出站时）
    "callbackUrl": null,    // 可空 = 沿用源（入站时）
    "desc": "从 IF-X 复制"   // 可空
  }
  ```
  appId / groupId 不由请求携带：复制固定归入源应用与源分组。
- 优点：语义清晰、一次请求原子完成、API 可被脚本/批量复用；改名校验在服务端；DRAFT 产出便于审后再发。
- 缺点：后端新增约 1 个端点 + 服务方法（工作量大头在测试）；弹窗需做 code/path 自动建议与即时查重。

### 方案 C：模板库 / 批量复制（远期，不在本期）
- 「应用级保存为模板」：源接口显式存为模板（脱离运行时），模板中心可跨应用实例化；支持同构批量（读多个供应商端点一次性生成 N 个接口）。依赖方案 B 的 copy 内核做实例化。本期不做，仅留扩展位（copy 服务方法天然可被模板中心复用）。

### 方案 B+：跨版本复制（轻量扩展，可与 B 合并评估）
- 复制时目标版本可选「源当前版本」或「源某历史快照」（版本历史弹窗加「以此为模板新建」）——内核 = 把 SnapshotSerializer.toRequest(configJson) 的结果作为 copy 的源。若选 B，建议二期再叠加，本期只做“当前版本”。

## 4. 关键语义决策（评审重点）

| 决策点 | 建议语义 | 原因 |
|---|---|---|
| 复制快照历史？ | 不复制；新接口 v1.0 起步，change_note=复制自源 | 快照按 interface_id 隔离，继承会破坏“源历史可回滚”的审计边界 |
| 复制凭证？ | 不复制（凭证属应用）；跨应用后用新应用的凭证 | 凭证明文永不经管理面接口，复制无源可拿 |
| 复制范围（应用/分组） | **不支持跨应用**：固定源应用/源分组 | 拍板确认；复制后如需调整，走编辑改归属即可 |
| code/path 冲突 | 前端提交拦截空值 + 后端唯一校验兜底（与 create 同文案） | uk 约束不可绕行；不做自动建议，由用户命名 |
| 供应商/回调地址 | 沿用源，弹窗可显式覆盖（留空 = 沿用） | 跨环境复制必改地址 |
| 产物状态 | DRAFT（不自动发布） | 复制后应先测试再发布，与 create 一致 |
| 运行数据/日志/指标 | 全部不复制（新 id） | 保持监控/对账口径干净 |
| 接口类型/协议/参数 | 完整逐项拷贝（IN/OUT 参数、Body、映射、RESP/ACK、绑定 version） | 子表语义即接口定义 |

## 5. 方案对比

| 维度 | A 前端预填 | B 后端 copy 端点 | C 模板/批量（远期） |
|---|---|---|---|
| 后端改动 | 0 | 中（1 端点 + 服务方法） | 大 |
| 前端改动 | 小（拷贝预填） | 中（弹窗 + 查重 + 自动建议） | 大 |
| 复制保真度 | 高（全字段预填可再改） | 高（服务端深拷贝原子） | 高 |
| 可脚本化/批量 | 否 | 是 | 是 |
| 语义清晰度 | 弱（=预填新建） | 强（真·复制） | 强 |
| 跨应用纠偏 | 依赖人工 | 弹窗显式选择 | 模板参数化 |
| 风险 | 大 payload 前端中转、易漏子表 | 低（复用 create 全量路径） | 需设计模板 schema |
| 测试面 | 前端为主 | 后端集成 + 前端 | 大 |

## 6. 推荐

**方案 B（后端 `POST /{id}/copy`）+ 前端弹窗**，理由：
- 内核零旁路：copy 组装后直调现有 `create`（全量替换路径 = 校验/归属/唯一性/快照一次性复用），后端新增是纯"取源→组目标"逻辑，回归面最小；
- 产物是 DRAFT + 独立 v1.0 历史 + change_note 来源审计，语义与 M5 版本体系一致；
- 留了 B+（跨版本复制）与 C（模板中心）的复用位，后续迭代只需扩展 copy 方法参数。

## 7. 实施拆解（方案 B）

| 任务 | 内容 | 依赖 |
|---|---|---|
| B-1 后端 | `CopyRequest` DTO（code/path 必填，其余可空）+ `InterfaceService.copy`（归属固定源、产物 DRAFT v1.0、change_note=复制自源）+ `POST /api/admin/interfaces/{id}/copy` 端点（返回新 id） | — |
| B-2 前端 | 详情抽屉「复制」按钮 → 弹窗（code/path 置空必填、名称默认「{源名} 副本」、地址可覆盖、其余沿用源）→ 成功后打开新接口详情 | B-1 |
| B-3 测试 | 集成：复制后子表语义等价（映射/绑定/参数/协议逐项断言）、新 id 新 v1.0 快照 + change_note 含源、code/path 冲突 40001、跨应用校验（新 app 归属/分组不匹配拒绝）、入站/出站两类型各一例、运行数据不复制 | B-1 |
| B-4 文档 | CLAUDE/README 功能清单、整体测试方案用例库补「复制」用例；本设计稿标注已落地 | B-2/B-3 |

验收点：
- 复制出站接口 → 供应商调用成功（WireMock 验证报文与原一致）；复制入站接口 → 模拟回调闭环；两者都可用测试端点走链；
- 新接口可独立编辑/回滚，源接口及其版本历史不受影响；删除副本不影响源；
- 同应用复制与跨应用复制各验证一遍；code/path 冲突提示与 create 一致。

## 8. 待拍板问题

1. **选型**：A / B / B+（含跨版本）？（推荐 B，B+ 二期）
2. **名称/路径自动建议规则**：code 建议 `{源code}-COPY`、path 建议 `{源path}-copy`？是否保留段（如 `/m5/ver-copy`）还是同目录改名？
3. **弹窗默认归属**：默认同应用同分组；跨应用复制是否需要「连带提示：凭证将用目标应用的」明示？
4. **产物是否自动发布**：默认 DRAFT（推荐）；是否提供「复制并发布」选项？
5. **复制入口位置**：仅详情抽屉、或列表行也加（推荐两者：列表行有「复制」icon，避免为复制先进详情）。

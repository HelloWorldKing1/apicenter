# apicenter · 低代码集成平台可行性分析与技术设计

> 关联原型：[低代码集成平台原型.html](../低代码集成平台原型.html)（基于 [api演示 demo.html](../api演示%20demo.html) 技术架构）
> 现有实现：`com.deepx.apicenter`（Spring Boot 4.1 · Java 21 · 设计文档见 `设计文档.md`）

---

## 1. 背景与目标

### 1.1 现状

当前 apicenter 的字段映射、路由、处理逻辑是**写死在代码**里的：

- 字段映射：MapStruct 编译期生成 `OrderMapperImpl`（`mapper/OrderMapper.java`），加一个渠道就要改 Java 代码、重新编译；
- 处理逻辑：金额元→分、时间格式化、状态枚举映射等散落在 `OrderMapper` 与各 Service 中；
- 路由：`PartnerInvoker` 里 `if/else` 按渠道硬编码（`service/PartnerInvoker.java:65` 注释「生产可按 orderType/渠道配置同时路由」）。

每接入一个新第三方，都需要开发介入，无法由业务/实施人员自助完成。

### 1.2 目标

把 apicenter 升级为**配置驱动的低代码集成平台（类 ETL 工具，类比 Kettle / Talend / Apache NiFi）**：

- 用户在界面配置 **源（Source）**、**目标（Target）**、**字段映射（Field Mapping）**、**数据处理（Transform）**、**函数处理（Function）**；
- 系统基于配置生成执行管线，完成 API 中转（验签 → 读取 → 映射/处理 → 送达 → 日志/补偿）；
- 新增第三方渠道**不再改代码**，只做配置。

### 1.3 非目标（本期）

- 不做拖拽式自由画布的高级实现（原型用「节点 + 步骤」简略表达）
- 不引入重量级 BPM / 规则引擎（Camunda / Drools）
- 不承载业务规则判断（仍坚持「连接 + 适配 + 可靠传输」边界）

## 2. 可行性结论（TL;DR）

**结论：技术可行，建议分三阶段演进。**

| 维度 | 判断 | 依据 |
|---|---|---|
| 技术栈 | ✅ 完全可承载 | 现有 Java 21 / Spring Boot 4.1 / Jackson 3 / JDBC 已具备动态配置解析与协议适配能力 |
| 字段映射动态化 | ✅ 可行，有取舍 | 编译期 MapStruct → 运行时「规则 + 函数」映射；复杂转换用 SpEL |
| 协议适配 | ✅ 可行 | JSON（Jackson 3）/ XML（`jackson-dataformat-xml`）均已具备；@HttpExchange + RestClient 可配置化复用 |
| 可靠传输 | ✅ 可直接复用 | @Retryable / CompensationWorker / 死信 / 对账 / call_log 全套状态机可复用到配置驱动引擎 |
| 前端 | ✅ 可行 | 现有 Vue3 前端 / 静态原型已演示配置 UI 概念 |
| 核心风险 | ⚠️ 需管控 | ① 动态映射/表达式性能与安全 ② XML 动态序列化 ③ 配置版本/兼容性管理 ④ 从 MapStruct 迁移的取舍 |

**演进路径**：一期「字段映射配置化」（POC）→ 二期「流程编排配置化」（执行引擎）→ 三期「可视化低代码 UI + 任务管理/版本/监控」。

## 3. 核心概念模型

```
集成任务 IntegrationJob = Source + TransformSteps + Target
```

| 概念 | 说明 | 对应现有实现（复用点） |
|---|---|---|
| **Source（源）** | 数据从哪来，四种形态：HTTP 接口 / JSON 源 / SQL 源 / Function 源；协议 JSON/XML；鉴权方式 | Flow A `OrderController` / Flow B `CallbackController` / `IncrementalSyncJob`（HTTP）；新增 JSON/SQL/Function 读取器 |
| **Target（目标）** | 数据送往哪：第三方 API / ERP 回调 URL；协议与鉴权 | `PartnerAClient` / `PartnerBClient` / `ErpCallbackClient` |
| **TransformSteps（处理步骤）** | 字段映射、金额/时间转换、脱敏、过滤、嵌套聚合，按顺序执行 | `OrderMapper` 的映射逻辑拆解为可配置步骤 |
| **FieldMappingRule（字段映射规则）** | 源字段 → 目标字段 + 转换函数 + 示例 | `OrderMapper` 的 `@Mapping` + `@Named` 方法 |
| **Function（函数）** | 内置函数注册表，元数据驱动 UI 下拉 | `OrderMapper` 的 `yuanToCent` / `centToYuan` 等默认方法 |
| **元数据（Metadata）** | 函数签名、字段说明、协议能力描述，驱动 UI 渲染 | 新增（前端据此渲染下拉/表单） |

**源类型抽象（关键）**：源类型只决定「数据如何获取」（HTTP 接收 / 解析 JSON 文本 / 执行 SQL / 调用函数），获取后**统一为「源数据对象」（JSON 结构）**，后续字段映射、数据处理、函数处理、目标完全一致。这是 ETL 的核心抽象。

| 源类型 | 数据获取方式 | 复用点 |
|---|---|---|
| HTTP 接口 | 接收端点（ERP 推送 / 第三方回调）或定时拉取 | `OrderController` / `CallbackController` / `IncrementalSyncJob` |
| JSON 源 | 内联 JSON 文本 / 配置里的静态数据 | Jackson 3 |
| SQL 源 | 执行 SELECT 查询，结果集 → 源数据对象 | 现有 `JdbcTemplate`（H2→MySQL） |
| Function 源 | 调用函数库函数 / SpEL 产出对象 | §6 函数库 / SpEL |

**边界不变**：组件仍然只做「连接 + 适配 + 可靠传输」，业务决策交还 ERP；配置只描述「怎么连、怎么映射、怎么处理」，不描述「要不要做业务判断」。

## 4. 配置模型（数据模型）

### 4.1 方案 A：JSON 配置 Blob（一期推荐）

每个集成任务存一条 JSON 配置，Jackson 3 解析为 Java 对象后交给引擎执行。

```jsonc
{
  "flowCode": "ERP_ORDER_TO_PARTNER_A",
  "version": 1,
  "source": {
    "type": "HTTP", "protocol": "JSON", "method": "POST",
    "url": "/api/orders", "auth": { "type": "HMAC", "secretRef": "erp-secret" },
    "readTimeoutMs": 3000
  },
  "target": {
    "type": "HTTP", "protocol": "JSON", "method": "POST",
    "url": "/v1/order/push", "auth": { "type": "BEARER", "tokenRef": "token-a" },
    "readTimeoutMs": 3000
  },
  "transforms": [
    { "type": "FIELD_MAPPING", "rules": [
      { "src": "orderId", "target": "orderNo", "fn": "pass" },
      { "src": "totalAmount", "target": "totalAmountCent", "fn": "yuanToCent" },
      { "src": "createdTime", "target": "createdAt", "fn": "dateFormat", "args": ["yyyy-MM-dd'T'HH:mm:ss"] },
      { "src": "buyerPhone", "target": "buyer.mobile", "fn": "maskPhone" },
      { "src": "buyerName", "target": "buyer.name", "fn": "nest" },
      { "src": "shippingAddress.province", "target": "receiver.province", "fn": "pass" }
    ]}
  ]
}
```

优点：灵活、迭代快、一期落地成本低。缺点：无强类型约束、跨任务复用靠复制。

> **语义说明**：`source.url` 为「接收入口路径」（ERP 调组件的端点 `/api/orders`，或 Source 类型为「定时拉取」时的拉取地址）；`target.url` 为「调用目标地址」（组件调第三方的端点 `/v1/order/push`）。两者语义不同，勿混淆。

**`source.type` 四种形态**（获取后统一为「源数据对象」，`transforms` 段不变）：

| type | 专属字段（示例） | 说明 |
|---|---|---|
| `HTTP` | `protocol / method / url / auth / readTimeoutMs` | 接收端点或定时拉取 |
| `JSON` | `jsonBody: "{...}"` | 内联 JSON 文本，Jackson3 解析 |
| `SQL` | `sql: "SELECT ... WHERE id=?"`、`datasourceRef: "ds-main"` | JdbcTemplate 执行 SELECT |
| `FUNCTION` | `functionName: "generateOrder"`、`args: [...]` | 调用函数库/SpEL 产出对象 |

### 4.2 方案 B：关系表（二期完善，对齐现有 `schema.sql` 风格）

| 表 | 关键列 | 说明 |
|---|---|---|
| `integration_flow` | id、flow_code、name、source_id、target_id、enabled、version、created_at | 任务头 |
| `flow_source` / `flow_target` | type、protocol、method、url、auth_type、auth_secret_ref、read_timeout_ms | 源/目标配置 |
| `field_mapping_rule` | flow_id、seq、src_field、target_field、fn_name、args、sample_value | 字段映射规则 |
| `transform_step` | flow_id、seq、step_type、config_json | 处理步骤（映射/过滤/清洗） |
| `function_lib` | fn_name、params_json、return_type、desc | 函数元数据（驱动 UI 下拉） |
| `flow_version` | flow_id、version、config_snapshot | 配置版本快照（灰度/回滚） |

建议：**一期 JSON Blob + 少量元数据表（function_lib），二期拆表 + 版本管理**。

## 5. 运行时引擎设计

```
SourceReader → TransformerChain → TargetWriter
        │            │                 │
   (验签/鉴权)   (字段映射/函数)     (协议适配/送达)
        └──────────── 复用状态机 / 补偿 / 日志 ────────────┘
```

### 5.1 配置解析

- 用 Jackson 3（`tools.jackson`）把配置 JSON 解析为 `IntegrationFlow` record/POJO；
- 启动时加载所有 enabled 流程到内存 Map（`flowCode → IntegrationFlow`），运行时按 `flowCode` 路由；配置变更走版本发布，不热更。

### 5.1.1 SourceReader 多态（四类源）

`SourceReader` 为统一抽象，按 `source.type` 选择实现，输出统一的「源数据对象」（`Map` / `JsonNode`）：

| Reader | 职责 | 依赖 |
|---|---|---|
| `HttpSourceReader` | 接收端点（ERP 推送 / 第三方回调）或定时拉取，验签/鉴权后解析 body | `OrderController` / `CallbackController` / `IncrementalSyncJob` |
| `JsonSourceReader` | 解析内联 JSON 文本（`jsonBody`） | Jackson 3 |
| `SqlSourceReader` | 执行 SELECT（`JdbcTemplate`），结果集 → `Map`/`JsonNode`（列名用 AS 别名转 camelCase） | 现有 `JdbcTemplate`（H2→MySQL） |
| `FunctionSourceReader` | 调用函数库函数 / SpEL 产出对象 | §6 函数库 / SpEL |

四类源取到数据后统一为「源数据对象」，后续 `TransformerChain`（字段映射/函数处理）与 `TargetWriter` **完全不感知源类型**。

### 5.2 字段映射求值

- 规则 `{ src, target, fn, args }`：
  1. `getPath(source, src)` 按 `.` 路径取源值（支持数组下标 `[n]`）；
  2. `applyFn(fn, value, args, source)` 调用函数（内置注册表反射）；
  3. `setPath(target, targetPath, result)` 写目标，嵌套路径自动建父节点（`buyer.name` → `buyer:{name:...}`）；
- 与现有 `OrderMapper` 的差异：映射不再编译期固定，而是运行时按规则执行——**功能等价，代价是类型安全与编译期检查让位于配置校验**。

### 5.3 协议适配

- 复用 `config/RestClientConfig.java` 的 `HttpServiceProxyFactory` + `RestClient` 模式，但 URL/鉴权/超时从配置读取；
- JSON：Jackson 3；XML：`jackson-dataformat-xml`（`XmlMapper`），动态字段名用运行时构造 `@JacksonXmlProperty` 或 XmlMapper 的 `PropertyNamingStrategy`/树模型（`JsonNode` → 按目标字段名写节点）；
- 回调入站（Source 为回调）复用 Flow B：验签 → 解析 → 引擎处理 → 送达 ERP。

### 5.4 可靠传输复用

| 现有能力 | 复用方式 |
|---|---|
| `SignatureService`（HMAC-SHA256 验签） | 按配置的 auth_type/secret 选择验签或 Bearer |
| `PartnerInvoker` 的 `@Retryable`（5xx/429/超时指数退避） | 参数（attempts/退避）从配置读取，仍放独立 Bean |
| `OrderSyncService.RequestStatus` 状态机 | 出站执行器沿用 INIT→…→SUCCESS/DEAD_LETTER/UNKNOWN |
| `CompensationWorker`（3s 扫描补偿） | 扫描待补偿任务，按配置重放 |
| `LoggingAspect` + `integration_call_log` | 全链路日志沿用（traceId、脱敏、direction） |
| `IncrementalSyncJob`（高水位游标 + 防重） | Source 类型为「定时拉取」时复用 |

## 6. 函数库与表达式选型

### 6.1 内置函数注册表

Java 静态方法 + 元数据（`fn_name / params / return_type / desc`），引擎按名称反射调用，UI 按下拉渲染。函数示例：

| 函数 | 签名 | 返回 | 说明 |
|---|---|---|---|
| 直传 | `pass(v)` | 原值 | 源→目标原样复制 |
| 元→分 | `yuanToCent(v)` | long | `value * 100` |
| 分→元 | `centToYuan(v)` | BigDecimal | `value / 100` |
| 时间格式化 | `dateFormat(v, pattern)` | string | ISO ↔ `yyyyMMddHHmmss` |
| 手机号脱敏 | `maskPhone(v)` | string | `138****1234` |
| 枚举映射 | `enumMap(v, map)` | value | `NEW→1 / PAID→2 / SHIPPED→3` |
| 嵌套写入 | `nest(v)` | value | 源值写入点号目标路径，自动建父对象（`buyer.name`） |
| 明细列表映射 | `mapItems(items[])` | array | 对明细 items[] 逐项映射（qty→quantity、金额元→分） |
| 路径取值 | `jsonPath(src)` | value | 按点号路径从源数据取值（src 即路径） |
| 默认值 | `defaultValue(v, d)` | value | 空值兜底 |

### 6.2 动态表达式选型对比

当「声明式规则 + 内置函数」不够（条件分支、复杂计算）时，引入动态表达式。对比：

| 引擎 | 类型 | 性能 | 安全 | 集成成本 | 结论 |
|---|---|---|---|---|---|
| **SpEL** | Spring 内置 | 中 | 需配置限制 | 低（同项目已用 Spring） | ✅ **推荐**（复杂逻辑） |
| Aviator | 独立轻量 | 高 | 较好（无反射逃逸） | 中 | ⚠️ 备选（追求性能） |
| JEXL | Apache | 中 | 一般 | 中 | 一般 |
| Groovy | JVM 脚本 | 低 | 需沙箱 | 高 | ❌ 不推荐（沙箱成本） |

**建议**：字段映射**默认用「声明式规则 + 内置函数」**（性能好、可校验、可预览）；复杂逻辑用 **SpEL**（Spring 自带、类型安全）；不引入 Groovy。

### 6.3 安全

- 函数白名单（`function_lib` 注册表即白名单）；
- 表达式引擎限制：禁用反射/类加载/文件/网络访问（SpEL 用 `SimpleEvaluationContext`）；
- 配置校验：规则字段存在性、函数参数类型、循环引用检测；保存前「预览执行」沙箱验证。

## 7. 与现有 apicenter 能力复用映射

| 现有能力 | 复用/改造 | 落点 |
|---|---|---|
| Flow A 出站状态机 | 复用（执行器改为按配置路由） | `OrderSyncService` + `integration_request` |
| Flow B 入站回调 | 复用（回调 URL/验签密钥改从配置读） | `CallbackController` + `CallbackDeliveryService` |
| `@Retryable` 短重试 | 复用（参数配置化） | `PartnerInvoker` |
| 补偿 worker | 复用（扫描范围改为 integration_flow 任务） | `CompensationWorker` |
| AOP 日志 / call_log / traceId | 复用（不改） | `LoggingAspect` + OpenTelemetry |
| 定时增量同步 | 复用（Source 类型=定时拉取） | `IncrementalSyncJob` + `sync_watermark` / `idempotency_key` |
| SQL 源 | 复用现有 `JdbcTemplate`（H2→MySQL） | 新增 `SqlSourceReader` |
| JSON 源 | 复用 Jackson 3 解析内联 JSON | 新增 `JsonSourceReader` |
| Function 源 | 复用 §6 函数库 / SpEL | 新增 `FunctionSourceReader` |
| MapStruct 编译期映射 | **改造**为运行时「规则+函数」映射 | 新增 `MappingEngine`（`OrderMapper` 逻辑迁移） |
| 渠道配置 `application.yaml` | 部分迁移到 DB 配置（保留本地默认） | `ChannelProperties` + `integration_flow` |

**边界**：引擎不解释业务，只按配置机械执行；错误仍走死信/对账，决策交还 ERP。

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **动态映射性能** | 运行时反射 + 路径求值慢于编译期 | 内置函数为主、路径求值缓存、批处理；复杂场景用 SpEL 预编译 |
| **XML 动态序列化** | JacksonXml 动态字段名/包装器成本高 | 运行时用 XmlMapper 树模型按目标字段写节点；或模板化（FreeMarker）渲染 XML body |
| **表达式/脚本安全** | 注入、逃逸风险 | 函数白名单 + SpEL `SimpleEvaluationContext` + 预览沙箱 |
| **SQL 注入（SQL 源）** | 配置的 SELECT 被注入/越权读写 | 参数化 SQL（`?` 占位）、表/列白名单、只允许只读 SELECT、数据源最小权限 |
| **Function 源沙箱** | 函数/脚本越权（文件/网络/反射） | 复用 §6.3：函数白名单 + SpEL `SimpleEvaluationContext`；不引入 Groovy |
| **配置复杂度** | 规则一多难维护、易配错 | 元数据驱动 UI、配置校验、预览执行、版本回滚 |
| **从 MapStruct 迁移的取舍** | 现有 `OrderMapperImpl` 迁移成本 | 一期保留 MapStruct 映射到「默认 flow」，新增渠道走配置引擎，双轨过渡 |
| **配置兼容性** | 升级/灰度时旧配置失效 | `flow_version` 快照 + 灰度发布 + 全量配置回归测试 |
| **Demo → 生产** | 内存/单机限制 | 沿用现有生产化规划：MySQL、XXL-JOB、Redis 分布式锁 |

## 9. 演进路径（三阶段）

### 一期 · 字段映射配置化（POC，目标 1-2 周）

- 目标：跑通「ERP 订单 → PARTNER_A」完全由配置驱动，不写死映射代码
- 交付：`MappingEngine`（规则+函数执行）、`function_lib` 元数据、配置 JSON 落库、执行预览
- 验收：用本原型「执行预览」相同用例，后端返回相同目标 JSON 且日志完整

### 二期 · 流程编排配置化（引擎）

- 目标：Source/Target/Transform 全配置化，出站/入站/定时三种 Source 类型通用
- 交付：`IntegrationFlow` 领域模型 + 执行器、协议适配配置化、重试/补偿参数配置化
- 验收：新增一个第三方渠道，全程零代码，只配 JSON/UI

### 三期 · 可视化低代码 UI + 运维

- 目标：本原型落地为真实前端（Vue3），支持任务管理/版本/灰度/监控
- 交付：配置 CRUD、预览执行、发布/回滚、执行监控看板（call_log + traceId + Prometheus）
- 验收：实施人员可自助配置上线一个新渠道

## 10. 验收示例（一期 POC）

**用例**：「ERP 订单 → PARTNER_A JSON」（与现有 Flow A 等价）

输入（ERP 入站）：
```json
{
  "orderId": "SO202608170001", "orderType": "PUSH", "orderStatus": "PAID",
  "totalAmount": 199.00, "currency": "CNY",
  "buyerName": "张三", "buyerPhone": "13812341234", "createdTime": "2026-08-17T10:30",
  "remark": "618 大促订单",
  "items": [
    { "skuCode": "SKU-001", "qty": 1, "unitPrice": 99.00, "amount": 99.00 },
    { "skuCode": "SKU-002", "qty": 1, "unitPrice": 100.00, "amount": 100.00 }
  ],
  "shippingAddress": { "province": "浙江", "city": "杭州", "detail": "西湖区 xxxx" }
}
```

# M4 手动验收测试方案

> 用途：M4 容错与监控的手动端到端验收（补充自动化测试的平台实操验证），全程约 35 分钟。
> 模拟上游用**本地 WireMock**（stub 随仓库 `src/test/resources/m4-manual-stubs/`：熔断 scenario / 慢上游 / 死信 404→200 / 正常回显）。
> 本方案按实施后实际行为校准（对应 `M4开发计划.md` §5，D-M4-1~6 语义）。
> 前置：M4 DDL 已应用（reconcile_audit / alert_event 两表 + idx_outreq_updated 索引——开发库已于 2026-09-04 执行；其他环境先跑 schema.sql 增量段）。

---

## 0. 验收目标总览（先花 1 分钟看懂要验什么）

M4 交付四类能力。验收过程就是「制造故障 → 观察平台反应 → 核对数据库留痕」，每项能力的白话解释：

| 能力 | 白话解释 | 在哪里验 | 定稿 |
|---|---|---|---|
| **熔断器** | 上游持续报错时，平台「拉闸」停止请求，避免雪崩；冷却后试探恢复 | 阶段二 ① | D-M4-1 |
| **UNKNOWN 对账** | 上游超时时，请求结果未知（可能到了也可能没到），平台先挂起，人工确认或超时自动降级 | 阶段二 ②③ | D-M4-2 |
| **死信重放** | 上游 4xx（调用方侧错误）重试无意义，直接进死信箱；修复后可人工重放 | 阶段三 ① | D-M4-3 |
| **可观测** | 每次调用落 IN/OUT 两条日志（敏感值脱敏）、traceId 三方贯穿、Prometheus 指标、告警规则 | 阶段一 + 阶段三 ② | D-M4-4/5 |
| **接入层防护** | QPS 限流、IP 黑白名单，在请求进链路之前拒绝且不留运行表记录 | 阶段三 ③ | D-M4-6 |

**总体通过标准**：三个阶段全部步骤的「预期结果」逐条满足，且 `mvn clean test` 全库测试全绿。

### 1.4 stub 约定（已随仓库，不需改动）

WireMock 是本地假供应商：平台把请求发给它，它按下面的剧本回话。**scenario** 是它的「剧本模式」——同一 URL 第 N 次请求可以给出不同响应（用 Playwright 的话说：先装死、后复活），这是死信重放演示的关键。

| stub | 行为 | 用途 |
|---|---|---|
| `/echo-ok` | 恒 200 `{"ok":true}` | 阶段一可观测演示的正常上游 |
| `/breaker-supplier` | 恒 500 | 熔断开闸演示（恢复经 WireMock 管理 API 运行时切 200，见阶段二 ① 步骤 4） |
| `/slow-supplier` | 200 但**固定延迟 5 秒**（> 默认读超时 3s） | 制造 UNKNOWN（对账演示） |
| `/reject-supplier` | **scenario：第 1 次 404 → 之后 200** | 制造死信（重放后恢复） |

> ⚠️ 注意：WireMock 占 18080 与集成测试同端口——**手动验收期间勿同时跑 `mvn test`**（端口冲突），验收完毕再跑测试。

### 步骤 2：发起两次调用（终端 curl）

```bash
curl -X POST http://localhost:8080/m4/obs -H "Content-Type: application/json" \
  -H "Authorization: Bearer my-demo-token-123456789" -H "X-Trace-Id: trace-m4-manual-1" \
  -d '{"hello":"world"}'
```

执行 **2 次**（连按两次 ↑ 回车即可）。两个 Header 是故意埋的「验收探针」：

- `Authorization: Bearer my-demo-token-123456789` —— 调用方凭证，**落库时应被脱敏**；
- `X-Trace-Id: trace-m4-manual-1` —— 调用方自定义 traceId，**平台应透传**并贯穿日志 / 运行表 / 上游请求三方。

**✅ 预期**：两次均返回统一信封 `code=0`、`msg=""`、`data={"ok":true}`。

| 今日成功率 | 100% |
| 待补偿 / 待重送 | 0 / 0 |
| 死信 / 对账中 | 0 / 0 |

**调用日志面板**：

- [ ] 出现 **4 条**记录（2 次调用 × 每次 IN / OUT 各一条）——「方向」列有 IN / OUT 标签区分；
- [ ] 在 traceId 过滤框输入 `trace-m4-manual-1` 回车 → **恰 2 条**（IN + OUT 各 1）——traceId 过滤可用；
- [ ] 两条记录 URL 不同（IN 条是平台路径 `/m4/obs`，OUT 条是上游 URL），状态码均 200。

## 阶段二：容错——熔断 / UNKNOWN 对账 / TTL 降级（约 15 分钟）

### ① 熔断三态（D-M4-1，约 3 分钟含冷却等待）

> **背景知识（30 秒看懂熔断）**：熔断器像电路保险丝，三态流转——
> **CLOSED（闭合=正常）**：请求照常转发，但统计「10 秒滑动窗口」内的失败率；窗口内至少 10 次调用且失败率 ≥50% → 拉闸；
> **OPEN（打开=熔断）**：**不再请求上游**，请求直接失败转补偿顺延（防止拖垮平台和上游）；持续 30 秒；
> **HALF_OPEN（半开=试探）**：30 秒后放 **2 次探测**（走完整链路含短重试），2 次全成功 → 回 CLOSED，否则回 OPEN。
> 默认参数即上述值（窗口 10s / 最小 10 次 / 失败率 50% / open 30s / 探测 2 次，见 application.yaml `app.api-center.circuit`）。

**步骤 1：建接口**：「接口管理」→ 新建 `IF-BRK-01`（照步骤同阶段一，仅以下字段不同）→ **发布**：

| 字段 | 值 |
|---|---|
| 接口标识 | `IF-BRK-01` |
| 平台侧路径 | `/m4/breaker` |
| 上游侧路径 | `/breaker-supplier`（恒 500） |

**步骤 2：连续 curl 12 次，观察「从慢变快」**：

```bash
for i in $(seq 1 12); do
  echo "--- 第 $i 次 ---"
  curl -s -o /dev/null -w "%{http_code} 耗时 %{time_total}s\n" \
    -X POST http://localhost:8080/m4/breaker -H "Content-Type: application/json" -d '{}'
done
```

**为什么是 12 次**：开闸需要 10 秒窗口内凑满 ≥10 个失败样本；且补偿 worker 的重放也计入失败样本，所以开闸点会略有浮动——连发 12 次确保触发。

**✅ 预期（关键观察点是耗时的突变）**：

- [ ] **前若干次**：HTTP 502、每次**耗时约 3.5 秒**——这是「重试耗尽」路径：上游 5xx → 短重试 4 次（共 5 次尝试 + 指数退避）→ 耗尽转 COMPENSATING；
- [ ] **中途起（约第 8~12 次）**：HTTP 502 但**耗时 < 0.5 秒**——这是**熔断短路**：不再开上游连接、不触发短重试，直接转 COMPENSATING 顺延；
- [ ] 终端 1 后端日志出现「出站请求 xx 熔断短路（接口 xx OPEN）」。

> 💡 若 12 次内未观察到 <0.5s 的记录：再连发 4 次即可（窗口样本凑满 10 个后必然开闸）。

**步骤 3：查库确认短路记录特征（不计数、只顺延）**：

```sql
SELECT id, status, attempt_count, error_code, next_retry_at
FROM outbound_request WHERE interface_id = (SELECT id FROM interface WHERE code='IF-BRK-01')
ORDER BY id DESC LIMIT 3;
```

**✅ 预期**：短路记录 `status=COMPENSATING`、`error_code='50202'`（区别于重试耗尽的 `50201`）、**`attempt_count` 不再增长**（未触达上游不计尝试——这就是「顺延」语义，恢复后由 worker 补做）。

**步骤 4：冷却后半开恢复（上游「复活」）**：

先经 WireMock 管理 API 运行时注册高优先级 200 stub——**原理**：文件 stub 优先级默认最低，注册一个 `priority=1` 的 stub 即可覆盖它，**无需重启 WireMock**，等于上游修好了：

```bash
# 上游恢复：注册高优先级（priority=1）200 stub 覆盖恒 500 的文件 stub
curl -X POST http://localhost:18080/__admin/mappings -H "Content-Type: application/json" \
  -d '{"priority": 1, "request": {"method": "POST", "url": "/breaker-supplier"},
       "response": {"status": 200, "jsonBody": {"ok": true}}}'

sleep 31    # OPEN 持续 30 秒，等 31 秒确保进入 HALF_OPEN
curl -s -X POST http://localhost:8080/m4/breaker -H "Content-Type: application/json" -d '{}'; echo
curl -s -X POST http://localhost:8080/m4/breaker -H "Content-Type: application/json" -d '{}'; echo
```

> 为什么是 2 次 curl：默认 half-open-probes=2，**两次探测均成功才闭合**。

**✅ 预期（逐条勾选）**：

- [ ] 两次 curl 均返回 `code=0`、`data={"ok":true}`（探测走完整链路，恢复成功）；
- [ ] 此前积压的 COMPENSATING 记录被补偿 worker（3 秒一轮）逐条重放成功——**管理面「接口监控」统计卡「待补偿」在数秒内归零**；
- [ ] `curl -s http://localhost:8080/actuator/prometheus | grep circuit_state` 值回落为闭合态（0）。

### ② UNKNOWN 人工对账（D-M4-2，M2 缺口闭环）

> **背景知识（30 秒看懂 UNKNOWN）**：读超时（默认 3s）时，平台**不知道**请求最终有没有到达上游——可能上游已处理只是回得慢。此时**不能盲目重试**（业务可能已成功，重试会重复扣款/重复建单）。设计语义：状态置 UNKNOWN 挂起 → 等人确认（人工对账）或超时自动降级（③）。这正是 M2 遗留的「超时→对账」分支在 M4 的落地。

**步骤 1：建接口**：同上新建 `IF-SLOW-01` → **发布**：

| 字段 | 值 |
|---|---|
| 接口标识 | `IF-SLOW-01` |
| 平台侧路径 | `/m4/slow` |
| 上游侧路径 | `/slow-supplier`（固定延迟 5 秒 > 读超时 3 秒） |

**步骤 2：制造一条 UNKNOWN**（curl 约 3 秒后返回——正好是读超时时长）：

```bash
curl -s -X POST http://localhost:8080/m4/slow -H "Content-Type: application/json" -d '{}'; echo
# 预期：HTTP 504、code=50401「上游超时，结果待对账（UNKNOWN）」
```

**步骤 3：管理面人工对账**：「接口监控」页 →「**对账（UNKNOWN）**」面板（10 秒自动轮询）：

- [ ] 列表中出现刚产生的记录（错误码 50401）；
- [ ] 点「**置为已到达**」→ 弹窗「人工对账（UNKNOWN 置位）」：**操作人填 `admin`（必填，不填提交会校验拒绝）**、依据说明随意（如「上游后台确认」）→ 点「确认置位」；
- [ ] 记录从列表消失（已收敛 SUCCESS）。

**步骤 4：查库核对审计留痕**：

```sql
SELECT o.id, o.status, a.from_status, a.to_status, a.source, a.operator, a.created_at
FROM outbound_request o JOIN reconcile_audit a ON a.outbound_request_id = o.id
WHERE o.interface_id = (SELECT id FROM interface WHERE code='IF-SLOW-01')
ORDER BY o.id DESC LIMIT 3;
```

**✅ 预期**：`o.status=SUCCESS` + 一条 audit：`from_status=UNKNOWN → to_status=SUCCESS`、`source=MANUAL`、`operator=admin`。

**步骤 5（可选变体）：「置为未到达」分支**：再造一条 UNKNOWN（curl 同步骤 2）→ 点「**置为未到达**」→ 转 COMPENSATING 入补偿队列。因 `/slow-supplier` 恒慢，worker 重放会**再次超时回到 UNKNOWN**——这不是缺陷：**重放不盲目、回 UNKNOWN 继续对账正是设计语义**。如需看到重放成功，把接口上游路径改回 `/echo-ok` 后再置位。

### ③ TTL 自动降级（M0-03 §3.1 分支二）

> **背景知识**：UNKNOWN 不能永远挂着。规则：挂起超过 **10 分钟**（`unknown-ttl-minutes: 10`）仍无人处理 → 补偿 worker 自动转 COMPENSATING 交给补偿队列兜底，并写一条 `source=TTL` 的审计。人工造一条等 10 分钟太久，所以**直接改库把 updated_at 回拨**模拟「已经挂了 11 分钟」。

**步骤 1：再造一条 UNKNOWN，并回拨时间**：

```bash
curl -s -X POST http://localhost:8080/m4/slow -H "Content-Type: application/json" -d '{}'; echo
```

```sql
UPDATE outbound_request
SET updated_at = DATE_SUB(NOW(), INTERVAL 11 MINUTE)
WHERE interface_id = (SELECT id FROM interface WHERE code='IF-SLOW-01')
  AND status = 'UNKNOWN';
```

**步骤 2：等补偿 worker 一轮（3 秒）→ 查库核对两条**：

```sql
SELECT id, status, error_code FROM outbound_request
WHERE interface_id = (SELECT id FROM interface WHERE code='IF-SLOW-01') ORDER BY id DESC LIMIT 1;
-- 预期：status=COMPENSATING（error_code 保留 50401 超时成因——降级不改写死因）

SELECT source, operator FROM reconcile_audit ORDER BY id DESC LIMIT 1;
-- 预期：source=TTL、operator=TTL-WORKER（与②的 MANUAL/admin 合计，审计两来源齐备）
```

## 阶段三：死信重放 / 告警 / 限流（约 10 分钟）

### ① 死信重放（D-M4-3）

> **背景知识**：上游 4xx（非 429）= 调用方侧或参数类错误，**重试没有意义**（再发还是 4xx）→ 直接写 `dead_letter` 表、状态 DEAD_LETTER。修复诱因后可在管理面「重放」：重新入队，由补偿 worker 自然重放。stub 的 scenario 剧本（第 1 次 404、之后 200）保证重放时上游已「修好」。

**步骤 1：建接口 + 制造死信**：新建 `IF-REJ-01` → **发布** → curl 一次：

| 字段 | 值 |
|---|---|
| 接口标识 | `IF-REJ-01` |
| 平台侧路径 | `/m4/reject` |
| 上游侧路径 | `/reject-supplier`（scenario：第 1 次 404 → 之后 200） |

```bash
curl -s -X POST http://localhost:8080/m4/reject -H "Content-Type: application/json" -d '{}'; echo
# 预期：HTTP 502、code=50201、msg 含「死信编号 N」（上游 404 → 4xx 不重试直接死信，请求应秒回）
```

**步骤 2：管理面重放**：「接口监控」→「**死信**」面板：

- [ ] 有一条 PENDING 记录（类型 OUTBOUND、死因含「上游 404…」、关联记录指向 outbound_request id）；
- [ ] 点「**重放**」→ 确认弹窗（提示：重新入队，由 worker 自然重放）。

**步骤 3：等 3 秒（worker 扫描一轮）→ 查库核对**：

```sql
SELECT o.status, o.attempt_count, d.status AS dead_status, d.handled_at
FROM outbound_request o JOIN dead_letter d ON d.ref_id = o.id
WHERE o.interface_id = (SELECT id FROM interface WHERE code='IF-REJ-01')
ORDER BY o.id DESC LIMIT 1;
```

**✅ 预期（逐条勾选）**：

- [ ] `o.status=SUCCESS`——scenario 已放行 200，重放成功；
- [ ] `o.attempt_count=0`——重放前重置尝试计数；
- [ ] `d.status=HANDLED`、`handled_at` 非空；
- [ ] 管理面死信面板刷新后该记录变「已处理」标签、重放按钮置灰；
- [ ] **重复重放拒绝**：对该记录再触发一次重放（直连 curl 或刷新前操作）→ `40001`「已处理」拒绝。

### ② 告警规则（D-M4-5）

> **背景知识**：告警 worker 每 30 秒评估一次启用的规则；规则保存后有 ≤60 秒规则缓存刷新；命中后同一规则 **5 分钟内不重复触发**（冷却）。所以「造出数据 → 看到告警」最长要等约 90 秒，属预期。

**步骤 1：新建规则**：「接口监控」→「**告警**」面板 →「**＋ 新建规则**」：

| 字段（弹窗标签） | 填写值 |
|---|---|
| 规则名 | `死信堆积演示` |
| 指标（下拉） | **死信PENDING堆积（条）** |
| 阈值表达式 | `> 0` |
| 通知渠道 | 默认（首期仅随事件记录，邮件/IM v1.1） |
| 启用 | 是 |

保存（提示：生效延迟 ≤ 60s 缓存刷新）。

**步骤 2：制造数据 + 等待触发**：① 已产生过 PENDING 死信；若已被你重放为 HANDLED，则再造一条（确认 IF-REJ-01 上游路径为 `/reject-supplier`，重启 WireMock 以重置 scenario 后再 curl 一次）→ **等约 30~90 秒**（worker 30s 轮询 + 规则缓存 60s）。

**✅ 预期**：

- [ ] 告警面板事件区出现「**严重**」级事件，内容含当前值（1）与阈值（> 0）；
- [ ] **不重复**：再等 30 秒以上，同一规则不产生第二条事件（冷却 5 分钟生效）；
- [ ] 查库留痕：`SELECT level, metric, message, created_at FROM alert_event ORDER BY id DESC LIMIT 3;` 有对应行。

**步骤 3（可选变体）：内置告警（验签连续失败）**：对种子入站回调接口连发 10 次错误签名（阈值 `verify-fail-alert-threshold: 10`，5 分钟窗口）：

```bash
for i in $(seq 1 10); do
  curl -s -o /dev/null -X POST http://localhost:8080/callback/fastmoss/order-state \
    -H "Content-Type: application/json" -H "X-Timestamp: $(date +%s)" \
    -H "X-Partner-Signature: deadbeef" -d '{"event_id":"evt-x","order_id":"O-1","state":"PAID"}'
done
# 等 30~90 秒 → 告警面板出现「应用 FASTMOSS 回调验签连续失败 10 次（5 分钟窗口）」（rule_id 为空的内置告警）
```

### ③ QPS 限流（D-M4-6，M2 缺口闭环）

> **背景知识**：QPS 用**固定秒级窗口**计数（每自然秒一个桶）：限流=2 时，同一秒内第 3 个请求起被拒；若恰跨秒边界，两个窗口各放 2 个 → 最多看到 4 个 200。**拒绝发生在防护层（请求未进链路）→ 不落运行表、不污染状态机**——这是与「链失败」的本质区别（M0-01 D7）。单实例内存口径，重启清零。

**步骤 1：给应用设限**：「应用管理」→ `M4DEMO` 编辑 → **QPS 限流 = 2** → 保存（**立即生效**，应用配置无缓存）。

**步骤 2：快速连发 6 次**：

```bash
for i in $(seq 1 6); do
  curl -s -o /dev/null -w "%{http_code} " -X POST http://localhost:8080/m4/obs \
    -H "Content-Type: application/json" -d '{}'
done; echo
```

**✅ 预期**：输出 6 个状态码、**200 与 429 混合**（同秒窗口上限 2；跨秒边界时至多 4 个 200）。

**步骤 3：拒绝响应体与「不污染状态机」验证**：

单发一次观察被拒时的响应体（**不要加 `-o /dev/null`** 才能看到信封）：

```bash
curl -s -X POST http://localhost:8080/m4/obs -H "Content-Type: application/json" -d '{}'
# 预期（若被拒）：HTTP 429、信封 code=42901「QPS 限流」
```

```sql
SELECT COUNT(*) FROM outbound_request
WHERE interface_id = (SELECT id FROM interface WHERE code='IF-OBS-01');
-- 预期：记录数增量 = 放行（200）次数；被拒（429）请求无任何运行表记录
```

**步骤 4（可选变体，IP 黑名单）**：编辑 `M4DEMO` →「IP 黑名单」填 `127.0.0.1` → 保存 → 再 curl：

- [ ] HTTP **403**、信封 `code=40103`「来源 IP 被拒（黑名单）」；
- [ ] 移除黑名单 → 恢复 200。

## 常见问题排查（验收中如果卡住）

| 现象 | 最可能原因 | 处理 |
|---|---|---|
| curl 平台路径 404 | 接口未「发布」或平台路径写错 | 接口列表确认状态列=已发布、路径与 curl 一致 |
| 熔断 12 次全程都是 ~3.5s | 开闸点浮动（补偿 worker 重放也计入失败样本，样本凑满 10 才开） | 再连发 4~6 次，必然出现 <0.5s 短路记录 |
| 半开探测返回 502 | priority=1 stub 注册失败（看 WireMock 返回的 JSON 是否含 id）或 sleep 不足 31s | 重新注册 stub；重造失败样本等下一轮 OPEN→HALF_OPEN |
| 对账面板看不到 UNKNOWN 记录 | 面板 10 秒才轮询一次 | 点面板「刷新」按钮；确认查库 `status='UNKNOWN'` 存在 |
| TTL 降级不生效 | UPDATE 回拨语句未命中（WHERE 条件按 interface code + status=UNKNOWN 过滤） | 核对子查询返回的接口 id；确认 status 仍为 UNKNOWN |
| 死信重放后仍 404 | WireMock 重启过、scenario 已重置但接口还没重放；或重放了但看的是旧记录 | 死信面板刷新；查库确认 `d.status='HANDLED'` |
| 告警 90 秒后还没出现 | 规则未启用 / 阈值表达式格式错 / 死信已被重放（指标=0 不触发） | 告警面板规则区确认启用开关；再造一条 PENDING 死信 |
| QPS 全部 200 没有限流 | 应用 QPS 限流未保存成功；或 6 次连发跨了多个自然秒 | 应用列表确认限流值=2；用 `for` 循环一次性快发（不要逐条回车） |
| mvn test 端口冲突 | 验收期间跑了集成测试（同为 18080） | 验收完毕再跑测试 |

## 已知边界（非缺陷，验收时知悉）

- **通知渠道未对接**（邮件 / IM v1.1）：notify_channel 仅随告警事件记录；
- **熔断 / 限流 / 日配额为单实例内存口径**：多实例部署各实例独立（v1.1 分布式）；日配额重启后重新计数；
- **`/test`、`/mock-callback` 调试端点不落 IN 条 call_log**（避免污染成功率口径）；OUT 条照常落库——IN/OUT 条数不配对属预期；
- **`/mock-callback` 自调真实网关**：该路径会产生 IN 条 call_log（走真实网关，非调试直调）；
- **告警规则生效延迟最长约 90 秒**（worker 30s 轮询 + 规则缓存 60s）；
- **IP 黑白名单为精确 IP 匹配**（CIDR v1.1）；来源地址默认取 remoteAddr，生产反代后需开 `trust-xff: true`；
- **P99 统计卡为空**：前端卡片数据来自 overview SQL（调用量/成功率/积压），P99 走 Prometheus Timer（`/actuator/prometheus` 的 `apicenter_gateway_latency_seconds` 分位）——压测与看板接入在 M5。

> 查库可用 Navicat 连 PolarDB（开发实例 alicloud.mysql.polardb.rds.aliyuncs.com，白名单已通），库名 apicenter。

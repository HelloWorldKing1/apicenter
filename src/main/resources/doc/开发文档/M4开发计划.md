## 2. 设计定稿（编码前必读）

### 2.1 D-M4-1 熔断器（CircuitBreaker + 闸门前置）

**组件与位置**：`engine/CircuitBreakerRegistry`（`ConcurrentHashMap<Long, CircuitBreaker>`，key = interface_id）+ 三态状态机。包归属 `engine/`（与 UpstreamInvoker 同包，CLAUDE.md 包结构不变）。

- **粒度定稿**：按 `interface_id` 熔断。接口归属唯一应用（供应商），`interface_id` 维度即「接口 + 供应商」（设计 §6.4），键更简且天然隔离坏接口。
- **三态与参数**（`application.yaml` 前缀 `app.api-center.circuit.*`，含 `enabled` 总开关，默认 true）：

| 参数 | 默认 | 语义 |
|---|---|---|
| failure-rate-threshold | 0.5 | 滑动窗口内失败率阈值。**计数口径 = 每请求一次**（评审定稿）：`invoke` 整体出口计一次成败，@Retryable 内部 4 次重试不逐次计数（耗尽透传异常 = 失败一次）；失败 = 5xx / 429 / 超时连接异常，**4xx 非 429 与 2xx 计成功；链失败不进统计**（未发起上游调用） |
| sliding-window-seconds | 10 | 滑动窗口（时间片计数，实现细节编码定，语义 = 最近 N 秒内成败计数） |
| minimum-number-of-calls | 10 | 窗口最小请求数（不足不开闸，防低流量误熔断） |
| open-duration-seconds | 30 | OPEN 冷却时长 |
| half-open-probes | 2 | 半开放行探测数 |

- **闸门位置**：`OutboundEngine` 在调用 `UpstreamInvoker.invoke` **之前**判断（`doInvoke` 首送与 `replay` 补偿重放两处，抽私有方法共用；M0-03 §1.4「OPEN 时短路、不触发 @Retryable」）。**已核实** `UpstreamInvoker.invoke(OutboundRequestSpec)` 为出站与入站送达共用——闸门收敛在 OutboundEngine 侧，入站送达（InboundEngine 直调）天然不经闸门，与「熔断只覆盖出站」的范围纪律一致。
- **OPEN 短路语义**：
  - 首送短路：不发起调用、不短重试；`outbound_request` 置 COMPENSATING、`next_retry_at = now + min(冷却剩余秒, 3s)`（与补偿固定间隔 3s 口径一致，**已核实** `classifyInvokeFailure` 现状为固定 +3s）、`error_code = 50202`；调用方收错误信封 50202（msg 注明已入补偿队列）。
  - 补偿重放短路：worker 扫到但闸门 OPEN → 只顺延 `next_retry_at` 后返回，**不 incrementAttempt（未触达上游不计尝试）**——否则熔断期间空转消耗重试预算。
  - **顺延无上限为有意语义**（评审定稿）：上游宕机期间消息保留在 COMPENSATING、不耗尽不死信——不因上游故障杀死消息；预留可选 `max-defer-seconds` 兜底（默认无限）。熔断短路恒走 COMPENSATING（设计 §6.4 的 DEAD_LETTER 分支指不可重试类失败，非短路去向）。
- **HALF_OPEN**：冷却结束后的请求进入探测，放行 `half-open-probes` 个走完整路径（含 @Retryable）；期间其余请求仍短路；探测全部成功 → CLOSED，任一失败 → OPEN 重新计时。
- **状态存储**：单实例内存（多实例各自独立熔断，v1.1 分布式，类注释明示）。
- **可观测**：Micrometer Gauge `apicenter.circuit.state{interface}`（0/1/2 = CLOSED/OPEN/HALF_OPEN）+ 状态转换 `log.info`（interface/app/traceId）。
- **测试隔离（关键）**：registry 暴露 `reset()`；既有 M1-M3 的 5xx 用例累计失败可能达开闸条件（如 M1IntegrationTest 多个 5xx 场景同接口累计 ≥10 次）——**集成测试 `@BeforeEach` 调 reset()**，必要时用例内以 `circuit.enabled=false` 关闭，防止熔断污染既有断言（风险 §7.1）。

### 2.2 D-M4-2 UNKNOWN 对账（TTL 自动降级 + 人工置位 + 审计留痕）

- **TTL 自动降级**（M0-03 §3.1 分支二）：`CompensationWorker` 新增 `scanUnknown()`（共用现有定时器与 `retry-worker-fixed-delay-ms`）：`status='UNKNOWN' AND updated_at ≤ now - unknownTtl`（`unknown-ttl-minutes` 配置项**已存在**，默认 10，application.yaml 注释「M4 实现」即本项）→ 逐条转 **COMPENSATING** + `next_retry_at = now+3s`（`error_code` 保持 50401 保留超时成因）+ 写审计（source=TTL）。前置：上游对 biz_id 幂等（ADR5）。limit 100 分批。
- **人工对账端点（补 M2 缺口）**：`POST /api/admin/monitor/outbound-requests/{id}/reconcile`，body `{target: "SUCCESS"|"COMPENSATING", operator, reason}`：
  - 仅 UNKNOWN 态可操作（其余 → 40001）；SUCCESS → status=SUCCESS + error_code 置 null；COMPENSATING → `next_retry_at = now`（立即入队，由 worker 重放）；
  - `operator` 必填（前端弹窗，默认 "admin"——**管理面无用户体系为 M1 现状**，权限校验随管理面整体鉴权 v1.1 统一，本文档明示）；
  - 审计落 `reconcile_audit`（§2.7）。
- **查询入口**：`GET /api/admin/monitor/outbound-requests?status=&bizId=&traceId=&page=`（监控页 UNKNOWN 列表 + 按 bizId/traceId 快速定位失败请求——设计 §4.5「失败诊断」）。
- **自动查询分支**：v1.1（`reconcile_path` 不加列，M0-03 C3）。

### 2.3 D-M4-3 死信管理与重放

- **查看**：`GET /api/admin/monitor/dead-letters?bizType=&status=&page=`（分页过滤）。
- **重放 = 重新入队**（技术架构 §4.7），**复用既有执行路径、零新执行逻辑**（**已核实** `OutboundEngine.replay` 按 `in_payload` 重走链、`InboundEngine.redeliver` 按 payload + `callback_url_snapshot` 重送）：
  - `POST /api/admin/monitor/dead-letters/{id}/replay`：OUTBOUND → 关联 `outbound_request` 置 COMPENSATING + **attempt_count 重置 0**（否则立即再转死信死循环）+ `next_retry_at=now`；INBOUND → `inbound_delivery` 置 PENDING + attempt_count=0 + `next_retry_at=now`（payload / 回调地址快照不变）；
  - `dead_letter` 置 HANDLED + `handled_at=now`；仅 status=PENDING 的死信可重放（HANDLED → 40001）；
  - 重放后由 worker 自然扫描执行；出站重放经熔断闸门（OPEN 则顺延，§2.1）。
- **重放留痕**：`dead_letter.status/handled_at` 本身即痕迹 + 平台日志记 operator（**不新增列**——死信重放为运维操作，审计深度低于对账；如评审要求可扩展 §2.7 审计表）。
- 死信堆积告警归 §2.5。

### 2.4 D-M4-4 调用日志（AOP 双向 + 脱敏 + 异步写）+ 出站 traceId 透传

**记录点定稿**：每次业务请求 2 条——`direction=IN`（网关入口：调用方→平台 / 供应商回调→平台）+ `direction=OUT`（平台→上游 / 平台→回调地址）。**适配器链节点明细不进 call_log**（归 OTel span，§2.5）——每请求 6+ 适配器若各记一条则写入量不可控，且节点耗时语义归链路追踪。**管理面调试端点（`/test`、`/mock-callback`）直调引擎、不经网关 → 无 IN 条**（有意为之：调试流量不污染成功率口径），但 OUT 条经 Invoker 切面照常落库——IN/OUT 条数不配对属预期。

- **切点矩阵**（`aspect/CallLogAspect`，@Aspect + @Around）：

| 条 | 切点 | 元数据来源 |
|---|---|---|
| IN | `GatewayController.dispatch(..)` | 请求 URI/method/headers/body + 响应（信封或裸 ack）+ latency；interface_id/app_id 经 ThreadLocal（引擎填充，见下）；路由未命中（40401）时 interface_id=NULL（schema 允许） |
| OUT | `UpstreamInvoker.invoke(OutboundRequestSpec)` | spec 全量（url/method/headers/body/响应/latency/status_code）+ 元数据字段（见下） |

- **切面顺序定稿**（评审补充）：`@Order` 使 CallLogAspect 位于 @Retryable advisor **之外**——每业务请求恰一条 OUT 记录（短重试不逐次落日志）、Timer 时长含全部重试；此即 C6「一次出站调用 = IN + OUT 两条」的断言口径。
- **`OutboundRequestSpec` 契约扩展（元数据，不改传输语义）**：增加只读属性 `interfaceId / appId / traceId`（默认 0/null）——出站与入站送达组装 spec 时填充。M0-03 §1.2 契约的元数据扩展，本文档定稿（比 ThreadLocal 传递干净，M2 maxRetries ThreadLocal 已有先例教训）。
- **IN 条元数据 ThreadLocal**：`CallLogContext`（interfaceId/appId/traceId），`OutboundEngine.execute` / `InboundEngine.handle` 入口 set、网关切面 finally 读取并 **remove**（防泄漏，踩坑记录回链）。
- **脱敏（落库前完成，内存中不留原始值）**：
  - Header 敏感键（不区分大小写）：`authorization / proxy-authorization / x-api-key / x-auth-token / x-access-token / cookie / set-cookie / x-partner-signature / x-signature` → 值替换「前 4 + **** + 后 4」，长度 < 12 全 `****`；
  - Body：大陆手机号 `1[3-9]\d{9}`（前后非数字边界）→ 前 3 + **** + 后 4；JSON 键名匹配 `(secret|token|password|apikey|api_key|credential)`（不区分大小写）的字符串值 → 同遮蔽；
  - 截断：req_body / resp_body 超 4096 字符截断加 `...[truncated]`（1MB 报文全量落库不可取）。
- **异步批量写**（技术架构 §4.7「异步批量写」，M5 压测验证不阻塞）：`CallLogWriter` 单线程 ExecutorService + `ArrayBlockingQueue(1000)`：主链路只 `offer`（非阻塞）；攒 50 条或 1000ms 批量 `batchUpdate`；队列满丢弃 + `log.warn` + Counter `apicenter.calllog.dropped`（监控数据可容忍丢失，不重试不阻塞）；`@PreDestroy` 尽力 flush 余量。
- **出站 traceId 透传（补 M2 缺口）**：OutboundEngine / InboundEngine 组装 spec 公共头时加 `X-Trace-Id: {traceId}`（平台→上游 / 平台→回调地址，M0-03 §1.2）——WireMock verify / httpbin 回显可断言。

### 2.5 D-M4-5 指标 / 链路 / 告警 / 监控页

**Micrometer 指标**（埋点收敛在 CallLogAspect 内，一次切面两职责）：

| 指标 | 类型 | 维度 | 说明 |
|---|---|---|---|
| `apicenter.gateway.requests` | Counter | direction, interface, app, outcome | outcome ∈ success / business_fail / transport_fail / rejected（限流配额拒绝） |
| `apicenter.gateway.latency` | Timer | direction, interface, app | publishPercentiles(0.5, 0.95, 0.99) + histogram |
| `apicenter.backlog` | Gauge | kind | compensating / pending / unknown / dead_letter（AlertWorker 每轮更新） |
| `apicenter.circuit.state` | Gauge | interface | §2.1 |
| `apicenter.calllog.dropped` | Counter | — | §2.4 |

**链路（Micrometer Observation，OTel 由 starter 桥接）**：
- 基座 `spring-boot-starter-opentelemetry` 已在 pom（**已核实**）；埋点统一用 **Observation API**（不直接绑 OTel SDK，Boot 4 生态路径）；
- `ChainEngine.execute` 外层 Observation（`apicenter.chain`，tag：interfaceId/appId/ifType）+ 六阶段各一子 Observation（`apicenter.chain.stage`，tag：stage 名）——「适配器链每个节点手动 span」（技术架构 §4.7）；
- **MDC**：最前置 Filter `MDC.put("traceId", 业务traceId)`（沿用 X-Trace-Id 透传/生成值，finally remove），日志 pattern 加 `%X{traceId}`；OTel 自身 traceId 独立，span 附 tag `business.traceId` 关联——**跨系统（日志 / 运行表 / trace 导出）统一用业务 traceId 串联**；OTLP 导出保持 false（无 collector），验证走单测（SimpleObservationRegistry 断言 span 与 tag）+ Prometheus 指标。

**告警（alert_rule 落地 + alert_event 载体）**：
- 新 worker `AlertWorker`（`app.api-center.alert-worker-fixed-delay-ms` 默认 30000，`alert-cooldown-minutes` 默认 5）：
  1. 加载 enabled 规则（缓存 60s）；
  2. 计算四指标（**数据源 = SQL 聚合，不用 Micrometer**——Counter 无窗口语义，且单测可离线验证）：

| metric | 语义 | 数据源 |
|---|---|---|
| success_rate | 近 5 分钟出站终态成功率（百分数 0-100） | outbound_request（updated_at 窗口，SUCCESS / (SUCCESS+DEAD_LETTER)）；**依赖新增索引 `idx_outreq_updated`**（§2.7 评审定稿——现有索引 (status, next_retry_at) 对 updated_at 范围过滤只能走 status 前缀扫全部历史 SUCCESS 行，表增长后聚合不可用） |
| p99_latency | 近 5 分钟出站调用 P99（ms） | call_log（direction=OUT，Java 端分位，limit 5000 保护） |
| dead_letter_backlog | 死信 PENDING 堆积数 | dead_letter 计数 |
| retry_backlog | 待重试积压（COMPENSATING + PENDING） | outbound_request + inbound_delivery 计数 |

  3. threshold 解析：`<op> <number>`（op ∈ `< <= > >=`，如 `< 95`、`> 100`）；metric 决定语义与单位；非法表达式 → 该规则跳过 + `log.error`（不崩 worker）；
  4. 命中且冷却期外（rule 维度 5min）→ 插 `alert_event`（§2.7）+ `log.warn`；**通知渠道 notify_channel 首期仅随事件记录（context 内），SMTP/IM 对接 v1.1**（范围纪律）；
  5. **内置告警（rule_id=NULL）**：验签连续失败——HMAC 回调验签失败按 app 维度 5 分钟窗口计数 ≥10 → alert_event（metric=verify_fail_streak）。M3 遗留的「连续验签失败告警」由此闭环；**临时封禁仍属安全能力（多鉴权批 / v1.1），不在 M4**。

**监控页（MonitorController + MonitorStatsService + Monitor.vue 接真数据）**：
- `GET /api/admin/monitor/overview`：统计卡四张（原型形态）——今日调用量（call_log IN 条当日计数）/ 今日成功率（今日 outbound_request 终态占比）/ P99（Timer percentile 当前进程值，卡片标注「实时」）/ 积压三元组（待补偿 / 死信 / 对账中）；**惰性缓存 TTL 30s**（请求触发、过期才聚合，避免定时空转）；
- `GET /api/admin/monitor/call-logs?traceId=&interfaceId=&page=`（分页过滤）；
- `GET /api/admin/monitor/alerts?page=`；
- 对账 / 死信端点见 §2.2 / §2.3；
- **前端**：统计卡 + 调用日志 + 告警三面板平移原型；**对账（UNKNOWN 列表 + 置位操作弹窗）与死信（列表 + 重放按钮）两面板按设计方案 §4.5「失败诊断与对账查询」扩展**（原型监控页无此二面板，语义以设计方案为准）。

### 2.6 D-M4-6 接入层限流 / 配额 / IP 黑白名单（M2 补缺）

- **位置**：网关入口（GatewayController，路由命中 + 应用启用校验之后、`createRecord` 之前）——**拒绝发生在链执行与落库之前，outbound_request 无记录（不污染状态机，M2 测试点断言口径）**；**响应形态（已核实定稿）**：与既有 40102 同模式——网关恒 `ResponseEntity.ok`，统一信封 HTTP 200 + code=42901/42902/40103；
- **QPS**：`app.qps_limit > 0` → 内存固定窗口计数（appId + 秒级 key）超限 → 统一信封 `42901`（QPS 限流）。固定窗口有交界突刺（最坏 2×limit），保护语义达标，取简单实现（注释明示，滑动窗口 v1.1）；
- **日配额**：`app.daily_quota > 0` → AtomicLong 按 (appId, yyyyMMdd Asia/Shanghai) 计数滚动重置，超限 → `42902`；
- **IP 黑白名单**：`ip_blacklist` 命中 → `40103`（401xx 鉴权段内新增：来源 IP 被拒）；`ip_whitelist` 非空且未命中 → 同 40103；匹配为精确 IP 文本（IPv4/IPv6），**CIDR 不支持（v1.1）**；来源地址取 `remoteAddr`，`app.api-center.trust-xff`（默认 false）开启后取 X-Forwarded-For 首值（生产反代后置 true，防伪造 XFF 绕过）；
- **单实例内存口径**：QPS 窗口 / 日配额重启清零（日配额重启后重新计数，偏差可接受，注释与文档明示；多实例 v1.1）；
- 拒绝同时打 Counter（outcome=rejected）。

### 2.7 schema 变更汇总（2026-09-04 评审确认，16 → 18 张 + 1 索引）

| 表 | 列 | 用途 |
|---|---|---|
| `reconcile_audit`（17） | id / outbound_request_id / from_status / to_status / source(MANUAL\|TTL) / operator / reason / created_at；KEY (outbound_request_id) | 对账审计（M0-03 §3.2「谁、何时、UNKNOWN→?」；TTL 降级同记，operator="TTL-WORKER"） |
| `alert_event`（18） | id / rule_id（NULL=内置告警）/ metric / level(WARN\|CRITICAL) / message / context(JSON 详情) / created_at；KEY (created_at)、KEY (rule_id) | 告警事件持久化（监控页展示 + 冷却判重 + 通知预留） |
| `outbound_request` 加索引（评审新增） | `KEY idx_outreq_updated (updated_at)` | AlertWorker success_rate 5 分钟窗口聚合（现有索引无法支撑 updated_at 范围过滤，只能走 status 前缀扫全部历史 SUCCESS 行） |

**加表而非加列 / 复用的理由**：outbound_request 加 operator 列只留末次对账且侵入运行热表；复用 call_log 则 direction/method 列语义被绑架（call_log 列注释已定 IN/OUT）。两表均为低频写（对账 / 告警事件），独立表不动既有 16 张。**同步义务**：表结构设计.html + schema.sql + CLAUDE.md「16 张表」表述（§7 文档同步）。

## 5. 手动验收方案（约 35 分钟）

> 全程管理面 + curl + 查库；模拟上游用本地 WireMock（stub 随仓库 `src/test/resources/m4-manual-stubs/`，M4.5 交付；**与集成测试同端口 18080，验收期间勿同时跑 `mvn test`**）。查库 Navicat 连 PolarDB 开发实例。

stub 约定：

- `/breaker-supplier`：scenario 前 20 次 500 → 之后 200（熔断开闸与恢复演示）；
- `/slow-supplier`：fixed-delay 5000ms（> 默认读超时 3000，UNKNOWN 制造）；
- `/delivery-ok`：200（复用 M3 stub 结构，独立目录）。

**阶段一：可观测（约 10 分钟）**

1. curl 调黄金用例 IF-FM-001 两次 → Monitor 页统计卡出值（今日调用量 ≥2、成功率、P99、积压全 0）→ 调用日志表出现 4 条（2 次 × IN/OUT）→ 按 traceId 过滤联动；查库：
   ```sql
   SELECT direction, interface_id, status_code, latency_ms, req_headers, LEFT(req_body, 120)
   FROM call_log ORDER BY id DESC LIMIT 4;   -- Authorization 已遮蔽；trace_id 两条相同
   ```
2. curl `/actuator/prometheus | grep apicenter_` → requests / latency / backlog / circuit 指标齐全。

**阶段二：容错（约 15 分钟）**

1. **熔断**：管理面建演示应用 + 接口指 `http://localhost:18080/breaker-supplier`（Noop 鉴权，发布）→ 脚本连调 12 次 → 观察响应从「约 15 秒后 50201（5 次短重试耗尽）」变为「**立即** 50202」、查 Gauge state=1、查库 COMPENSATING 记录 next_retry_at 顺延而 attempt_count 不再增长 → 等 30 秒再调 → stub 已放行 → 恢复 200 / state=0；
2. **人工对账**：接口改指 `/slow-supplier` → 调用（约 3 秒）→ 50401 UNKNOWN → Monitor「对账」面板看到该记录 → 置位「已到达」（operator 填写）→ 状态 SUCCESS；再造一条 → 置位「未到达」→ COMPENSATING → worker 重放（上游已恢复地址则成功）；查 `reconcile_audit` 两条 MANUAL；
3. **TTL 降级**：再造 UNKNOWN → 查库手工回拨 `updated_at` 10 分钟前（`UPDATE outbound_request SET updated_at = DATE_SUB(NOW(), INTERVAL 11 MINUTE) WHERE id=?`）→ 等 worker 一轮 → 自动 COMPENSATING + `reconcile_audit` 一条 source=TTL。

**阶段三：死信 / 告警 / 限流（约 10 分钟）**

1. **死信重放**：接口指 4xx stub（或错 token 走 401）→ 调用 → DEAD_LETTER + dead_letter 落库 → Monitor「死信」面板 → 重放（上游已切回 200 地址）→ outbound_request 回 COMPENSATING → worker 补偿 → SUCCESS、死信 HANDLED；
2. **告警**：建 alert_rule（metric=dead_letter_backlog，threshold `> 0`）→ 再造一条死信 → 等 30 秒 → Monitor「告警」面板出现事件 → 5 分钟内不重复（冷却）；查 `alert_event`；
3. **限流**：演示应用配 qps_limit=2 → 快速连发 5 次 → 部分 42901 + 查库 outbound_request 无对应记录；应用黑名单加 `127.0.0.1` → 40103 → 移除恢复。

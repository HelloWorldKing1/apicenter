# M2 手动验收测试方案

> 用途：M2 出站链路的手动端到端验收（配合自动化测试 34/34 的补充验证），全程约 20 分钟。
> 模拟上游选择 **httpbin.org**：无需鉴权、可回显请求（证明请求真实发出）、可模拟 4xx/5xx/超时（已验证本机连通，2026-09-02）。
> 真实 fastmoss 联调见阶段三（需真实 token）。

## 前置：启动

```bash
# 终端 1：后端
mvn spring-boot:run          # 8080，seed 幂等（fastmoss 已存在则跳过）

# 终端 2：前端
cd frontend && npm run dev   # http://localhost:5173
```

## 阶段一：管理面浏览（验收 M1，约 5 分钟）

1. 打开 http://localhost:5173：
   - **应用管理**：看到 `FastMoss`（种子导入）→ 点行进入详情 → 凭证区显示 `****oken`（遮显）、状态 ACTIVE → 点「更新凭证」输入任意值保存，观察旧凭证转 ROTATING（M0-04 并存 24h 演示）；
   - **接口管理**：IF-FM-001 已发布 → 点「编辑」查看：入站/出站参数各 4 条、字段映射为空（整体透传）、RESP 字段 total/list、绑定 ADP-101（Bearer）+ ADP-201（信封）；
   - **适配器**：鉴权/协议/报文三类 tab 各看一遍；
2. **CRUD 闭环**：新建应用「测试应用」→ 建分组 → 建接口（出站、路径 /test/demo）→ 发布 → 删除（应用/分组/接口各走一遍增删）。

## 阶段二：执行面调用（验收 M2 黄金用例四分支，约 10 分钟）

在管理面新建**演示应用**（全部走前端操作）：

| 项 | 值 |
|---|---|
| 应用 | 标识 `HTTPBIN`、服务地址 `https://httpbin.org`、鉴权留空（Noop 直通）、报文适配器留空 |
| 凭证 | 无（Noop 鉴权） |
| 分组 | 演示分组 |
| 接口① 成功 | 标识 IF-DEMO-ECHO、出站、POST、平台路径 `/demo/echo`、上游路径 `/anything`、空映射、发布 |

**① 成功路径（等价 G1）**：新建终端 3 调：

```bash
curl -X POST http://localhost:8080/demo/echo -H "Content-Type: application/json" -d '{"hello":"world"}'
```

预期：统一信封 `{"code":0,"msg":"ok","data":{...}}`，data 是 httpbin 回显——`"headers"` 能看到请求头、`"data"` 是原样透传的 `{"hello":"world"}`。**证明：配置 → 链执行 → 出站 → 反向适配 → 统一信封，整条链路真实打通。**

**② Bearer 凭证头验证**：给 HTTPBIN 应用补出站凭证（凭证管理 → 更新，值填 `demo-token`），应用「供应商签名适配器」选 ADP-101（Bearer）。再调一次 ①，httpbin 回显的 `headers.Authorization` 应为 `Bearer demo-token`。

**③ 4xx 死信（等价 G2）**：建接口②（上游路径 `/status/401`，平台路径 `/demo/dead`）→ 调用 → 响应 `"上游拒绝…死信编号 N"`。查库：

```sql
SELECT id, status, error_code FROM outbound_request ORDER BY id DESC LIMIT 3;  -- DEAD_LETTER
SELECT * FROM dead_letter ORDER BY id DESC LIMIT 2;                              -- 死信记录
```

**④ 5xx 补偿（等价 G3）**：建接口③（上游 `/status/500`，路径 `/demo/comp`）→ 调用 → 约 1 秒后返回 `"已进入补偿队列"`（背后短重试 4 次）。此后**每 3 秒**补偿 worker 自动重放一次，反复查 `outbound_request`：`attempt_count` 持续递增；重试 5 次耗尽后自动转 `DEAD_LETTER` + 死信落库。想看「补偿成功」：把接口③的上游路径改成 `/anything` 再等一次 worker 扫描 → 状态转 `SUCCESS`（演示配置变更即时生效）。

**⑤ 超时 UNKNOWN（等价 G4）**：建接口④（上游 `/delay/5`，延迟 5 秒 > 3 秒读超时）→ 调用（约 3 秒）→ 返回 `"上游超时，结果待对账（UNKNOWN）"` → 查库状态 `UNKNOWN`、error_code `50401`。

## 附：接口测试按钮（管理面调试工具）

接口详情 → 「测试接口」：无需 curl 即可在管理面内真实走一遍出站链路。

- **请求体**：自动预填接口入站 Body 模板（可编辑）；发送后右侧深色响应区展示统一信封（成功绿色 / 失败红色，含死信编号、补偿队列、UNKNOWN 等诊断信息）。
- **语义**：与接入层路由等价（链执行 + 状态机全分支），但不做 PUBLISHED / 方法校验（草稿态也可测）；每次测试落一条 `outbound_request` 记录（biz_id 前缀 `TEST-`）。
- **典型用途**：配置完成后先点「测试接口」验证链路（如 fastmoss 在占位 token 下应看到 401 → 死信诊断），再走阶段二 / 阶段三的外部 curl 验证。

## 阶段三（可选）：真实 fastmoss 联调

拿到真实 token 后：管理面 → FastMoss 详情 → 凭证管理 →「更新凭证」填入真实 token → 调：

```bash
curl -X POST http://localhost:8080/fastmoss/creatorList -H "Content-Type: application/json" -d '{"filter":{"seller_id":"7494312521977267257"},"orderby":[{"field":"units_sold","order":"desc"}],"page":1,"pagesize":1}'
```

预期与黄金用例断言一致（开发计划 §2.3）：`code=0`、`data.total=822`、`data.list[0].nickname="megan!"`（如 fastmoss 数据未变）。

## 验收对照

| 步骤 | 对应出口标准 |
|---|---|
| 阶段一 | M1 配置闭环（应用/分组/接口/适配器/凭证全走通） |
| ①② | M2 G1 成功路径 + Bearer 出站鉴权 |
| ③ | G2 4xx → 死信 |
| ④ | G3 5xx → 短重试耗尽 → 补偿 worker 兜底 |
| ⑤ | G4 超时 → UNKNOWN 对账 |

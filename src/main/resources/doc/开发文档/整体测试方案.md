## 1. 为什么需要这套测试（测试目标与原理）

| 层 | 被测什么 | 回答什么问题 | 手段 |
|---|---|---|---|
| 配置面 | 应用/分组/接口/适配器/凭证 5 类配置的 CRUD、状态机、互斥校验、下拉联动 | 配得对、存得对、错配拦得住 | 手动 + M1 自动化 |
| 链路正确性 | 两核心链路（出站 Flow A / 入站 Flow B）端到端 | 「配置 → 链执行 → 真实收发 → 状态机」整条通路通不通 | 手动 + M2/M3/M4/M5 集成测试 |
| 语义正确性 | 字段映射 6 操作、协议 JSON/XML、信封剥壳、RESP 白名单、ACK 回执 | 报文对不对、字段转得准不准 | MappingEngine/Xml/Envelope 单测 + 端到端 |
| 容错 | 状态机全分支：4xx 死信 / 5xx 补偿 / 超时 UNKNOWN / 熔断 / 限流 | 供应商乱来系统不乱、账目可对 | 手动 + M4 自动化 |
| 可观测 | call_log 双向、脱敏、traceId 贯穿、指标、告警、对账/死信面板 | 出事查得见、查得全、能收口 | 手动 + Monitor/Dashboard |
| 版本快照/回滚 + 绑定切换 | 快照/回滚/绑定即实例切换/事件即时失效/留痕 | 变更可追溯、回滚可用、切换即时生效 | 手动 + M5 自动化 |
| 性能稳定性 | 吞吐、P99、异步写零丢弃、补偿批量扫描 | 线上扛得住、不拖垮主链路 | wrk 压测（D-M5-3） |
| 安全健壮 | XXE、SSRF、报文大小、脱敏、签名验签、乐观锁 | 不裸奔、不漏密钥、不脏数据 | 自动化 + 手动抽查 |

**贯穿全项目的三条原则（来自设计定稿，测试预期都以它为据）：**
1. **链失败与防护拒绝不污染状态机**（M0-01 D7 / D-M4-6）：解码/映射/编码/验签失败、QPS/日配额/IP 拒绝 → 只落 call_log，不写 outbound_request / inbound_delivery。验证「有/无记录」是常见断言点。
2. **收到即回 ack、与送达解耦**（§5.5/§6.1）：入站送达失败也回 ack 给供应商，由补偿 worker 重送——预期里「ack 成功但 delivery PENDING」是正常态，不是 bug。
3. **失败分类器口径**：5xx/429 → 短重试耗尽 → 补偿（COMPENSATING）→ worker 重放；4xx（非 429）→ 死信不重试；读超时/连接异常 → UNKNOWN 对账。

**验证预期结果（每个分支测完，按下面对照核对，三条同时可见 = 自检 ④⑤⑥ 全过）：**

## 4. 管理面配置用例库（M1——五模块增删改查 + 状态机 + 凭证轮换）

> 每个场景：**目的** = 验证什么业务规则；**操作** = 填什么/选什么；**预期**。查库 SQL 统一见 §11.2。

### C1 应用 CRUD 与字段口径
- 目的：应用字段落库、弹窗内凭证卡片联动、状态机 DRAFT→ENABLED→DISABLED→CANCELLED、停用即拒请求。
- 操作：应用管理 →「＋ 新建」：
  - 应用标识 `TESTAPP01`（规则：字母/数字/`_`/`-` 1~32，填 `中文` 应被拒）、名称 `测试供应商`、服务地址 `http://localhost:18080`（**本地 WireMock 根地址**，别填 8080 自己）、供应商签名适配器/回调验签/默认报文三下拉**留空**（= Noop/继承语义，此时凭证卡片不出现）、QPS 限流与日配额留 0（不限）、IP 白名单/黑名单留空、描述随意 → 保存 → 状态「草稿」；
  - **凭证卡片联动**（v0.2）：把「供应商签名适配器」选成任一非 Noop 实例（如 `Bearer Token`）→ 下方**就地展开凭证卡片**（字段取该 impl 的 secret 字段；未声明时退化为单「密钥 / Token」框）；填值保存 → 详情凭证区出现 ACTIVE（尾 4 指纹）；留空保存 → 不改动凭证；
  - 行操作「启用」→「已启用」→ 直接 curl 平台路径应 200（网关放行）→「停用」→ 同一 curl 应返回 40102「应用已停用」→ 验证停用即拒；「启用」恢复。
- 预期：列表/详情字段与填一致；**列表两列并存：「ID」= 数字主键（app 表 2026-09-12 新增 `id BIGINT AUTO_INCREMENT UNIQUE`）、「应用标识」= app_id**（对外契约仍用 app_id）；停用后拒绝且**不落运行表**（§11.2 SQL-1 查无新行）。
  > 2026-09-12：应用列表的「凭证」角标列已按使用反馈移除（后端 `hasOutboundCredential` / `hasCallbackCredential` 字段保留，供接口复用；凭证状态改由应用弹窗卡片与详情抽屉呈现）。
- 常见：标识重复/非法标识被拒；停用后忘了启用 → 后续链路全 40102（先查应用状态）。

### C2 凭证配置与轮换（M0-04 定稿，出站与回调两类 kind 独立；v0.2 入口内联到应用弹窗）
- 目的：弹窗内首次配置 + 留空不改动 + ACTIVE→ROTATING（并存 24h）→ACTIVE/RETIRED 迁移、验签并存期间新旧都收。
- 操作（**入口一：应用弹窗 → 凭证卡片**）：应用管理 → 点应用行「编辑」→ 选供应商签名适配器（非 Noop）→ 卡片出现 → 填 `token-v1`（写入方式保持「更新」）→ 保存 → 卡片状态行变 `ACTIVE ****v1`；
  - 不填任何凭证再保存 → 指纹与状态**不变**（留空 = 不改动）；
  - 再填 `token-v2` → 保存 → 卡片提示「ROTATING · 并存至 …」，详情凭证区可见 v1 ACTIVE + v2 ROTATING；
  - 「重置」需二次确认，确认后旧值**立即** RETIRED（无并存期）；
  - 独立验证**回调验签凭证**：选回调验签适配器 → 卡片出现 → 填 `cb-secret` —— 与出站互不影响。
- 操作（**入口二：详情抽屉高级轮换**）：应用管理 → 点应用行 → 详情「凭证」区：`prepare` 生成随机值（明文仅本次回显）→「激活」→ 旧 ACTIVE 转 ROTATING（24h）→「完成轮换」；出站签名切换为 v2（WireMock 看 Authorization 头值变化可证）。
- 预期：遮显规则 = 只显示 `****` + 尾 4 位指纹，**永不回显明文**（含编辑回显）；两 kind 各自成链；**过期的 ROTATING 不再阻塞新一轮「生成」**（E2 修复点）。
- 原理：凭证实时读（M5 明确不进链缓存）→ 轮换即时生效，无需任何缓存失效。

### C3 分组管理
- 目的：分组从属于应用、应用内名称唯一、删除守卫。
- 操作：分组管理 → 新建：所属应用选 `TESTAPP01`（或直接在各应用下的「分组详情」内联创建）→ 名称 `演示分组` → 排序 0。再建同名分组应被拒；该分组下建了接口后删分组应被拒（先删/移接口）。

### C4 适配器管理（impl 目录驱动表单）
- 目的：三类适配器注册表、参数按 impl schema 动态渲染与校验、凭证类参数不落适配器配置、**D6 (impl,version) 维度**启用约束。
- 操作：适配器管理 → 顶部 tab 全部/鉴权/协议/报文 →「＋ 新建适配器」。关键填值示例（**填什么随 impl 走**，后端 `AdapterImplCatalog` 提供动态表单）：
  - **鉴权 - HMAC 签名**（HmacAuthAdapter）：标识 `ADP-T-HMAC`、名称随意、类型=鉴权、实现=`HMAC 签名`、签名算法选 `HMAC-SHA256`、签名 Header 名选 `X-Signature`、时间戳容差(秒)=`300`、防重放=关、版本 `1.0`、启用=开；
  - **报文 - 信封报文适配**（EnvelopeMessageAdapter）：实现=信封报文适配、业务数据容器 `data`、供应商状态码字段 `code`、成功值 `0`、错误码映射可留空、消息字段 `message`、兜底错误码留空；
  - **凭证类字段**（ApiKey 的 apiKey 等）不会出现在参数表单——输入框为灰字只读提示「凭证值请在『应用管理 → 新建/编辑应用 → 凭证卡片』中维护」；若强行把密钥写进 params 提交，后端显式报「凭证类参数不落适配器配置，请在应用凭证中配置」——这是**特性**不是缺陷；
  - **D6' 语义（2026-09-08 定稿）**：同 (impl, version) **允许多条启用并存**（实例靠 id + `adapter.name` 区分）；`adapter.name` 全表唯一（重名拒绝）；多实例并行首选同 impl 不同 version（version 仅记录，不参与路由——绑定即实例）。
- 预期：协议类实例（JSON/XML 编解码）即使建了也不参与绑定（自动推导），接口高级区下拉只会出现 鉴权 / 报文 实例。

### C5 接口 CRUD 与类型互斥（最易填错，逐字段核对）
打开接口管理 →「＋ 新建」。**先选类型**（OUTBOUND=出站中转 / INBOUND=入站回调），随后表单互斥联动：

- 入站：必填**回调地址**（完整 URL 且非内网，SSRF 白名单校验）、禁止供应商接口路径、只许 ACK 字段、绑定 MESSAGE+CALLBACK_AUTH、**必填出站侧（送达报文）参数**；
- 类型互斥字段在切换类型时自动清空（前端 `onTypeChange`）；已保存接口改类型会二次校验。
- 状态行操作：草稿/下线 →「发布」；已发布 →「下线」；重复发布/重复下线被拒。详情「测试接口」只对出站显示、「模拟回调」只对入站显示（按钮门控）。
- 通用字段：方法 POST/GET/PUT/DELETE；协议入/出 JSON|XML（勾「入站=出站」联动）；读超时(ms) 默认 3000；最大重试默认 4；透传开关（出站）= 映射为空整体转发。

## 5. Flow A 出站链路端到端用例（M2/M3 链路 + M4 容错）

> 分册：《M2手动验收测试方案.md》（httpbin 成功/Bearer/死信/补偿/超时）、《M4手动验收测试方案.md》（熔断/对账/TTL/死信重放/QPS/IP）。以下给出**统一场景与填值基准** + 分册引用。

### F1 应用+接口「黄金用例」四分支（映射空=透传；Body 区出站侧选 json 按钮填 raw 报文）

在管理面新建（全部走前端；WireMock 扮演供应商时应用服务地址填 `http://localhost:18080`）：

| 场景 | 应用 | 接口 code | 平台路径 | 供应商接口路径 | 期望分支 |
|---|---|---|---|---|---|
| ① 成功直通 | `M4DEMO` | IF-O-OK | `/t/ok` | `/echo-ok`（m4 stub 200） | SUCCESS code=0 |
| ② 4xx 死信 | 同上 | IF-O-DEAD | `/t/dead` | 自注册 401 stub（§11.3 模板把 status 改 401）→ 供应商接口路径填该 stub 路径 | DEAD_LETTER + 死信 |
| ③ 5xx 补偿 | 同上 | IF-O-COMP | `/t/comp` | `/breaker-supplier`（m4 stub 恒 500） | 短重试耗尽 → COMPENSATING → worker 重放 |
| ④ 超时 UNKNOWN | 同上 | IF-O-UNK | `/t/unk` | `/slow-supplier`（m4 stub 5s > 3s 读超时） | UNKNOWN 50401 |
| ⑤ 熔断 | 同上 | IF-O-BRK | `/t/brk` | `/breaker-supplier` | 连续失败→OPEN→50202 短路 |

> 注：② 与 ③⑤ 共用 M4DEMO（WireMock 扮演的供应商）即可闭环，不必引入 httpbin——httpbin 的 `/status/401` 用法留在 M2 分册原场景（HTTPBIN 应用）。

**每分支必验三点：调用方信封、库状态机轨迹、call_log 留痕。**
- 调用（信封校验）：`curl -s -X POST http://localhost:8080/t/ok -H "Content-Type: application/json" -d '{"hello":"world"}'`
- 状态机 SQL（§11.2 SQL-2/SQL-3）：按 app_id 查 status/attempt/error_code/next_retry_at 序列；
- 日志对照：M2 分册给出 5xx 补偿全轨迹日志样例（attempt 1→5 递增、耗尽转死信），照抄核对。

### F2 熔断三态（M4 核心，详见 M4 分册阶段二①）
- 填值与前置：接口指向 `/breaker-supplier`（恒 500），**连发 ≥12 次**（窗口 10s/最小 10 次/失败率 50% 默认参数）触发 OPEN；
- 观察：前几次每次 ~3.5s（4 次短重试耗尽），之后变 <0.5s 秒回——**OPEN 短路**；库状态 50202/COMPENSATING 顺延（不 incrementAttempt，防熔断期空转消耗重试预算）；
- 恢复验证：WireMock `priority=1` 注册 200 stub（§11.3 模板）→ sleep 31s（OPEN 30s）→ 放行 2 次探测 → HALF_OPEN→CLOSED 恢复；期间原 COMPENSATING 行由补偿 worker 补做成功。
- 原理：闸门在 @Retryable Invoker 调用前，按「接口+供应商」粒度；计数口径=每请求一次（内部重试不逐次计数）。

### F3 UNKNOWN 对账 + TTL 降级（M4，详见 M4 分册阶段二②③）
- 造数：调超时接口（读超时 3s < /slow-supplier 5s）→ 得 UNKNOWN；
- **人工对账**：Monitor 页「对账（UNKNOWN）」行 → 实际到达则「置为已到达（SUCCESS）」，未到则「置为未到达（COMPENSATING）」→ 弹窗**操作人必填**（`admin`）、依据说明可选（审计用）→ 保存；查 `reconcile_audit` 表 source=MANUAL 落一行（operator/reason 入库）；
- **TTL 降级**：不人工处理，等 10 分钟（`unknown-ttl-minutes`）→ 自动按 COMPENSATING 续期 → 审计 source=TTL；
- 语义：对账双来源均写审计，可追溯是谁/系统何时裁定的。

### F4 死信重放（M4 阶段三①）
- 前置：仓库/验收遗留 PENDING 死信可直接演示（biz 指向本地 WireMock 则安全重放）；
- 操作：Monitor 死信区 → PENDING 行「重放」→ 该死信**立即置 HANDLED**（再次重放被拒：“死信已处理（HANDLED）”），关联运行记录置回 COMPENSATING（attempt 清零）→ ≤3s 后补偿 worker 按 in_payload 重走整链 → 供应商已恢复则 SUCCESS、仍失败则再次耗尽产生新死信；
- 重放语义：按死信 ref_id 关联的运行记录 in_payload 重走整链（配置/凭证取最新），不是简单转发原始响应。

### F5 QPS / 日配额 / IP 名单（M4 阶段三，防护层语义）
- QPS：应用编辑把 QPS 限流填 `50` → `wrk -t4 -c200 -d10s`（或 200 并发 curl）→ 通过量≈50/s、其余 42901「触发限流」；**拒绝不落运行表**（SQL-1 验证）。
- 日配额：日调用量上限填 `10` → 调 11 次 → 第 11 次 42902；重启后清零（单机内存口径）。
- IP 名单：IP 黑名单填 `127.0.0.1` → 本地调用 40103 拒绝；白名单填其它 IP → 本地调用被拒（同理由）。
- 单实例内存口径边界：多实例各自计数、QPS 固定秒级窗口交界最坏 2×limit——属**已知语义**非缺陷。

### F6 报文语义深度（映射/信封/XML，自动化已覆盖，手动抽查 1~2 例）
- 信封剥壳：应用默认报文适配器绑 Envelope（data/code/successValue=0）→ 供应商回 `{"data":{...},"code":"0"}` → 调用方收到 data 即业务内容、非 0 业务码透传且状态机仍 SUCCESS（C2 口径）；
- RESP 白名单：声明 RESP 字段后 data 只含声明字段（XML `ts` 未声明被滤）；清空声明=不过滤；
- XML：见 M3 分册阶段二（同名 item 合并数组、number 类型解析、ts 过滤差异演示）；**真实端点验证见 §6.6（USGS atom / hnrss 可解码，httpbin `/xml` 为混合内容 40002 反例，均免密钥）**；
- 每改一处映射/绑定后**先点「测试接口」再 curl**（详见 §8 chainTrace 一节）——这是 M2 起养成的快速验证习惯。

### F7 动态映射 6 操作手动抽查（M-1，补齐 UI 层逐 op 覆盖）
> 自动化已有 MappingEngineTest 14 例全 op + null_strategy 矩阵；M0-02 附录有 24 例预期输出矩阵。此处只要求**经管理面建接口、逐 op 各建一条规则做端到端冒烟**（同一接口重复编辑会生成版本快照，正好顺带验证 §8 V1）。建议在 IF-M-OP 接口（供应商 `/echo-ok` 回显，用 WireMock `/__admin/requests` 看实际出站 body 最直观）上逐轮执行：

| op | 规则填法（source / target / param） | 入站 → 预期出站（查 WireMock 收到的 body） | 语义原理 |
|---|---|---|---|
| rename | `state` → `order_state`（param 空） | `{"state":"PAID"}` → `{"order_state":"PAID"}` | 保形重命名 |
| typeCast | `qty` → `qty_num`，param=`INT` | `{"qty":"5"}` → `{"qty_num":5}`（数字） | 按类型注册表转换（TypeRegistry） |
| enumMap | `state` → `order_state`，param=`PAID→已支付` | `{"state":"PAID"}` → `{"order_state":"已支付"}` | 枚举映射（多对用逗号分隔：`1→0, 2→1`） |
| default | source 空 → `region`，param=`CN` | 任意入站 → 恒含 `{"region":"CN"}` | 常量注入（仅 default 可空 source） |
| condition | `state` → `state`，param=`state == 'PAID'` | PAID → 保留原值；其他值 → 按 null_strategy（KEEP=出站不含该字段） | Aviator 条件过滤（纯解释器防注入）；表达式内以入站字段名引用 |
| aggregate | `items`(数组) → `total`，param=`SUM` | `{"items":[1,2]}` → `{"total":3}` | source 须数组；SUM/MAX/MIN/CONCAT[:sep] |

> 入站字段含敏感键（token 等）时可在 Monitor 调用日志里顺带核对 body 已脱敏（§7）。

### F8 健壮性抽查（报文超限 / 长度越界 / SSRF）
- **报文 >1MB → 40002 且不落运行表**：双道防护（BodySizeLimitInterceptor 按 Content-Length 预检 + GatewayController 读后兜底）。
  ```bash
  head -c 1100000 /dev/zero | tr '\0' 'a' > /tmp/big.json
  curl -s -X POST http://localhost:8080/t/ok -H "Content-Type: application/json" --data-binary @/tmp/big.json
  # 预期：40002 报文超限信封；SQL-1 验证 outbound_request 无新行
  ```
- **变更说明/回滚字段越界 → 友好 400 而非 500**（M5 H2 修复回归）：PUT 带超 250 字 `X-Change-Note` → 40001「变更说明超长」；回滚 operator/reason 超 100 字 → 400 校验信息；
- **SSRF（回调地址）——按开关状态断言（重要）**：`application.yaml` 当前 `callback-allow-private: true`（**dev 默认放行本地回环**，本地 WireMock stub 验收的前提，勿改）→ 入站接口回调地址填 `http://127.0.0.1:18080/x` **保存通过**（属预期）；真实验证拒绝需把开关改 `false` 后重启后端（可选，自动化 CallbackUrlValidatorTest 4 例为主防线）；出站供应商接口路径带 `http://` 或 `..` → 保存被拒（C5 已含，此处做负向复核一次即可）。

## 6. Flow B 入站回调链路端到端用例（M3 能力，分册含全填值表）

> 分册：《M3手动验收测试方案.md》阶段三（逐字段 4 张表：凭证/适配器/应用绑定/接口六段）。这里给最小闭环基线 + 关键语义。

**最小闭环（照 M3 分册配置一遍，应用沿用 `M3DEMO`，与 §3 隔离命名 / 清理 SQL 对齐）：** CALLBACK 凭证（值 `demo-secret`）→ HMAC 回调验签实例 ADP-HMAC-DEMO（HMAC-SHA256 / X-Partner-Signature / 容差 300）→ 应用编辑绑定为「回调验签适配器」→ 入站接口 IF-CB-01（回调地址 `http://localhost:18080/delivery-ok`，IN 参 3 条 / OUT 送达参 3 条，保形映射 3 条 rename，ACK 字段 returnCode number + returnMsg string，CALLBACK_AUTH 绑定留空=继承应用默认）→ 发布。

| 用例 | 动作 | 预期（含为什么） |
|---|---|---|
| B1 正常闭环 | 详情「模拟回调」→ 发送 | 页面显示供应商视角 ack `{"returnCode":0,"returnMsg":"success"}` + 送达状态 ACKED；查 inbound_delivery 新行 ACKED、payload=送达报文（映射后 order_state） |
| B2 验签失败 | curl 手发错签名 / 时间戳超容差 | HTTP 401（40100 签名错误 / 40101 过期）；**查库无新行**（验签失败不落运行表 D7）；call_log 有记录可查 |
| B3 ack 与送达解耦 | 回调地址改 `/delivery-flaky`（前 8 次 500 后放行）→ 模拟回调 | ack 仍即时回（供应商不重发）；库 PENDING attempt=1 → worker 每 3s 重送递增 → 放行后 ACKED——手动可见 PENDING→ACKED |
| B4 快照漂移防护 | 回调地址改 `/delivery-fail`（恒 500）→ 重送将耗尽前把接口回调地址改 `/delivery-ok` | 重送**仍按旧快照** `/delivery-fail` 失败（callback_url_snapshot 快照语义）→ 耗尽 DEAD_LETTER + dead_letter 落库（biz_type=INBOUND） |
| B5 送达 4xx | 回调地址指向返回 4xx 的 stub/地址 | 送达失败 → 死信（不无限重试 4xx） |
| B6 签名正确性交叉 | 模拟回调自签名成功 + 手工重放同一报文两次（防重放开时） | 开防重放 → 同签名在容差窗口内第二次被拒 40100「重复请求（防重放）」 |

**密钥外泄回归点（M3 评审缺陷 1 修复）：** 入站送达请求**不得带**应用出站签名头（WireMock 送达目标收到请求的 headers 不应含 `Authorization: Bearer …`）——每次回归都该瞄一眼 WireMock 收到的送达请求头。

### P2 回调闭环（需公网 HTTPS，验证 Flow B 真实送达）

> **先分清两个地址（都带 callback，极容易混）**：回传是两跳，不是一跳——
> ```
> evolink（云端）
>   │ ① 完成时主动 POST → 收件方 = curl body 里的 callback_url（给 evolink 看的：你在公网的入站入口）
>   ▼    填 https://<子域名>.ngrok-free.app/ai/cb（ngrok→8080→平台路由 /ai/cb→IF-EVL-CB）
> 平台 :8080（入站接口 IF-EVL-CB）
>   │ ② 平台把通知转投给业务收件端 → 收件方 = 接口表单的「回调地址（送达）」
>   ▼    填 http://localhost:18080/delivery-evl（WireMock 假业务端）
> WireMock 桩（本地的假业务收件端）
> ```
> 判定口诀：**callback_url 是给云端 evolink 看的（必须公网 HTTPS，填 ngrok+/ai/cb）；「回调地址（送达）」是平台转发给你业务系统的（本地填 delivery-evl 桩）**。两处都填 ngrok 会环路；callback_url 填 localhost 则 evolink 公网够不着。

> Flow B 机制（先读懂再动手）：evolink 回调 POST 到平台入站路径 → 平台按接口「入站参数（IN）声明」解析回调、验签（本用例 Noop）→ 经「字段映射」把 IN 字段保形搬到 OUT → 编码成**送达报文**（outbound body）→ POST 到接口配置的「回调地址（送达收件端）」→ 成功 ACKED；送达与 ack 解耦（失败也回 2xx，由 worker 重送）。**没有「零声明全量透传」**：送达报文字段来自 OUT 声明 + 映射，所以必须先拿到 evolink 真实回调样例再声明（下述 A）。

**A. 抓首包（拿 evolink 真实回调样例，必做，约一次任务时长）**
1. 浏览器开 https://webhook.site → 复制你的唯一 URL `https://webhook.site/<uuid>`（https，evolink 只收 https）。
2. 用该 URL 当 callback_url 建一次任务（会真实计费一次）：
```bash
curl -s -X POST http://localhost:8080/ai/gen -H "Content-Type: application/json" \
  -d '{"model":"gpt-image-2","prompt":"一只微笑的可爱小猫","callback_url":"https://webhook.site/<uuid>"}'
```
3. 任务完成后 evolink 会回调 webhook.site——**在页面拿到真实 payload**（方法/请求头/JSON body），保存 body 样例，下一步照着声明字段。格式以它为准（下表只是占位示例，勿照抄）：
```json
{"event_id":"evl_xxx","status":"completed","task":{"id":"xxx","model":"gpt-image-2"},"results":[{"url":"https://.../img.png"}]}
```

**B. 起隧道 + 送达收件端桩**
4. 新终端 `ngrok http 8080`（或 cloudflared），记下公网地址 `https://<子域名>.ngrok-free.app`。
5. 确认送达桩就绪（前置块命令已注册 `/delivery-evl` 200）：`curl -s -o /dev/null -w "%{http_code}" -X POST http://localhost:18080/delivery-evl -d '{}'` 应回 `200`；没起/没注册就回前置块命令。

**6. 建入站回调接口主表单 IF-EVL-CB（接口管理页，「＋ 新建」）**
| 字段 | 填/选 |
|---|---|
| 类型 | **入站回调**（INBOUND；切后表单互斥联动：供应商接口路径禁填、出现回调地址与 ACK/送达字段） |
| 方法 / 平台侧路径 | POST / `/ai/cb` |
| 名称 / 接口标识 | `evolink 回调` / `IF-EVL-CB` |
| 归属应用 / 分组 | `EVOLINK` / `默认分组` |
| 回调地址（送达） | `http://localhost:18080/delivery-evl`（前置块命令已注册该桩；本地桩需 `callback-allow-private: true` dev 默认放行） |
| 协议 入站 / 出站 | JSON / JSON |
| 读超时(ms) / 最大重试 | 默认（3000 / 4；送达桩本地返回快） |

**6 续 · 请求参数区（按 3 抓到的真实样例逐字段声明，关键一步）**
- **入站参数（IN，= evolink 回调里的字段）**：对照样例顶层字段逐条加：字段名（同 JSON 键）、类型（string/number/object/array 按值选）、必填按需、样例可粘贴对应值。示例（若样例真为 3 抓到的形态）：`status`(string)、`task.id`(string, object 用点号子字段)、`event_id`(string)。
- **出站侧送达参数（OUT，= 送给收件端的字段）**：至少一条（C5：入站必填出站送达参数）。最省事做法：声明与 IN 同名的 `status` 即可——映射后送达报文含 status。
- **字段映射区**：为每条 IN→OUT 保形加 rename：source=`status`、op=`rename`、target=`status`、param 空、null_strategy=KEEP（同名字段也可以只加 OUT 关心的那几条，不用全字段）。
- **ACK 回执字段**：留默认即可（evolink 只要 2xx 即认为成功；不声明也能回结构 ack）。
- **回调验签适配器**：留空（Noop，evolink 回调无签名）。
- 保存 → 列表/详情「发布」→ 状态「已发布」。（缺发布：evolink 回调平台会 404）

**D. 触发全流程并验收**
7. 重发建任务，callback_url 换成平台入站完整公网 URL：
```bash
curl -s -X POST http://localhost:8080/ai/gen -H "Content-Type: application/json" \
  -d '{"model":"gpt-image-2","prompt":"一只微笑的可爱小猫","callback_url":"https://<子域名>.ngrok-free.app/ai/cb"}'
```
8. **预期时序**：出站秒回任务 id（SUCCESS）→ evolink 处理几十秒~几分钟 → 完成时 POST `https://<子域名>.ngrok-free.app/ai/cb`（body=真实完成通知）→ 平台验收入站 → 送达 `http://localhost:18080/delivery-evl` → 收件端 200。
9. **逐项验收**：
   - 送达报文核对：`curl -s http://localhost:18080/__admin/requests?limit=5 | jq '.requests[].request.body'` → body = OUT 声明字段编码（含 status 等），且**不含**出站签名 Authorization 头（B 系密钥外泄回归点）；
   - `inbound_delivery`：该回调行 ACKED（SQL-7 查）；Monitor 双向 call_log（IN=evolink 回调 / OUT=送达各一条）；
   - 入站送达视图：Monitor「调用日志」按 traceId（后端日志/响应头 X-Trace-Id）双向收敛；送达结果以 `inbound_delivery.delivery_status` 呈现（ACKED，SQL-7 / 死信 Tab 查）——**状态链本期只做出站，入站暂无状态链**，勿在 Monitor「状态机与对账」里找入站行；
   - evolink 侧：任务状态 completed、无「回调失败」提示（它收到平台 200 ack）。
10. **首包对不上 / 校验失败的常见处理**：声明字段与样例不符会导致解码/映射异常（400 信封，不落运行表，D7）——回 6 按真实样例改字段声明与映射，重新触发；若只想先把闭环跑通，OUT 只留一条 `status`（或样例里最确定存在的字段）再试。evolink 后续若提供回调签名头，回适配器管理补 HMAC 回调验签实例并绑「回调验签适配器」（CALLBACK_AUTH 角色）。

### 收尾与回归隔离

## 6.6 真实 XML 协议出站（可选联调）：免密钥真实 XML 端点

> 定位：**免密钥、可真调的真实 XML 用例**——验证「真发 HTTP → 真收 `application/xml` → XML 解码 + RESP 白名单 + 同名合并」整条出站链路，无需 WireMock、无需供应商账号。
> 与 §6.5 的关系：§6.5 验 JSON 真实供应商 + 回调闭环，本节点补真实 **XML 响应**方向；两者都属「需真实外部依赖」，**不进 `mvn clean test`**。

### 可用端点（实测 2026-09-10）

| 端点 | 实测返回 | 根剥离后模型 | 可解码 | 适用 |
|---|---|---|---|---|
| `GET https://earthquake.usgs.gov/earthquakes/feed/v1.0/summary/2.5_day.atom` | `200 application/atom+xml` | `<feed>` → `{title,updated,author,id,icon,entry:[…]}` | ✅ | **首选**：根下字段多，能实证 RESP 白名单 |
| `GET https://hnrss.org/frontpage` | `200 application/xml` | `<rss>` → `{channel:{…item:[…]}}` | ✅ | 实时新闻，演示真实供应商数据 |
| `GET https://httpbin.org/xml` | `200 application/xml` | — | ❌ **40002** | 反例：含混合内容（见下），**勿用** |

> **只认 GET**：平台对 GET/DELETE 不带 body（`UpstreamInvoker` 保守处理），出站 XML 编码产物被丢弃，只验响应解码——这正是本节点要覆盖的方向。
> **响应按 `protocol_out` 解码**，不看响应 `Content-Type`（D-M3-4）；故 atom/RSS 的 `application/atom+xml` 也能用 XML 适配器解。

### X-R1 基础：USGS atom + RESP 白名单（约 5 分钟）

1. 建应用 `USGSXML`：服务地址 `https://earthquake.usgs.gov`、鉴权/回调验签/报文全留空（Noop 直通）→ **启用**；
2. 建分组 `演示分组`（归属 `USGSXML`）；
3. 建接口 `IF-XML-REAL`（「＋ 新建」逐字段）：

   | 字段 | 填/选 |
   |---|---|
   | 类型 | 出站中转（默认） |
   | 方法 / 平台侧路径 | **GET** / `/demo/xml-real` |
   | 供应商接口路径 | `/earthquakes/feed/v1.0/summary/2.5_day.atom` |
   | 协议 入站 / 出站 | JSON / **XML**（关掉联动，手动把出站改 XML） |
   | RESP 响应字段 | 加一条：name=`entry`、type=`array` |
   | 请求参数 / 字段映射 / 绑定 | 全部留空（透传、Noop） |

   → 保存 → **发布**；
4. 调用：

   ```bash
   curl -s http://localhost:8080/demo/xml-real | jq '.data.entry | length'   # 预期 ≥1（当日实况）
   ```

   **预期**：`code=0`，`data` **只剩** `entry`（根下的 `title/updated/author/id/icon/link` 全被滤）；每个 entry 形如：

   ```json
   {"entry":[{"id":"urn:earthquake-usgs-gov:nc:75432942","title":"M 3.6 - 26 km W of Petrolia, CA",
               "updated":"2026-09-10T01:40:13.935Z","link":null,
               "summary":"<p class=\"quicksummary\">…</p>（CDATA 原文）",
               "point":"40.29349 -124.58516","elev":"-19229.99",
               "category":[null,null,null]}]}
   ```

   断言点（对应 D-M3-1 / D-M3-3）：根元素 `feed` 剥离；**RESP 白名单实证**（`title` 等根下字段全滤掉）；自闭合空元素 `<link .../>` → `null`；重复 `<category>`（每条数量随实况）同名合并为数组；CDATA（`summary`）按文本原文保留；命名空间前缀剥离（`georss:point` → `point`）；
5. **变体（过滤差异直观可见）**：清空 RESP 再调 → `data` 多出 `title/updated/author/id/icon/link`（`author` 是对象 `{name,uri}`）——这就是「空声明=不过滤」；
6. 观测：Monitor「调用日志」方向 OUT 一条 2xx；「状态机与对账」该行状态链 `INIT→MAPPING→SUCCESS`（首送无重试节点）。无密钥，故无脱敏差异可验。
7. **失败自检（实测高频坑：`code=0` 但 `.data.entry` 为空 / 0）**：十有八九是接口的**「出站协议」仍是 JSON**——前端默认「入站=出站」联动开启，只改了入站没改出站；此时 Atom XML 被按 JSON 解码，`parseResponse` 宽松处理成空对象，RESP 过滤后 `data={}`，`entry` 自然取不到。
   判定命令（三条对应三种原因）：
   ```bash
   # ① 完整信封 + data 键集：data_keys=[] 说明解码失败或 RESP 名不符；code≠0 则是走了失败分支
   curl -s http://localhost:8080/demo/xml-real | jq '{code,msg,data_keys:(.data|keys)}'
   # ② 查接口真实配置：protocolOut 必须为 "XML"（另核 method=GET / upstreamPath / status=PUBLISHED）
   ID=$(curl -s "http://localhost:8080/api/admin/interfaces?keyword=IF-XML-REAL" | jq -r '.data[0].id')
   curl -s "http://localhost:8080/api/admin/interfaces/$ID" | jq '.data|{method,protocolIn,protocolOut,upstreamPath,status}'
   curl -s "http://localhost:8080/api/admin/interfaces/$ID" | jq '.data.fieldDefs'   # 应有 kind=RESP name=entry type=array
   # ③ 后端日志：出现「响应报文解析失败（按空对象处理）」= 解码失败；「出站请求 N 成功（响应 32294 字节）」= 真拿到了响应
   ```
   有库时一锤定音：`SELECT status,error_code,out_payload FROM outbound_request ORDER BY id DESC LIMIT 1;` —— `out_payload={}` 是解码失败（协议没选 XML），含 `"entry"` 则是 RESP 名称/类型写错。
   修复：编辑接口 → 取消「入站=出站」联动 → 出站协议改 `XML` → 保存（版本 +0.1，`ConfigChangedEvent` 即时生效）——不必重建接口。

### X-R2 变体：hnrss 实时新闻

- 应用服务地址改 `https://hnrss.org`（或另建 `HNXML` 应用）、供应商接口路径 `/frontpage`、协议 JSON → **XML**；RESP 声明 `channel`(object) → 发布；
- `curl -s http://localhost:8080/demo/xml-real | jq '.data.channel.title'` → `"Hacker News: Front Page"`；`.data.channel.item | length` → 当日新闻条数（每次调都不同，**证明是真实实时数据**）；
- 结构点：`<channel>` 下的 `<link>`（有文本）与 `<atom:link/>`（自闭合）同名合并为 `["https://news.ycombinator.com/", null]`；`<item>` 内标题/描述均为 CDATA；`<dc:creator>` → `creator`（前缀剥离）。

### 反例：httpbin.org/xml（混合内容 → 40002，勿用）

`GET https://httpbin.org/xml` 返回里第二个 `<slide>` 的
`<item>Why <em>WonderWidgets</em> are great</item>` 是**混合内容**（文本与子元素并列，实测 2 处），
`XmlProtocolAdapter` 直接拒（`40002 报文格式非法：混合内容不支持`）——这是**有意设计**（D-M3-1 首期不支持混合内容），不是 bug。

价值 = **真实反例**：用它建接口调用一次，可实证「真实报文触发的 40002」；断言点在封装信封 `code=40002` 且该请求**不落 `outbound_request`**（链失败不污染状态机）。
另外该端点 `POST` → **405**（只认 GET），更不可用于 XML 请求方向。

### X-R3 补测：XML 请求方向的「自收自发」（无外部供应商）

> 公开真实服务里没有接受平台出站 XML 请求体的（原因见「边界」），要验证 XML **编码**方向，让平台自己当服务端：

1. 建**入站回调**接口 `IF-XML-IN`：类型 INBOUND、方法 POST、平台侧路径 `/demo/xml-in`、协议入站 **XML**、回调地址指向本地可达收件端（如 WireMock `/delivery-ok`，或任一能收 POST 的地址）、ACK 字段 `returnCode`(number)/`returnMsg`(string) → **发布**；
2. 直接 POST 真实 XML 到平台：

   ```bash
   curl -i -X POST http://localhost:8080/demo/xml-in \
     -H "Content-Type: application/xml" \
     -d '<request><event_id>evt-1</event_id><order_id>ORD-1</order_id></request>'
   ```

   **预期**：平台回 **XML 格式 ack** `<response><returnCode>0</returnCode><returnMsg>…</returnMsg></response>`（AckRenderer 按 `protocolIn` 渲染，XML 进 → XML ack）；
3. 这一步真实覆盖「XML 请求解码 → 映射/送达 → XML 响应渲染」，收发端均为本机——无 stub，但也不是外部供应商。

### 边界（别误判为缺陷）

- **XML 出站根元素写死 `<request>`**：`XmlProtocolAdapter` 默认 `xmlRoot=request`（仅 ACK 渲染传 `response`），协议适配器不参与绑定、`interface` 表无协议参数字段（M0-01 D5「首期一律平台默认参数」）。因此 **SOAP 服务**（要 `<soap:Envelope>`、带命名空间）与任何要求特定根元素的 REST-XML 服务**当前调不通**，属已知设计边界；
- 要接真实 XML 供应商需先扩展协议适配器（rootElement / namespace / SOAP 可配置）——**属 M0-01 D5 口径变更，先过评审再排期**，勿在验收里当缺陷报；
- `POST https://httpbin.org/xml` → **405**（该端点只认 GET），且其响应含混合内容会 40002——它只作反例，XML 请求方向请走 X-R3；
- 这些都是公共免费服务，仅用于联调抽查，**不做稳定性/性能断言**（实测 NASA RSS → 429、w3schools → 403）。

### 收尾与回归隔离
- 验完按 §10.4 清理 `USGSXML`（或 `HNXML` / `IF-XML-IN`）造数（先清运行表再删接口/分组/应用）；
- **不进 `mvn clean test`**（真实外部依赖 + 公网不确定性，同 §9.5「需真实外部依赖」边界）；
- 踩坑速查：`40401` → 应用没启用或接口没发布；`40002 混合内容不支持` → 该 XML 含「文本+子元素」并列（如 httpbin `/xml`），换 USGS/hnrss；`40002` 其他 → 端点返回的不是 XML（如误用 `/anything` 返回 JSON）；`data` 字段全空 → RESP 声明名与根下字段名不符（对照实际 XML 结构调整）；`50401` → 公网慢，调大读超时。

- 版本历史：详情 →「版本历史」→ 两行（v1.0「初始创建」、v1.1 自动摘要如「变更：字段映射 1→1（修改 1 条）」）→ 点「变更详情」查看结构化 diff（JSON：fields/params/mappings…，raw 只记 hasChanged）；点「快照」查看完整 config_json（可重建）；
- 回滚：v1.0 行 →「回滚到此版本」→ 弹窗**只二次确认**（已无 operator/reason 输入）→ 确认 → 版本变 v1.2（**每次 +0.1 只增不倒退**）、状态仍「已发布」（快照不含 status）；新版本 change_note=「回滚至 v1.0」，且「变更详情」**可用**（type=ROLLBACK：回滚前当前配置 vs 目标版本差异，如「读超时(ms) 5000→3000」）；
- 行为验证：curl `/m5/ver` 回滚后（v1.2）映射恢复 rename（供应商收到的 body 是 `order_state=PAID` 而非「已支付」）；
- 异常：回滚到不存在版本 40403；并发（旧 currentVersion）40001。
- 原理：回滚 = 用快照重建 InterfaceRequest 走**全量替换**路径（不旁路校验），乐观锁防覆盖；快照含 appId 不含 status；变更说明统一走 SnapshotChangeDiff（旧快照缺失时回退现场构建旧 JSON，保证摘要必生成）。

### V2 绑定切换即时生效（D6'：绑定即实例，version 不路由）
- 前置（D6' 验证）：适配器管理新建两个**同实现**信封适配器实例并都启用：`ADP-ENV-1`（v9.1，codeField=`code`、successValue=`0`）与 `ADP-ENV-2`（v9.2，codeField=`status`、successValue=`ok`）——同 (impl, version) 允许多启用，只需**名称不重复**（name 全表唯一）；
- 绑定：出站接口高级 tab「报文适配器」选 `ADP-ENV-1` → 发布；供应商（WireMock 改 stub，§11.3）回 A `{"data":{"v":1},"code":"0","status":"bad"}` → 调用方收到 v=1（按 code=0 判成功）；
- **切换**：编辑把「报文适配器」改为 `ADP-ENV-2`（绑定即实例——已无版本下拉，version 仅记录不路由）→ 保存（变更说明可填「切 v2」）→ 供应商回 B `{"data":{"v":2},"code":"x","status":"ok"}` → **立即**（不等 5 分钟）curl 收 v=2——ConfigChangedEvent 事件失效即时生效的实测；
- chainTrace：详情「测试接口」响应 data 含 `chainTrace:[{role:MESSAGE,adapterId:ADP-ENV-2,impl:EnvelopeMessageAdapter,version:9.2}, …]`（test 端点强制实时解析，永远反映当前绑定实例）；
- 容灾回退：停用 ADP-ENV-1（或绑定实例缺失）→ 调用不 500，自动回退（应用默认→Noop 直通）且后端日志 warn「适配器绑定回退」；重新启用恢复；
- 留痕三通道对照：后端日志「链装配 … 绑定解析 → MESSAGE=…」行（通道 1）与 chainTrace（通道 3）内容一致；span tag（通道 2）仅压测/链路面看。

### V3 接口复制（方案 B，2026-09-08）
- 入口：接口详情抽屉「复制」→ 弹窗（code/path **必填且置空由你填**、名称默认「{源名} 副本」、供应商接口路径/回调地址留空=沿用源）；
- 语义：固定归入**源应用/源分组**（不支持跨应用）；产物 **DRAFT v1.0**，change_note=`复制自 {源code}#v{源版本}`；凭证沿用本应用；快照历史与运行数据不复制；
- 验证：复制出站接口 → curl 调用成功（报文与原一致）→ 新接口详情子表与源等价、可独立编辑/回滚，源及其版本历史不受影响；复制入站接口 → 「模拟回调」闭环；
- 冲突：code/path 撞库 → 与 create 同文案 40001。
- API：`POST /api/admin/interfaces/{id}/copy` body `{"code":"IF-X2","path":"/x2","name":"X 副本","upstreamPath":null,"desc":null}` → 返回新接口 id。

## 12. 执行 FAQ（2026-09-08 会话答疑沉淀）

> 执行/评审中高频疑问的问答速查。答随实现走（日期标注当次口径），与正文冲突时以最近日期为准并回改正文。

### Q1 新建适配器报「同 (impl, version) 至多 1 条启用记录」？
**A**：这是**旧 D6 语义**（2026-09-08 已被 D6' 取代）：现同 (impl, version) **允许多条启用并存**，唯一约束改为 `adapter.name` 全表唯一（重名才拒）。仍见该文案 = 后端未更新 / 命中旧实现。详见 §4 C4 与《M5开发计划.md》顶部 D6' 注记。

### Q2 不同的适配器会互相版本冲突吗？
**A**：不会。冲突判定键是 **(impl, version) 二元组**——不同 impl 即使 version 都填 1.0 也可同时启用（库里 ADP-101 Bearer 1.0、ADP-000 Noop 1.0、ADP-201 Envelope 1.0 全启用即反证）；type / name / id 不进判定。

### Q3 同 impl 且同 version 会冲突吗？
**A**：D6' 下**不会**（可建第二条并同时启用，靠 adapter.id + adapter.name 区分）。若想「替换而非并存」：先停旧实例再启用新实例即可（全局同 (impl,version) 允许多条 enabled，无启用数上限）。

### Q4 evolink P2 里 callback_url 到底填 ngrok 还是 delivery-evl？
**A**：两个都要填但**位置不同、作用不同**（回传是两跳，不是一跳）：
- **callback_url（curl body 里）** = 给云端 evolink 看的收件地址（它必须走公网）→ 填 `https://<子域名>.ngrok-free.app/ai/cb`（隧道 → 平台入站接口）；
- **回调地址（送达，接口表单里）** = 平台把通知转投给你业务收件端 → 填 `http://localhost:18080/delivery-evl`（WireMock 假业务端）。
口诀：callback_url 给 evolink（公网）；送达地址给平台转投业务（本地桩）。两处都填 ngrok 会环路；callback_url 填 localhost 则 evolink 公网够不着。详见 §6.5 P2 顶部两跳图。

### Q5 入站接口的「入站参数」和「出站侧送达参数」各是哪到哪？为什么必填？
**A**：
- 入站参数（IN）= **供应商 → 平台**：回调报文里的字段（平台解析 / 校验 / 取样用）；
- 出站侧送达参数（OUT）= **平台 → 业务收件端**：平台拼出的「送达报文」字段（投给回调地址的正文）。
必填口径（以代码为准）：**硬必填只有 OUT（送达报文至少一条）**——平台在 Flow B 是「构造新报文投递」而非转发，两端契约不同，必须有 OUT 结构定义才能生成送达报文（payload 快照 / 重放都依赖它）；IN 非硬必填，但字段映射的 source 只能从 IN 声明选，要做映射就也得声明。对比出站接口可整体透传：出站转发的是同一个 body（语义一致）；入站的回调 ≠ 收件端契约，故必须显式构造。详见 §6 B 系与 §6.5 C。

### Q6 ACK 回执字段和报文适配器有什么区别？
**A**：一句话：**ACK 是回给供应商的「我收到了」应答，报文适配器是加工业务报文的组件**。
- ACK（`interface_field_def kind=ACK`，仅入站接口）：平台收到回调后回给供应商的 HTTP 响应体（AckRenderer 渲染：声明前两个字段 = code 0 + message success；无声明兜底 `{code:0,msg:"ok",data:null}`）。**收到即回、与送达解耦**——送达失败也回 2xx，供应商不重发；
- 报文适配器（MESSAGE 绑定，`EnvelopeMessageAdapter` 等）：处理业务报文信封（剥 data / 按 codeField+successValue 判业务成败 / 错误码映射 / 打包），作用在业务数据上。
判定：这报文是回给供应商表示「收下了」→ ACK；对业务报文做结构加工 → 报文适配器。另注意出站接口的 RESP 字段是「过滤出站响应给调用方」，与 ACK 是同一子表的不同 kind，按接口类型切换，勿混。

### Q7 evolink 回调时平台真的会回 ack 吗？
**A**：**会，恒回**（入站引擎最后一行无条件执行 `ackRenderer.render`）。只要回调被正常路由 / 验签 / 解码（否则抛 401/400 非 ack），无论 delivery-evl 送成没送成都会回 `HTTP 200` + 结构 ack（无 ACK 声明时兜底 `{code:0,msg:"ok",data:null}`），满足 evolink「回调需 2xx 快回」。验证：ack 是平台回给 evolink 的，**不会出现在 WireMock(delivery-evl) 里**——想看原样可 `curl -v` 直接打平台 `/ai/cb` 观察 200 响应体。

### Q8 如何给 P2 提供公网 HTTPS（隧道）？
**A**：evolink `callback_url` 仅收 HTTPS，本地 8080 需公网暴露：
- **ngrok**：`brew install ngrok/ngrok/ngrok` → 官网注册拿 authtoken → `ngrok config add-authtoken <token>` → `ngrok http 8080`（免费版 URL 随机、进程退出即失效）；
- **cloudflared（推荐，免注册免 token）**：`brew install cloudflared` → `cloudflared tunnel --url http://localhost:8080`，输出 `https://<随机>.trycloudflare.com`。
验证：`curl -s https://<子域名>…/actuator/health` 回 UP 即隧道通。

### 1.2 启动（三条命令 + 两个前端）

```bash
# ① 清残留端口（8080 后端 / 18080 桩）
lsof -tiTCP:8080 -sTCP:LISTEN | xargs kill 2>/dev/null
lsof -tiTCP:18080 -sTCP:LISTEN | xargs kill 2>/dev/null
sleep 2

# ② 本地供应商桩（L1 用；m4 目录提供 /echo-ok、/breaker-supplier、/slow-supplier、/reject-supplier）
java -jar ~/.m2/repository/org/wiremock/wiremock-standalone/3.9.1/wiremock-standalone-3.9.1.jar \
  --port 18080 --root-dir src/test/resources/m4-manual-stubs &
sleep 4 && curl -s -X POST http://localhost:18080/echo-ok -d '{}'   # 预期 {"ok":true}

# ③ 后端（另一终端）
mvn spring-boot:run            # :8080；连 application.yaml 配置的 PolarDB

# ④ 前端（再一终端）
cd frontend && npm run dev     # :5173，/api 代理到 8080
```

> ⚠ **两套 stub 目录不能同时由 `--root-dir` 加载**（该参数只接受一个目录，且仅在启动时读取一次）：m4 目录给 `/echo-ok`、`/breaker-supplier`、`/slow-supplier`、`/reject-supplier`（5 条）；m3 目录给 `/xml-supplier`、`/delivery-ok`、`/delivery-fail`、`/delivery-flaky-1..9`（12 条）。
>
> 演示中若需**并用**（如既验本地出站又验入站送达），**不要重启换目录**——向运行中的实例热注册另一套即可（两套 stub 都是内联 `jsonBody`/`body`，不依赖 `__files/`，热注册与随启动加载行为一致）：
>
> ```bash
> # 保持 m4 实例运行，把 m3 全量 stub 热注册进来（含 xml-supplier 与 delivery-*）
> for f in src/test/resources/m3-manual-stubs/mappings/*.json; do
>   curl -s -X POST http://localhost:18080/__admin/mappings -H "Content-Type: application/json" -d @"$f" > /dev/null
> done
> curl -s http://localhost:18080/__admin/mappings | jq '.meta.total'   # 预期 17 = m4 5 + m3 12
> curl -s -X POST http://localhost:18080/xml-supplier -d '{}'          # 预期 XML 报文
> ```
>
> 反过来说：若启动时 `--root-dir` 用错目录（或不在项目根目录执行导致相对路径失效），请求会返回 `Request was not matched`，其中「Closest stub」列会暴露**当前实际加载的是哪套 stub**，是最快的排查线索。

### 1.4 原理 / 设计思路 / 实现方式（环境层）

- **原理**：管理面与执行面**同一进程、不同入口**——`/api/admin/**` 走管理面 Controller，其余任意路径走接入层通配路由 `GatewayController`，由「平台侧路径」在 `interface` 表反查命中接口。配置只写库，执行面按配置解释执行。
- **设计思路**：**配置与执行分离**（《技术架构》§2.3 原则 1）——管理面不做业务流转，执行面不写配置；因此「改配置 → 生效」必须靠**链缓存失效事件**而非重启。
- **实现方式**：`controller/GatewayController.java`（`@RequestMapping("/{*path}")` 通配，仅 GET/POST/PUT/DELETE）+ `controller/admin/*Controller.java`（6 个管理面 Controller，统一 `ApiResult<?>` 信封）；前端 `frontend/src/api/http.js` 统一解包信封。

## 2. 环节 A：界面配置面（应用 → 凭证 → 适配器 → 分组 → 接口）

> 本环节全部在 `http://localhost:5173` 点选完成；等价 curl 见《API中心使用教程》§3。
> 数据模型：**应用（= 供应商）→ 分组 → 接口**，适配器与凭证挂在应用上，接口可覆盖应用默认。

```
app（应用=供应商）
 ├── app_credential（凭证：OUTBOUND 出站签名 / CALLBACK 回调验签，两类独立）
 ├── adapter（适配器实例，全局池；应用/接口绑定引用）
 └── app_group（分组，纯归类）
       └── interface（接口：出站中转 / 入站回调，互斥）
             ├── interface_param（入/出两侧参数声明）
             ├── interface_body（入站请求体 / 出站转发方式）
             ├── interface_field_mapping（字段映射，6 操作）
             ├── interface_field_def（RESP 响应白名单 / ACK 回执字段）
             └── interface_adapter_binding（绑定角色：MESSAGE / AUTH / CALLBACK_AUTH）
```

### A1 建应用并启用

**操作（应用管理页）**

| 字段 | 填/选 |
|---|---|
| 应用标识 | `QD1`（规则：字母/数字/`_`/`-`，1~32；填中文应被拒） |
| 应用名称 | `演示应用` |
| 服务地址 | `http://localhost:18080`（**供应商根地址**，勿填 8080 自己） |
| 供应商签名 / 回调验签 / 默认报文 | 全留空（= Noop / 继承语义） |
| IP 黑白名单 / QPS / 日配额 | 留空 / 0（不限） |

保存 → 状态「草稿」→ 行操作「启用」→ 状态「已启用」。

- **原理**：应用 = 供应商，既是接口归属也是出站目标（`interface.app_id` 同时表达归属与目标）。`base_url` 是「函数参数」而非完整 URL——最终地址 = `base_url + interface.upstream_path`，所以接口只需配相对路径。
- **设计思路**：设计方案 §1.1「供应商即供应商，不再区分归属应用与供应商应用」，省掉一层映射；§1.3 生命周期 `DRAFT → ENABLED → DISABLED → CANCELLED`，**停用即拒请求**（`40102`）。
- **实现方式**：`service/AppService.java`（状态机流转 + 乐观锁）、`repository/AppRepository.java`；网关侧 `AppService.isRequestAllowed()` 在引擎入口二次校验。
- **自检**：应用列表状态「已启用」；`curl -s -X POST http://localhost:8080/qd/ok -d '{}'` 此时应 40401（接口还没建），说明路由确实按库查；停用后再调任意接口 → `40102`。

> ⚠ 应用**必须启用**，否则后续所有调用 `40102 应用已停用`；这是演示最常见的「链路全挂」原因。

### A2 配凭证（应用行 → 凭证区）

**操作**：点 `QD1` 行进入详情 → 凭证区 →「更新凭证」：

| 凭证类型 | 内容 | 结果 |
|---|---|---|
| 出站签名（OUTBOUND） | `token-v1` | 出现 ACTIVE（尾 4 指纹） |
| 再更新为 `token-v2` | — | 旧转 ROTATING（新旧并存），新 ACTIVE |
| 回调验签（CALLBACK） | `cb-secret` | 与出站凭证**互不影响** |

- **原理**：两类凭证按鉴权方向拆开——**出站签名**证明「平台是调用方」，**回调验签**证明「来的是真供应商」（仅入站接口生效）。签名/验签都要用**明文密钥重算**，因此必须可逆加密存储（不能单向哈希）。
- **设计思路**：M0-04 定稿——`ACTIVE / ROTATING / RETIRED` 三态；轮换期间**验签新旧并存**（任一新旧命中即通过），但**签名只用 ACTIVE**；管理面**永不回显明文**（只显尾 4 指纹）。
- **实现方式**：`repository/CredentialRepository.findActive(appId, kind)`；`service/CryptoService.java`（AES-256-GCM，密钥见 `CryptoProperties`）；链引擎 `ChainEngine.injectCredential()` **每请求实时读**，不进链缓存（M5 明确）——所以轮换天然即时生效。
- **自检**：凭证只显示 `****` + 尾 4；`app_credential` 表 `credential` 列为密文；后续 WireMock 收到的 `Authorization` 头能观察到从 `Bearer token-v1` → `Bearer token-v2` 的变化。

> **Why 每请求实时读**：凭证是**变更最敏感、读取最便宜**的配置（一次主键查询）；若烘焙进链缓存，轮换就需要额外失效事件，且明文密钥会长期驻留内存。取舍结果：绑定/映射/参数进缓存，凭证实时读。

### A3 建适配器（适配器管理页）

**操作**：顶部 tab 选「鉴权」→「＋ 新建适配器」：

| 字段 | 填/选 |
|---|---|
| 实现 | `Bearer Token`（选定后下方表单按 impl schema 动态渲染） |
| 适配器名称 | `演示 Bearer`（**adapter.name 全表唯一**，重名被拒） |
| 标识 | `ADP-DEMO-TOKEN` |
| Token 字段 | **留空**（灰字提示「凭证值在应用管理→凭证中维护」） |
| Token Header 名 / 前缀 | `Authorization` / `Bearer` |
| 版本 / 启用 | `1.0` / 开 |

- **原理**：适配器**无状态、配置驱动、全局单例**；链引擎只认 `Adapter.process(ctx)`，按 `ctx.phase()` 分流。`adapter.params`（JSON）就是适配器运行时的全部可配参数。
- **设计思路**：
  - **三类适配器**（鉴权 / 协议 / 报文，§5.1）；**字段映射不是适配器**，是链上固定步骤（接口级配置，D3）；
  - **协议适配器不参与绑定**——按接口的 `protocol_in / protocol_out` 自动推导；
  - **凭证类参数不进适配器配置**（`AdapterImplCatalog` 显式拦截）：密钥只存 `app_credential`，避免「同一密钥两处存」；
  - **D6'（2026-09-08 定稿）**：`adapter.name` 全表唯一；同 `(impl, version)` **允许多条启用并存**（实例靠 `id + name` 区分）；`binding.version` 仅记录、**不再参与路由**（绑定即实例）。
- **实现方式**：`engine/Adapter.java`（统一契约）、`engine/AdapterContext.java`（链上下文）、`service/AdapterImplCatalog.java`（impl 目录 + 参数 schema，驱动前端动态表单）、`adapter/auth/BearerTokenAuthAdapter.java`（`OUTBOUND_AUTH` 阶段读 `ctx.attrs("outboundCredential")` 加头）。
- **自检**：适配器列表出现该实例；尝试建第二个同名实例 → 被拒；协议类实例（JSON/XML）即使建了也不会出现在接口「高级 · 绑定」下拉里。

### A4 建分组（分组管理页）

**操作**：所属应用 `QD1`、名称 `默认分组`、排序 0 → 保存。

- **原理**：分组是**纯组织单元，不承载配置**（不参与链、不进路由键）；接口归属 = 应用 + 分组。
- **设计思路**：§2.1「应用 → 分组 → 接口」三段式，新建接口时「归属」是两级下拉（先应用后分组），保证接口一定挂在某应用下。
- **实现方式**：`service/GroupService.java`；删除守卫——分组下有接口时删除被拒（引用完整性由应用层保证，无数据库外键）。
- **自检**：接口表单「分组」下拉按当前所选应用过滤；分组详情内可见组内接口并可跳转。

### A5 建接口并发布（接口管理页）

**操作**：「＋ 新建」，**先选类型**（出站中转 / 入站回调），表单按类型互斥联动：

| 字段 | 出站中转（本次填值） |
|---|---|
| 接口标识 / 名称 | `IF-QD-OK` / `演示成功` |
| 请求方法 | `POST` |
| 平台侧路径 | `/qd/ok`（全局唯一，**网关路由键**） |
| 归属应用 / 分组 | `QD1` / `默认分组` |
| 供应商接口路径 | `/echo-ok`（**相对路径**；拼服务地址 = `http://localhost:18080/echo-ok`） |
| 入站 / 出站协议 | `JSON` / `JSON`（默认联动「入站=出站」） |
| 入站请求体 | 选 `json`，模板 `{"hello":"world"}`（调试用，非必填） |
| 出站侧转发方式 | 保持「透传」（映射为空 = 整体转发） |
| 读超时 / 最大重试 | `3000` / `4` |
| 字段映射 / 绑定 / RESP | 全空（Noop 直通 + 全量响应） |

保存 → 详情或列表点「发布」→ 状态「已发布」→ 详情「测试接口」→ 发送 → `code=0`。

- **原理**：
  - **类型互斥**（§3.1）：出站必填「供应商接口路径」、禁填回调地址、只许 RESP 字段、绑定只许 MESSAGE+AUTH；入站必填「回调地址」、禁填供应商路径、只许 ACK 字段、绑定只许 MESSAGE+CALLBACK_AUTH、**必填出站侧（送达报文）参数**；
  - **发布是路由开关**：只有 `PUBLISHED` 的接口才可被网关命中（`40401 接口未发布`）；
  - **空映射 = 整体透传**（M0-02 D3），非空则是**白名单**（未声明 target 的字段会被丢掉）。
- **设计思路**：
  - 类型互斥字段在切换类型时由前端 `onTypeChange` 自动清空，避免「脏字段跨类型残留」；
  - 入站必须显式声明送达报文（OUT），因为 Flow B 是「**构造新报文投递**」而非转发（两端契约不同，快照重放依赖 OUT 结构）——这是与出站「可整体透传」的**有意差异**；
  - 平台侧响应恒为统一信封 `{code,msg,data}`，不逐接口配置（§3.1）。
- **实现方式**：`service/InterfaceService.java`（CRUD + 类型互斥校验 + 乐观锁 + 发布/下线 + 事件发布）、`repository/InterfaceRepository.java`（`findByPath` 是网关路由的唯一入口）、`service/CallbackUrlValidator.java`（回调地址 SSRF 校验，dev 默认 `callback-allow-private=true` 放行 127.0.0.1）。
- **自检**：接口详情子表与填写一致；「测试接口」返回 `{chainTrace:[...], result:{...}}`（`chainTrace` 是 M5 留痕通道 3，强制实时解析当前链）；改类型后互斥字段被清空。

> ⚠ **两个高频坑**：① `list()` 不返回子表（params/mappings 恒空），断言子表必须走 `detail()`；② 平台侧路径全局唯一——`/qd/ok` 被占用时要么改路径要么删旧接口。

### A6 环节 A 的原理串联（一次完整装配发生了什么）

配置动作本身不触发任何执行；真正让「配置变成行为」的是**链装配**（首次调用或缓存失效后）：

```
请求命中接口
  → ChainEngine.assemble(iface)
      ├─ 读 interface_adapter_binding（角色 → adapter_id）
      │    └─ 逐角色 resolveBound：接口覆盖 → 应用默认 → 平台默认 Noop（D6' 回退链）
      ├─ 按 protocol_in / protocol_out 推导协议适配器（JSON/XML）
      ├─ 读 interface_field_mapping（映射规则）→ 烘焙进链
      ├─ 读 interface_param(side=IN)（入站参数类型）→ 烘焙进链
      └─ 六阶段 steps 全部就绪 → CachedChain（TTL 5 min）
  → 逐阶段执行（凭证在 OUTBOUND_AUTH 阶段每请求实时注入）
```

- **原理**：装配一次、执行多次；装配是「读配置 + 解析绑定」，执行是「跑数据」。
- **设计思路**：**M5.2 解析时机上移**——绑定 / 映射 / 参数从「每请求查库」上移到「装配时一次解析并烘焙」。收益：主链路每请求少 3~4 次远程库往返（远程 PolarDB ~百 ms/往返，读放大在压测中收益明显）；代价：配置变更必须靠**事件失效**（见下）。
- **实现方式**：`engine/ChainEngine.chain()`（TTL 5 min 兜底）+ `ChainEngine.assemble()`（六阶段槽位填充）；`ChainEngine.onConfigChanged()` 用 `@TransactionalEventListener(fallbackExecution=true)` 监听 `ConfigChangedEvent`——**事务提交后**才清缓存，消除「提交前清 → 并发请求用旧配置重新装配 → 陈旧链残留」竞态（M5 代码评审 H1 修复）。
- **失效面清单（新增配置入口必须补发事件，否则最长 5 分钟不生效）**：

| 变更 | 事件 scope | 效果 |
|---|---|---|
| 接口 update / rollback / publish / offline / delete | `INTERFACE` | 精准移除该接口缓存 |
| 适配器增改 / 启停 / 删、应用默认绑定 / 启停 | `ADAPTER` / `APP` | 全清（影响面不定） |
| 凭证轮换 | 不发事件 | 凭证每请求实时读，天然即时 |

## 3. 环节 B：本地黄金闭环（Flow A 出站四分支）

> 目标：用 §2 配好的 `QD1` 应用，一条接口上演示出站状态机的**四个分支**，并看到状态链。
> 对应《整体测试方案》§1.5 速通（13 项自检）+ §5 F1。

### B0 链路全景（先懂再点）

```
调用方 ──POST /qd/dead──▶ 网关通配路由
   └ GatewayGuard（QPS / 日配额 / IP）        ← 防护拒绝不落运行表（40103/42901/42902）
   └ 应用启用校验（40102）
   └ OutboundEngine.dispatch：findByPath + PUBLISHED + method 匹配（40401）
   └ createRecord → outbound_request(status=INIT, attempt=1)
   └ ChainEngine.execute（六阶段，见 A6）
   └ 补全出站规格：base_url+upstream_path / method / timeout / X-Trace-Id / 元数据
   └ 熔断闸门（OPEN → 50202 短路转补偿，不计数）
   └ status=MAPPING → UpstreamInvoker（@Retryable 5xx/429 退避重试）
        ├─ 2xx → 响应按 protocol_out 解码 → 报文适配（信封）→ RESP 白名单 → SUCCESS → 统一信封
        ├─ 4xx(非429) → DEAD_LETTER + dead_letter 落库 → 50201
        ├─ 5xx/429 重试耗尽 → COMPENSATING(next_retry_at=+3s) → 补偿 worker 重放
        └─ 读超时/连接异常 → UNKNOWN(50401) → 对账
   └ 状态链节点攒批，出口一次批量落库（outbound_request_state_log）
```

### B1 成功直通（SUCCESS）

**操作**：调用 `POST /qd/ok`（或详情「测试接口」）。

```bash
curl -s -X POST http://localhost:8080/qd/ok -H "Content-Type: application/json" \
  -H "X-Trace-Id: trace-demo-0001" -H "X-Biz-Id: biz-demo-0001" -d '{"hello":"world"}'
# 预期：{"code":0,"msg":"ok","data":{"ok":true}}（WireMock /echo-ok 回显）
```

- **原理**：2xx 后要做**两次不同的加工**——① 响应按 `protocol_out` 解码（不是按响应 `Content-Type`，D-M3-4）；② 若绑了信封报文适配器，则「剥信封 + 读 codeField/successValue 判业务成败 + 错误码映射」，最后再过 RESP 白名单。
- **设计思路**：**业务失败 ≠ 传输失败**（M0-03 C2 定稿）——供应商回 2xx 但业务码非 0 时，状态机仍记 `SUCCESS`（传输层已获明确结果），业务码透传给调用方；否则会把「明确失败」误判成「结果不确定」。RESP 白名单**仅成功路径生效**（D-M3-3）。
- **实现方式**：`OutboundEngine.handleSuccess()` → `ChainEngine.decodeResponse()`（按 `protocol_out` 推导协议适配器）→ `EnvelopeMessageAdapter.adaptResponse()` → `engine/RespFieldFilter.filter()`；`client/OutboundRequestSpec.java` 承载 URL/method/headers/body/timeout/traceId。
- **自检**：信封 `code=0`；Monitor「状态机与对账」出现 `SUCCESS` 行，状态链 = `INIT → MAPPING → SUCCESS`（首送无重试节点）；调用日志 OUT 方向一条含 traceId。

### B2 4xx 死信（DEAD_LETTER）

**操作**：先注册 401 stub（唯一一条造数命令），再建接口 `IF-QD-DEAD`（`/qd/dead` → `/qd401`）：

```bash
curl -s -X POST http://localhost:18080/__admin/mappings -H "Content-Type: application/json" -d '{
  "priority":1,"request":{"method":"POST","url":"/qd401"},"response":{"status":401,"body":"denied"}}'
```

- **原理**：4xx（非 429）表示**请求本身有问题**，重试无意义且可能造成重复副作用 → 直接落死信，不重试、不补偿。
- **设计思路**：错误分类器口径（设计 §6.1）——「4xx 死信 / 5xx·429 补偿 / 超时 UNKNOWN」三分。死信 = 需要人介入的失败，必须**可查看、可重放**（重放按 `in_payload` 重走整链、配置/凭证取最新，不是简单转发）。
- **实现方式**：`OutboundEngine.classify()`（4xx 分支）→ `OutboundRequestRepository.insertDeadLetter("OUTBOUND", recordId, reason, body)`；`dead_letter.ref_id` 多态引用（`biz_type` 区分 OUTBOUND / INBOUND）。
- **自检**：返回 `50201` + msg 含「死信编号 N」；Monitor「死信」区出现 PENDING 行（可点「报文」预览原始出站报文）；`SELECT * FROM dead_letter ORDER BY id DESC LIMIT 5;`

### B3 5xx 补偿（COMPENSATING）

**操作**：建接口 `IF-QD-COMP`（`/qd/comp` → `/breaker-supplier`，WireMock 恒 500）。

- **原理**：5xx/429 是**供应商侧暂时不可用**——先做**短重试**（进程内、指数退避、有上限），耗尽后转**补偿**（跨进程、由 worker 按 `(status, next_retry_at)` 扫描重放），避免长时间占用调用方线程。
- **设计思路**：两级重试的分工——短重试消化「秒级抖动」，补偿消化「分钟级恢复」。**动态重试预算必须走 predicate 扩展点**：Spring 7 `@Retryable` 的 `MethodRetrySpec` 按方法缓存，`maxRetriesString` 的 SpEL 只在首次调用求值一次（ThreadLocal + SpEL 方案对后续调用不生效，实测踩坑）；且 `@Retryable` **必须放独立 Invoker 类**（AOP 自调用不触发代理）。
- **实现方式**：`engine/UpstreamInvoker.java`——注解 `maxRetries=RETRY_CAP(16)` 固定上限，真实预算由 `InterfaceRetryBudgetPredicate`（读 `RETRY_FAILURES` vs `MAX_RETRIES`）收紧；引擎以 `beginRetryBudget(iface.maxRetries()) / endRetryBudget()` 包裹顶层调用（ThreadLocal 防线程池串账）。耗尽后在 `OutboundEngine.doInvoke` 的 catch 中分类为 `COMPENSATING`，`next_retry_at=now+3s`。
- **自检**：返回 `50201` +「进入补偿队列」（约数秒，含 4 次短重试）；`SELECT id,status,attempt_count,max_attempts,error_code,next_retry_at FROM outbound_request WHERE app_id='QD1' ORDER BY id DESC LIMIT 5;` 该行 `status=COMPENSATING`、`error_code=50201`；状态链终态 detail 含「短重试 4 次」。

### B4 超时 UNKNOWN（对账）

**操作**：建接口 `IF-QD-UNK`（`/qd/unk` → `/slow-supplier`，WireMock 延迟 5s > 读超时 3s）；想快速看到结果可把「最大重试」设为 0。

- **原理**：**读超时 / 连接异常 ≠ 失败**——请求可能已经到达供应商并产生了副作用，此时重试会造成重复。所以既不能重试也不能判死，只能标 `UNKNOWN` 交给对账。
- **设计思路**：M0-03 §3 定义 UNKNOWN 三分支——**M2 人工置位**（运维裁定：已到达 → SUCCESS / 未到达 → COMPENSATING）、**M4 TTL 自动降级**（默认 10 分钟，按 COMPENSATING 续期）、**v1.1 自动查询**（调供应商查询接口）。两种来源都写 `reconcile_audit` 审计（`source=MANUAL/TTL`），可追溯「谁/系统何时裁定」。
- **实现方式**：`OutboundEngine.classifyInvokeFailure()`（`ResourceAccessException` → UNKNOWN / `HttpServerErrorException` → COMPENSATING / `TooManyRequests` → COMPENSATING）；TTL 扫描在 `worker/CompensationWorker.scanUnknown()` → `MonitorService.downgradeExpiredUnknown()`。
- **自检**：返回 `50401`「待对账 UNKNOWN」；Monitor「状态机与对账」tab 出现 `对账中` 行，可点「置为已到达」清掉（人工对账弹窗**操作人必填**，落 `reconcile_audit`）。

### B5 状态链与短重试留痕

**操作**：Monitor「状态机与对账」→ 任一行点「状态链/详情」→ 抽屉顶部时间线。

- **原理**：`outbound_request.status` 只存当前值、被原地覆盖，无法回溯流转过程。状态链用**事件溯源**追加记录每次**真实状态变化**（`from_status → to_status` + `trigger` + `detail`）。
- **设计思路**：
  - **只记真实落库转移**：短重试发生在 `@Retryable` 内部、不写库，所以 `SENDING / RETRYING` **不产生节点**；短重试次数并入终态 detail（如「5xx 重试耗尽（短重试 4 次）」）——与设计 §6.1 声明状态机的**有意差异**，运维价值等价（能回答「重试了几次才耗尽」）；
  - **分层写入（WAN 性能决策）**：高频主路径（首送/补偿重放）请求内攒批、出口 `flushStateChain` **一次批量 INSERT**；低频运维路径（人工对账 / TTL / 重放 / 耗尽）即时写。背景：逐节点 `SELECT+UPDATE+INSERT` 在远程库下会拖慢主链路并破坏熔断窗口等时序敏感测试（实测 M4 熔断用例因此失败）；
  - **状态列与链解耦**：状态列由各路径即时 `updateState`（worker 扫描/熔断/对账依赖实时状态）；状态链只是历史镜像，允许 flush 失败丢链（只影响可观测）。
- **实现方式**：`OutboundRequestRepository.flushStateChain()` + `transition()`；`OutboundEngine` 内 `ThreadLocal CHAIN_BUFFER` 攒批；`trigger` 七值枚举（`FIRST_SEND / COMPENSATE / CIRCUIT_OPEN / RECONCILE_MANUAL / TTL_DOWNGRADE / REPLAY / EXHAUSTED`；物理列名 `trigger_src`——`trigger` 是 MySQL 保留字，API 层仍叫 `trigger`）。
- **自检**：时间线末节点带「当前」角标，与 `outbound_request.status` 一致；`SELECT o.id,s.seq,s.from_status,s.to_status,s.attempt,s.trigger_src,s.detail FROM outbound_request_state_log s JOIN outbound_request o ON o.id=s.outbound_request_id WHERE o.app_id='QD1' ORDER BY o.id DESC, s.seq;`

### B6 熔断三态（M4 核心）

**操作**：接口指向 `/breaker-supplier`（恒 500），连发 ≥12 次（默认窗口 10s / 最小 10 次 / 失败率 50%）。

- **原理**：熔断器是**快速失败闸门**——供应商持续不可用时，不再逐请求重试（否则既压垮供应商又占用线程/连接），直接短路。
- **设计思路**：**闸门前置**于 `@Retryable` Invoker 调用之前；**粒度「接口 + 供应商」**（一个坏供应商不拖垮所有接口）；**计数口径 = 每请求一次**（内部短重试不逐次计数）；OPEN 短路转 `COMPENSATING` **顺延**且 **不 incrementAttempt**（熔断期空转不消耗重试预算，也不写死信），冷却后由补偿 worker 补做。
- **实现方式**：`engine/CircuitBreaker.java` + `CircuitBreakerRegistry.java`（三态 CLOSED/OPEN/HALF_OPEN，参数失败率阈值 / 窗口 / 熔断时长 / 半开探测数）；`OutboundEngine.doInvoke` 与 `replay` 入口 `tryAcquire()`。
- **自检**：前几次每次数秒（短重试耗尽），触发后变 <0.5s 秒回（`50202`）；库状态 `50202/COMPENSATING`；注册 200 stub + sleep 31s → 放行 2 次探测 → `HALF_OPEN → CLOSED`，期间原 COMPENSATING 行被补偿补做成功。

### B7 动态映射 6 操作（可选加深）

**操作**：在 `IF-QD-OK` 上逐轮加一条映射规则，用 WireMock `/__admin/requests` 看实际出站 body。

| op | 规则填法（source → target，param） | 入站 → 出站 | 语义 |
|---|---|---|---|
| `rename` | `state` → `order_state`（空） | `{"state":"PAID"}` → `{"order_state":"PAID"}` | 保形重命名 |
| `typeCast` | `qty` → `qty_num`，`INT` | `{"qty":"5"}` → `{"qty_num":5}` | 按类型注册表转换 |
| `enumMap` | `state` → `order_state`，`PAID→已支付` | `{"state":"PAID"}` → `{"order_state":"已支付"}` | 枚举映射 |
| `default` | source 空 → `region`，`CN` | 任意 → 含 `{"region":"CN"}` | 常量注入（仅它可空 source） |
| `condition` | `state` → `state`，`state == 'PAID'` | PAID 保留；否则按 null_strategy | Aviator 条件过滤 |
| `aggregate` | `items`(数组) → `total`，`SUM` | `{"items":[1,2]}` → `{"total":3}` | source 须数组 |

- **原理**：映射规则是**运行时解释**的（管理员随时改），不能用编译期代码生成；6 种 op 覆盖「改名/改型/改值/补值/条件/聚合」。
- **设计思路**（M0-02）：**规则间无可见性**（source 一律读入站原始模型，D2）；**空规则=透传，非空=白名单**（D3）；**null 触发优先于 op 本体**（source 缺失/NULL 即按 `nullStrategy` 处理，D5）；`condition` 是唯一**先求值再判空**的 op（否则「条件过滤」退化成「字段必填」）；表达式内核选 **Aviator 5**（纯解释器、无反射、天然防注入沙箱）。
- **实现方式**：`mapping/MappingEngine.java`（规则执行器）+ `mapping/ConditionEvaluator.java`（Aviator 封装）+ `mapping/TypeRegistry.java`（类型转换矩阵）；`nullStrategy` 四值 KEEP / NULL / DEFAULT / ERROR。
- **自检**：每改一条规则**先点「测试接口」再 curl**（养成 M2 起的快速验证习惯）；`curl -s http://localhost:18080/__admin/requests?limit=3 | jq '.requests[].request.body'`。

### B8 健壮性抽查

```bash
# 报文 >1MB → 40002 且不落运行表（双道防护：Content-Length 预检 + 读后兜底）
head -c 1100000 /dev/zero | tr '\0' 'a' > /tmp/big.json
curl -s -X POST http://localhost:8080/qd/ok -H "Content-Type: application/json" --data-binary @/tmp/big.json
```

- **原理 / 设计思路**：报文超限 / XML 混合内容 / XXE / SSRF 都属「**链失败或防护拒绝，不污染状态机**」（M0-01 D7 / D-M4-6）——只落 `call_log`，不写 `outbound_request` / `inbound_delivery`。这是全项目最重要的断言口径之一。
- **实现方式**：`config/BodySizeLimitInterceptor.java`（第一道，按 Content-Length）+ `GatewayController`（第二道，chunked 无 Content-Length 时按实际字节）；`CallbackUrlValidator`（回调地址 SSRF）；`XmlProtocolAdapter`（XXE/深度）。
- **自检**：`code=40002`；`SELECT COUNT(*) FROM outbound_request WHERE app_id='QD1';` 无新增行。

## 4. 环节 C：真实供应商闭环（evoLink 生图，Flow A + Flow B）

> 定位：真实第三方 AI 生图服务（evolink.ai）的端到端黄金用例，**同 fastmoss「可选联调」定位**——真实调用计费 + 依赖公网，**不进 `mvn clean test`**。

### P2 回调闭环（需公网 HTTPS，验证 Flow B 真实送达）

#### P2.0 先分清「两跳地址」（最容易混）

```
evolink（云端）
  │ ① 完成时主动 POST → 收件方 = 生图请求 body 里的 callback_url（给 evolink 看的公网入口）
  ▼    填 https://<子域名>.ngrok-free.app/ai/cb（隧道 → :8080 → 平台路由 /ai/cb → IF-EVL-CB）
平台 :8080（入站接口 IF-EVL-CB）
  │ ② 平台把通知转投给业务收件端 → 收件方 = 接口表单的「回调地址（送达）」
  ▼    填 http://localhost:18080/delivery-evl（WireMock 假业务端）
WireMock 桩（本地假业务收件端）
```

> 判定口诀：**`callback_url` 给 evolink（公网 HTTPS）；「回调地址（送达）」给平台转投业务（本地桩）**。两处都填 ngrok 会环路；callback_url 填 localhost 则 evolink 公网够不着。

- **原理**：Flow B 是**两跳、两个契约**——evolink 与平台的契约（回调报文 + ack），平台与业务系统的契约（送达报文）。平台在中间做**解码 → 映射 → 重编码**，不转发原始 body。
- **设计思路**：**没有「零声明全量透传」**——送达报文字段来自接口的 OUT 声明 + 映射，所以必须**先拿到 evolink 真实回调样例再声明字段**（下述 A/B）。这也是为什么 P2 不能凭想象填字段。
- **实现方式**：`engine/InboundEngine.handle()`（路由 → 链 → 落 PENDING → 同步送达 → 回 ack）；送达 URL 取 `iface.callbackUrl()`。

#### P2.C 建入站回调接口 `IF-EVL-CB`

**主表单**

| 字段 | 填/选 |
|---|---|
| 类型 | **入站回调**（切后表单互斥联动：供应商接口路径禁填、出现回调地址与 ACK/送达字段） |
| 方法 / 平台侧路径 | `POST` / `/ai/cb` |
| 名称 / 接口标识 | `evolink 回调` / `IF-EVL-CB` |
| 归属应用 / 分组 | `EVOLINK` / `默认分组` |
| **回调地址（送达）** | `http://localhost:18080/delivery-evl` |
| 协议 入站 / 出站 | JSON / JSON |
| 读超时 / 最大重试 | 默认（3000 / 4） |

**请求参数区（按 A 抓到的真实样例逐字段声明，关键一步）**

- **入站参数（IN，= evolink 回调里的字段）**：对照样例顶层字段逐条加（字段名同 JSON 键、类型按值选、必填按需）。示例（以样例为准）：`status`(string)、`task.id`(string，object 用点号子字段)、`event_id`(string)；
- **出站侧送达参数（OUT，= 送给收件端的字段）**：**至少一条**（C5 硬必填）。最省事：声明与 IN 同名的 `status`；
- **字段映射**：为要送达的字段各加一条 `rename`（source/target 同名，param 空，`null_strategy=KEEP`）；
- **ACK 回执字段**：留默认（evolink 只要 2xx 即认为成功；不声明也能回结构 ack）；
- **回调验签适配器**：留空（Noop，evolink 回调无签名）。

保存 → 「发布」→ 「已发布」。（缺发布：evolink 回调平台会 404）

- **原理**：入站链同样是六阶段，但入站鉴权阶段执行的是 **CALLBACK_AUTH（回调验签）**而非调用方鉴权；解码用 `protocol_in`；映射 IN→OUT；编码用 `protocol_out` 产出**送达报文**。
- **设计思路**：
  - **回调验签凭证独立于出站签名**（M0-04 / ADR 3）——evolink 无回调签名，所以留空 Noop；若供应商将来提供签名，只需补一个 HMAC 回调验签实例并绑 `CALLBACK_AUTH`，接口无需改；
  - **OUT 必填的契约原因**：平台在 Flow B 是「构造新报文投递」，送达报文可能被快照重放（`inbound_delivery.payload`），必须有确定的 OUT 结构；
  - **ACK 是回执不是响应**：只回「收到了」，与送达解耦（§5.5 / ADR 4）。
- **实现方式**：`ChainEngine.assemble()` 中 `INBOUND` 分支解析 `CALLBACK_AUTH`（接口覆盖 → 应用默认 → Noop）；`InboundEngine.handle()` 把请求头注入 `ctx.attrs("headers")` 供验签读取（大小写不敏感 TreeMap，评审 N1 修复）。

**逐项验收**

| 验什么 | 怎么看 |
|---|---|
| 送达报文 | `curl -s http://localhost:18080/__admin/requests?limit=5 \| jq '.requests[].request.body'` → 为 OUT 声明字段编码（含 status），且**不含**出站签名 `Authorization` 头 |
| 送达状态 | `SELECT id,delivery_status,attempt_count,callback_url_snapshot,ack_to_partner FROM inbound_delivery ORDER BY id DESC LIMIT 5;` → `ACKED` |
| 双向日志 | Monitor「调用日志」：IN（evolink 回调）+ OUT（送达）各一条，按 `traceId` 收敛 |
| ack | 平台恒回 `HTTP 200` + 结构 ack（evolink 侧无「回调失败」提示）。ack 是回给 evolink 的，**不会出现在 delivery-evl 桩里**——想看原样可 `curl -v` 直接打平台 `/ai/cb` |
| 状态链 | ⚠ 状态链本期**只做出站**，入站行不会出现在「状态机与对账」；入站看 `inbound_delivery.delivery_status` |

**首包对不上 / 校验失败的处理**：声明字段与样例不符 → 解码/映射异常（400 信封，**不落运行表**，D7）→ 回 P2.C 按真实样例改字段与映射，重新触发；只想先跑通闭环可 OUT 只留最确定存在的一条字段。

- **原理**：入站「落库即 PENDING、`next_retry_at=now+5s`」——防补偿 worker 与同步送达**抢跑**；同步送达成功转 ACKED；崩溃后由 worker 自然兜底。**ack 与送达解耦**：送达失败也回 200，供应商不重发。
- **实现方式**：`InboundEngine.handle()`（`INITIAL_DELIVERY_DELAY_SECONDS=5`）+ `deliver()`（复用 `UpstreamInvoker` 短重试）+ `safeState/safeDeadLetter`（运行表写入抛异常不冒泡，保证 ack 恒 200，评审缺陷 2 修复）；`AckRenderer.render()`（按 `protocol_in` 渲染）。

## 5. 环节 D：真实 XML 出站（USGS / hnrss / 自收自发 / 反例）

> 定位：**免密钥、可真调**的真实 XML 用例——验证「真发 HTTP → 真收 `application/xml` → XML 解码 + RESP 白名单 + 同名合并」整条出站链路，无需 WireMock、无需供应商账号。
> 与环节 C 的关系：C 验 JSON 真实供应商 + 回调闭环，D 补真实 **XML 响应**方向。同属「需真实外部依赖」，**不进 `mvn clean test`**。

### D0 可用端点（实测 2026-09-10）

| 端点 | 实测返回 | 根剥离后模型 | 可解码 | 适用 |
|---|---|---|---|---|
| `GET https://earthquake.usgs.gov/earthquakes/feed/v1.0/summary/2.5_day.atom` | `200 application/atom+xml` | `<feed>` → `{title,updated,author,id,icon,entry:[…]}` | ✅ | **首选**：根下字段多，能实证 RESP 白名单 |
| `GET https://hnrss.org/frontpage` | `200 application/xml` | `<rss>` → `{channel:{…item:[…]}}` | ✅ | 实时新闻，演示真实供应商数据 |
| `GET https://httpbin.org/xml` | `200 application/xml` | — | ❌ **40002** | 反例：含混合内容，**勿用** |

> **只认 GET**：平台对 GET/DELETE 不带 body（`UpstreamInvoker` 保守处理），出站 XML 编码产物被丢弃，只验响应解码——这正是本环节要覆盖的方向（XML 请求方向见 D3）。
> **响应按 `protocol_out` 解码，不看响应 `Content-Type`**（D-M3-4）；故 atom/RSS 的 `application/atom+xml` 也能用 XML 适配器解。

### D1 X-R1 基础：USGS atom + RESP 白名单（约 5 分钟）

**操作**

1. 应用 `USGSXML`：服务地址 `https://earthquake.usgs.gov`；鉴权/回调验签/报文全留空（Noop）→ **启用**；
2. 分组 `演示分组`（归属 `USGSXML`）；
3. 接口 `IF-XML-REAL`：

| 字段 | 填/选 |
|---|---|
| 类型 | 出站中转 |
| 方法 / 平台侧路径 | **GET** / `/demo/xml-real` |
| 供应商接口路径 | `/earthquakes/feed/v1.0/summary/2.5_day.atom` |
| 协议 入站 / 出站 | JSON / **XML**（**关掉「入站=出站」联动**，手动把出站改 XML） |
| RESP 响应字段 | 一条：name=`entry`、type=`array` |
| 请求参数 / 映射 / 绑定 | 全空（透传、Noop） |

→ 保存 → **发布**；

```bash
curl -s http://localhost:8080/demo/xml-real | jq '.data.entry | length'   # 预期 ≥1（当日实况）
```

**预期**：`code=0`，`data` **只剩** `entry`（根下 `title/updated/author/id/icon/link` 全被滤）；每个 entry 形如：

```json
{"entry":[{"id":"urn:earthquake-usgs-gov:nc:75432942","title":"M 3.6 - 26 km W of Petrolia, CA",
            "updated":"2026-09-10T01:40:13.935Z","link":null,
            "summary":"<p class=\"quicksummary\">…</p>（CDATA 原文）",
            "point":"40.29349 -124.58516","elev":"-19229.99",
            "category":[null,null,null]}]}
```

**断言点（对应 D-M3-1 / D-M3-3）**：

| 现象 | 语义 |
|---|---|
| 根元素 `feed` 剥离 | 根名不进模型（编解码对称） |
| `title` 等根下字段全滤 | **RESP 白名单实证** |
| `<link .../>` → `null` | 空元素 / 纯空白 → NULL |
| 重复 `<category>` 合并为数组 | 同名元素多次 → ARRAY |
| `summary` 保留 `<p>` 原文 | CDATA 按文本处理 |
| `georss:point` → `point` | 命名空间前缀剥离（localName） |

**变体（过滤差异直观可见）**：清空 RESP 再调 → `data` 多出 `title/updated/author/id/icon/link`（`author` 是对象 `{name,uri}`）——这就是「空声明=不过滤」。

- **原理**：XML 是**同一份数据的不同格式**，平台在链上先解码成**格式无关的统一内部模型**（树 + 类型标注），再做映射/过滤/编码，所以「JSON 进 XML 出」「XML 进 JSON 出」只是链两端协议不同。
- **设计思路**：
  - **用 Woodstox StAX 事件流，而非 XmlMapper 树模型**：`readTree` 无法区分 XML 属性与子元素，事件流能精确实现 D-M3-1 语义（同名合并 / 空元素 / CDATA / 前缀剥离 / 属性保留）；
  - **首期语义边界**：混合内容（文本与子元素并列）→ `40002` 拒绝（有意设计，不是 bug）；DTD/实体声明 → `40002`（XXE 防护）；深度上限 512；
  - **响应方向类型转换归 RESP 过滤**（`field_def.type`），不走进站参数声明（D-M3-3）。
- **实现方式**：`adapter/protocol/XmlProtocolAdapter.java`（StAX 编解码，`XMLInputFactory` 禁 DTD/外部实体）+ `engine/RespFieldFilter.java`（白名单 + 类型矩阵）+ `ChainEngine.decodeResponse()`（按 `protocol_out` 走同一条 DECODE 路径）。

**失败自检（实测高频坑：`code=0` 但 `.data.entry` 为空）**：十有八九是接口的**出站协议仍是 JSON**（前端默认联动开着，只改了入站）——Atom XML 被按 JSON 宽松解码成空对象，RESP 过滤后 `data={}`：

```bash
# ① 完整信封 + data 键集
curl -s http://localhost:8080/demo/xml-real | jq '{code,msg,data_keys:(.data|keys)}'
# ② 查接口真实配置：protocolOut 必须为 "XML"
ID=$(curl -s "http://localhost:8080/api/admin/interfaces?keyword=IF-XML-REAL" | jq -r '.data[0].id')
curl -s "http://localhost:8080/api/admin/interfaces/$ID" | jq '.data|{method,protocolIn,protocolOut,upstreamPath,status}'
curl -s "http://localhost:8080/api/admin/interfaces/$ID" | jq '.data.fieldDefs'   # 应有 kind=RESP name=entry type=array
# ③ 库中一锤定音：out_payload={} 是解码失败（协议没选 XML）；含 "entry" 则是 RESP 名称/类型写错
SELECT status,error_code,out_payload FROM outbound_request ORDER BY id DESC LIMIT 1;
```

**修复**：编辑接口 → 取消「入站=出站」联动 → 出站协议改 `XML` → 保存（版本 +0.1，`ConfigChangedEvent` 即时生效）——**不必重建接口**。

### D2 X-R2 变体：hnrss 实时新闻

- 应用服务地址改 `https://hnrss.org`（或另建 `HNXML`）；供应商接口路径 `/frontpage`；协议 JSON → **XML**；RESP 声明 `channel`(object) → 发布；
- `curl -s http://localhost:8080/demo/xml-real | jq '.data.channel.title'` → `"Hacker News: Front Page"`；
- `.data.channel.item | length` → 当日新闻条数（**每次调都不同 = 真实实时数据**）；
- 结构点：`<channel>` 下的 `<link>`（有文本）与 `<atom:link/>`（自闭合）同名合并为 `["https://news.ycombinator.com/", null]`；`<item>` 内标题/描述均为 CDATA；`<dc:creator>` → `creator`（前缀剥离）。

- **原理 / 设计思路**：与 D1 同一条链，只换数据源——证明**「配置驱动」而非「编码驱动」**：同一个接口定义 + 同一套适配器，换 baseUrl/path/RESP 就能接不同供应商。

### D3 反例：httpbin.org/xml（混合内容 → 40002，勿用）

`GET https://httpbin.org/xml` 的第二个 `<slide>` 里
`<item>Why <em>WonderWidgets</em> are great</item>` 是**混合内容**（文本与子元素并列，实测 2 处），`XmlProtocolAdapter` 直接拒（`40002 报文格式非法：混合内容不支持`）。

- **价值 = 真实反例**：用它建接口调用一次，可实证「真实报文触发的 40002」；断言点 = 信封 `code=40002` 且该请求**不落 `outbound_request`**（链失败不污染状态机）。
- 另外该端点 `POST` → **405**（只认 GET），更不可用于 XML 请求方向。

### D4 X-R3 补测：XML 请求方向的「自收自发」

> 公开真实服务里没有接受平台出站 XML 请求体的（原因见「边界」），要验证 XML **编码**方向，让平台自己当服务端。

**操作**

1. 建**入站回调**接口 `IF-XML-IN`：类型 INBOUND、方法 POST、平台侧路径 `/demo/xml-in`、**协议入站 XML**、回调地址指向本地可达收件端（如 WireMock `/delivery-ok`）、ACK 字段 `returnCode`(number) / `returnMsg`(string) → **发布**；
2. 直接 POST 真实 XML 到平台：

```bash
curl -i -X POST http://localhost:8080/demo/xml-in \
  -H "Content-Type: application/xml" \
  -d '<request><event_id>evt-1</event_id><order_id>ORD-1</order_id></request>'
```

**预期**：平台回 **XML 格式 ack** `<response><returnCode>0</returnCode><returnMsg>success</returnMsg></response>`（`AckRenderer` 按 `protocol_in` 渲染，XML 进 → XML ack）。

- **原理**：ack 渲染格式**跟随入站协议**——供应商按 XML 回调，就应收到 XML 应答（否则对端解析不了）。根元素取约定名 `response`。
- **实现方式**：`engine/AckRenderer.java` —— 读 `interface_field_def(kind=ACK)` 按 `sort_order` 排序：第 1 个字段 = code（值 `0`）、第 2 个 = message（值 `"success"`），其余声明忽略 + warning；无声明 → 兜底平台信封 `{code:0,msg:"ok",data:null}`；XML 时复用 `XmlProtocolAdapter` ENCODE 并传 `xmlRoot=response`。
- **自检**：`curl -i` 看到 `Content-Type: application/xml` + `<response>` 结构；`inbound_delivery` 新增一行。

### D5 边界（别误判为缺陷）

- **XML 出站根元素写死 `<request>`**：`XmlProtocolAdapter` 默认 `xmlRoot=request`（仅 ACK 渲染传 `response`）；协议适配器不参与绑定、`interface` 表无协议参数字段（M0-01 D5「首期一律平台默认参数」）。因此 **SOAP 服务**（要 `<soap:Envelope>`、带命名空间）与任何要求特定根元素的 REST-XML 服务**当前调不通**，属已知设计边界；
- 要接真实 XML 供应商需先扩展协议适配器（rootElement / namespace / SOAP 可配置）——**属 M0-01 D5 口径变更，先过评审再排期**，勿在验收里当缺陷报；
- 这些都是公共免费服务，仅用于联调抽查，**不做稳定性/性能断言**（实测 NASA RSS → 429、w3schools → 403）。

### D6 收尾与回归隔离

- 验完按 §9.2 清理 `USGSXML` / `HNXML` / `IF-XML-IN` 造数（先清运行表再删接口/分组/应用）；
- **不进 `mvn clean test`**（真实外部依赖 + 公网不确定性，同 §9.5「需真实外部依赖」边界）；
- 踩坑速查：`40401` → 应用没启用或接口没发布；`40002 混合内容不支持` → XML 含「文本+子元素」并列（如 httpbin `/xml`），换 USGS/hnrss；`40002` 其他 → 端点返回的不是 XML；`data` 字段全空 → RESP 声明名与根下字段名不符；`50401` → 公网慢，调大读超时。

## 6. 环节 E：入站回调闭环（本地 HMAC 版，Flow B 全语义）

> 环节 C 的 P2 验证了「真实供应商 Noop 验签」的入站闭环；本环节用**本地 WireMock + HMAC 验签**补齐 Flow B 的**安全与容错语义**（验签失败 / ack 解耦 / 快照漂移 / 送达 4xx / 防重放）。
> 对应《整体测试方案》§6 B1–B6 + 《M3手动验收测试方案》。

### E1 前置配置（应用沿用 `M3DEMO`，与测试方案命名隔离对齐）

| 步骤 | 内容 |
|---|---|
| ① 回调凭证 | 应用 `M3DEMO` 凭证区 → 类型**回调验签（CALLBACK）** → 值 `demo-secret` |
| ② 验签适配器 | 适配器管理 → 鉴权 → 实现 `HMAC 回调验签` → 标识 `ADP-HMAC-DEMO`、算法 `HMAC-SHA256`、签名头 `X-Partner-Signature`、容差 `300`、防重放开 |
| ③ 应用绑定 | 应用 `M3DEMO` 编辑 → **回调验签适配器** = `ADP-HMAC-DEMO` |
| ④ 入站接口 | `IF-CB-01`：INBOUND、POST `/m3/cb`、回调地址 `http://localhost:18080/delivery-ok`、IN 参 3 条 / OUT 送达参 3 条、保形 `rename` 映射 3 条、ACK 字段 `returnCode`(number)+`returnMsg`(string)、CALLBACK_AUTH 绑定留空（继承应用默认）→ **发布** |

### E2 用例矩阵

| 用例 | 动作 | 预期（含为什么） |
|---|---|---|
| **B1 正常闭环** | 详情「模拟回调」→ 发送 | 供应商视角 ack `{"returnCode":0,"returnMsg":"success"}` + 送达状态 `ACKED`；`inbound_delivery` 新行 ACKED、payload=**映射后**的送达报文 |
| **B2 验签失败** | curl 手发错签名 / 时间戳超容差 | HTTP 401（`40100` 签名错误 / `40101` 过期）；**查库无新行**（D7 不污染状态机）；`call_log` 有记录 |
| **B3 ack 与送达解耦** | 回调地址改 `/delivery-flaky`（前 8 次 500 后放行）→ 模拟回调 | ack **仍即时**回（供应商不重发）；库 PENDING → worker 每 3s 重送 attempt 递增 → 放行后 ACKED |
| **B4 快照漂移防护** | 回调地址改 `/delivery-fail`（恒 500）→ 重送耗尽前把接口地址改成 `/delivery-ok` | 重送**仍按旧快照** `/delivery-fail` 失败（`callback_url_snapshot` 语义）→ 耗尽 DEAD_LETTER + `dead_letter(biz_type=INBOUND)` |
| **B5 送达 4xx** | 回调地址指向返回 4xx 的 stub | 送达失败 → **直接死信**（4xx 不无限重试，与出站口径对齐） |
| **B6 防重放** | 开防重放 → 容差窗口内重放同一签名报文两次 | 第二次被拒 `40100`「重复请求」 |

### E3 原理 / 设计思路 / 实现方式

- **原理**：Flow B 是「**验签 → 适配 → 落库 → 送达 → 回 ack**」五步，其中 **ack 与送达解耦**——ack 表示「平台收到了」，送达表示「业务系统收到了」，两者成败独立。
- **设计思路**：
  - **凭证独立**（ADR 3）：回调验签用 CALLBACK 凭证、出站签名用 OUTBOUND 凭证；**验签新旧并存**（ROTATING 也参与验签），**签名只用 ACTIVE**；
  - **快照语义**（`callback_url_snapshot`）：重送按**入站时快照**的地址，不随接口后续改址漂移——防止「重送打到新地址」造成重复投递或语义错乱；
  - **重放不重走链**：重送直接用 `payload` + `callback_url_snapshot`（不再映射），因为入站映射结果已在首送时固化；
  - **密钥外泄防护（M3 评审缺陷 1 修复）**：入站送达请求**不得带**应用出站签名头——`ChainEngine` 对 INBOUND 的 `OUTBOUND_AUTH` 阶段强制 Noop，`不解析应用默认供应商签名、不注入出站凭证`；
  - **入站无 UNKNOWN 对账态**：送达失败保持 PENDING 续期（重送安全性按 ADR 5 依赖业务端幂等）；4xx 直接死信。
- **实现方式**：`adapter/auth/HmacCallbackVerifyAdapter.java`（`Hex(HMAC(secret, timestamp + "." + rawBody))`，时间戳头 `X-Timestamp`，防重放内存缓存单实例）+ `adapter/auth/HmacSigner.java`（模拟回调自签名）+ `engine/InboundEngine.java`（`claimForRedeliver` 条件认领，防并发双扫重复送达；`safe*` 包裹保证 ack 恒 200）+ `InterfaceController.testCallback()`（模拟回调：按 CALLBACK ACTIVE 凭证签名后自调真实网关路径，返回 ack + 送达状态）。
- **自检**：
  - **密钥外泄回归点**：每次回归都瞄一眼 WireMock 收到的送达请求头——**不应含** `Authorization: Bearer …`；
  - `SELECT id,delivery_status,attempt_count,callback_url_snapshot,ack_to_partner FROM inbound_delivery ORDER BY id DESC LIMIT 5;`
  - Monitor「调用日志」IN / OUT 双向按 traceId 收敛。

### F1 Monitor 五区块与 Dashboard

| 区块 | 演示点 |
|---|---|
| 统计卡 | 今日调用量 / 成功率随演示真实变化。**口径**：今日成功率 = 今日终态（SUCCESS+DEAD_LETTER）中 SUCCESS 占比，当日无终态显示 100 |

| 死信 | 类型/状态过滤（bizType=OUTBOUND/INBOUND、status=PENDING/HANDLED）+「报文」预览 + PENDING 才可重放 |
| 告警 | 规则管理 → 新建规则（指标选「死信PENDING堆积（条）」、阈值 `> 0`）→ 扫到触发后 `alert_event` 出记录、冷却 5 分钟 |
| Dashboard | 主卡（含积压角标深链）+ 1h/24h/7d 趋势（IN 柱 / 出站终态失败线）+ P50/P99 + TOP 接口（每行「监控」深链）+ 运行队列面板 |

- **原理**：**调用日志（call_log）**回答「这次请求发生了什么」；**运行表 + 状态链**回答「这条业务请求走到哪了」；**指标（Micrometer）**回答「整体健康度」；**告警**回答「什么时候该叫我」。四者分层，量级与保留期不同。
- **设计思路**（D-M4-4）：
  - call_log **每个业务请求两条**（IN：调用方/供应商 → 平台；OUT：平台 → 供应商/回调地址），**适配器链节点明细不进 call_log**（归 OTel span，控量 + 语义边界）；
  - 切面 `@Order(HIGHEST_PRECEDENCE)` 位于 `@Retryable` advisor **之外**——每业务请求恰一条 OUT（短重试不逐次落日志）、Timer 时长含全部重试；
  - **脱敏先于落库**（内存中不留原始值）：header 敏感键值「前 4 + `****` + 后 4」（长度 < 12 全遮）；body 内 `secret/token/password/apikey/credential` 键值同规则、大陆手机号遮中段；超 4096 字符截断缀 `...[truncated]`；
  - **异步批量写**（`CallLogWriter`）：有界队列 1000，满则丢弃 + Counter（`apicenter.calllog.dropped` 应恒 0/不增长）——监控数据可容忍丢失，**不阻塞主链路**。
- **实现方式**：`aspect/CallLogAspect.java` + `aspect/SensitiveDataMasker.java` + `worker/CallLogWriter.java` + `service/MonitorService.java` + `worker/AlertWorker.java`。
- **自检**：日志「明细」抽屉**无明文密钥**；traceId 从响应头 → `call_log.trace_id` → 后端日志可全文检索。

### F2 对账（UNKNOWN 人工 + TTL）

- **操作**：调超时接口得 UNKNOWN → Monitor「对账（UNKNOWN）」行 → 实际到达则「置为已到达（SUCCESS）」/ 未到则「置为未到达（COMPENSATING）」→ 弹窗**操作人必填**、依据可选 → 保存；TTL 则什么都不做，等 10 分钟。
- **原理 / 设计**：对账是「**用外部事实收敛不确定状态**」——必须先确认供应商是否真的收到了，再决定成功还是补偿。双来源都写 `reconcile_audit`（`source=MANUAL/TTL`），审计可追溯。
- **实现方式**：`service/MonitorService.java`（人工置位 + `downgradeExpiredUnknown`）+ `repository/ReconcileAuditRepository.java` + `CompensationWorker.scanUnknown()`。
- **自检**：`SELECT * FROM reconcile_audit ORDER BY id DESC LIMIT 10;`（`source` 区分 MANUAL/TTL）。

### F3 死信重放

- **操作**：Monitor 死信区 → PENDING 行「重放」。
- **原理**：重放**不是简单转发原始响应**，而是按死信 `ref_id` 关联的运行记录 `in_payload` **重走整链**（配置/凭证取最新）——所以「改好配置再重放」是有效运维手段。
- **实现方式**：`service/MonitorService`（重放）+ `DeadLetterRepository`（重放后立即置 `HANDLED`，再次重放被拒「死信已处理」；关联运行记录置回 COMPENSATING、attempt 清零）→ ≤3s 后补偿 worker 重走。
- **自检**：重放后死信行转 HANDLED；关联 `outbound_request` 转 COMPENSATING → 成功则 SUCCESS，仍失败则再次耗尽产生新死信。

### F4 防护：QPS / 日配额 / IP 名单

| 项 | 操作 | 预期 |
|---|---|---|
| QPS | 应用编辑 QPS 填 `50` → `wrk -t4 -c200 -d10s` | 通过量 ≈50/s，其余 `42901`；**拒绝不落运行表** |
| 日配额 | 日调用量上限填 `10` → 调 11 次 | 第 11 次 `42902`；重启后清零 |
| IP | 黑名单填 `127.0.0.1` → 本地调用 | `40103` 拒绝 |

- **原理 / 设计**（D-M4-6）：防护闸门放在**路由命中后、落运行表之前**——拒绝**不污染状态机**（与链失败 D7 同口径）。
- **实现方式**：`service/GatewayGuard.java`（固定秒级窗口 + `(appId, yyyyMMdd Asia/Shanghai)` 日计数 + 精确 IP 匹配；`trust-xff` 默认 false 防伪造 XFF 绕过）。
- **已知语义（非缺陷）**：QPS/日配额/熔断/告警是**单实例内存口径**（多实例各自计数、重启清零，v1.1 分布式）；QPS 固定秒级窗口交界最坏 2×limit。

### G1 版本快照与回滚（V1）

**操作**

1. 建出站接口 `IF-M5-VER`（`/m5/ver` → `/echo-ok`，映射 `rename state→order_state`）→ 发布；首次创建留空说明 → v1.0 `change_note=初始创建`；
2. 编辑：映射 op 改「枚举映射」、param `PAID→已支付`（编辑表单底部「变更说明（可选）」= `X-Change-Note` 请求头，是**备注**）→ 保存 = v1.1，版本历史自动生成摘要「变更：…」；
3. 点「变更详情」看结构化 diff（JSON）；点「快照」看完整 `config_json`；
4. 选 v1.0 行 →「回滚到此版本」→ 弹窗**只二次确认**（无 operator/reason）→ 确认。

**预期**：版本变 v1.2（**每次 +0.1、只增不倒退**）、状态仍「已发布」（快照不含 status）；`change_note=回滚至 v1.0`；「变更详情」可用（`type=ROLLBACK`）。行为验证：curl `/m5/ver` 后供应商收到 `order_state=PAID`（映射恢复 rename）。

- **原理**：**配置变更即版本**——每次保存生成一份完整配置快照（`config_json`），版本历史可查、快照可重建。回滚 = 用历史快照**全量重建** `InterfaceRequest` 走正常更新路径（不旁路校验）+ 乐观锁防覆盖。
- **设计思路**：
  - 版本号**只增不回退**（回滚也 +0.1）——保证「历史是单向的账本」，避免版本号歧义；
  - **快照含 appId 不含 status**——回滚不应改变生命周期（发布/下线是运维动作，不是配置内容）；
  - 发布/下线**不生成版本**（生命周期流转 ≠ 配置变更）；
  - 变更说明走 **`X-Change-Note` 请求头**（不扩展 `InterfaceRequest` DTO），随 PUT 保存写入新快照；回滚 body `{targetVersion, operator, reason, currentVersion}`（目标缺失 `40403` / 乐观锁冲突 `40001`）。
- **实现方式**：`service/SnapshotSerializer.java`（config_json 序列化/反序列化）+ `service/SnapshotChangeDiff.java`（自动摘要；旧快照缺失时回退现场构建旧 JSON，保证摘要必生成）+ `repository/SnapshotRepository.java` + `InterfaceController` 的 `/versions`、`/versions/{version}`、`/rollback` 端点。

### G2 绑定切换即时生效（V2，D6' 验证）

**操作**：新建两个**同实现**信封适配器实例并都启用：`ADP-ENV-1`（v9.1，`codeField=code`、`successValue=0`）与 `ADP-ENV-2`（v9.2，`codeField=status`、`successValue=ok`）——同 `(impl, version)` 允许多启用，只需**名称不重复**；接口绑定 `ADP-ENV-1` → 发布 → 调用；编辑改为 `ADP-ENV-2` → 保存 → **立即**调用。

**预期**：切换后**立即**（不等 5 分钟）收到 v2 结果——`ConfigChangedEvent` 事件失效的实测；「测试接口」响应 `data.chainTrace` = `[{role:MESSAGE, adapterId:ADP-ENV-2, impl:EnvelopeMessageAdapter, version:9.2}, …]`（test 端点强制实时解析，永远反映当前绑定）；停用绑定实例 → 调用不 500，自动回退（应用默认 → Noop）且日志 warn「适配器绑定回退」。

- **原理与实现**：见 A3（D6'）+ A6（装配与事件失效）。
- **留痕三通道对照**：后端日志「链装配 … 绑定解析 → MESSAGE=…」（通道 1）与 chainTrace（通道 3）内容一致；span tag（通道 2）供压测/链路面看。
- **自检**：`curl -s "http://localhost:8080/api/admin/interfaces/$ID" | jq '.data.bindings'`；编辑保存后**立刻** curl（验证事件失效，不等 TTL 5 分钟）。

### G3 接口复制（V3）

**操作**：接口详情「复制」→ 弹窗（**code/path 必填且置空由你填**、名称默认「{源名} 副本」、供应商路径/回调地址留空 = 沿用源）→「复制为草稿」。

**语义**：固定归入**源应用/源分组**（不支持跨应用）；产物 **DRAFT v1.0**，`change_note=复制自 {源code}#v{源版本}`；凭证沿用本应用；**快照历史与运行数据不复制**。

- **设计思路**：复制是「**从当前配置派生一份新草稿**」，不是克隆历史——所以新接口从 v1.0 起步，源接口与版本历史不受影响；强制 DRAFT 是为了让人先确认再发布。
- **实现方式**：`POST /api/admin/interfaces/{id}/copy` body `{"code","path","name","upstreamPath","desc"}` → 返回新 id；code/path 撞库与 create 同文案 `40001`。
- **自检**：复制出站接口 curl 成功（报文与原一致）；新接口子表与源等价、可独立编辑/回滚；复制入站接口「模拟回调」闭环。

### G4 种子与数据重置（V4）

- 种子默认**不自动导入**（`app.api-center.seed.enabled=false`）：需要 fastmoss 基线时 `POST /api/admin/seed/import`（幂等/增量补齐）；
- 清库脚本 `src/main/resources/doc/reset-dev.sql`（默认 TRUNCATE、自增从 1 起、adapter 保留；附录 A DELETE、附录 B 连 adapter 一起重置）；
- **验收动作**：清库 → 重启 → `/api/admin/apps` 为空 → `POST seed/import` → 出现 fastmoss 数据；重复 import 幂等不重复插。
- **设计思路**：种子做成**显式幂等命令**而非启动副作用——避免「开发库被演示数据污染」；清库脚本与建表脚本同目录，保证「建/清」对称。
- **实现方式**：`seed/SeedDataInitializer.java` + `controller/admin/SeedController.java`。

### 11.4 演示常见问题（速查）

| 现象 | 首查 |

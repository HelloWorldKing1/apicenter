# 低代码集成平台原型 · 落地可行性报告

> 原型：`../低代码集成平台原型.html`
> 现有实现：`com.deepx.apicenter`（Java 21 · Spring Boot 4.1 · Spring Framework 7）
> 关联文档：`设计文档.md`、`实现指南.md`、`原型说明文档.md`

---

## 1. 背景与目标

当前 apicenter 是「代码写死」的 API 三方调用组件：字段映射靠 MapStruct 编译期生成、渠道路由在 `PartnerInvoker` 里 `if/else`、渠道配置在 `application.yaml`。每接入一个新第三方都要改 Java 代码、重新编译发布。

原型（低代码集成平台）演示了「**配置驱动**」的目标形态：用户在界面配置**源数据源 → 处理步骤（算子编排）→ 目标接口**，以及定时调度、接口契约、安全策略、运行监控，系统据此执行 API 中转。

本报告评估：**将该原型落地到现有 apicenter 技术架构的可行性**，重点回答「哪些能复用、哪些要新建、风险在哪、怎么演进」。

## 2. 现有技术架构盘点（可复用资产）

| 资产 | 位置 | 落地复用价值 |
|---|---|---|

| `OrderSyncService.RequestStatus` 出站状态机 | `service/OrderSyncService.java` | 编排执行的状态机载体复用 |
| `CallbackDeliveryService`（入站送达 + 补偿） | `service/CallbackDeliveryService.java` | Flow B 入站复用 |
| `CompensationWorker` / `IncrementalSyncJob` | `worker/` | 补偿、定时增量拉取复用 |

**结论**：现有 apicenter 已经具备「连接、适配、可靠传输」的完整底座（验签、映射、重试、补偿、日志、状态机），缺的是「**配置化**」——把硬编码变成运行时读取配置。

## 4. 核心可行性分析（逐项）

### 4.1 配置驱动的字段映射（替代编译期 MapStruct）

**可行性：✅ 高**，但有关键取舍。

- 现有 `OrderMapper` 是 MapStruct 编译期生成，字段映射（元→分、时间格式、嵌套、脱敏）是**类型安全但写死**的
- 落地为「声明式规则 + 内置函数」运行时求值：`{ src, target, fn, args }` 规则数组，`MappingEngine` 用 `getPath/applyFn/setPath` 执行
- **取舍**：编译期类型检查让位于运行时配置校验；性能从编译期方法调用降为运行时反射/路径求值（可缓存路径、内置函数为主）

**建议**：一期保留 MapStruct 映射到「默认规则集」过渡，新增渠道走配置引擎，双轨并行。

### 4.2 运行时编排引擎（SourceReader → TransformerChain → TargetWriter）

**可行性：✅ 高**，架构清晰。

```
SourceReader（多态：HTTP/JSON/SQL/Function）
  → TransformerChain（字段映射 + 过滤 + 函数 + 清洗，按算子顺序）
  → TargetWriter（@HttpExchange 转发 / 脚本执行）
  └─ 全程复用：验签 + @Retryable + 状态机 + 补偿 + 日志
```

- **SourceReader**：`HttpSourceReader`（复用 `OrderController`/`CallbackController` 接收）、`JsonSourceReader`（Jackson 3 解析）、`SqlSourceReader`（复用 `JdbcTemplate`）、`FunctionSourceReader`（复用函数库/SpEL）
- **TransformerChain**：处理步骤算子（映射/过滤/函数/清洗），配置化执行
- **TargetWriter**：转发复用 `@HttpExchange` + `RestClient`（URL/鉴权/超时从配置读）；脚本模式用脚本引擎/函数库

### 4.3 定时调度（cron / 固定间隔）

**可行性：✅ 高**。

- 现有 `@EnableScheduling` + `CompensationWorker`（3s 扫描）+ `IncrementalSyncJob`（60s 增量）已证明定时能力
- 落地：任务的 `scheduleType/cron/fixedSeconds` 配置，调度器（`@Scheduled` 或生产 XXL-JOB）按配置触发编排执行
- cron 解析：前端已实现 6 段 Quartz 解析（原型），后端可用 Spring `CronExpression` 或 Quartz

### 4.4 接口管理（转发第三方 / 脚本代码）

**可行性：✅ 高**，两模式都能落地。

- **转发模式**：本质是「接口代理」，复用 `@HttpExchange` 转发到第三方（含 Body 透传）
- **脚本模式**：脚本代码用 Groovy（沙箱）或函数库 + SpEL；SQL 复用 `JdbcTemplate` 执行 SELECT
- **安全**：脚本需沙箱隔离（白名单函数 + SpEL `SimpleEvaluationContext`，不引入无约束 Groovy）

### 4.5 接口监控（流量/调用次数/响应时长/调用日志）

**可行性：✅ 高**。

- 调用日志复用现有 `integration_call_log`（traceId/spanId/statusCode/latency/direction/req_headers/req_body/resp_body），已有 AOP `LoggingAspect` 写入
- 指标（流量/次数/响应时长）新增指标聚合表或直接聚合 `integration_call_log`，配合 Micrometer/Prometheus
- 趋势折线图前端 SVG 已实现，后端提供聚合查询接口

### 4.6 安全设置（白名单/黑名单/平台校验）

**可行性：✅ 高**。

- 验签复用 `SignatureService`（HMAC-SHA256 + 时间戳容差 + 恒定时间比较）
- IP/AppId/渠道白名单新增「访问控制层」，在验签前做过滤（多层防御：IP → 身份 → 验签 → 限流）

## 5. 数据模型设计（配置存储）

在现有 `schema.sql` 基础上新增配置表（或 JSON 配置 Blob）：

| 表 | 关键字段 | 说明 |
|---|---|---|
| `integration_flow` | flow_code、name、source_type、target_id、schedule_type、cron、fixed_seconds、enabled、version | 集成流程（定时任务）主记录 |
| `flow_step` | flow_id、seq、step_type（mapping/filter/function/cleanse）、config_json | 处理步骤算子 |
| `field_mapping_rule` | flow_id、seq、src_field、target_field、fn_name、args、sample | 字段映射规则 |
| `api_definition` | name、category、protocol、auth_type、api_key、method、params_json、headers_json、body_type、body_raw、mode、script、sql_text | 接口契约（Postman 风格） |
| `datasource_def` | name、type、url、method、auth、timeout、json_text、db_type、db_driver、db_url、db_user、db_password、sql_text、function_name、script | 数据源配置 |
| `function_lib` | fn_name、params_json、return_type、desc | 函数元数据（驱动 UI） |
| `api_metric` | api_id、req_bytes、resp_bytes、total_calls、success_calls、fail_calls、avg_ms、p95_ms | 接口监控指标 |

**一期建议**：`integration_flow` 用 JSON 配置 Blob（Jackson 3 解析，灵活快速）+ 少量元数据表（`function_lib`、`datasource_def`、`api_definition`）；二期拆关系表 + 版本管理。

## 7. 技术风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 编译期 MapStruct → 运行时映射的性能损失 | 路径求值/反射慢于编译期 | 路径缓存、内置函数为主、批处理；复杂逻辑 SpEL 预编译 |
| 动态字段映射的正确性（无编译期类型检查） | 配置错误不易发现 | 配置校验（字段存在性/函数参数/循环引用）+ 保存前「预览执行」沙箱验证 |
| 脚本/SQL 注入风险 | 越权读写、逃逸 | 脚本白名单 + SpEL `SimpleEvaluationContext`；SQL 参数化 + 表/列白名单 + 只读 SELECT |
| XML 动态序列化 | JacksonXml 动态字段名成本高 | XmlMapper 树模型按目标字段写节点，或模板化渲染 |
| 配置版本/兼容性 | 升级灰度时旧配置失效 | `flow_version` 快照 + 灰度发布 + 全量配置回归 |
| Demo → 生产 | 内存/单机限制 | 沿用生产化规划：MySQL、XXL-JOB、Redis 分布式锁 |

## 8. 演进路径（三阶段）

### 一期 · 字段映射配置化（POC，1-2 周）
- 目标：`ERP 订单 → PARTNER_A` 完全由配置驱动，不写死映射代码
- 交付：`MappingEngine`（规则+函数）、`function_lib` 元数据、配置 JSON 落库、执行预览
- 验收：与现有 `OrderMapper.toPartnerA` 输出一致，改规则不改代码

### 二期 · 流程编排配置化（引擎，2-4 周）
- 目标：Source/Transform/Target 全配置化，四类 Source 通用，调度配置化
- 交付：`IntegrationFlow` 领域模型 + 执行器、`SourceReader` 多态、转发/脚本模式、重试/补偿参数配置化
- 验收：新增一个第三方渠道全程零代码

### 三期 · 可视化低代码 UI + 运维（4-8 周）
- 目标：原型落地为真实前端（Vue3），支持任务管理/版本/灰度/监控
- 交付：配置 CRUD、预览执行、发布/回滚、监控看板（复用 `integration_call_log` + Prometheus）
- 验收：实施人员可自助配置上线新渠道

---

## 9. 结论

**技术可行，强烈建议分三阶段演进。**

核心判断：
1. **底座已具备**：验签、重试、补偿、日志、状态机、定时能力全部可复用，无需推翻现有架构
2. **关键改造点**：把 MapStruct 编译期映射改为「声明式规则 + 函数」运行时映射（一期核心），以及把渠道路由/配置从代码/ YAML 迁移到配置存储
3. **主要风险可控**：性能（缓存 + 内置函数）、安全（白名单 + 沙箱）、兼容（双轨过渡 + 版本管理）
4. **ROI 清晰**：一期小成本验证「配置驱动」核心，跑通 POC 后再投入引擎和 UI

> 注：原型本身有 6 处已知 bug（保存不持久化、delStep 引用不一致等，见 `原型说明文档.md` §7），落地实现时不应照搬，而应基于后端正确实现这些持久化与状态同步逻辑。

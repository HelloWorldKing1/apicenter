# 接口监控（Monitor）升级设计方案

> 版本：v0.3（2026-09-11；v0.1 监控升级 + v0.3 报文美化）｜范围：`frontend/src/views/Monitor.vue` + `Dashboard.vue` + `utils/payload.mjs` + 调用日志/出站记录端点增强
> 实施状态：M1 信封业务码检索首版不做（traceId 定位替代）；M2 冷却提示与内置/规则来源列已加；M3 不加 backlog 端点（复用 overview）；M4 索引已应用。call-logs 已支持 direction/appId/statusGroup/statusCode/时间窗/url 子串过滤；新增 `/monitor/outbound-requests/{id}` 详情。
> 原则：不动 M4 已交付的运维闭环（对账置位 / 死信重放 / 告警冷却），在其上做「查得全、查得快、能下钻、口径一致」的观测升级。

## 1. 现状盘点（对应代码事实）

当前 Monitor 页为**五区块纵排卡片**（无 tab）：
1. 统计卡 4 张：今日调用/成功率/待补偿·待重送/死信·对账中 —— `/monitor/overview`，10s 轮询；
2. 调用日志：分页表 + **仅 traceId 过滤**；列=时间/方向/接口ID/应用/状态码/耗时/URL/traceId（`/monitor/call-logs`，后端仅支持 traceId + interfaceId 过滤）——**不可查明细体**（脱敏 req/resp 已落库却未展示）、无时间/状态/应用过滤；
3. UNKNOWN 对账：仅 status=UNKNOWN 列表 + 置位弹窗（SUCCESS/COMPENSATING，operator/reason）——后端已支持 status/bizId/traceId 过滤与 **audits 审计时间线端点**，前端未接；
4. 死信：分页列表 + PENDING 重放（后端已支持 bizType/status 过滤，前端未用）；
5. 告警：事件列表 + 规则 CRUD（后端校验 metric 白名单与阈值表达式，`≤60s 缓存生效`）——无「规则触达统计/最近触发」视图。

问题：
- 日志是监控第一入口但**检索能力最弱**（无方向/应用/接口下拉、无时间窗、无 HTTP/错误码、无明细）；
- 出站状态机（outbound_request 全态）后端可查但前端只开放 UNKNOWN 一个状态 → 无法追「补偿进行中/耗尽中/超时待对账」全谱系；
- 审计时间线（对账 history）与死信 payload 有数据无入口；
- 无任何**时间序列/排行**可视化（与 Dashboard 互补但 Dashboard 只放首页聚合）；
- 页面所有列表共用一个纵向滚动，多区块同屏拥挤。

## 2. 设计目标

- **日志可查**：5 类过滤 + 明细抽屉 + 深链直达；查询即抄 traceId 场景；
- **状态机全谱可见**：出站记录新增「全部状态」视图（复用后端 findPaged），状态分布一览 + 每行审计/轨迹下钻；
- **告警可答**：「规则现在判什么、最近触发什么、内置验签失败事件在不在」；
- **Dashboard ↔ Monitor 双向深链**：query 参数（appId/interfaceId/status/traceId/range）成为两页公共协议；
- 口径表与《概览仪表盘设计方案.md》§5.1 共享，不另造口径。

## 3. 页面结构（目标态：顶部统计 + 6 个 tab）

```
页面头：接口监控         [时间范围 1h/24h/7d]（作用于趋势与日志查询默认）  [自动刷新开关]
┌─────────── 健康条（4 卡，同 Dashboard 口径，10s 轮询）─────────────┐
│ 今日调用 · 今日成功率 · 待补偿/待重送 · 死信/对账中（含角标）      │
├────────── Tab 区 ────────────────────────────────────────────────┤
│ [总览] [调用日志] [状态机与对账] [死信] [告警] [保留(设置)]          │
├──────────────────────────────────────────────────────────────────┤
│ Tab 1 总览：微型趋势(IN 流量/失败数) + P50/P99 + 积压分布 + 告警条  │
│ Tab 2 调用日志：过滤条 + 表格 + 明细抽屉                           │
│ Tab 3 状态机与对账：状态分布条形 + 全状态列表 + 审计时间线抽屉      │
│ Tab 4 死信：bizType/status 过滤 + payload 详情 + 重放              │
```

## 4. 各 Tab 详设

### Tab 1 总览（监控首屏）
- 内容：Dashboard 同源迷你趋势（复用 `/monitor/stats/trend`，只读前 12~24 桶）+ 积压四件与告警最近 5 条事件；
- 目的：Monitor 独立打开也有「概况」，不必跳 Dashboard。

### Tab 2 调用日志（重点改造）
**过滤条**（新增后端参数支持，见 §5.2）：
| 过滤 | 控件 | 说明 |
|---|---|---|
| 时间窗 | 快捷 近1h/6h/24h + el-date-picker | 默认近 1h（远程库注意大窗成本） |
| 方向 | 下拉 IN/OUT/全部 | call_log.direction |
| 应用 | 下拉（/apps） | app_id |
| 接口 | 下拉（按应用联动 /interfaces） | interface_id |
| HTTP 结果 | 分组：全部/2xx/4xx/5xx（statusCode 区间） | |
| 错误码 | 文本（信封 code 段，如 42901/50202）——需要后端解析信封？**降级**：只按 status_code + direction 过滤，信封业务码检索走 traceId 场景（拍板点 M1） |
| traceId | 文本 | 既有 |
- 查询触发：条件变化即查（防抖 300ms）+「查询」按钮；分页沿用；
- **明细抽屉**：行点击（列新增「查看」或行可点）→ 右抽屉渲染 req_headers（脱敏字符串 `k: v | k: v`）、req_body、resp_body（已 4096 截断，超长标「…[truncated]」），url/method/latency/trace；操作：复制 traceId / 跳对账（若该 trace 有 UNKNOWN）/ 打开接口详情；
- 列增强：URL 已含目标地址，补 method；状态码着色沿用。

### Tab 3 状态机与对账
- **状态分布条**：当前计数（INIT/MAPPING… 只显示非零的：SUCCESS/COMPENSATING/DEAD_LETTER/UNKNOWN 今日与累计？**建议只显示可运维态**：COMPENSATING/DEAD_LETTER/UNKNOWN/PENDING→对应出站/入站）——数据来源 overview + outbound paged；
- **出站记录列表**（全状态）：过滤 = 状态下拉（全态）+ bizId + traceId + 应用；列：ID/接口/应用/bizId/状态/attempt/max/error_code/next_retry_at/updated/trace；
  - 行操作：UNKNOWN →「置为已到达/未到达」（弹窗同现状）；任意态 →「审计时间线」（GET `/outbound-requests/{id}/audits`，渲染 MANUAL/TTL 来源、from/to/operator/reason/时间）→「重放」（仅 DEAD_LETTER 由死信 tab 负责，这里只读）；
- 数据：现有 `/monitor/outbound-requests` 已支持 status/bizId/traceId 分页——前端放开状态下拉即可，仅需补**单行详情**（见 §5.4）。

### Tab 4 死信
- 过滤：bizType（OUTBOUND/INBOUND）+ 状态（PENDING/HANDLED，后端已支持）；
- 列增「报文预览」：点击弹窗展示 payload（快照原文，死信为重放依据）与 reason（超 2000 字符截断提示）；
- 重放：PENDING → 确认弹窗 → 后端置 HANDLED + 记录回队（现状保留）。

### Tab 5 告警
- 顶部：规则卡列表（名/metric/threshold/启用/「编辑」「删除」），沿用 modal；
- 事件表列增：级别 tag、规则名/来源（内置 vs 规则）、**冷却状态提示**（同一规则 5 分钟内去重——现状只显示事件，需把冷却命中说明为列或 tooltip，拍板点 M2）；
- 内置告警：验签连续失败事件在来源列展示「内置」，规则区显示只读卡片说明（不可删/可改阈值属于 v1.1）。

## 5. 后端接口契约

### 5.1 复用（现状已满足）
`/monitor/overview` · `/monitor/outbound-requests`（分页 + status/bizId/traceId）· `/monitor/outbound-requests/{id}/audits` · `/monitor/dead-letters`（bizType/status）· `/monitor/alerts` · `/monitor/alert-rules` CRUD。

### 5.2 增强 `GET /monitor/call-logs` 过滤参数（向后兼容，非破坏）
```
新增：direction? · appId? · statusCode?（精确）或 statusRange?（2xx|4xx|5xx）
      timeFrom? · timeTo?（ISO，含端点）· keyword?（url 子串）
排序：保持 id DESC（即时间倒序）；pageSize 上限 100 不变
```
- 实现：`CallLogRepository.findPaged` 按可选条件拼 WHERE（全部走既有 idx_call_time / 新增可选 idx_call_app_time），`count` 同步；参数白名单防注入（JdbcTemplate 参数化）。

### 5.3 新增 `GET /monitor/stats/trend` 与 `GET /monitor/top-interfaces`
- 与《概览仪表盘设计方案.md》§5.2/5.3 **同一端点**（Monitor 与 Dashboard 共用一份聚合与 60s 缓存）；
- Monitor Tab1 只消费其子集。

### 5.4 新增 `GET /monitor/outbound-requests/{id}`
```
出参：{ ...OutboundRequestRow, inPayload 预览（截断提示）, respPayload 预览, audits[]（含时间线） }
```
- 供 Tab3 行详情抽屉（含对账历史）；payload 全量可由审计场景单独拉，避免列表拖大。

### 5.5 可选 `GET /monitor/backlog-snapshot`
- 返回 AlertWorker 已维护的积压快照（compensating/pending/dead/unknown），供健康条秒开；现状 overview 同值，可先不加（拍板点 M3）。

## 8. 调用日志报文美化（v0.3，2026-09-11 落地）

**需求**：调用日志明细的请求体 / 响应体（JSON 或 XML）默认美化后呈现。

**拍板结论**：① 只在前端美化（后端零改动）；② **美化只增删空白、不改写任何 token**；③ 顺带覆盖 Dashboard 最近日志抽屉与状态机 Tab 的 in/out/resp 预览；④ 语法高亮放 P2；⑤ 增加前端零依赖单测。

### 8.1 为什么不用 `JSON.parse` + `stringify` / `DOMParser`

实测（`node -e`）对同一条报文：

```
原样            {"seller_id":7494312521977267257,"amount":1.10,"exp":1e3,"a":1,"a":2}
parse+stringify {"seller_id":7494312521977267000,"amount":1.1,"exp":1000,"a":2}
```

损失：**19 位数字尾数被改写**（fastmoss 黄金用例的 `seller_id` 就是 19 位）、`1.10`→`1.1`、`1e3`→`1000`、重复键丢前一个、`\uXXXX` 被还原。XML 同理：`DOMParser` 会规范化 CDATA / 实体 / 属性引号 / 命名空间声明顺序。
→ 因此改用**字符串感知的扫描式缩进器**（JSON：`inString/escape/depth`；XML：标签 / 属性引号 / 注释 / CDATA / PI / DOCTYPE 分别处理），只对结构位置插入换行与缩进，token 逐字节保留。副产品：**被截断的半截报文也能缩进**。

### 8.3 验收断言

1. 明细里紧凑 JSON / XML 多行缩进，`node -e` 打印同条报文的数字与展示**逐字节一致**；
2. 脱敏后的值（`abcd****wxyz`）正常参与缩进；
3. 超 4096 字符报文出现「已截断」标签，缩进仍可用；
4. form-urlencoded / 二进制 / 纯文本原样降级，无「美化」切换；
5. `cd frontend && npm test` 全绿（单测 14 例 + 组件 SSR 冒烟 5 例）。

### 8.4 已知回归与修复（2026-09-12）

- **现象**：调用日志明细的请求体 / 响应体只显示占位符「—」，美化与原文两种模式均无内容（工具栏的格式标签与字符数正常）。
- **根因**：`PayloadViewer.vue` 的 `shown` computed 里写成 `view.formatted ? view.pretty : view.raw` —— `view` 是 computed ref，**JS 里必须 `.value` 才会解包**（只有模板会自动解包，所以工具栏用 `view.lang` / `view.length` 恰好正常）；结果为 `undefined` → `{{ shown || emptyText }}` 落到占位符。
- **修复**：把取值规则提为纯函数 `pickPayloadText(analyzed, mode)`（`payload.mjs`），组件只调它；并新增两类测试：单测 «回归：任何非空报文在默认模式下展示文本必须非空» + **组件级 SSR 冒烟**（`npm run test:ssr`，5 例断言 `<pre>` 正文）。
- **教训（写进 CLAUDE.md）**：`<script setup>` 里的 computed/watcher 在 **JS 代码**中一律 `.value`；跨函数复用的展示规则提成纯函数，让单测能覆盖，别留在组件内部。

| 批次 | 项目 | 实现要点 |
|---|---|---|

| 2 | 全屏 / 宽度记忆 | `全屏` 按钮 → 组件级 `position: fixed` 全屏（Esc 退出，**不复制 DOM 结构**）；抽屉宽度 `resizable` 拖拽后经 `@resize-end` 持久化（Monitor / Dashboard 各自 key） |
| 3 | 折叠 / 展开 | 超过 `FOLD_LINES=60` 行默认折叠 + 「展开全部（共 N 行）」；展开超过 `RENDER_MAX_LINES=20000` 行时提示改用复制 |
| 3 | 大报文 Worker | >256KB 交 `workers/payloadFormat.worker.mjs` 后台格式化（上限 `WORKER_FORMAT_LIMIT=2MB`），期间显示原文 + 「正在后台美化…」；Worker 不可用 / 超上限时静默降级（实测 770KB → 1.27MB 美化结果，数字仍逐字节保真） |
| 4 | Content-Type 提示 | `analyzePayload(text, contentType)`；`contentTypeOf(headers)` 从脱敏头串提取（去参数、小写），调用方在调用日志行上直接传入 |
| 4 | form-urlencoded | `isFormLike` 从严探测（无提示需 ≥2 对，避免把「订单 a=b 已受理」误判）+ `formatForm` 逐行拆 `k = v` 并做 `decodeURIComponent`（失败保留原值） |
| 4 | 二进制 / 图片 | `detectBinary`：NUL 或控制字符占比 >5% 判二进制；纯 Base64 且解出图片魔数（PNG/JPEG/GIF/WEBP）→ 提示 + **内容完整时**给 Base64 内联预览（落库 4096 截断的图片必然残缺，故截断时明确不给预览） |

**评测口径（为什么这样分工）**：扫描式缩进很快（实测 250KB ≈ 9ms），主线程阈值 256KB 是给「格式化 + 上万行 token 渲染」留余量；
真正的渲染压力由「默认折叠 60 行 + 展开上限 20000 行」兜住，Worker 只服务于 >256KB 的大报文。

**验证**：`cd frontend && npm test` = 单测 26 例 + 组件 SSR 冒烟 10 例，全绿；`npm run build` 产出 `assets/payloadFormat.worker-*.js`（Worker 分块）。

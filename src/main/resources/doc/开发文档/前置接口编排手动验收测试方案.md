# 前置接口编排 手动验收测试方案

> 版本：v1.0（2026-09-18，按实施后实际行为校准）｜适用：出站接口「前置步骤（编排）」能力（《前置接口编排设计方案.md》PS-1..PS-9）
> 预计耗时：**约 15 分钟**（三阶段）｜前置：后端 8080 + 前端 5173 已起；本地 WireMock 桩在 18080（见下）
> 自动化覆盖（先跑这一组，再手工）：`mvn -Dtest=PreStepIntegrationTest test`（12 例：串行/隔离/透传/失败四分支/留痕/校验/链路长度/删除守卫/下线提示/快照回滚/深度防护）
> 本方案只做**自动化不易覆盖的部分**：界面交互、真实观测面（Monitor / 调用日志）、断链与应急回退现场。

---

## 0. 准备（一次性，约 1 分钟）

```bash
# 1) 本地供应商桩（若已按其他分册起过可复用；端口 18080）
#    auth：返回 token；main：接收宿主出站报文；两者都在同一 WireMock 上
curl -s -X POST http://localhost:18080/__admin/mappings -d @- <<'JSON'
{"request":{"method":"POST","urlPath":"/up-auth"},
 "response":{"status":200,"jsonBody":{"token":"T-123","code":0},"headers":{"Content-Type":"application/json"}}}
JSON
curl -s -X POST http://localhost:18080/__admin/mappings -d @- <<'JSON'
{"request":{"method":"POST","urlPath":"/up-main"},
 "response":{"status":200,"jsonBody":{"ok":true},"headers":{"Content-Type":"application/json"}}}
JSON

# 2) 应用（指向本地桩；开发环境 callback-allow-private=true 允许回环地址）
curl -s -X POST http://localhost:8080/api/admin/apps -H 'Content-Type: application/json' \
  -d '{"appId":"PST-DEMO","name":"编排演示供应商","baseUrl":"http://localhost:18080"}'
curl -s -X POST http://localhost:8080/api/admin/apps/PST-DEMO/enable
# 取分组 id（弹窗里也能选）
curl -s "http://localhost:8080/api/admin/groups?appId=PST-DEMO"
```

> 说明：前置接口必须**已发布**；B 的出站报文由其自己的字段映射决定，本演示 B 不配映射（= 透传，A 的入站报文原样发给 B）。

## 阶段一 · 界面配置与引用链（约 4 分钟）

| # | 操作 | 预期 / 自检 |
|---|---|---|
| 1.1 | 接口管理 → 新建出站接口 `IF-PS-AUTH`（平台路径 `/ps/auth`、供应商路径 `/up-auth`）→ 发布 | 列表中状态「已发布」 |
| 1.2 | 新建出站接口 `IF-PS-MAIN`（`/ps/main` → `/up-main`）→ **先不发布** | — |
| 1.3 | 打开 `IF-PS-MAIN` 编辑 → 看到「**前置步骤**」Tab（仅出站中转有）→ `＋ 添加前置步骤`：步骤名 `auth`、前置接口选 `IF-PS-AUTH`、策略「阻断后续（ABORT）」 | 弹窗内「引用方式」提示 `steps.auth.<字段>` |
| 1.4 | 点该步「**可用字段**」 | 抽屉列出可引用字段（`steps.auth.*`）；无声明时提示「未声明出站响应字段 / 出站参数」 |
| 1.5 | 切到「字段映射」加一条：`source=steps.auth.token` → `target=api_token` → 保存 → 发布 | 列表出现 `⇢ 1 步` 角标；详情抽屉出现「前置步骤」表 |
| 1.6 | 调用 `curl -s -X POST http://localhost:8080/ps/main -H 'Content-Type: application/json' -d '{"orderId":"O-1"}'` | 返回 `{"code":0,...}` |
| 1.7 | 查看供应商桩实际收到的报文：`curl -s -X POST http://localhost:18080/__admin/requests/find -d '{"urlPath":"/up-main"}'` | 报文含 `"api_token":"T-123"`；**不含** `steps` 键 |
| 1.8 | 看前置接口收到的入参：把 `urlPath` 换成 `/up-auth` 重复上一步 | 报文 = A 的入站报文（`{"orderId":"O-1"}`），**看不到** `steps`（模型隔离） |
| 1.9 | 接口详情 →「测试接口」→ 发送 | 响应 `data` 含 `chainTrace` / `steps`（每步 步骤名·前置接口·HTTP·耗时·结局）/ `result`；界面步骤表出现一行 `auth HTTP 200 …ms SUCCESS` |

## 阶段二 · 失败分支与观测面（约 6 分钟）

> 每步都用 `POST http://localhost:18080/__admin/reset` 清桩后重新注册，避免旧桩残留（WireMock 匹配按注册顺序）。

| # | 操作 | 预期 / 自检 |
|---|---|---|
| 2.1 | 把 `/up-auth` 桩改成 **404** → 调 `/ps/main` | HTTP 400、`code=40001`、msg 点名「前置步骤 auth 失败…HTTP 404」；供应商桩 `/up-main` **零调用**（`requests/find` 为空） |
| 2.2 | 打开「接口监控 → 状态机与对账」查该次 traceId | 记录状态 = **INIT**（不推进状态机：无死信、不入补偿队列） |
| 2.3 | 改成 **500** → 调 `/ps/main` | 502、`code=50201`「已进入补偿队列」；记录状态 = `COMPENSATING` |
| 2.4 | 恢复 `/up-auth` 为 200 → 等补偿 worker（≤3s）或手动触发重放 | 记录转 `SUCCESS`；状态链出现 `前置步骤` 节点（`trigger=PRE_STEP`）+ 后续 `MAPPING/SUCCESS` 节点 |
| 2.5 | 给 B（接口编辑 →「高级」）设「读超时」= **300ms**；把 `/up-auth` 桩加固定延迟 `withFixedDelay(1500)` → 调 `/ps/main` | 504、`code=50401`「结果待对账（UNKNOWN）」；记录状态 `UNKNOWN`（**不会自动重试**，需人工对账） |
| 2.6 | 恢复 B 的读超时 3000ms；把 `IF-PS-AUTH` **下线** → 调 `/ps/main` | 40001「目标接口未发布」（**硬失败**，不是静默跳过前置）；该记录停留在 `INIT` |
| 2.7 | 观察 `POST /api/admin/interfaces/{B的id}/offline` 的响应（对已下线的再调会 40001，可在 2.6 之前先验证） | data 为 `warnings[]`，内容含「被前置步骤引用：IF-PS-MAIN(步骤 auth)」——管理面弹黄色提示 |
| 2.8 | 调用日志 Tab：按 `traceId` 过滤 → 应看到 A 的 IN/OUT 与 B 的 OUT 共 3 条；用「前置步骤名」筛选框填 `auth` | B 的 OUT 条「步骤」列显示 `前置·auth`；按步骤名可筛出该条 |
| 2.9 | 把 B 重新发布 → 调 `/ps/main` | 恢复正常（400→200） |

## 阶段三 · 约束、快照与应急回退（约 5 分钟）

| # | 操作 | 预期 / 自检 |
|---|---|---|
| 3.1 | 编辑 A → 步骤名改 `bad.name` → 保存 | 40001「仅允许字母/数字/下划线」 |
| 3.2 | 步骤名改成 `steps` → 保存 | 40001「不得为保留名 steps」 |
| 3.3 | 加两步都用 `auth` 为名 → 保存 | 40001「前置步骤名重复」 |
| 3.4 | 新建一个**只存草稿**的接口 `IF-PS-DRAFT` → 在 A 的步骤里选它 | 40001「前置接口未发布（D-PS-8）」 |
| 3.5 | 步骤指向 A 自身 → 保存 | 40001「不能指向接口自身」 |
| 3.6 | 造三级链：`IF-PS-C`→(无)、`IF-PS-B`→C、A→B 允许；再建 `IF-PS-A2`→B 使链长 4 | 40001「前置链长度超限（最多 3 层，含宿主）」；A2→C（3 层）应放行 |
| 3.7 | 删除 `IF-PS-AUTH`（被 A 引用） | 40001「接口被 1 个前置步骤引用，禁止删除：IF-PS-MAIN(步骤 auth)」 |
| 3.8 | 给 A 再加一步（共 2 步）→ 保存 → 版本历史 | 新版本 change_note 含「前置步骤 1→2」；「变更详情」里 `steps` 段有 ADD 记录 |
| 3.9 | 把两步都删掉 → 保存；再**回滚**到上一步的版本 | 步骤恢复为 2 条，且 `targetCode` 正确显示（快照存 code → 回滚解析回 id） |
| 3.10 | 复制 A（详情抽屉「复制」）→ 打开副本 | 副本带同名的 2 步前置（指向同一个 B），`⇢ 2 步` 角标 |
| 3.11 | 把 `application.yaml` 的 `app.api-center.pre-step.enabled` 改 `false` → 重启后端 → 调 `/ps/main` | **不再调用 B**（供应商桩 `/up-auth` 零请求）；A 的出站报文 = 其映射结果；再改回 `true` 重启恢复——**应急回退验证** |
| 3.12 | 手工造环（可选，模拟脏数据）：`UPDATE interface_step SET target_interface_id=<A的id> WHERE interface_id=<B的id>;` → 调 A | 40001「前置链深度超限」，记录停留 `INIT`（运行期防护生效） |

## 已知边界（别误判为缺陷）

1. 一期失败策略**只有 ABORT**（阻断后续）；`CONTINUE` / `FALLBACK` 是二期能力，界面里置灰；
2. 不支持入参常量覆盖（overlay）、条件执行、并行组、每跳超时覆盖、拖拽排序——二期；
3. 前置**不落自己的运行记录**：B 的调用只在 `call_log`（OUT 条 + `step_code`）与宿主的 `PRE_STEP` 状态链节点里可见；
4. 前置调用**不计**宿主的 QPS / 日配额（内部调用不经接入层防护），也不计 B 所属应用的限额；
5. 前置超时 → 宿主 UNKNOWN 属**有意语义**（结果不确定不可安全重试），不是「重试没生效」。
